## 4. Decisions

1. **One cover concept: `tenants.cover_image_{key,width,height}`, served as `Studio.cover`, merged into the theme's hero slot at the seam.** The storefront's `storefrontInput(studio)` puts a non-null `Studio.cover` into `branding.heroImage` of the theme input; `parseThemeConfig` and every TAT-54 image check run unchanged on it. With no cover, `storefrontInput` returns exactly what it returns today (`undefined` on real pages), so the default theme object and markup are untouched. The contract says `branding.heroImage` is never sent: TAT-56 must reuse the Settings, Profile cover, never add a second upload. *Rejected:* sending `Studio.storefront.branding.heroImage` now (it would pre-empt TAT-56's contract, its size cap and its strip-before-dehydrate work); making `parseThemeConfig` take the cover as a third argument (rewrites the 779-line config test and the deposit loader for the same result).
2. **Columns on `tenants`, not a table, for the cover.** One per studio, read from the tenant row that `publicTenant` already loaded: `getStudio` stays at one query. All-or-none check like `artists_photo_all_or_none`.
3. **`artist_work_photos` is hard-deleted, not soft-deleted.** A removed photo must stop being reachable at once (a client may ask a studio to take a photo of their skin down); soft-deleted records keep their files by convention, so a soft delete would keep a public file alive. Added to the README's list of tables that are not soft-deleted, with this reason. Soft-deleting the artist or tenant leaves the photo rows and files (hidden with the artist, like the portrait).
4. **The database holds at most six per artist:** `check (position between 0 and 5)` plus `unique (tenant_id, artist_id, position) deferrable initially immediate`. Deferrable so a swap or a compaction can be one UPDATE (checked at the statement's end). The service counts under the artist's row lock as well, so a seventh upload gets a friendly field error instead of a constraint error. `MAX_WORK_PHOTOS = 6` in code; a test inserts a seventh row directly and expects the check to fire.
5. **Upload order:** count first, unlocked (a full set is refused before any decode), then `ImageService.store` inside `withTransaction` with `afterRollback` right after it, then lock the artist row `FOR UPDATE`, count again, insert at `position = count`. The row lock is the one `ArtistService.save` takes, so an upload and a profile save never interleave. A test subclass stages "the other upload landed between the two counts" through a `protected countPhotos` hook (the `ImageService.makeVariants` precedent). *Rejected:* an advisory lock (a second lock order to keep).
6. **Purposes with fixed names:** `studio_cover` (public; copies 640, 960 and 1280 px: 960 keeps a phone at DPR 2 to 2.75 off the 1280 copy, about half the bytes of the first screen) and `artist_work_photo` (public; `VARIANT_WIDTHS` 320, 640, 1280: the dashboard's 320 thumbnail and the strip). The purpose is a constant in each service, never from the request.
7. **Descriptions (alt text): optional, one line, at most 200 characters, per work photo.** Public `alt` is the description or `null`; the storefront then writes "Tattoo by {name}, photo {n} of {count}". The cover has no description: the API sends `alt: null` and the page shows it with `alt=""`, because the studio's name in the h1 sits on it. (User decision 1.)
8. **One photo per upload, with a native Inertia `<Form>`** (its `processing`, `progress`, `errors` and `resetOnSuccess`). A phone photo is 3 to 10 MB and the dashboard's request limit is 20 MB, and the dashboard has no client-side resize (the intake's lives in the storefront, which the platform may not import). The tray keeps the intake's shape otherwise: current photos with their count, "Add a photo", a full state, a field error. *Rejected:* a multi-select input posting files one by one from a client loop (custom state, network and 413 edge cases), or one request with several files (fails at 20 MB). (User decision 3.)
9. **Roles.** Work photos follow `ArtistService.findEditable`: an owner manages every live artist's photos, an artist only their own linked live profile's; the service re-checks the link under the row lock (as `updateOwn` does). The cover is in the settings group: owners only. Six routes: `POST /t/:tenant/artists/:id/photos` (`:id` = artist), `PUT /t/:tenant/artists/photos/:id`, `POST /t/:tenant/artists/photos/:id/move`, `DELETE /t/:tenant/artists/photos/:id` (`:id` = photo), `PUT /t/:tenant/settings/cover`, `DELETE /t/:tenant/settings/cover`. One `:id` per route because the isolation harness substitutes exactly one (`tests/helpers/isolation.ts:9-31`).
10. **Public payload, additive:** `Studio.cover: Image | null` (always `alt: null`), `Artist.workPhotos: WorkPhoto[]` (`maxItems: 6`, `[]` when none; `WorkPhoto` = url, width, height, alt, variants, all required). No photo id, key, artist id, position or timestamp. Cache headers unchanged. Queries: `getStudio` 1 (unchanged), `listArtists` 2 (1 when no artist is visible), `getArtist` 2.
11. **Visibility:** photos follow the artist. Hidden and deleted artists' photos are in no answer (there is no endpoint that lists photos on their own). Visible artists who are closed for inquiries still show their work (the card and page already show them with their closed message). (User decision 2.)
12. **Work photos take the strict image rule** on the storefront (`readBrandImage`: the API's origin only, copies on the same origin), not the artist portrait's looser one: the change does not widen what can reach the page.
13. **Cover hero:** the photo with the name, location line and any logo over it, 4:3 below 60rem and 21:9 from 60rem, inside the page margins with the stencil frame (not full-bleed, so `coverSizes`' margin model holds). A scrim token behind every text line keeps `--on-photo` text at 7:1 or better even over a white photo; the photo's box shows a dark placeholder until the image arrives, so the name reads first on a slow line. The box grows with a long name (an `aspect-ratio` box's automatic minimum height). (User decision 5.)
14. **Roster:** the first 3 work photos as fixed 5rem squares inside one link, "See work by {name}", to `/artists/<slug>#work`. The squares are `alt=""` because the link's own text names where it goes; the safety helper allows that for `class="work-thumb"` only. No viewer on the studio page. Fixed 5rem (3 × 5 + 2 × 0.375 = 15.75rem) fits the narrowest card body (26rem card less the 9rem photo and its gap) and makes `sizes` one plain length.
15. **Artist page viewer:** a 3-column square grid (at most 48rem wide); each photo is a `<button type="button" aria-haspopup="dialog">` that calls `dialog.showModal()` on that photo's own `<dialog>`; the dialog holds a `<form method="dialog">` Close button, "Photo n of m", the large image (the widest copy up to 1280 px) and the description. Escape, initial focus and focus return are the browser's; no scroll lock, no focus code, no state; the only DOM call is `showPhoto(id)` in `src/studio/lightbox.ts`. Without JavaScript (or before hydration) the grid is the content and the buttons do nothing. *Rejected:* plain links to the image file (they leave the studio's page for the API host and an `http:` dev API fails `ALLOWED_HREF`), a CSS `:target` overlay (not modal: Tab reaches the hidden page behind it), a custom lightbox with an index state.
16. **Store keeps its redirect to the artists list;** the create form gets a note that photos are added once the artist is saved. (Avoids changing TAT-31's tested flow.)
17. **No new rate limit.** Dashboard uploads are members only, bounded by six rows per artist, one cover, 10 MB per file, 20 MB and 120 s per request and 2 decodes at once.
18. **Removal and freshness (documented, not engineered):** a removed photo's or replaced cover's files are deleted right after the commit, so nobody can fetch them from then on. A studio page or API answer cached before can still name the old URL for up to about 12 minutes (the API's `max-age=60, stale-while-revalidate=600`; the page's `s-maxage=60, stale-while-revalidate=600`), and shows an empty square with its alt text there. A visitor's browser that already downloaded the file may show its own copy (the file server sends `Last-Modified` and no `Cache-Control`, so browsers may cache heuristically). TAT-27 must purge a deleted key from any CDN or keep a short `max-age` on these purposes.

User-only decisions (each with the default the builder uses): see the last section.

export const LARGE_WIDTH = 1280;
export function largeSource(image: { readonly src: string; readonly width: number; readonly srcSet?: string }, max = LARGE_WIDTH): string {
	if (image.width <= max || !image.srcSet) return image.src;
	let best: { url: string; width: number } | null = null;
	for (const candidate of image.srcSet.split(", ")) {
		const [url, descriptor] = candidate.split(" ");

		if (width <= max && (!best || width > best.width)) best = { url, width };
	}
	return best?.url ?? image.src;
}

## 12. Risks and rollback

- **The cover's first-screen bytes.** A detailed 1280 px JPEG at quality 80 can pass 250 KB; DPR 3 phones pick it. Measure; if it is over, the fix is a follow-up (a per-purpose quality or a 1120 px copy), not a blocker for this ticket. Write the measured value in the report.
- **`aspect-ratio` growth with a very long name** makes the box taller than 4:3, so the photo is cropped more and slightly enlarged beyond what `coverSizes` asked for. Rare; accepted.
- **Native dialog differences:** focus return on close and `overscroll-behavior` inside a dialog differ on old iOS. No custom code is the trade; the browser pass records what it saw.
- **Stacked branch:** a change to TAT-112 in review (copy widths, `shownImage`) ripples here; rebase before the PR and rerun the storefront `srcset` tests.
- **Logo over the cover:** no studio has a logo until TAT-56; a dark logo on the scrim may not read. TAT-56 must check it.
- **Hard delete:** a removed photo cannot be restored. Intended; the confirm says so.
- **Rollback:** revert the branch's commits. The two migrations roll back cleanly (`pnpm migrate:rollback` as the owner) only while no code reads the columns; the API change is additive, so an older storefront keeps working and a newer storefront treats a missing `cover` / `workPhotos` as none. Stored cover and work photo files left after a rollback sit under their own purpose folders and can be deleted by prefix.
