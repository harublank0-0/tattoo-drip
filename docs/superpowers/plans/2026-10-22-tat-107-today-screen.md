## 4. Decisions

- **D1. Every member lands on Today** (`tenantHome` and joining a studio go to `tenant.today`; the route is
  `MEMBERS`). An artist's Today is scoped like everything else of theirs: their own projects (through
  `ProjectService.listActive`, the `findFor` rule) and their own sessions (`CalendarService.load`), and never
  new requests, payment screenshots, deposit links, the setup checklist, the studio link or the pilot
  numbers. Reason: "who is in my chair today and which of my projects needs a price or a session" is the
  artist's day too, and one home for everyone keeps the landing code and its tests to one rule.
  Rejected: artists keep landing on Projects (a list sorted by last contact that says nothing about today).
  *User decision U1.*
- **D2. One service decides what waits, for Today and for TAT-109.** `WaitingService`
  (`#modules/projects/services/waiting_service`) with three public methods: `forProjects(tenant, member,
  projects, now?)` (facts and the waiting state of projects the caller already loaded: TAT-109 passes its
  page of rows), `work(tenant, member, now?)` (every active project the member may see, split into "needs
  you" and "waiting on the client", each sorted by how long it has waited) and `needsYouCount(tenant,
  member, now?)` (the Today tab's badge). The rules are pure (`#modules/projects/waiting`: `waitingOf`,
  `waitingText`, `WAITING_HASH`, `groupOf`, `sinceOf`), so TAT-109's "waiting" line is `waitingText` of the
  same result. It asks the owning modules' services, never their tables. Rejected: computing in the
  controller (TAT-109 would copy it), or extending `PaymentService.listFlags` (owners only, and it reads no
  links or sessions).
- **D3. The rules, one state per project (first match wins).** Studio side ("needs you"):
  1. `proof_to_check`: a deposit screenshot waits (owners only; an artist gets nothing for this project).
  2. `price_to_send`: `reviewing` (accepted, no price yet). *Added beyond the ticket's five; user U2.*
  3. `quote_ending`: `quoted`, `on_hold` or `deposit_pending`, the current quote not expired, its expiry
     would still cancel the project (ProjectService's rule: `deposit_pending` unless the deposit is covered;
     `quoted`/`on_hold` unless a non-zero deposit is covered), and it expires before the studio's midnight
     three days ahead: the last valid day is today, tomorrow or the day after.
  4. `deposit_link_missing` (owners): `deposit_pending`, deposit not covered, and no link or a link that no
     longer opens. *Added beyond the five; user U2.*
  5. `deposit_unpaid` (owners): the same with a working link made 72 hours ago or more (a new link
     restarts the clock: the row's `updated_at`).
  6. `no_session`: `booked` with no scheduled tattoo session, or `deposit_pending` with the deposit covered
     and none (settleBooking only books once a session exists).
  Client side ("waiting on clients"): `price_sent` (`quoted`), `on_hold`, `deposit_link_sent` (owners: a
  working link younger than 72 hours), `deposit_due` (artists: any uncovered deposit; they never see links).
  An expired quote that the sweep has not yet cancelled shows nowhere (the Projects list's flags own it).
  Reason: each project appears once, the five ticket rules are all there, and the two additions are the
  studio's next step on the same projects at no extra query. Rejected: one row per rule (a project ending
  tomorrow and unpaid would show twice).
- **D4. A fixed number of queries.** `work` = `listActive` (1, plus `ArtistService.list` inside `scopeTo` for
  an artist) + `QuoteService.currentFor` (1) + `DepositService.depositStates` (1, new) +
  `DepositLinkService.statesFor` (1, new, owners only) + `projectsWithScheduledTattoo` (1): at most 5 for
  either role, whatever the number of projects. Each batch method skips its query for an empty id list.
  `depositStates` uses a new pure `depositSettled(quote, payments)` next to `depositMoney`; `isSettled` stays
  as it is (it is on the booking path), and a test proves the two agree.
- **D5. Counts: nothing is counted twice.** Inbox badge = new requests (unchanged, owners). **Today badge** =
  `needsYouCount` (the project rows of "Needs you", both roles; new requests are left to the Inbox, so the
  page's "New requests" group is not in it). The **Projects badge goes away**: its screenshots are in
  Today's count (`proofCount` and its shared prop are removed). The **bell** counts only alert kinds no tab
  counts: for an owner none (new-inquiry alerts are the Inbox's count, screenshot alerts Today's), so an
  owner's bell shows no number and no query runs; for an artist both kinds (they have no Inbox, and their
  Today has no screenshots). The bell stays as the way to the alert history; the Alerts page is unchanged.
  `bellKinds(role)` holds the rule, so a future alert kind counts on the bell until a tab counts it.
  *User decision U3.* Rejected: the bell keeps all unread (P-11's double count), or the bell is removed (the
  history and the emailed links need it).
- **D6. Cost of the Today badge.** It runs `needsYouCount` on every tenant page: +5 small indexed reads,
  −1 (`proofCount`), and −1 for owners (no bell query): +3 for an owner, +5 for an artist (whose bell query
  stays). Accepted for a pilot studio's tens of active projects; the fallback if it ever shows up slow is in
  Risks. The Today page computes `work` again in its controller instead of passing results through the
  context (simpler, and the badge must be right on every page anyway).
- **D7. More is a menu, not a page.** On the phone the fifth tab is a "More" button opening the existing
  `DropdownMenu` upwards (`side="top"`), with Clients, Artists and Settings rows (44 px below `lg` by the
  component rule). Artists are reached in two taps (More, Artists) with one page load, and no new route or
  isolation case. Artist members have no More items, so they see three tabs (Today, Projects, Calendar).
  The desktop sidebar lists all seven destinations, with a `Separator` before the three "more" ones.
  Rejected: a `/more` page (a second page load on a slow phone, a route, roles and an isolation case);
  shadcn `sheet` (`shadcn add` downloads; the menu is enough).
- **D8. Active tab = where the page lives, not where you came from.** `isCurrentPath` stays the rule: an
  inquiry opened from Today highlights Inbox, a project page highlights Projects, `/clients/*`, `/artists/*`
  and `/settings/*` highlight More (and the matching row inside the menu carries `aria-current="page"`),
  `/today` highlights Today, `/alerts` highlights only the bell. Settings loses `also: /artists` (Artists
  has its own item). Reason: predictable after a reload, Back and a shared link; Back returns to Today.
  Rejected: remembering the origin tab (state that breaks on reload).
- **D9. Time zone.** All of Today is in the tenant's `timezone` (instants are stored in UTC): the date line
  (`todayIn`), today's sessions (`dayBounds(today)`, the calendar's own window, overlapping sessions
  included), "ends within 3 days" counted in studio days (D3.3), "for 3+ days" as elapsed time (72 hours,
  `now − link made`), "2 days ago" with `daysAgoText` (studio calendar days). `now` is a parameter of every
  rule so tests fix it. A tab left open past midnight is stale until reload (accepted; the day agenda's
  Now marker already follows the browser clock, as on the calendar).
- **D10. The setup checklist and the pilot numbers move to Today** (owners): the checklist shows until all
  four steps are done (`setup` is null once complete), first on the page when nothing needs you, else after
  the sessions; the pilot card sits at the bottom. The Inbox drops both props (and two services from its
  controller); its empty New view keeps the studio link card. Reason: owners now land on Today, and the
  same checklist on two screens is noise. *User decision U4.*
- **D11. Rows land on the card.** Each row's target is computed on the server as `{ route, id, hash }`
  (like `alertTarget`): screenshots `#payments`, prices to send `#quote-form`, prices ending and price sent
  `#quote`, deposit rows `#deposit`, sessions to book and today's sessions `#sessions`, new requests the
  inquiry page. The project page gets the ids `quote`, `deposit` and `quote-form` with the top-bar
  `scroll-mt` that `#payments` uses, and `#sessions` gets it too. TAT-108 must keep these five ids (Risks).
- **D12. Each group shows at most 5 rows** (`TODAY_ROWS`), oldest wait first, with "See all N in the Inbox"
  (requests) or "See all N on Projects" (a status filter where one status holds the whole group:
  `reviewing` for prices to send, `deposit_pending` for deposits; the Active list otherwise). Props carry
  only the rows shown and the counts.
- **D13. The day agenda is shared.** `DayAgenda`, `NowMarker`, `SessionItem` and `useNow` move unchanged to
  `inertia/components/day_agenda.tsx` and both pages use them; `sessionRow` moves to
  `#modules/scheduling/calendar`. Two fixes ride along because Today needs them: the client name loses
  `truncate` (ui.md: names wrap, `wrap-anywhere`), and a session opens its project at `#sessions`.

## 5. Design

Voice: a calm studio manager, short and specific (design doc, Voice). Tokens only; no hex, no palette
colour, no custom class. Names (Latin or Devanagari, e.g. `सीता थापा`) are never truncated, clamped,
upper-cased or letter-spaced: `wrap-anywhere`, line height 1.5 in rows. Every tappable row and link is at
least 44 px tall below `lg`.

 * What waits on a project, and on whom (TAT-107): the rules behind Today's "Needs you" and "Waiting
 * on clients", and TAT-109's "waiting" line. Pure: WaitingService gathers the facts from each
 * module's own service and calls these.

export const QUOTE_ENDING_DAYS = 3;
/** An unpaid deposit link needs a nudge once it is this many days (72 hours) old. */
export const DEPOSIT_CHASE_DAYS = 3;
/** Today shows at most this many rows per group. */
export const TODAY_ROWS = 5;

const DAY_MS = 86_400_000;
const QUOTE_STATUSES: readonly ProjectStatus[] = ["quoted", "on_hold", "deposit_pending"];

	| "price_to_send"
	| "quote_ending"
	| "deposit_link_missing"
	| "deposit_unpaid"
	| "no_session";

export type Waiting =

	| { side: "client"; reason: ClientWaitReason };

	status: ProjectStatus;
	/** When the project was made (accepted or booked). */
	since: DateTime;
	/** A deposit screenshot waits for an owner. */
	proofWaiting: boolean;
	/** The current quote of a quoted, on_hold or deposit_pending project; null otherwise. */
	quote: { issuedAt: DateTime; expiresAt: DateTime; depositAmount: number } | null;
	/** The current quote's deposit is covered (a zero deposit is); false without a quote. */
	depositSettled: boolean;

	depositLink: { madeAt: DateTime; works: boolean } | null;
	/** A tattoo session is scheduled. */

const plusDays = (date: string, days: number) =>
	DateTime.fromISO(date, { zone: "utc" }).plus({ days }).toFormat("yyyy-MM-dd");

/** The studio's midnight QUOTE_ENDING_DAYS days ahead: a quote expiring by then ends soon. */
export function quoteEndingBefore(now: DateTime, timezone: string): DateTime {
	return dayBounds(plusDays(todayIn(timezone, now), QUOTE_ENDING_DAYS), timezone).from;
}

/** Whether the quote's expiry would still cancel the project (ProjectService's expiry rule). */
function expiryWouldCancel(facts: WaitingFacts, depositAmount: number): boolean {
	if (facts.status === "deposit_pending") return !facts.depositSettled;
	return depositAmount === 0 || !facts.depositSettled;
}

/** The project's one waiting state, or null when nothing waits (first rule that matches wins). */
export function waitingOf(
	facts: WaitingFacts,
	{ isOwner, now, timezone }: WaitingContext,
): Waiting | null {
	if (facts.proofWaiting) {
		return isOwner ? { side: "studio", reason: "proof_to_check" } : null;
	}
	const { status, quote } = facts;
	if (status === "reviewing") return { side: "studio", reason: "price_to_send" };
	if (QUOTE_STATUSES.includes(status) && quote) {
		// An expired quote is the sweep's, and the Projects list's flags', not Today's.
		if (isExpired(quote, now)) return null;
		if (
			expiryWouldCancel(facts, quote.depositAmount) &&
			quote.expiresAt.toMillis() <= quoteEndingBefore(now, timezone).toMillis()
		) {
			return { side: "studio", reason: "quote_ending" };
		}
	}
	if (status === "deposit_pending") {
		if (facts.depositSettled) {
			return facts.scheduledTattoo ? null : { side: "studio", reason: "no_session" };
		}
		if (!isOwner) return { side: "client", reason: "deposit_due" };
		const link = facts.depositLink;
		if (!link?.works) return { side: "studio", reason: "deposit_link_missing" };
		return now.toMillis() - link.madeAt.toMillis() >= DEPOSIT_CHASE_DAYS * DAY_MS
			? { side: "studio", reason: "deposit_unpaid" }
			: { side: "client", reason: "deposit_link_sent" };
	}
	if (status === "booked") {
		return facts.scheduledTattoo ? null : { side: "studio", reason: "no_session" };
	}
	if (status === "quoted") return { side: "client", reason: "price_sent" };
	if (status === "on_hold") return { side: "client", reason: "on_hold" };
	return null;
}

/** One project and what waits on it. `facts` stays on the server: it holds owner facts. */
export type ProjectWaiting = {
	project: TattooProject;
	facts: WaitingFacts;
	waiting: Waiting | null;
	/** waitingText, or null when nothing waits. */
	text: string | null;
	/** The card on the project page where the member acts (WAITING_HASH), or null. */
	hash: string | null;
	/** How long it has waited: the sort key (sinceOf). */
	since: DateTime;
};

type TenantZone = Pick<Tenant, "id" | "timezone">;

/**
 * What waits on a studio's projects, and on whom (TAT-107): Today's "Needs you" and "Waiting on
 * clients", its tab badge, and TAT-109's list line. Asks each module's own service, in at most five
 * queries however many projects: QuoteService.currentFor, DepositService.depositStates,
 * DepositLinkService.statesFor (owners only: artists never get link facts) and
 * SessionService.projectsWithScheduledTattoo. The rules are waitingOf (#modules/projects/waiting).
 */
@inject()
export default class WaitingService {
	constructor(
		private projects: ProjectService,
		private quotes: QuoteService,
		private deposits: DepositService,
		private links: DepositLinkService,
		private sessions: SessionService,
	) {}

	/** Pass only projects `member` may see (ProjectService.list or listActive). */
	async forProjects(
		tenant: TenantZone,
		member: Member,
		projects: TattooProject[],
		now: DateTime = DateTime.now(),
	): Promise<Map<string, ProjectWaiting>> {
		const isOwner = member.role === "owner";
		const idsIn = (statuses: readonly ProjectStatus[]) =>
			projects.filter(({ status }) => statuses.includes(status)).map(({ id }) => id);
		const quotes = await this.quotes.currentFor(
			tenant,
			idsIn(["quoted", "on_hold", "deposit_pending"]),
		);
		const deposits = await this.deposits.depositStates(
			tenant,
			projects.map(({ id }) => id),
			quotes,
		);
		const links = isOwner
			? await this.links.statesFor(tenant, idsIn(["deposit_pending"]))
			: new Map<string, { madeAt: DateTime; works: boolean }>();
		const withTattoo = await this.sessions.projectsWithScheduledTattoo(
			tenant,
			idsIn(["booked", "deposit_pending"]),
		);
		const context = { isOwner, now, timezone: tenant.timezone };
		return new Map(
			projects.map((project) => {
				const quote = quotes.get(project.id) ?? null;
				const deposit = deposits.get(project.id);
				const facts: WaitingFacts = {
					status: project.status,
					since: project.createdAt,
					proofWaiting: deposit?.proofWaiting ?? false,
					quote: quote && {
						issuedAt: quote.createdAt,
						expiresAt: quote.expiresAt,
						depositAmount: quote.depositAmount,
					},
					depositSettled: deposit?.settled ?? false,
					depositLink: links.get(project.id) ?? null,
					scheduledTattoo: withTattoo.has(project.id),
				};
				const waiting = waitingOf(facts, context);
				return [
					project.id,
					{
						project,
						facts,
						waiting,
						text: waiting && waitingText(waiting, facts, now, tenant.timezone),
						hash: waiting && WAITING_HASH[waiting.reason],
						since: waiting ? sinceOf(waiting, facts) : project.createdAt,
					},
				];
			}),
		);
	}

## 12. Risks and rollback

- **TAT-108 (project page restructure) must keep the ids** `payments`, `quote`, `quote-form`, `deposit`,
  `sessions`, or change `WAITING_HASH` with them; a missing id only scrolls to the top (Inertia's fallback),
  so it fails soft. ui.md says so.
- **TAT-109 reuses `WaitingService.forProjects`** and `waitingText` for its list line; it may add facts (a
  next session, the balance) to `WaitingFacts`, keeping the five-query budget by batching.
- **Badge cost:** `needsYouCount` loads every active project on every tenant page. Fine for a pilot studio;
  if a studio's active list ever grows into the hundreds or the page shows up slow, the fallback is to share
  only the screenshot count as Today's badge (one query, `countPendingProofs`) and keep the full count on
  the Today page.
- **Owners' bell has no number:** an owner who relied on it sees the same events as Inbox and Today badges;
  the alert emails and the Alerts page are unchanged (U3).
- **A waiting screenshot on a closed project** is not on Today (closed projects are not read); it was in the
  old Projects badge. Rare (expiry spares a project while a screenshot waits); the project page still shows it.
- **Muscle memory:** owners used to land on the Inbox; the Inbox is one tap away with its badge.
- **Rollback:** revert the merge commit. No migration, no contract change, no data written by this ticket.
