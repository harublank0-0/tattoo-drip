## 4. Decisions

- **D1: the account page is `/account`, outside any studio,** in the existing signed-in group (`auth`, then `dbContext`; no `tenant`, no `role`, no `verifiedEmail`: an unconfirmed account may change its password). It acts only on `auth.user`: no id in the path or body, so there is nothing to scope and no IDOR. `users` and `account_tokens` have no RLS; every query runs in the request transaction (models and `dbClient()`), so the tripwire stays quiet. Rejected: `/t/:tenant/account` (a person's account is not a studio's record, an artist would need a role entry, and an account without a studio could not reach it) and studio Settings (owners only).
- **D2: passwords are 8 to 128 characters for signup, a reset and a change; sign-in keeps no length rule.** One constant, `PASSWORD_LENGTH = { min: 8, max: 128 }` in `#modules/identity/passwords`, feeds the validator, the messages and (by a pinned copy) the pages. 128 fits every common password manager's generator and is far below anything the body parser or scrypt cares about (facts). No stored password becomes unusable: forms never stored more than 32, and sign-in and the current-password field take any length. Rejected: 64 (TAT-18's floor; some generators go to 100 and more), 256 (no gain, a longer hint), adding a maximum to sign-in (could lock out an account seeded by hand with a longer password, and buys nothing).
- **D3: "Change password" asks for the current password, the new one and the new one again,** like signup and the reset (`passwordConfirmation`, `sameAs`). The new one must differ from the typed current one (`notSameAs("currentPassword")`): with the current password checked right, equal strings mean "the stored password". Validation runs before any check, so a body with an invalid new password never tests the current one (no extra oracle).
- **D4: the current password is checked before any lock, inside `throttlePasswordCheck`, against the hash the `auth` middleware loaded** (`user.verifyPassword`, scrypt with `safeEqual`). A wrong one is a field error on `currentPassword`, "That isn't your current password.", and nothing else differs between right and wrong (same validation path, same timing class). Counts: per client address 10 and per account 5 wrong checks per 15 minutes, address first, both taken before the check, a right one gives its two points back while their windows are open, wrong ones stay counted (exactly `throttleLogin`'s rules, sharing `giveBack`). Rejected: counting with a `limiter.define` middleware (it would count right passwords too, and no other change is rate-sensitive: each success emails the account and needs the then-current password).
- **D5: one locked write per action, with a stale-session check.** `AccountService.changePassword(user, password)` revokes a pending reset link (the lock order's first row), locks the user row `FOR UPDATE`, and throws `SessionEndedError` if the locked row's `session_version` is not the one the request signed in with (`user.sessionVersion` of the `auth` instance): another request (a reset, a change or a sign-out from another device) ended this session after `auth` ran. Otherwise it sets the password and `session_version + 1` in ONE `save()` (one UPDATE), queues the notice with `sendMailInTransaction`, and clears the stored address's login failures after the commit, like the reset. `signOutOtherSessions(user)` takes the same lock and check and raises the version only. Throwing inside `withTransaction` rolls the savepoint back, so a refused change revokes nothing. The check matters: without it, a stolen session whose request was already past `auth` when the owner signed everyone out would wait for the lock, raise the version again and adopt it, so the thief would stay and the owner would be out. The invariant it relies on (every write of `users.password` raises `session_version` in the same UPDATE, so an unchanged version means the checked hash is still the stored one) goes in the service comment and backend.md.
- **D6: the asking session stays signed in by signing it in again** (`auth.use("web").login(updatedUser)` after the service returns): the session stores the new version and gets a new id (facts), so a planted or copied session id does not survive the change, and a copied cookie-store session (production keeps sessions in cookies) holds the old version and is signed out. If the request's commit then failed, the session would hold a version the row does not have and be signed out on its next request: fail closed. On `SessionEndedError` the controller does what `SessionController.destroy` does (logout, forget `LAST_TENANT_KEY` and staged tokens), flashes "You were signed out on another device. Sign in again." and redirects to `/login`.
- **D7: "Sign out of other devices" keeps this device and asks no password;** it asks in the page with `InlineConfirm` (never `window.confirm`), limited to 10 per account an hour (`throttleSignOutOthers`, a `limiter.define` with `perAccount`). It changes no credential, so it sends no email. The hour limit also keeps `session_version` astronomically far from the 9-digit ceiling of `IDENTIFIER` (at 10 an hour, about 11,000 years). The worst a stolen session can do with it is sign the owner out once; the owner signs in again (the thief has no password) and signs the thief out for good. (User decisions U1, U2.)
- **D8: a change ends a pending reset link** (`tokens.revoke(user.id, "reset_password")`, before the user lock): the person just set a password they know, and a live link would be a second way in for an hour. The confirmation link is left alone (a change proves the password, not the mailbox). Rejected: also revoking on sign-out (it has nothing to do with credentials).
- **D9: no password reaches the session's flash on the dashboard's path.** `backWithThrottleMessage` also leaves out `currentPassword` (one shared list `UNFLASHED_INPUTS` in `handler.ts`). Validation failures of Inertia requests flash no input (facts). Accepted, not changed: a hand-made non-Inertia post keeps its own typed `passwordConfirmation`/`currentPassword` in its own encrypted session flash for one request (no prop, no log, no other person), as signup and reset do today; overriding the session package's renderer is out of proportion.
- **D10: the notice says which devices were signed out.** `PasswordChangedMail` gets `signedOut: "everywhere" | "elsewhere"` (required, so both call sites choose): the reset keeps "every device that was signed in was signed out"; a change says "every device that was signed in was signed out except the one used to change it". Same subject, same `/forgot-password` link (the "if it wasn't you" path: a completed reset raises the version and signs the thief out too), no token, no link that signs in, to the stored address.
- **D11: the page uses `AppLayout`, and the shell keeps its top bar at every width when there is no studio,** with the wordmark (to `home`, which lands on the last studio) where the switcher was; no tab bar, no sidebar (they list studio pages). The page also has a "Back to your studio" link (`dashboard`), or "Set up your studio" for an account without one (one `hasTenant` query). Rejected: `AuthLayout` (the marketing split with "Inquiries, quotes and deposits…") and `MarketingLayout` (no account menu), and a studio shell for `/account` (would need tenant context, role and badges).
- **D12: "Your account" is a row of the account menu for every role,** above "Your artist profile" (`KeyRound` icon): the menu is on every page at both widths. Not in More (studio pages, owners only).
- **D13: UI rules live in a pure module** `inertia/components/account.ts` (words, the range hint, the back label, the submit label, `describedBy`), unit-tested; `PASSWORD_HINT` is pinned equal to the server's range. The submit button reuses `takesFocusBack` (imported, not copied) so it keeps focus after a save; a refusal moves focus to the first invalid field (`focusFirstInvalid`). `InlineConfirm` gains an optional `busyLabel` (default "Saving…") so the sign-out says "Signing out…".

### Decisions only the user can make (the builder proceeds with the default)

- **U1. Does "Sign out of other devices" ask for the password?** Default: **no**, an in-page confirmation only (D7). The alternative (current password, counted by the same limits) blocks a thief with a stolen session from signing the owner out once, at the cost of one more field.
- **U2. Does "Sign out of other devices" email the account?** Default: **no** (it changes no credential; the person is signed in when they do it). The alternative is a short "Every other device was signed out" notice.

  /**

  	const ipWindow = await perIp.consume(ipKey);
  	const userWindow = await perUser.consume(userKey);
  	const right = await verify();
  	if (right) {

  	/**
  	 * Changes the password of a signed-in account (TAT-95): the caller has
  	 * checked the current password (throttlePasswordCheck). Ends a pending
  	 * reset link, then, under the user's lock, sets the password and raises the
  	 * session version in one UPDATE (every other session is signed out on its
  	 * next request), emails the stored address and, once committed, clears its
  	 * login failures. Returns the account with its new version, for the
  	 * caller to sign the asking session in again. Lock order: the reset
  	 * token's row (revoke), then the user (see the class).
  	 */
  	async changePassword(user: User, password: string): Promise<User> {
  		return withTransaction(async (trx) => {
  			await this.tokens.revoke(user.id, "reset_password");
  			const locked = await this.lockSession(user);
  			locked.password = password;
  			locked.sessionVersion += 1;
  			await locked.save();
  			await sendMailInTransaction(
  				new PasswordChangedMail({
  					to: locked.email,
  					changedAt: changedAtText(DateTime.now()),
  					resetUrl: appLink("/forgot-password"),
  					signedOut: "elsewhere",
  				}),
  				trx,
  			);
  			const storedEmail = locked.email;
  			afterCommit(() => clearLoginFailures(storedEmail));
  			return locked;
  		});
  	}

  	 * "Sign out of other devices" (TAT-95): raises the session version under the
  	 * user's lock, so every other session is signed out on its next request.
  	 * Returns the account with its new version, for the caller to sign the
  	 * asking session in again.
  	 */
  	async signOutOtherSessions(user: User): Promise<User> {
  		return withTransaction(async () => {
  			const locked = await this.lockSession(user);
  			locked.sessionVersion += 1;
  			await locked.save();
  			return locked;
  		});
  	}

  	 * Locks the account of the session that asked and checks that the session
  	 * still holds its current version (`user` is the instance auth loaded, so
  	 * its version is the session's). Another request may have raised it since
  	 * (a reset, a change or a sign-out elsewhere): then this session is over
  	 * and SessionEndedError rolls the caller's work back. Every write of
  	 * `users.password` raises `session_version` in the same UPDATE, so an
  	 * unchanged version also means the hash the caller checked is the stored
  	 * one: keep that true in any new path that sets a password.
  	 */
  	private async lockSession(user: User): Promise<User> {
  		const locked = await User.query().where("id", user.id).forUpdate().first();
  		if (!locked || locked.sessionVersion !== user.sessionVersion) {
  			throw new SessionEndedError();
  		}
  		return locked;
  	}

     * The person's own account (TAT-95), outside any studio: the signed-in group
     * (auth, then the request transaction). Every action is on auth.user only.
     * Changing the password and "Sign out of other devices" raise the session
     * version, then sign this session in again, which stores the new version
     * under a new session id: this device stays, every other one is out.
     */
    @inject()
    export default class AccountController {
    	constructor(
    		private accounts: AccountService,
    		private tenancy: TenancyService,
    	) {}

    	async show({ auth, inertia }: HttpContext) {
    		const hasStudio = await this.tenancy.hasTenant(auth.getUserOrFail());
    		return inertia.render("account/show", { hasStudio });
    	}

    	/** The current password is checked (and counted) before anything is locked. */
    	async changePassword(ctx: HttpContext) {
    		const { request, auth, session, response } = ctx;
    		const { currentPassword, password } = await request.validateUsing(
    			changePasswordValidator,
    		);
    		const user = auth.getUserOrFail();
    		const right = await throttlePasswordCheck(request.ip(), user.id, () =>
    			user.verifyPassword(currentPassword),
    		);
    		if (!right) {
    			throw new errors.E_VALIDATION_ERROR([
    				{ field: "currentPassword", message: WRONG_CURRENT_PASSWORD, rule: "currentPassword" },
    			]);
    		}
    		const changed = await this.unlessEnded(ctx, () =>
    			this.accounts.changePassword(user, password),
    		);
    		if (!changed) return;
    		await auth.use("web").login(changed);
    		session.flash("success", "Password changed. Other devices are signed out.");
    		return response.redirect().toRoute("account.show");
    	}

    	async signOutOthers(ctx: HttpContext) {
    		const changed = await this.unlessEnded(ctx, () =>
    			this.accounts.signOutOtherSessions(ctx.auth.getUserOrFail()),
    		);
    		if (!changed) return;
    		await ctx.auth.use("web").login(changed);
    		ctx.session.flash("success", "Signed out of every other device. You're still signed in here.");
    		return ctx.response.redirect().toRoute("account.show");
    	}

    	/**
    	 * Runs a write; when another request ended this session meanwhile
    	 * (SessionEndedError, its savepoint already rolled back), signs the
    	 * session out as logout does and sends it to sign in.
    	 */
    	private async unlessEnded(
    		ctx: HttpContext,
    		write: () => Promise<User>,
    	): Promise<User | null> {
    		try {
    			return await write();
    		} catch (error) {
    			if (!(error instanceof SessionEndedError)) throw error;
    			await ctx.auth.use("web").logout();
    			ctx.session.forget(LAST_TENANT_KEY);
    			forgetStagedTokens(ctx.session);
    			ctx.session.flash("error", "You were signed out on another device. Sign in again.");
    			ctx.response.redirect().toRoute("session.create");
    			return null;
    		}
    	}

## 11. Review focus (Fable and Codex)

- **Session handling:** the stale check under the row lock (a request that passed `auth` before another raised the version can never raise it again and adopt it); the asking session's re-login stores the new version and rotates the id; an old cookie-store session is dead by its version; the invariant "every password write raises the version" holds on every path (`User.create`, reset, change); the 9-digit identifier ceiling is unreachable under the limits.
- **Atomicity and lock order:** the password hash and the version in one UPDATE; the reset token's row before the user's row (the class comment's order; no deadlock with `resetPassword`); a refused change rolls back the revoke; the notice exists only if the change committed; `clearLoginFailures` only after the commit.
- **The password check:** before any lock; counted per address then per account before checking; refunds only on a right password; no difference between right and wrong besides the field error; validation (including `notSameAs`) before the check.
- **Information exposure:** no password in any flash (the throttle path's list, the Inertia validation path), prop, log or email; the email goes to the stored address and holds no token and no link that signs in; `/account` is `private, no-store`.
- **Route protection:** the three routes are in the signed-in group only (auth, dbContext), CSRF-protected writes, no tenant context needed (users and tokens have no RLS, no raw `db` use); the exhaustive route list in `account_routes.spec.ts` has no hole.

- **Accessibility:** field errors tied by `aria-describedby`, focus after save, refusal and confirm; 44 px targets; no `window.confirm`.

## 12. Risks and rollback

- **A double-submitted change** (two requests from one session with the right password): the second finds the version moved and signs this session out (fail closed). The submit button is disabled while the first is out, so it takes a hand-made race. Accepted.
- **A commit that fails after the re-login:** the session holds a version the row does not have and signs out on its next request (fail closed).
- **Shared addresses (carrier NAT):** ten wrong current passwords from one address in 15 minutes block that address's checks for everyone on it; only signed-in people can try. Accepted, like sign-in's address limit.
- **A stolen session** can sign the owner out once (D7, U1); it cannot change the password without the current one.
- **Hand-made non-Inertia posts** keep their own typed passwords in their own session flash for one request (D9). Accepted.
- **Rollback:** revert the seven commits; no migration, no data to undo. Passwords of 33 to 128 characters set meanwhile still sign in after a rollback (sign-in has no length rule); a later reset would then ask for 32 or fewer. Mails already queued are rendered and unaffected.
