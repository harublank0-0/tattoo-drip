# Job Queue Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **This plan is implemented by hand by the user.** Claude does not write the product code. After each task, the user says it's done and Claude reviews the diff against that task before the next one starts.

**Goal:** A Postgres-backed job queue with a worker process, every email sent through it, and a helper that queues jobs inside a database transaction.

**Architecture:** `@adonisjs/queue` with its `database` driver stores jobs in a `queue_jobs` table in the app's own Postgres. `node ace queue:work` runs them in a separate process. `mail.sendLater` hands each email to a `SendMailJob` through a mail messenger. `dispatchInTransaction` points a dispatcher at the caller's transaction, so the job commits or rolls back with the data.

**Tech Stack:** AdonisJS 7, `@adonisjs/queue` 0.6.2, `@boringnode/queue` 0.6.0, `@adonisjs/mail` 10, Lucid on PostgreSQL 18, Japa, Podman with podman-compose 1.3.0.

**Spec:** `docs/superpowers/specs/2026-10-05-job-queue-design.md`

## Global Constraints

- Run commands from `apps/platform` unless a step says the repo root.
- Exact versions: `@adonisjs/queue` **0.6.2** and `@boringnode/queue` **0.6.0**, installed with `pnpm add -E`. Never add one without the other or with a range; two copies of `@boringnode/queue` break transactional dispatch.
- The queue driver is `database` in development, tests and production. `sync` stays configured but is never the default.
- The Lucid connection name is `pg` (see `config/database.ts`).
- Shared queue plumbing goes in `app/jobs/`. Domain jobs go in `app/modules/<module>/jobs/`. Non-job files never go in a jobs folder, because the worker loads every file there as a job.
- App code sends email with `mail.sendLater`. `mail.send` is only used inside jobs.
- No tenant context code. Jobs that touch tenant data carry `tenantId` in their payload; TAT-28 applies it.
- The `psql` commands in this plan assume the example `DB_USER=postgres` and `DB_DATABASE=tattoo_drip`; adjust them if your `apps/platform/.env` differs.
- Never read, print or commit `apps/platform/.env`. Never hand-edit `database/schema.ts` or `.adonisjs/`; they are regenerated.
- Formatting: Biome, tabs, double quotes. Run `pnpm format:fix` from the repo root before committing.
- Commits: Conventional Commits with scope `platform` (no scope for root-only changes), body ending with `Refs: TAT-7`.

## Review Focus

- **SMTP unreachable** (Mailpit stopped, provider outage): the email is retried 3 times with backoff, then kept as a `failed` row with its error, never silently lost. Pinned by the manual SMTP-down check in Task 2.
- **Worker killed while a job runs:** the job is recovered as stalled and run again, so an email can be sent twice. Delivery is at-least-once. No test; it's documented in the AGENTS.md Jobs section in Task 4.
- **Template data that isn't plain JSON** (model getters, `Date`, `Buffer`): after the queue, getters are gone and dates are strings. Pinned by the JSON round trip in the `SendMailJob` test in Task 2, and documented in Task 4.
- **`dispatchInTransaction` with a faked or non-database queue:** it dispatches normally instead of crashing or bypassing the fake. Pinned by the third test in Task 3.
- **Development without the worker running:** emails wait in `queue_jobs` and go out once `pnpm worker` starts. Pinned by the manual check in Task 2 (queue first, start the worker second).

### Task 0: Make local Postgres start

**Why:** `pnpm podman:up` can't start Postgres today. podman-compose 1.3.0 resolves `${POSTGRES_USER…}` from the service's own `environment:` when that service defines `POSTGRES_USER`, so the container gets the literal text `${POSTGRES_USER:-postgres}` as its username and crash-loops in `initdb`. Reading the platform's own `DB_*` names instead avoids the collision, and passing `apps/platform/.env` to compose means one file configures both the container and the app. Every later task needs a working database.

**Files:**
- Modify: `docker-compose.yml` (the `postgres` service)
- Modify: `package.json` at the repo root (the `podman:up` script)
- Modify: `README.md` (Setup)

- Consumes: `DB_USER`, `DB_PASSWORD`, `DB_DATABASE` and `DB_PORT` from `apps/platform/.env`, falling back to the `.env.example` values when the file doesn't exist yet.
- Produces: a local Postgres 18 whose user, password, database and host port match `apps/platform/.env`, with the database created on first start.

```ts
		emitter.restore();

	test("sends a queued message, rendering its templates at send time", async ({
		assert,
	}) => {
		mail.fake();
		const events = emitter.fake(["mail:sent"]);

		const user = new User();
		user.email = "ink@example.com";
		user.fullName = "Ada Ink";

			"https://app.tattoo-drip.test/verify-email?token=abc",
```

- [ ] **Step 4: Write `SendMailJob`**

```ts
import logger from "@adonisjs/core/services/logger";
import mail from "@adonisjs/mail/services/main";
import type {
	MailersList,
	MessageBodyTemplates,
	NodeMailerMessage,
} from "@adonisjs/mail/types";
import { Job } from "@adonisjs/queue";

export type SendMailPayload = {
	mailerName: string;
	mailMessage: { message: NodeMailerMessage; views: MessageBodyTemplates };
	sendConfig?: unknown;
};

/**
 * Sends one email queued by `mail.sendLater`. The templates render here,
 * in the worker, from the JSON stored in queue_jobs. Retries come from the
 * defaults in config/queue.ts.
 */
export default class SendMailJob extends Job<SendMailPayload> {
	async execute() {
		const { mailerName, mailMessage, sendConfig } = this.payload;
		await mail
			.use(mailerName as keyof MailersList)
			.sendCompiled(mailMessage, sendConfig);
	}

	/**
	 * Runs once retries are used up. Logs who and what, never the body.
	 */
	async failed(error: Error) {
		const { message } = this.payload.mailMessage;
		logger.error(
			{ err: error, jobId: this.context.jobId, to: message.to, subject: message.subject },
			"email could not be sent",
		);
	}
}
```

### Task 3: Queue a job inside a transaction

**Why:** this is the reason for using a Postgres queue. A job queued with the caller's transaction exists only if that transaction commits, so there's never an alert for an inquiry that was rolled back, or an inquiry with no alert.

**Files:**
- Test: `apps/platform/tests/functional/queue/dispatch_in_transaction.spec.ts`
- Create: `apps/platform/app/services/queue.ts`

**Interfaces:**
- Consumes: `config/queue.ts` (the default adapter is `database`); `@boringnode/queue@0.6.0` from Task 1.
- Produces: `export function dispatchInTransaction(dispatcher: Dispatcher, trx: TransactionClientContract): Promise<DispatchResult>` at `#services/queue`, where `Dispatcher` is any job dispatcher: `{ with(adapter: AdapterFactory): unknown; run(): Promise<DispatchResult> }`. Usage: `await dispatchInTransaction(SomeJob.dispatch(payload), trx)`.

- [ ] **Step 1: Write the test**

`tests/functional/queue/dispatch_in_transaction.spec.ts`. It's the first database test. Each test runs inside a transaction that's rolled back afterwards, so nothing is left in your dev database.

```ts
import testUtils from "@adonisjs/core/services/test_utils";
import db from "@adonisjs/lucid/services/db";
import { Job } from "@adonisjs/queue";
import queue from "@adonisjs/queue/services/main";
import { test } from "@japa/runner";
import { dispatchInTransaction } from "#services/queue";

class NoopJob extends Job<{ label: string }> {
	async execute() {}
}

async function jobExists(jobId: string) {
	return Boolean(await db.from("queue_jobs").where("id", jobId).first());
}

test.group("dispatchInTransaction", (group) => {
	group.each.setup(() => testUtils.db().withGlobalTransaction());
	group.each.teardown(() => queue.restore());

	test("keeps the job when the transaction commits", async ({ assert }) => {
		const { jobId } = await db.transaction((trx) =>
			dispatchInTransaction(NoopJob.dispatch({ label: "commit" }), trx),
		);

		assert.isTrue(await jobExists(jobId));
	});

	test("drops the job when the transaction rolls back", async ({ assert }) => {
		let jobId = "";

		await assert.rejects(
			() =>
				db.transaction(async (trx) => {
					({ jobId } = await dispatchInTransaction(
						NoopJob.dispatch({ label: "rollback" }),
						trx,
					));
					throw new Error("roll back");
				}),
			"roll back",
		);

		assert.isNotEmpty(jobId);
		assert.isFalse(await jobExists(jobId));
	});

	test("dispatches normally when the queue isn't the database adapter", async () => {
		const fake = queue.fake();

		await db.transaction((trx) =>
```

`app/services/queue.ts`:

```ts
import type { TransactionClientContract } from "@adonisjs/lucid/types/database";
import queue from "@adonisjs/queue/services/main";
import type { AdapterFactory, DispatchResult } from "@adonisjs/queue/types";
import { KnexAdapter, knex } from "@boringnode/queue/drivers/knex_adapter";

type Dispatcher = {
	with(adapter: AdapterFactory): unknown;
	run(): Promise<DispatchResult>;
};

/**
 * Queues a job inside `trx`, so the job exists only if the transaction
 * commits. Pass the dispatcher, not the job, to keep the queue's chaining:
 *
 *   await dispatchInTransaction(AlertStaffJob.dispatch(payload).toQueue("alerts"), trx)
 *
 * Only the database adapter can join a transaction. With the sync driver,
 * or a faked queue in tests, the job is dispatched normally.
 */
export function dispatchInTransaction(
	dispatcher: Dispatcher,
	trx: TransactionClientContract,
) {
	if (queue.use() instanceof KnexAdapter) {
		dispatcher.with(knex(trx.knexClient));
	}
	return dispatcher.run();
}
```
