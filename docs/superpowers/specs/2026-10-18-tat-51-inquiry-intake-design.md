# Inquiry intake: POST /inquiries with references, client matched by phone (TAT-51)

Date: 2026-10-18
Refs: TAT-51. Builds on TAT-32 (see "Depends on TAT-32"), TAT-37 (`Inquiry`, `ReferenceImage`, `Client`), TAT-21 (`ImageService`), TAT-41/43 (`ClientService`), TAT-31 (artists' `visible`, `accepting_inquiries`), TAT-7 (the queue, `TenantJob`, `dispatchInTransaction`). Absorbs TAT-68 (ruling 1). Blocks TAT-57 (intake form) and TAT-55 (abuse protection). The ticket text is the contract; this spec departs from three of its lines, each in a ruling: "inquiry JSON" (2), "or HEIC" (4) and the code for a hidden or unknown artist (8). Carry-forwards honoured: TAT-41/43 (`findByPhone` first, `create` exists, never overwrite a client, the frozen contact copy: rulings 5, 6), TAT-46 (images on the inquiry, `position` order, `tenants/<id>/reference_image/` keys: 9), the TAT-21 review (rate limits, a decode concurrency limit, sharp's cache, the pixel limit: 11).

## Goal

A person on a studio page sends one multipart request: the inquiry and up to 5 reference images. The API matches the studio's client by phone (or creates one), stores the images privately, saves a `new` inquiry the inbox (TAT-46) shows and queues the staff alert, all or nothing. The contract, SDK and React hook move from the booking draft to `createInquiry`.

Written without the user (unattended run): every open question is a ruling below. **No migration.**

## Rulings

1. **TAT-68 is absorbed, except the deposit endpoints.** This ticket replaces `createBooking` with `createInquiry`, drops `bookings` and `useCreateBooking`, adds `useCreateInquiry` and tags the V1 operations `V1`; TAT-65 adds `deposits.*` with its own shapes. The PR closes TAT-68 and says so. Rejected: a separate TAT-68 PR (two edits of the same lines back to back).
2. **Multipart with flat fields, not a JSON part (against the ticket's "inquiry JSON").** `multipart/form-data` with camelCase text fields named like the inquiry columns (`idea`, `placement`, `approximateSize`, `preferredDates`, `preferredArtistId`, `budget`, `sourceChannel`, `contactName`, `contactPhone`, `contactEmail`), each image a `referenceImages` part, and `challengeToken`. Any other body is 415 `unsupported_media_type`. Why: one validator over the parsed body with the parser's trimming and empty-to-null, no second parser whose own failure (bad JSON in a good multipart body) needs its own error; OpenAPI describes each form field with its limits; `fields` keys equal the SDK's input keys. Rejected: a JSON `inquiry` part; bracket names (`contact[name]`); also accepting JSON bodies. The `client: {…}` / `tattoo: {…}` sketch in `docs/sdk.md` is replaced.
3. **Limits are the columns'.** Required: idea (4000), placement (120), approximateSize (120), preferredDates (500), sourceChannel (enum), contactName (120), contactPhone (40 as typed, stored E.164 through `phoneNumber`). Optional: preferredArtistId (uuid), budget (120, free text), contactEmail (254, email), challengeToken (2048). Trimmed; empty means none; a NUL character is a field error (PostgreSQL can't store it; it would be a 500). Images: at most 5, each 10 MB with jpg/jpeg/png/webp (`imageFile()`), 20 MB of files per request (the existing multipart limit) and 2 MB of text (the parser's default), both 413. Rejected: raising the global multipart limit to 50 MB (the dashboard's too, and 50 MB anonymous disk writes; TAT-57 compresses in the browser).
4. **No HEIC decoder (against the ticket's "or HEIC").** JPEG, PNG and WebP only; `ImageService` is unchanged, and a HEIC file gets "Upload a JPEG, PNG or WebP image." iPhones convert HEIC when the file input accepts only these types, and TAT-57 re-encodes in the browser anyway; a decoder means a custom libvips build or a WASM decoder running on hostile input. The requirements line changes to match. Rejected: libheif or a WASM decoder.
5. **Matching never changes a client.** `ClientService.matchByPhone` takes the studio's live client with the E.164 phone under a row lock (`findByPhone` plus `FOR UPDATE`), else creates one with the submitted name and email (no notes). A found client is never written. A deleted client's phone is free, so it gets a new client. An anonymized client still holding its phone (none exist; TAT-42 hasn't shipped) is reused untouched: refusing would lose the inquiry and reveal the match, and the unique index keeps a second client off the phone; TAT-42 must null the phone when it anonymizes. The inquiry stores what was sent (trimmed, phone in E.164). Owner-only client code (TAT-41) is unchanged.
6. **Same-phone submissions serialize.** A found client's row lock holds until commit; for a new phone the unique index does it: the second insert waits, fails with `phone_taken` inside its savepoint, then finds and locks the winner's client. Rejected: advisory locks, SERIALIZABLE.
7. **The open-inquiry cap lives here.** "Open" means a live (not deleted) inquiry with status `new` (not yet accepted or declined) whose frozen `contact_phone` is this E.164 phone, in this studio. With 3 open, the next is 409 `too_many_open_inquiries`. It is counted under ruling 6's lock, so concurrent submissions can't overshoot. Counting the phone, not the client, also covers a deleted client's open inquiries; anonymized ones (no phone) don't count. TAT-55's identical checkbox is met here. Rejected: counting `client_id`; a TAT-55 middleware (no lock, a second match).
8. **Artist rules; a hidden or unknown artist is a field error.** `preferredArtistId` must be one of the studio's live, visible artists (`ArtistService.listVisible`, compared in memory, so a malformed id never reaches a query). The ticket's "clear error code" for a hidden or unknown artist is `validation_failed` with `fields.preferredArtistId` ("Choose an artist from the list, or none."), the same for unknown, hidden, deleted and another studio's. A visible artist with accepting off is 409 `artist_not_accepting`. No artist chosen while the studio has visible artists and none accepts is 409 `studio_not_accepting`; a studio with no visible artists still takes general inquiries (nobody closed anything). Rejected: a 404 or a separate code (it belongs next to the picker, and `fields` come only with `validation_failed`); one code for both closed cases (the form says different things).
9. **Order and atomicity.** `IntakeService.submit`, one transaction (the request's, through `withTransaction`): artist rules, match (lock), cap, store images, insert the inquiry and its reference rows (`position` 0 to n-1), queue the alert (16). Every refusal comes before any image is decoded. Each image registers `afterRollback` deletion right after `store()` resolves, so a bad image 3 of 4 (`validation_failed` on `referenceImages.2`), a later failure or a failed commit leaves no row, no job and no file. Only a process crash between storing and rollback can orphan a file (a sweep of unreferenced keys can come with TAT-27). Rejected: storing images before the transaction (TAT-32 opens it before the controller).
10. **Temp uploads are always deleted.** The body parser writes every upload to a temp file before route code runs, and nothing deletes rejected ones, so anonymous uploads could fill the disk. `discardUploads(request)` (`#services/uploads`) removes every leftover: in the exception handler's API branch (body parser 413 or 400, unknown or old slug, every refusal) and in the controller's `finally` (success, stray file fields). Tests send uploads to `tmp/storage/uploads` to check it. Rejected: `processManually` for this route (our own streaming code instead of the parser's).
11. **Decode limits (TAT-21 carry-forward).** At most 2 images decode at once per process (`limitConcurrency`), sharp's cache is off, and the cheap format sniff runs before waiting for a slot. The 40 MP limit stays (lowering it refuses more uncompressed phone photos). Rate limits are TAT-38's and TAT-55's. Risk: a request waiting for a slot holds its pooled connection (the transaction is already open), so TAT-38 must land before any public deploy.
12. **No enumeration beyond what the phone's owner needs.** New and returning phones get the same 201 `{ data: { id } }`: no echo, no client, no URLs. The only phone-dependent answer is the cap's 409, checked after every phone-independent rule; it says "You already have requests waiting with this studio. They will reply on WhatsApp or Viber.", never a count, a name or which inquiries. Accepted because the requirement asks for the cap, and TAT-55's per-phone limit bounds probing. Rejected: silently dropping capped inquiries (a real request would vanish).
13. **No idempotency key.** Duplicates come from resubmitting after a timeout: uploads get 2 minutes (14), the hook never retries, TAT-57 disables the button, the cap bounds a loop at 3, and an owner declines a duplicate in one tap. Rejected: a key (a migration, a CORS header or field, replay logic) for a pilot.
14. **SDK and React.** `inquiries.create(input, { signal?, timeoutMs? })` sends a `FormData` (null and undefined fields left out, images in order, the token if given; fetch sets the boundary) and returns `InquiryReceipt`. `RequestOptions` gains `timeoutMs`; uploads default to 120 s, not the client's 10 s. No business rules in the SDK. `useCreateInquiry` is a plain mutation (no retry); hook tests stay TAT-11's. Rejected: a client-wide upload timeout option.
15. **CORS and caching need nothing new.** A browser `FormData` POST with only `Accept` is a CORS simple request (multipart is a safelisted type), so it doesn't preflight; a preflight naming `content-type` passes TAT-32's list (it names headers, not values, so the boundary is irrelevant). The POST stays `no-store`; a GET is TAT-32's 405 with `Allow: POST`.
16. **The staff alert: a queued job that TAT-52 fills in.** `submit` queues `NewInquiryAlertJob { tenantId, inquiryId }` (a `TenantJob`) with `dispatchInTransaction`, so it exists exactly when the inquiry commits. After this ticket the worker runs it in the tenant's context: it loads the inquiry, does nothing if it is gone or decided, and otherwise logs "New inquiry received." with the two ids (no contact details). No email, SMS or in-app notification is sent; TAT-52 replaces the log line with the owners' and preferred artist's alerts. The inbox badge already counts new inquiries. Rejected: an in-process event after commit (lost on a crash, and TAT-52 would want a job anyway); nothing (the ticket says "trigger").
17. **The bot challenge's slot (TAT-55).** `challengeToken` (the name TAT-55's ticket uses) is accepted, length-checked and ignored. TAT-55's challenge and honeypot become route middleware on `api.v1.inquiries.store` after `publicTenant`; its per-phone limit goes in the controller after validation (it needs E.164) and before `submit`, where a comment marks it. Unknown fields are dropped, so a honeypot field is harmless today.
18. **One code list, one envelope.** The three intake codes join TAT-32's `API_ERRORS` table (status and the one message each) and `ApiErrorCode`, and the controller throws them with `ApiException.of(code)`; the contract's `ErrorResponse` description and `docs/sdk.md` list them with the shared codes. Rejected: messages inline in the controller (a second list).
19. **A new `IntakeService`.** In the inquiries module, on `ArtistService`, `ClientService` and `ImageService`; `InquiryService` (the inbox) is unchanged. Rejected: growing `InquiryService` (two jobs, and its constructor is used in tests).

| Status | `code` | When |
|---|---|---|
| 201 | | `{ data: { id } }`, `no-store` |
| 400 | `bad_request` | Truncated or unreadable multipart (TAT-32) |
| 404 | `not_found` | Unknown slug, or any write under an old slug (TAT-32) |
| 409 | `artist_not_accepting`, `studio_not_accepting`, `too_many_open_inquiries` | Rulings 7, 8 |
