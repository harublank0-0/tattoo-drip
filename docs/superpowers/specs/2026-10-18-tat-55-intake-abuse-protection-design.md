# Abuse protection on the intake form: bot challenge, honeypot, rate limits (TAT-55)

Date: 2026-10-18
Refs: TAT-55. Builds on TAT-51 (the intake), TAT-32 (the public API stack), TAT-65 (the limiter's own pool), TAT-8 (the limiter, `digest`, `clientAddress`). Blocks TAT-57 (the form). Linear has no comments on TAT-55, TAT-57 or TAT-38 (checked 2026-10-18). Carry-forwards ruled on: TAT-51 ruling 17 (the slots), TAT-32 ruling 16 and its review amendment (what runs before the body), the TAT-21 review on TAT-51 (rate limits for the first anonymous upload: rule 8), TAT-12's deferred D2 (rule 12). Written without the user (unattended run): every open question is a ruling below. **No migration.**

## Goal

A scripted or flooded `POST /api/v1/tenants/:tenant/inquiries` is refused cheaply, before the body is read wherever possible; a person on a studio page doesn't notice. Platform, contract, SDK and React tests; the widget and the form are TAT-57's.

## Rulings

1. **Scope.** A server-side challenge check, a honeypot, three intake limits, the contract, SDK and React tests. The cap (acceptance line 4) is TAT-51's ruling 7, verified in the built code, not rebuilt: `OPEN_INQUIRY_LIMIT` = 3 live `new` inquiries with that E.164 `contact_phone` in the studio, counted in `submit` under `matchByPhone`'s row lock, refused 409 `too_many_open_inquiries`; the plan adds one test that the limits don't change it. Rejected: moving the cap into a middleware (no lock).
2. **Cloudflare Turnstile, a Managed widget shown only when Cloudflare needs an interaction.** Free, no puzzles for most people, no ad profile, one script and one server call; a person flagged by reputation (a carrier-NAT address shared with bots is the likely case in Nepal) gets a checkbox instead of a dead end. Rejected: hCaptcha (puzzles more often), reCAPTCHA (a Google profile), a self-hosted proof of work (seconds of CPU on the low-end phones the pilot's clients carry, and no bot signal), none (a script would face only the limits).
3. **The token travels in an `X-Challenge-Token` header, checked before any byte of the body is read.** The route reads its body itself (`processManually`), so a refused request writes nothing to disk. CORS allows the header on the API (`config/cors.ts`), so the intake now preflights: one extra round trip, cached 10 minutes. The `challengeToken` form field leaves the contract and `intakeValidator`; a client still sending it has it dropped as an unknown field, so nobody breaks (the field never did anything). The SDK input keeps the name `challengeToken` and sends it as the header. Rejected: keeping the field (readable only after up to 20 MB streamed to disk); a query parameter (access logs); checking a first multipart part as it streams (the client controls part order).
4. **One siteverify call, 3 s, no retry.** `POST https://challenges.cloudflare.com/turnstile/v0/siteverify`, form-encoded `secret` and `response`. Passed only on `success: true`; in production also `hostname` equal to the studio page's host (`STOREFRONT_URL` with the tenant's current slug, `studioHostname`) and `action` equal to `inquiry`. A missing token, an empty one or one over 2048 characters fails without a call. Outside production only `success` counts, so Cloudflare's test keys work locally; tests turn the host and action checks on explicitly. Rejected: `remoteip` (a dual-stack phone may reach Cloudflare and the API over different address families, and nothing installed documents its effect); binding `cdata` to the slug (the hostname already names the studio); a retry with an idempotency key (doubles the time a pooled connection waits, for an outage that fails closed anyway). The builder confirms the field names against Cloudflare's siteverify page before coding; the verifier's unit tests pin what we parse.
5. **Fail closed, with two codes and no reason.** Failed (missing, invalid, expired or replayed: `timeout-or-duplicate`, wrong host or action, a filled honeypot) is 403 `challenge_failed`, "We couldn't confirm this request came from a person. Please try again." Unavailable (timeout, network error, a non-2xx, a body that isn't the verdict, `internal-error`, a refused secret) is 503 `challenge_unavailable`, "We couldn't run the security check. Try again in a minute." Why closed: the widget needs Cloudflare too, so an outage stops the form in the browser anyway, while failing open would let every scripted request through whenever the check can't run; the form then points to the studio's WhatsApp and Viber links (TAT-48). The verifier logs a warning with a fixed cause (a refused secret is an error); never the token, the secret or Cloudflare's body. A 503 is reported like every API 5xx; 403s are not logged. Rejected: fail open; one code for both (a person would retry an outage forever); 422 (it isn't a field error).
6. **Settings.** `TURNSTILE_SECRET_KEY`, read as a `Secret`, required with `NODE_ENV=production` (the web process, the worker and every `ace` command refuse to start without it, as for `STOREFRONT_URL`), optional elsewhere: unset, the check is off and any request passes it, token or not. `.env.test` sets it empty, so a developer's `.env` never turns it on in tests. Tests swap `BotChallenge` in the container for one with the test secret and a fake `fetch` (the real parsing runs). Cloudflare's published test keys are not quoted here: nothing installed confirms them; take them from Cloudflare's Turnstile testing page when TAT-57 wires its dev setup. The site key is public and the storefront's (TAT-57). Rejected: requiring it in development (every contributor would need a Cloudflare account).
7. **The honeypot is a `website` field, and a filled one is refused like a failed challenge.** Any non-blank value (any of repeated parts) is 403 `challenge_failed`, checked right after `receiveUploads` and before validation; nothing is stored and the temp files go. Whitespace counts as empty. Why refuse and not fake a 201: a false positive (an autofill extension) would lose a real inquiry without anyone knowing (TAT-51 ruling 12's reason), while a refusal shows a message and the studio's chat links; the contract is public, so hiding that the field exists buys nothing, and one code gives no oracle between the trap and the token. Rejected: a fake 201 that writes nothing; `validation_failed` on `website` (the form can't show it, and it names the trap); a minimum fill time (needs a signed start time the API never issued, or trusts the client's clock; a token already expires within minutes).
8. **Three limits, each per studio, fixed windows, every attempt counted.** Per client address 20 per hour; per studio 60 per hour; per phone 10 per 24 hours. Keys: `inquiry_ip_<digest(tenant id, clientAddress(ip))>`, `inquiry_tenant_<tenant id>`, `inquiry_phone_<digest(tenant id, E.164)>` (`INTAKE_LIMITS`, `intakeLimitKeys`, `intakePhoneKey` in `#modules/inquiries/intake_limits`). Address: one person needs 1 to 3 tries; 20 matches TAT-65's uploads "sized for carrier NAT", where many customers share one IPv4; counted first, so a bot can't make the API call Cloudflare more than 20 times an hour per address and studio. Studio: one a minute for an hour is above any pilot studio's busiest hour (a flash-day post), and it caps what a challenge-solving flood puts in one inbox; counted only after a passed challenge, so nobody can close a studio's form without solving 60 challenges an hour. Phone: a real person sends 1 or 2 and the cap answers the 4th; 10 leaves room for retries after errors and bounds a loop on one number and repeated probes of the cap's answer; counted after validation (it needs E.164), before `submit`. At each step every request that reaches it counts, whatever happens after. Over a limit: TAT-32's 429 `rate_limited` with `Retry-After` (up to a day for the phone). Keys carry the tenant id, so one studio's counts never touch another's; spraying across studios is TAT-38's generic per-IP limit. The address is `request.ip()`: behind a proxy that isn't on loopback every visitor shares one address until `trustProxy` is set (production checklist). Rejected: `limiter.multi` (the challenge sits between the address and the studio counts); a platform-wide address count (one carrier-NAT address would share 20 tries across every studio); counting the studio before the challenge (anyone could close a form).
9. **Limits and the cap don't mix.** The cap is a rule (3 open, under the lock, 409); the phone limit is a rate (tries per day). A capped phone's tries still count; a decided inquiry frees a cap slot, not a limiter try.
10. **Where each check runs, cheapest first.** Only the middleware and controller lines are new.

    | Step | Where | Refusal |
    |---|---|---|
    | Slug shape, lookup, old-slug write | `publicTenant` (opens the transaction) | 404 |
    | Address count | `intakeGuard` | 429 |
    | Token (no call when missing or oversized) | `intakeGuard`, `BotChallenge.verify` | 403, 503 |
    | Studio count | `intakeGuard` | 429 |
    | Not multipart | controller | 415 |
    | Body to temp files (first disk write) | `receiveUploads` | 413, 400 |
    | Honeypot | controller | 403 |
    | Fields | `intakeValidator` | 422 |
    | Phone count | controller | 429 |
    | Artist rules, cap, then decode and store | `IntakeService.submit` | 422, 409 |

    `intakeGuard` is route middleware on `api.v1.inquiries.store`, after `publicTenant` (TAT-51 ruling 17): an unknown or old slug is TAT-32's 404 before any count or Cloudflare call, and the tenant is known for the keys and the host. Cost: the check (at most 3 s) runs while `publicTenant`'s pooled connection is held, as the upload already does; TAT-38's time bounds cover it. Rejected: a `router.use` middleware keyed on the route name before `publicTenant` (a write under an old slug would answer 403 instead of the 404, and a special case in the global stack).
11. **Contract, SDK, React.** `createInquiry` gains the required `X-Challenge-Token` header parameter, 403 and 503 responses, a 429 line naming the three limits, and `InquiryForm` swaps `challengeToken` for `website` (`maxLength: 0`, "a honeypot: leave it out"); `ErrorResponse` lists the two codes; the info's CORS line names the header. `inquiries.create` sends `challengeToken` as the header (never a field) and `honeypot` as the `website` part when non-empty; the SDK exports `INQUIRY_CHALLENGE_ACTION` (`inquiry`) and `INQUIRY_HONEYPOT_FIELD` (`website`). React code is unchanged (`retry: false` already): a token is single-use, so any automatic retry would replay a spent one; a test pins that `challenge_failed` is never retried. Rejected: retrying `challenge_unavailable` in the SDK (TAT-51 ruling 14: no business rules in the SDK).
12. **TAT-38's boundary.** TAT-55 owns the intake's own limits, the challenge and the honeypot, all on this one route. TAT-38 owns the generic per-IP limit before `publicTenant` (in `router.use` guarded by `isApiRequest`, so it also bounds old and unknown slugs, which TAT-55 never counts), per-tenant limits on every public endpoint, the server key, time bounds and the pool size. Nothing here blocks it: `intakeGuard` stays on the route and both sets of limits apply. Intake requests come straight from browsers, so a server key never changes their address. TAT-12's D2 (each random storefront host label costs a function run and a `getStudio`) is a read cost: TAT-38's, not TAT-55's.

## For TAT-57 (what the form sends)

Load Turnstile's script only for the `#inquiry` section, render a Managed widget with `action: "inquiry"` (`INQUIRY_CHALLENGE_ACTION`), shown only when an interaction is needed and run at submit, so the token is fresh (check the widget options in Cloudflare's docs). Pass the token as `challengeToken` to `useCreateInquiry()`; reset the widget after every answer, success or error, since a token is single-use even when the API refused the request for another reason. Render the honeypot as a text input named `website` (`INQUIRY_HONEYPOT_FIELD`) inside a wrapper that is off-screen (not `display: none`) and `aria-hidden="true"`, with `tabindex="-1"`, `autocomplete="off"` and a label "Leave this empty"; pass the input's DOM value as `honeypot`. Handle `challenge_failed` (403: reset and "Please try again"), `challenge_unavailable` (503: "Try again in a minute, or message the studio" with TAT-48's chat links), `rate_limited` (429: `error.retryAfter` seconds, shown in minutes or hours) and TAT-51's codes. A CSP, when one exists, must allow `https://challenges.cloudflare.com` for scripts and frames and `API_URL` for `connect-src`. The site key is a public storefront setting TAT-57 names. Register the studio pages' domain under the widget's hostnames in Cloudflare (check there whether subdomains are covered).

## Tests

The plan lists every case. In short: `checkChallengeSecret` (required in production, optional elsewhere, the value never in a message); `BotChallenge` with a fake `fetch` (off without a secret; the request it sends; passed; invalid, expired or replayed, wrong host, wrong action, no or oversized token without a call; timeout, network error, 5xx, non-JSON, a body without `success`, `internal-error`, a refused secret as unavailable; no token or secret in any log call; host and action ignored outside production); `studioHostname`; the codes; `INTAKE_LIMITS`, the keys (digests, per studio, IPv6 /64) and each window's reset (`mock.timers`); `honeypotFilled`; over HTTP with the swapped verifier: each outcome's envelope, `no-store` and no `Set-Cookie`, no temp file, no stored image and no row on every refusal before the body, the honeypot's refusal after it (temp files removed), a `challengeToken` field ignored, an old or unknown slug a 404 with no Cloudflare call, each limit's 429 with `Retry-After` after refused tries, one studio's limits leaving another's alone, the cap unchanged; the CORS preflight for the header; the route guard (`intakeGuard` after `publicTenant`); the SDK (the header, no token field, the `website` part, the codes, the constants) and React (inputs pass through, `challenge_failed` not retried).
