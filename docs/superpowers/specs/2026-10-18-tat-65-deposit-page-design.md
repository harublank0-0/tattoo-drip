# Deposit page: amount, studio QR codes, reference code, proof upload (TAT-65)

Date: 2026-10-18
Refs: TAT-65. Builds on TAT-32 and TAT-51 (see "Depends on TAT-32 and TAT-51"), TAT-37 (`Payment`, its guard trigger, `DepositService`), TAT-64 (`QuoteService.current`, `acceptQuote`, `formatMoney`, `validUntil`), TAT-26 (payment methods with `show_on_deposit_page`, `deposit_policy`), TAT-21 (`ImageService`, `payment_proof` purpose), TAT-8 (`@adonisjs/limiter`, `digest`, `clientAddress`). Blocks TAT-66. Carry-forwards on the ticket from TAT-37 (proof at insert, re-upload, money: rulings 7, 10, 11), TAT-64 (the link after `acceptQuote`, paid after a revision: 4, 5, 8), TAT-36 (`DepositService`, `corrects_payment_id`: 16), TAT-41 (Payments on the client profile: 16) and the TAT-21 security review (purpose, signed URLs: 10, 16) are each ruled on.

## Goal

An owner marks a quote accepted and copies a deposit link from the project page into WhatsApp. The client opens it on the studio's subdomain, sees what to pay, to whom and with which reference code, pays with the studio's own QR, and uploads a screenshot. The API stores it privately as a `submitted` deposit payment and alerts the owners. No money passes through Tattoo Drip.

Written without the user (unattended run): every open question is a ruling below. **One migration** (`deposit_links`).

## Rulings

1. **Scope: the platform, contract, SDK, React hooks and the dashboard control now; the storefront page is TAT-65b.** Subdomain-to-slug (TAT-12) and the storefront's SDK wiring (TAT-23) don't exist yet, and a thin path-based route would build half of TAT-23 (an API URL setting, a browser client, a provider) to be redone. TAT-65 ships everything the page needs and specifies it ("Storefront page (TAT-65b)"); **TAT-65b: storefront deposit page**, blocked by TAT-23 (itself blocked by TAT-12) and TAT-65, builds it and ticks the requirements box. The ticket's first acceptance line stays open until then; the PR says so. Rejected: a `/s/$tenant/deposit` route now.
2. **One link per project, in `deposit_links` (payments module).** Columns: `tenant_id`, `project_id` (composite key to the project, cascade), `reference_code`, `token_nonce`, `token_hash`, `expires_at`, timestamps. Unique: `(tenant_id, project_id)`, `(tenant_id, reference_code)`, `(token_hash)`; CHECKs pin the three formats. Tenant-owned with `enableTenantRls()`. Not soft-deleted: it is a credential, not a record; a new link replaces it in place, and a deleted project's link is dead because the page loads only live projects. Rejected: columns on `tattoo_projects` (the projects module's table); a row per issued token (history nobody reads).
3. **The token is 256 bits, derived, and stored only as a hash.** `token = base64url(HMAC-SHA256(APP_KEY, "deposit-link:v1:" + nonce))`, 43 characters; the row keeps the random 16-byte nonce and `token_hash = sha256(token)` (hex), which a request is looked up by. The dashboard rebuilds the link whenever an owner opens the project, so it can be copied and resent any time; the token is never stored, logged or put in a rate-limit key. The database alone gives no token; with `APP_KEY` it does, but `APP_KEY` already signs the dashboard's session cookies, so nothing new is exposed. Rotating `APP_KEY` kills every link (the hash stops matching; the panel offers a new one). Rejected: a random token shown once (resending it means replacing it, which kills the link the client already has); storing it encrypted (the same exposure, more code).
4. **A link works for 30 days; every dead link is the same 404.** "New link" (an owner) replaces the nonce, hash and expiry at once; the old token is dead. Nothing else revokes a link: a revision, the quote's expiry, cancellation, a waiting proof and a paid deposit change what the page says (ruling 5), so the client always learns what happened (the TAT-64 carry-forward: a project revised after its deposit was paid, back in `quoted`, still shows the deposit paid). Unknown, malformed (the route's matcher: no query at all), replaced, expired, another studio's token and a deleted project all get TAT-32's `not_found`; there is no 410, which would only confirm to the holder of an old token that it once worked. Rejected: expiry at the quote's expiry (the paid page would vanish with it, and revisions would have to move it); revoking on cancellation (the client would see "link doesn't work" instead of "cancelled").
5. **The page's state is computed, first match wins:** `cancelled` (project `cancelled` or `declined`); `paid` (nothing left to pay: a zero deposit, or verified deposit money in the quote's currency reaching it, in any other status); `submitted` (a deposit payment waits for the studio); `due` (`deposit_pending`, quote not expired) or `expired` (`deposit_pending`, quote expired, before the sweep cancels it); otherwise `updating` (`quoted`, `on_hold` after a revision, anything else). `lastProofRejected` is true in `due` when the studio's latest decision on a deposit payment was a rejection. A pure function, unit-tested over every status. Rejected: storing the state.
6. **The reference code: 6 characters per project, kept across new links, never the token.** From `23456789ABCDEFGHJKMNPQRSTVWXYZ` (no 0, 1, I, L, O, U; 30^6 = 729 million codes), unique per studio, drawn when the first link is made; a collision draws again in a savepoint, up to 5 times. It goes in the payment remark, so staff (TAT-66) match statements to projects; it grants nothing. Rejected: part of the token (a bank statement would leak the bearer link); a counter (guessable).
7. **The page shows what it needs, nothing private.** Studio name; the project's brief and artist name (never notes, the client, sessions, the quote history or price); the deposit (`amount`, `due` in paisa with `amountText`/`dueText` from `formatMoney`, `currency`, `payBy`, the current quote's last valid day in the studio's timezone, and `payByText`); the reference code; the state; `lastProofRejected`; `proofSubmittedAt`; the studio's deposit-page methods (kind, label, public QR URL, the kind's own details; cash never) only in `due`; the deposit policy. Never a proof image or URL. Amounts are int4 and a project has a handful of payments, so they are summed in JavaScript as `DepositService` already does. `no-store` (an `UNCACHED_GET_ROUTES` entry). Rejected: the quote total (not asked for; the client has the quote message); the client's name (a bearer page).
8. **Owners make the link while a deposit is due.** `POST /t/:tenant/projects/:id/deposit-link` makes the project's link or replaces it. Owners only: an artist, even the assigned one, gets the 404 of a project that isn't theirs, as `assignArtist` does (payments are owners' in the role table). Under the project's lock it needs `deposit_pending`, a current quote that hasn't expired, a deposit not yet covered, and at least one method shown on the deposit page; otherwise a flash error says what to fix. `acceptQuote` is unchanged. Rejected: making it in `acceptQuote` (artists accept quotes too and could never see the link).
9. **The dashboard panel, and the link's URL.** On the project page, for owners, while `deposit_pending`: the link (read-only field, Copy link), "Works until", the reference code, the deposit chat message (WhatsApp, Viber, Copy message; marks contacted like the quote message), "New link" behind a confirm, or the reason a link can't be made; "Payment screenshot received <date>" while a proof waits. The URL is `STOREFRONT_URL` (an origin with `{tenant}` for the slug, default `http://{tenant}.localhost:3000`, TAT-12's dev host) + `/deposit#<token>`. The token rides in the fragment, which browsers never send to the storefront host, its logs or a `Referer`. Rejected: a path segment (in every storefront log line).
10. **The proof is one multipart POST that inserts the `submitted` payment with its proof.** Fields: `proof` (the first such part; `imageFile()`: 10 MB, jpg, jpeg, png, webp; no HEIC, TAT-51 ruling 4), `method` (`fonepay`, `esewa`, `khalti` or `bank`, and one the page lists, else `validation_failed` on `method`), `expectedAmount` (the paisa the page showed). The row: kind `deposit`, amount = what is still due, the quote's currency, the method, and the proof key and size in the INSERT (TAT-37: proof columns can't be set later), status `submitted`. Stored through `ImageService.store` with the fixed purpose `payment_proof`, never a key or purpose from the request. Order: the limits (429, route middleware), the link (404), multipart (415), reading the body (`receiveUploads`: 413, 400; the route is in `processManually`, so nothing reached the disk before this), validation (422), the state without a lock (409, before any decode), store and register `afterRollback` deletion, lock the project, re-read link and state under the lock (409), insert, queue the alert. The image is stored before the row lock, as `backend.md` says, so no lock waits on a decode; the re-check makes a concurrent double submit safe, and the loser's file goes with its rollback. 201 with the page as it now is (`submitted`). Rejected: the client typing the amount (TAT-37: a different amount is rejected and recorded at the desk, TAT-66).
11. **One proof waits at a time; two endpoint codes.** While a deposit payment is `submitted`, another POST is 409 `deposit_not_due`, as is any state but `due`; the page refetches and shows why. `expectedAmount` other than what is due is 409 `deposit_changed` ("The deposit amount changed. Check the new amount before you upload."); the page refetches. After an owner rejects a proof (TAT-66) the page offers a new upload, which is a new payment. Both codes join `API_ERRORS`. Rejected: several waiting proofs (one link could fill the studio with rows and images); a code per state (the GET says which).
12. **Rate limits now, on TAT-8's limiter.** Fixed windows, reads and writes apart, per client address and per token: GET 120 per address and 60 per token per 10 minutes; POST 20 per address and 10 per token per hour (sized for carrier NAT, where many customers share one address). Keys are `digest()` of `clientAddress(ip)` and of the token, so `rate_limits` holds neither. A `depositThrottle` middleware on the two routes, after `publicTenant`, consumes the address first and then the token (`limiter.multi`); every request counts, 404s and refusals included. 429 is TAT-32's `rate_limited` with `Retry-After`. The upload route is in `multipart.processManually`, so a refused or dead-link upload is never written to disk. Per-address limits ahead of the tenant lookup are TAT-38's (the per-token limit stays). Rejected: waiting for TAT-38; `limiter.define` (one key per middleware).
13. **Owners are alerted: a queued job and an in-app count.** `DepositProofAlertJob { tenantId, paymentId }` (a `TenantJob`) is queued in the payment's transaction; it does nothing for a payment that is gone or decided and otherwise logs "Deposit proof received." with the tenant, project and payment ids (no token, URL or amount). TAT-52 sends email and in-app notifications from it. The Projects nav item shows owners how many deposit proofs wait (shared prop `proofCount`, read "to check"), and the project page says when the screenshot came. Rejected: the log line alone (no owner sees it before TAT-52).
14. **Isolation of the public routes.** The link is looked up by the path's tenant and the token's hash, in that tenant's RLS context, so another studio's token under this slug is the same 404 as an unknown one. The public harness grows `params` (for a route with more than `:tenant`, B's token under A's slug must be a 404 that leaves B unchanged) and `files` (the proof part). An old slug answers GET (TAT-32's alias); a POST under it is TAT-32's 404 before its body is read. Rejected: a definer function (the tenant is already known).
15. **SDK and React.** `deposits.get(token, call?)` and `deposits.submitProof(token, { proof, method, expectedAmount }, call?)` (multipart, TAT-51's 2-minute upload timeout). React: `tattooKeys.deposit(tenant, token)`, `tattooQueries.deposit` (no retry on a 4xx, so a dead link shows at once; refetch on focus kept, so coming back from the payment app refreshes), `useDeposit`, and `useSubmitDepositProof` (never retried; seeds the query with the answer) built on `tattooMutations.submitDepositProof`. `@tattoo-drip/react` gets `node:test` tests for these option factories; rendering tests stay TAT-11's. Rejected: polling.
16. **Carry-forwards.** `DepositService` is taken over: it gains `remaining`, `pendingProof`, `lastDecisionRejected`, `countPendingProofs` and `recordProof`, and keeps summing only the quote's currency. `corrects_payment_id` goes to TAT-66 (it creates corrections; this migration doesn't add it, since the column without the counting change would split one fix in two): see Carry-forwards. TAT-65 issues no proof URL anywhere, so the signed-URL rules, `Cache-Control: private, no-store` on `/files` and the tenant-prefix check in `ImageService.url` first apply in TAT-66, which shows proofs. The clients profile's Payments section and `settleBooking` after a verification are TAT-66's.

## Storefront page (TAT-65b)

Built by TAT-65b on TAT-12 (the slug from the host) and TAT-23 (a browser client and `TattooProvider`). It reads and writes only through `useDeposit` / `useSubmitDepositProof`.

- **Route and data.** `src/routes/deposit.tsx`, `/deposit` on the studio's subdomain; the token is `location.hash` without `#`. Data loads in the browser only (no loader, no SSR of deposit data): the API sees the customer's address for its limits, and the token never reaches the storefront server. A missing token, or one that isn't 43 base64url characters, shows the dead-link state without a request. Head: title "Pay your deposit", then "Pay your deposit · <studio>"; `<meta name="robots" content="noindex, nofollow">`; `<meta name="referrer" content="no-referrer">`. PostHog and Sentry must strip the fragment from every URL they record on this route (PostHog `before_send`, Sentry `beforeSend`, `beforeSendTransaction`, `beforeBreadcrumb`); nothing logs the token.
- **Layout.** Mobile-first at 375 px: one column, 16 px gutters, at most 28 rem wide and centred above that. `h1` "Pay your deposit to <studio>", then the brief and "with <artist>" when there is one. Then the state's block.
- **`due`.** The amount (`dueText`, large); when `due` is below `amount`, "Part of your <amountText> deposit was already received."; "Pay by <payByText>". The reference code in a large monospace box with "Write this code in the payment remark (or note)." and a "Copy code" button (`aria-label="Copy reference code <code>"`; "Copied" for 2 s in a polite live region). Each method in the API's order: its label as a heading, the QR (`alt="<label> QR code for <studio>"`, at most 280 px wide, the first eager, the rest lazy) with "Scan it with your <kind> app.", and its details (bank, account name, account number or wallet ID) with a Copy button on the number. No methods: "The studio hasn't added payment details yet. Message them to ask how to pay.", and no form. The deposit policy, when set, under "Deposit policy" (plain text, line breaks kept). With `lastProofRejected`, above the form: "The studio couldn't confirm your last screenshot. Check the amount and the reference code, then send a new one, or message the studio." The form, "After you pay, send a screenshot": "How did you pay?" (a radio group of the methods' kinds; preselected when there is one), "Payment screenshot" (`accept="image/jpeg,image/png,image/webp"`, hint "JPEG, PNG or WebP, up to 10 MB."; a wrong type or a file over 10 MB is refused before upload with that hint as the error), `expectedAmount` = `due`, "Send screenshot" (disabled with "Sending…" while in flight; never retried). On 201 the page shows `submitted` and focus moves to its message. Server errors: field messages under their fields; `deposit_changed` and `deposit_not_due` refetch and show the new state (the first with "The deposit amount changed. Check the new amount."); 413 "This image is too large. Use one of 10 MB or less."; 429 "Too many tries. Wait <n> minutes and try again." (from `retryAfter`); timeout or network "Couldn't send. Check your connection and try again."
- **Other states.** `submitted`: "We've sent your screenshot to <studio>, received <date>. They'll check it and confirm on WhatsApp or Viber.", the amount and reference code. `paid`: "Your deposit is paid. Thank you!" (amount 0: "No deposit is needed for this booking."). `updating`: "<studio> is updating your quote. They'll message you when it's ready." `expired`: "This quote has expired. Message <studio> if you still want to book." `cancelled`: "This booking was cancelled. Message <studio> if you think this is a mistake." No payment details or form in these. Dead link (404): "This link doesn't work any more. Ask the studio to send you a new one." 429 on load: "Too many tries. Wait a few minutes, then reload the page." Network: "We couldn't load your deposit. Check your connection." with "Try again". Loading: a skeleton with `aria-busy`.
- **Accessibility.** One `h1`; state messages in a `role="status"` region, errors `role="alert"`; labelled fields, the radio group in a `fieldset` with a `legend`; touch targets of 44 px; AA contrast; nothing told by colour alone. TAT-65b checks every state at 375 px in a browser, a keyboard-only upload, and that no request other than the API's carries the token.

## Carry-forwards (posted with the PR)

Show the reference code next to each proof. The clients profile's Payments section reads through a `PaymentService` read.
- **TAT-52.** `DepositProofAlertJob.handle` is where the owners' email and in-app alert go; the deposit chat message (`depositMessage`) becomes a template.
- **TAT-38.** Keep `DEPOSIT_LIMITS`' per-token limits; the per-address part may move ahead of `publicTenant`.
- **TAT-65b.** The page section above, the SDK hooks, and the fragment rule.
