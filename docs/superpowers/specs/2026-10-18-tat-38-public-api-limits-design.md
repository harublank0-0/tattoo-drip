## Goal

The last security gate before a public deploy. Every public API request is counted per caller before its body is read, reads also per studio; the hosted storefront's server proves itself with a key and gets its visitors their own budgets; no public request can hold the database pool for long; no request of any kind can stop the process through the multipart parser; one checklist says what production must set.

## Rulings

1. **Three separable parts, about 5 points, not 2.** Part 1: multipart hardening (ruling 16); Part 2: limits and the server key (2 to 11); Part 3: pool and time bounds (12 to 15). Each part's commits stand on their own, in that order: Part 1 is the most urgent (one anonymous request stops the web process today) and needs nothing else; Part 3's write slots sit in Part 2's gate and its deadline reaches Part 1's middleware. Rejected: new Linear tickets (the user files tickets; the PR text can split by part).
2. **One gate before the body.** `PublicGateMiddleware`, FIRST in `router.use`, acts only when `isApiRequest(ctx)`: after routing (the pattern is known; a URL no route matches never reaches it and costs no query), before the bodyparser, session and shield. It identifies the caller, counts it, and takes a write slot (13). So a body the parser then refuses (unreadable JSON, over 1 MB, a bad urlencoded or text body) is counted first: TAT-55 rule 12's limit before the bodyparser. It is inserted, never wrapping or reordering the bodyparser stack TAT-32 pinned (the parser still runs before `publicTenant`). Rejected: `server.use` (before routing: it would count unmatched URLs and preflights); the group `use` lists (after the bodyparser, TAT-32 amendment).
3. **Two kinds of caller; the key changes nothing else.** No key, or a key that doesn't match: *anonymous*, counted by `request.ip()`. A valid key: *storefront*, counted by its visitor (6), each kind in its own buckets, so a visitor's server-rendered calls never spend their own browser's budget. The key grants no data, no route, no field, no cache variant and no other authorization; the dashboard never reads it. Later throttles count `callerIp(ctx)` (`depositThrottle` and `intakeGuard` move to it), never `request.ip()`.
4. **`STOREFRONT_SERVER_KEYS`: one or two keys, required in production.** Comma-separated, each the storefront's rule (32 to 256 of `A-Za-z0-9._~+/-`, then at most two `=`), read as a `Secret`; errors name the variable and the rule, never a value. With `NODE_ENV=production` the web server, the worker and every `ace` command refuse to start without it (as for `STOREFRONT_URL`); elsewhere unset means no key is accepted. `.env.test` holds two test keys. Rotation: add the new key (`old,new`), restart the platform, switch the storefront, then drop the old one. Rejected: optional in production (a forgotten setting quietly throttles every studio page under load); a second `_NEXT` variable.
5. **The check.** Only `Authorization: Bearer <token68>`, at most 300 characters; SHA-256 of the token compared with every configured digest by `timingSafeEqual`, no early exit (digests made once at first use). A missing, malformed, wrong-scheme or unknown key is anonymous, never a 401; an unknown well-formed key logs one fixed warning at most every 10 minutes per process. Nothing logs, echoes or stores a key or any part of it. Rejected: 401 (a rotation slip would take down every page, and the answer helps nobody but a guesser); `===` (timing).
6. **The visitor: `X-Visitor-IP`, honoured only with a valid key.** One IP literal (`isIP`), trimmed, at most 45 characters: no list, port, brackets or zone. A private, loopback, link-local, carrier-NAT (100.64/10), unspecified or multicast address, or any IPv4-mapped form of one, does not count as a visitor. A keyed call without a usable visitor goes to one shared storefront budget and logs one fixed warning at most every 10 minutes. The visitor then goes through `clientAddress` (IPv6 by /64) and `digest` like every address, so `rate_limits` holds no address. CORS keeps refusing `Authorization` and this header (server-to-server only). Rejected: `X-Forwarded-For` (the host's proxy appends to it and `trustProxy` reads it: the proxy chain and the visitor would mix); refusing such a request (a storefront fault would take pages down); trusting private ranges (every such visitor would share one bucket).
7. **The storefront forwards it.** `visitorAddress(request)` (`src/tenancy/visitor.ts`, pure): the first `X-Forwarded-For` value if it is an IP literal (Vercel's edge overwrites that header; TAT-13 confirms on the first deploy), else the socket address the server exposes, else none. Only with a key, both server calls (TAT-12's lookup, TAT-23's per-request client) send it, through the SDK's `fetch` option (`withVisitorAddress`): no SDK or contract change. `STOREFRONT_SERVER_KEY` becomes required with `NODE_ENV=production` (`env.NODE_ENV` in `parseStorefrontConfig`, like TAT-57's site key). `check:page` asserts the header arrives. Rejected: an SDK option (a header only our storefront needs); a setting naming the header (one more setting for one host).
8. **Numbers.** Fixed windows on the existing limiter; every request counts, refused ones included; 429 `rate_limited` with the limiter's `Retry-After`.

    | Budget | Counted by | Limit | Why |
    |---|---|---|---|
    | Reads per caller | address (anonymous) or visitor (storefront), apart | 300 / 5 min | A page costs the storefront 2 keyed reads and a browser none (hydrated, fresh 60 s); carrier NAT shares addresses, so generous. TAT-65's 120 / 10 min stays the binding one on deposit reads. |
    | Writes per caller | the same | 60 / hour | Above TAT-55's 20 per studio and TAT-65's 20 uploads, which stay binding on their routes; bounds one address spraying many studios. |
    | Storefront without a visitor | one shared key | 3000 / 5 min | The fallback when forwarding fails: 10 a second keeps a pilot site up while the warning shows the fault. |
    | Reads per studio | storefront and anonymous apart | 6000 and 1500 / 5 min | Containment: a flood aimed at one studio can't take the platform. 10 uncached page views a second (each `fbclid`/`igsh` link misses the CDN) before the storefront's bucket binds; a direct-API flood can't spend the pages' bucket. |
    | Writes in flight | per process / per address (memory) | 4 / 2 | Ruling 13. |

9. **Per studio: reads only; a reusable slot.** `apiLimit({ name })` (named) runs after `publicTenant` on the tenant group with `tenantReads`; writes skip it. No generic per-studio write count: TAT-55 counts the studio after the challenge, deposits need a 256-bit token, and a count before the challenge would let anyone close a studio's form (TAT-55 ruling 8). Later tickets add an `API_LIMITS` entry (`scope` caller or tenant, `methods`, a budget per caller kind) and `.use(middleware.apiLimit({ name }))`. A guard test: every tenant route runs `apiLimit` right after `publicTenant`.
10. **Caching and headers.** A response a CDN or browser serves from cache never reaches the app and is not counted. Limits call `consume()`, never `limiter.define` middleware (which sets `X-RateLimit-*` on every success), so a cacheable 200 carries no per-caller header (TAT-32 ruling 16); 429 and 503 are `no-store`.
11. **`TRUST_PROXY`, required in production.** A proxy-addr list (`loopback`, `linklocal`, `uniquelocal`, IPs, CIDRs), comma-separated, into `http.trustProxy`; refused: `true`, `*`, `all`, `/0`. Unset in development and tests: `loopback` (today's default). Production sets the reverse proxy's addresses (`loopback` when it runs on the same host), plus Cloudflare's ranges if Cloudflare fronts the API. Rejected: keeping the silent default (behind a load balancer one person locks out everyone, TAT-8/55/65).
12. **An explicit pool, a short wait.** `pg`: `min 2, max 10` for the web server and tests, `min 0, max 6` for `ace` (the worker runs 5 jobs); `limiter`: `max 4` as now. Acquire timeouts 10 s and 5 s (knex: 60 s). An acquire timeout on an API request is 503 `service_busy` with `Retry-After: 10`, reported. Rejected: a pool-size setting (a number TAT-14 changes once, in code); 60 s (requests pile up for a minute before failing).
13. **Write concurrency, before the body.** Every API request that isn't GET or HEAD takes a slot in the gate after its write count: at most 4 per process and 2 per client address; over is 503 `service_busy` or 429 `rate_limited`, `Retry-After: 10`, not reported. Held until the response closes, so public writes hold at most 4 of the 10 connections whatever the body's speed. Rejected: a queue (waiting requests hold sockets and pile up); a list of capped routes (one more list to keep in sync).
14. **Time bounds.** `receiveUploads(request, { deadlineMs })` reads a body for at most 90 s on the API and 120 s on the dashboard, then destroys its parts and fails with 408 `request_timeout`. `http.requestTimeout` is 120 s (Node: 300 s). An error answer to a request whose body hasn't fully arrived sends `Connection: close`, so Node drops the socket instead of draining a trickle. Rejected: an idle timeout (a byte every few seconds defeats it); relying on the proxy (some hosts stream bodies unbuffered).
15. **The transaction stays where it is.** `publicTenant` keeps opening it before the body: with 13 and 14 an upload holds one of 4 slots for about 100 s at most. Opening it after the body needs a two-phase tenant resolution (look up, release, read, re-open, re-check a rename or delete between them) on the RLS path every public route shares, and moves TAT-55's guard. Revisit with direct-to-storage uploads (TAT-27 / V1), which take uploads off the API. Rejected: the two-phase request.
16. **Multipart hardening: nothing auto-processes multipart.** `multipart.autoProcess: false` (`processManually` goes). `WebMultipartMiddleware`, LAST in `router.use` (after silent auth), reads a non-API multipart body only for a signed-in user, through `receiveUploads` (its handler table covers every `Object.prototype` name), and always ends with `discardUploads` (the dashboard's leftover temp files go too). A signed-out multipart body outside `/api` is 415, unread. API upload routes keep reading their own body after `publicTenant` and the limits. A multipart form sends CSRF in the `X-XSRF-TOKEN` header (Inertia does), never a `_csrf` field. Rejected: `pnpm patch` of the parser (patches a compiled chunk, edits the lockfile with TAT-12's `latest` trap, redone on every upgrade; report upstream instead); a guard that only refuses multipart on routes without files (file routes stay open before auth); an `unhandledRejection` handler (the request hangs and other bugs hide); `autoProcess` as a list (the flawed lookup stays on listed routes).
17. **Random inputs and table growth: what is bounded.** Random host labels and query strings (TAT-12 D2) reach the API as keyed lookups counted per visitor (300 / 5 min) and, for a real studio, per studio; an unknown slug costs one definer lookup in a short transaction. No negative cache: random inputs defeat it and a new studio would stay unknown for its life. Random dead deposit tokens (TAT-65 D1) write at most two `rate_limits` rows each, bounded per address by the gate and TAT-65's address count (taken first); the store deletes rows expired over an hour ago every 5 minutes, so rows live at most a window plus about 65 minutes and no `expire` index is needed (no migration). Not bounded here: Vercel function runs and many-address floods (Vercel's firewall, Cloudflare in front of the API: recommendations). Cost notes (the transaction before the slug lookup, TAT-32 M-1; whole artist rows for one boolean, TAT-44; four page passes per proof, TAT-65 M2) are bounded by these limits and left as later optimizations.
18. **One checklist.** A new `apps/platform/docs/deploy.md`, "Public API production checklist", collects the API-process items (outline below); `database/README.md` keeps the database items and links to it. TAT-14 follows it.
19. **Contract.** `info` gains a "Rate limits" convention (per caller before the body, per studio on reads, 429 with `Retry-After`, 503 `service_busy`, 408 `request_timeout` on uploads) and describes the server key and `X-Visitor-IP` as operational, granting nothing. The `serverKey` security scheme and the top-level `security` go: the key is not a data-access scheme. Reads list 429; uploads list 408 and 503; `ErrorResponse` lists both new codes. The SDK and React need no change (open codes; the storefront retries 5xx reads, never writes).
20. **Accepted denial costs, written down (TAT-55 review).** The checklist lists them, since the owner gets no signal (429s and busy 503s are not logged; alerts are TAT-52): 60 solved challenges an hour from 3+ addresses close one studio's form for the rest of the hour; 10 solved challenges with a victim's phone lock that number out of the studio for up to 24 h; 4 slow uploads per process make uploads busy for about 100 s at a time; a many-address flood of one studio's pages spends its read budget; a carrier-NAT address shares 60 writes an hour platform-wide and TAT-55's 20 per studio, counted before Cloudflare. A shell- or CI-exported `STOREFRONT_SERVER_KEYS` or `TRUST_PROXY` wins over `.env.test` (testing docs). Rejected: per-studio exemptions or owner alerts now (TAT-52).

### Public API production checklist (outline of deploy.md)

1. Platform settings: `NODE_ENV`, `APP_KEY`, `APP_URL` (public https origin), `STOREFRONT_URL`, `TURNSTILE_SECRET_KEY`, `STOREFRONT_SERVER_KEYS`, `TRUST_PROXY`, app-role `DB_*`; no `DB_MIGRATION_PASSWORD` in web or worker.
2. Storefront settings: `API_URL` (the API's public origin), `STOREFRONT_URL`, `STOREFRONT_SERVER_KEY` (one of the platform's), `TURNSTILE_SITE_KEY`.
3. Processes: Node 24.3.0; migrate as the owner first; one web server (it upserts the schedules) and at least one worker.
4. Reverse proxy: request buffering on, body limit 21 MB, `client_header_timeout 15s`, `client_body_timeout 30s`, `proxy_read_timeout 130s`, `X-Forwarded-For` appended, its address in `TRUST_PROXY`; no access log for `/api/v1/tenants/*/deposits/*`.
5. Database: connections per process (web 10 + 4, worker 6), `max_connections` headroom, `idle_in_transaction_session_timeout = '3min'` for the app role.
6. Server key: generate, set both apps, rotation steps.
7. Recommended: Cloudflare in front of the API (its ranges in `TRUST_PROXY`, origin locked to it, a coarse rate rule), Vercel's firewall for the storefront.
8. Accepted denial costs (ruling 20), where to look when a studio's form "stopped working".
9. First-deploy checks: one studio page view, then no "unknown server key" or "no usable visitor" warning in the API log; a cacheable read carries no `X-RateLimit-*`; `pnpm check:page` before the deploy.

## Not in this ticket; before any public deploy
