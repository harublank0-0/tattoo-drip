# Storefront deposit page: amount, QR codes, reference code, screenshot upload (TAT-65b)

Date: 2026-10-19
Refs: TAT-65b (no Linear ticket yet). Builds on TAT-65 (its "Storefront page (TAT-65b)" section, rulings 4, 5, 7, 9 to 12 and 15, the built `deposits.get` / `deposits.submitProof`, `useDeposit` / `useSubmitDepositProof`, the contract's `DepositPage` and codes), TAT-66 (`lastProofRejected` and `paid` come from its decisions; a rejection's reason is for the studio's team only), TAT-57 (the browser image pipeline, `fill` / `<Fill>`, the form toolkit, the refusal conventions, `networkMode: "always"`), TAT-48 (the tokens, `links.ts`, `text.ts`, `studioViewModel`, heads and cache headers), TAT-23 (the per-tab SDK client, `TattooProvider`, the QueryClient defaults), TAT-12 (the studio from the `Host` header, old-slug 302s), TAT-38 (the browser's client carries no key; the API counts the visitor's own address) and TAT-38's `deploy.md` (no access log on the deposit API paths). Written without the user (unattended run): every open question is a ruling below.

**Storefront and docs only. No platform, contract, SDK or React change, no dependency change, no migration, no new setting.** Five details of TAT-65's page section change, each with its reason: rulings 4 (no analytics to configure), 6 (the title names the studio from the start), 13 (the copy buttons' accessible names), 14 (no 10 MB pre-check: the screenshot is re-encoded) and 18 (the status region is written as `aria-live`).

## Goal

A client in Nepal taps the deposit link the studio sent on WhatsApp, Viber or Instagram. On their phone, often on a slow connection, the page says how much to pay, by when, to whom and with which reference code, shows the studio's QR codes and account details, and takes one screenshot of the payment. It then says the studio will check it and confirm, and later that the deposit is paid, or that the studio couldn't confirm it and a new one is welcome, or that the quote expired, the booking was cancelled, the studio is updating the quote, or the link no longer works. The token in the link never reaches anything but the API.

## Base

Designed on f2c48ee, the tip of the whole stacked chain: the built public API chain (TAT-24, 32, 51, 65, 66), TAT-12, 23, 44, 48, 55, 57, 38, 9 and 85. Everything the page needs is built there. The plan's Task 0 checks each name it uses and stops otherwise.

## Rulings

1. **Scope: the storefront page and docs; nothing else changes.** TAT-65 built what the page needs and nothing is missing: `useDeposit` (no retry on a 4xx, `staleTime: 0`, so a focus refetch always runs), `useSubmitDepositProof` (never retried; seeds the page with the answer after cancelling a read in flight), the contract's `DepositPage` (every field the page shows), the codes `deposit_not_due` and `deposit_changed`, `Retry-After` exposed to browsers (`config/cors.ts`), the token's pattern. A `DepositPage` has no QR image size: the page reserves a square instead (ruling 12). The public page never shows why a screenshot was rejected: TAT-66 keeps the reason for the studio's team ("only your team sees it"), so the page says the fixed TAT-65 sentence. Rejected: QR `width`/`height` in the contract (a square placeholder is enough for a QR); a public rejection reason (TAT-66's privacy rule).

2. **One file route, `/deposit` (`apps/storefront/src/routes/deposit.tsx`).** A child of the root route, so the root's `loadStudio` has the studio. `src/routeTree.gen.ts` is regenerated by `pnpm build` (Start's Vite plugin writes the route tree and its Register footer; `tsr generate` alone writes no footer) and committed with the route; never edited by hand. TAT-48's guard test that lists the routes grows to three. Rejected: `/deposit/$token` (TAT-65 ruling 9: a path is in every log line); another path (the platform already builds `STOREFRONT_URL` + `/deposit#<token>`).

3. **The token is read in the browser only, strictly, and stays in the URL.** `readDepositToken(hash)`: the fragment without its `#`, exactly `^[A-Za-z0-9_-]{43}$` (the contract's `DepositToken`, pinned by a test), nothing trimmed or decoded. The screen reads `window.location.hash` through `useSyncExternalStore` with an `undefined` server snapshot, so the server and the hydrating render show the same loading shell and the browser then reads the fragment; a `hashchange` re-reads it (another token remounts the page for it). A missing or malformed token is the dead-link message with no request. The fragment stays in the address bar: a reload, a tab the phone discarded while the client was in the payment app, or reopening the chat link all work. Rejected: removing it with `history.replaceState` after reading (a reload would lose the page, and keeping the token anywhere else means storage); a lenient parse (a real token is never padded, encoded or followed by anything).

4. **Nothing but the API sees the token.** It goes only into the SDK's path (`/api/v1/tenants/<slug>/deposits/<token>`, whose proxy log TAT-38's checklist turns off). The page has no in-page `#` link, because following one would replace the token (the error summary's items are buttons); the router's scroll restoration, which keeps positions in `sessionStorage`, gets `getScrollRestorationKey` (`scrollRestorationKey`: the history entry's key, else the path), so a key can never be the href with its fragment; nothing is kept in storage, logged or tracked; no request carries a Referer (`Referrer-Policy: no-referrer` header and meta, `referrerpolicy="no-referrer"` on QR images). TAT-65 asked PostHog and Sentry to strip the fragment: PostHog left the storefront with TAT-48 and Sentry runs on the server only, which never sees a fragment, so there is nothing to configure now; the development guide records the rule for any browser-side reporter added later. A guard test bans storage, logging, analytics, `location.search` and `#` links in `src/deposit/`, and checks the route reads no URL itself. Rejected: a Content-Security-Policy now (TAT-57 ruling 17: none is sent yet).

5. **The server renders the shell; the deposit loads in the browser.** The route's loader returns `DepositShell` (`studioName`, `timezone`, `phone`), built from the studio the root already cached (`loadDepositShell`: no API call, which `check:page` pins). The server renders the `h1` "Pay your deposit to <studio>", a skeleton marked `aria-busy`, a `<noscript>` line ("Turn on JavaScript to see your deposit, or message <studio>.") and the studio's WhatsApp and Viber links. After hydration the screen reads the token and calls `useDeposit`; no deposit data is ever server-rendered or serialized (TAT-65). Rejected: `ssr: false` (a blank page until the JavaScript runs, and nothing at all without it); a loader that fetches the deposit (the server can't see the token, by design).

6. **Headers and head.** The page answers `Cache-Control: no-store`, `Referrer-Policy: no-referrer` and `X-Robots-Tag: noindex, nofollow`; its head has `robots` `noindex, nofollow` and `referrer` `no-referrer`, the title "Pay your deposit · <studio>" from the first byte (the studio is known on the server since TAT-12; TAT-65's "then" dates from before), a description, and Open Graph `og:type`, `og:site_name`, `og:title` and `og:description`, so the preview a chat app draws from the link (fetched without the fragment) names the studio. No canonical link, `og:url` or JSON-LD. The deposit data itself is the API's `no-store` and the query's `staleTime: 0`. Rejected: the studio pages' `s-maxage=60` (a CDN copy would save one cached lookup on a page each client opens a few times, and `no-store` keeps any future per-visitor change from being cached by accident).

7. **No bot challenge.** The API asks for none on the deposit routes (TAT-55's Turnstile and honeypot guard `inquiries.create` only); the unguessable token, TAT-65's per-address and per-token limits (GET 120 / 60 per 10 minutes, POST 20 / 10 per hour) and TAT-38's caps protect them. No Cloudflare script loads on this page. Rejected: Turnstile at Send (a third-party script on a payment page, and a failure mode the API doesn't need).

8. **No polling (TAT-65 ruling 15).** The page reads the deposit on mount, when the tab regains focus (coming back from the payment app), on reconnect, and after a refusal that may mean the page changed (ruling 17). No timer and no "check again" button: verification takes hours, the studio confirms on WhatsApp or Viber, and a reload does the rest. Rejected: a 60 s refetch while `submitted` (battery and the per-token read limit, for news the client gets in a chat anyway).

9. **States, in TAT-65's words.** The API computes the state; the page maps each to fixed copy (`src/deposit/copy.ts`, TAT-65's sentences word for word): `due` (the amount, the code, the methods, the policy, the form), `submitted`, `paid` (and "No deposit is needed for this booking." when the deposit is 0), `updating`, `expired`, `cancelled`. An unknown state from a newer API is shown as `updating` (no payment details). A 404 at any time is the dead-link message, even over data already shown (a replaced or expired link must stop showing payment details); a 429 on load and other load failures have their own messages, and "Try again" refetches. Payment methods and the form appear only in `due`, with methods, and with something to pay. Under the state, every state ends with one line, "Questions? Message <studio>:" with WhatsApp (prefilled "Hi <studio>, about my deposit (reference code <code>).") and Viber links built from the studio's phone, and the page's footer says "You pay <studio> directly. Tattoo Drip runs this page for them and never handles your money." Rejected: per-state link sets (one line everywhere is simpler and always helps).

10. **A long brief folds.** The brief (up to 4000 characters) shows as text when it is at most 240 characters, else inside a closed `<details>` "Your tattoo idea" with the whole text, so the amount stays on the first screen at 375 px; "with <artist>" follows when there is one. Rejected: a line clamp (TAT-48: no clamps or ellipses on user text); moving the brief below the payment (TAT-65's order).

11. **Amounts and dates.** Amounts are only the API's text (`dueText`, `amountText`: the platform's `formatMoney`, "NPR 3,000"); the integer `deposit.due` of the latest data at Send goes back as `expectedAmount`. "Pay by <payByText>" adds ", in 10 days", "by tomorrow" or "by today", counted in the studio's timezone (the cached studio's `timezone`) from the phone's clock, and nothing when the count is negative or the zone unknown. The screenshot's time reads "18 Oct 2026, 2:05 pm" in the studio's timezone (Intl parts with en-GB month names, as the platform's `formatDay`). No countdown. No number is typed, so Devanagari digits need no handling. Rejected: formatting paisa in the browser (a second formatter to keep equal); a live countdown (the quote ends on a day, and a ticking clock on a phone set to the wrong time misleads).

12. **QR codes and details, made for paying on the same phone.** Methods in the API's order, each a heading (its label), its QR (`safeImageUrl`; `alt` "<label> QR code for <studio>"; `width`/`height` 280 so a square is reserved while it loads, CSS keeps the image's own ratio and caps it at 17.5rem; white behind it in dark mode; the first QR `loading="eager"`, the others lazy), "Scan it with your eSewa app." (per kind; Fonepay "your bank or wallet app"), then its details: bank, account name, and the account number or wallet ID with a Copy button. Because most clients pay on the phone that shows the page, a line above the methods says: "Paying from this phone? Press and hold a QR code to save it, then choose it from your gallery in your payment app's scanner." A method of a kind the API can't take a screenshot for is left out. Rejected: a "Save QR" `download` link (browsers ignore `download` on another origin's image).

13. **Copy buttons work in in-app browsers and say what they copy.** `navigator.clipboard.writeText`, else a hidden textarea and `execCommand("copy")` (Instagram's, Facebook's and Viber's in-app browsers often refuse the clipboard API), else "Couldn't copy. Press and hold the text to copy it."; the code and numbers are `user-select: all`. "Copied" shows for 2 s in a polite live region beside the button. The accessible name starts with the visible words: "Copy code 7K3M9Q" and "Copy 9812345678" (WCAG 2.5.3, label in name, so speech input can say what it sees); this amends TAT-65's `aria-label="Copy reference code <code>"`. Rejected: TAT-65's label as written.

14. **The screenshot goes through TAT-57's pipeline, with a profile of its own.** `prepareReference`'s body becomes `prepareImage(source, codec, profile)` in `src/intake/images.ts` with the same type check, the 50 MiB and 100-megapixel bounds before any decode, the 20 s decode and encode timeouts and the bitmap always closed; `prepareReference` is `prepareImage` with `REFERENCE_PROFILE`, unchanged. `PROOF_PROFILE`: long edge 2048 px at 0.85, then 0.72, then 1600 px at 0.72 until at most 1.5 MiB; refused over 4 MiB; drawn on white; sent as `payment.jpg` (no EXIF, no name). 2048 px because the platform keeps proofs up to 2048 px and the owner reads small text (amount, transaction ID, remark). TAT-65's "a file over 10 MB is refused before upload" goes: what is sent is always the re-encoded JPEG of at most 4 MiB, so a 12 MB camera photo of a bank slip is taken; the hint says "A screenshot or a photo of the payment: JPEG, PNG or WebP.", the pipeline's refusals have their own words, and a 413 still says TAT-65's "This image is too large. Use one of 10 MB or less." Rejected: TAT-57's 1600 px (a tall screenshot's text at two thirds); sending the original (its metadata, and up to 10 MB over 3G).

15. **One screenshot.** A single file input (`accept="image/jpeg,image/png,image/webp"`, so iOS converts HEIC); picking again replaces the screenshot. While one is being prepared or sent, the picker does nothing (`aria-disabled`, its click prevented, focus kept) and Remove does nothing, so two decodes never run together and focus never drops. A HEIC the browser can't open says "take a screenshot of the payment instead". The preview is an object URL of the prepared JPEG, revoked on replace, remove, success and unmount (`previewOf`). After a pick, focus stays on the picker and its polite status says "Preparing your screenshot…", then "Screenshot added." or why it wasn't; Remove returns focus to the picker. A replacement that is refused leaves no screenshot, and the message says why. Rejected: queueing picks (one file, one decode).

16. **Sending.** TanStack Form (`useAppForm`, `field.ChoiceField` "How did you pay?" with the methods' kinds once each, preselected when there is one; validate on submit, then on change) beside the picker, which is a component of its own as TAT-57's photo tray is (its value is a file prepared asynchronously, not a form value). Send is `aria-disabled` (it keeps focus) while a screenshot is being prepared, while sending and while a rate limit lasts; one attempt at a time; the hook never retries; "Sending…", then "Still sending. On a slow connection this can take up to 2 minutes; keep this page open." after 15 s; the SDK's 120 s upload timeout stands; a `beforeunload` prompt while sending; offline it fails at once (`networkMode: "always"`). On 201 the hook puts the `submitted` page in the cache and focus moves to its message (TAT-65). Rejected: a cancel button (TAT-57 ruling 7: a request stopped after its body left may still land).

17. **Every refusal has fixed words and a way on** (table below; `describeProofError`). Field errors (`validation_failed` on `proof` or `method`, and a 413) go under their field and into an error summary that takes focus, whose items are buttons that focus the control. Everything else is one notice above Send with `role="alert"`, and focus stays on Send. `deposit_changed`, `deposit_not_due`, `not_found`, a 408, a timeout and a network error read the page again in the background; when it has left `due` (the upload did land, the studio acted, the link died), the new message or the dead-link message takes focus, so a client whose 201 got lost sees `submitted` instead of paying or sending twice. A 429 blocks Send for its `Retry-After` (60 s without one) and says the wait in minutes or hours. `error.message` is never shown; the API's field messages are, as text. Rejected: TAT-57's focused notices (`role="alert"` speaks without moving a keyboard user away from Send, which they may press again).

18. **Accessibility.** One `h1`; an `h2` per block (Deposit due, Reference code, How to pay, Deposit policy, After you pay, send a screenshot), an `h3` per method. The state message sits in a polite live region, written `aria-live="polite"` (what TAT-65's `role="status"` means; Biome's `useSemanticElements` refuses that role on a `div`), and an empty region takes no space but stays in the accessibility tree (`position: absolute` while `:empty`, never `display: none`); load errors and refusals are `role="alert"`; the radios are a `fieldset` with a `legend`, the picker a `fieldset` "Payment screenshot" with its hint and errors tied by `aria-describedby`; targets at least 44 px (`.action` 3rem, copy buttons 2.75rem); focus moves only after the client's own action; TAT-48's tokens keep AA contrast; nothing is told by colour alone; reduced motion stops the sending line.

19. **Look.** TAT-48's palette, type and focus ring. One column `min(28rem, 100% - 2rem)` wide (16 px gutters at 375 px, centred above). The amount in Eczar 700 at 2.5rem; the reference code in a dashed violet box, monospace, letter-spaced (it is ASCII, never a name); methods separated by hairlines, QR codes on white; the non-due states in the stencil's offset violet frame; red only for errors; the sending line is the one motion.

20. **Tests, and what only a browser shows.** `node:test` with `tsx` in `test/deposit/`: the pure modules (`token`, `copy`, `view-model`, `proof`, `problems`, `seo`, `loader`), the markup through `react-dom/server`, the server-rendered shell, and a guard over `src/deposit/`. `check:page` grows a `/deposit` check (200, the title, `no-store`, the two headers, the meta, the shell, and only the lookup asked of the API). `browser.ts` (the clipboard), the hash hook and the components' effects are the browser pass's: the built server against a stand-in API, every state at 375 px, a keyboard-only upload, refusals, offline, a 404 over data shown, an old slug's redirect keeping the fragment, and no request but the API's carrying the token.

21. **Docs and the requirement.** A "Deposit page" section in `apps/storefront/docs/development.md`; one line each in `docs/sdk.md`, `docs/architecture.md`, `apps/storefront/AGENTS.md`, `apps/storefront/README.md`, `docs/README.md`; a deposit-page rule in `docs/requirements.md` and its "Deposit page per project" box ticked (TAT-65 left it for this ticket); `README.md` and `apps/platform/docs/deploy.md` stop listing TAT-65b as missing and add a first-deploy check that `/deposit` reaches the storefront's and the CDN's logs without its fragment.

## Refusals and failures

After Send (`describeProofError`):

| Answer | The page shows | Then |
|---|---|---|
| 201 | the `submitted` message, focused | the hook seeds the page |
| 422 `validation_failed`, `proof` or `method` | the API's message under the field, and the summary (focused) | |
| 422, only `expectedAmount` | notice "The deposit amount changed. Check the new amount." | read again |
| 422, nothing placeable | "Your screenshot wasn't accepted. Reload the page, then send it again." | |
| 409 `deposit_changed` | "The deposit amount changed. Check the new amount." + "If you already paid the old amount, message <studio> before you send a screenshot." | read again: the new amount shows |
| 409 `deposit_not_due` (any 409) | "This page changed while you were on it." + "Check what it says now…" | read again: usually the new state replaces the form and takes focus |
| 404 | "This link doesn't work any more." + "Ask the studio to send you a new one." | read again: the dead-link message, focused |
| 413 | under the picker: "This image is too large. Use one of 10 MB or less." | |
| 429 | "Too many tries. Wait <20 minutes> and try again." | Send blocked for `Retry-After` (60 s without) |
| 400, 415 | "The upload was cut off." + "Check your connection, then send again." | |
| 408, `timeout`, `network_error` | "Couldn't send. Check your connection and try again." | read again: a send that landed shows `submitted` |
| 503 `service_busy` | "The page is busy right now." + "Send again in a minute." | |
| anything else | "Something went wrong on our side." + "Send again in a minute. If it keeps happening, message <studio>." | |

Loading (`screenFor`, `describeLoadError`): no or malformed token: the dead-link message, no request; pending: the skeleton; a 404 (also over data shown): "This link doesn't work any more. Ask the studio to send you a new one." (`role="alert"`); a 429: "Too many tries. Wait a few minutes, then reload the page."; anything else, after the query's own retries: "We couldn't load your deposit. Check your connection." with "Try again". A failed refresh over data already shown keeps that data.
