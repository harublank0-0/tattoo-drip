# Session cookie hardening and the app/storefront domain split (TAT-9)

Date: 2026-10-18
Refs: TAT-9 (1 point). Builds on TAT-28/29 (`role_guard.spec.ts`'s subprocess `boot`), TAT-8 (login throttle), TAT-32 (the public API is cookieless: `WebSessionMiddleware`, `WebShieldMiddleware`, `stateless.spec.ts`), TAT-65 and TAT-55 (`STOREFRONT_URL`, `#services/storefront_url`: `checkStorefrontUrl`, `studioHostname`, `pointsAtThisMachine`), TAT-12 (studio pages on `{tenant}.<domain>`, `*.localhost` in development), TAT-82 (plain-HTTP development from a phone) and TAT-38's design (`docs/deploy.md`, `TRUST_PROXY`). Custom studio domains are TAT-79; hosting, DNS and TLS are the user's TAT-14 (platform) and TAT-13 (storefront on Vercel). Written without the user (unattended run): every open question is a ruling below. **No migration, no route, no dependency change, no new setting.**

## Goal

Studio pages run on subdomains of the storefront's domain, and a studio can later bring its own domain. No page a studio is served on may ever read, set or overwrite the dashboard's session (cookie tossing, session fixation through a sibling subdomain), and none may be same-site with the dashboard, so `SameSite=Lax` keeps refusing their requests. So:

1. In production the session cookie is `__Host-td-session`: `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, no `Domain`. The prefix makes the browser itself refuse any version of it that isn't host-only and Secure.
2. The dashboard and the API live on a registrable domain of their own, separate from the studio pages': the platform refuses to start in production when `APP_URL` is plain http or sits on, under or above the studio pages' domain, and the checklist says the rest.
3. CSRF protection (Shield) stays on, with tests that pin it.

## Rulings

1. **One cookie policy, switched by `NODE_ENV=production` only.** A pure `#services/cookie_policy` gives `sessionCookieName(production)` and `cookieAttributes(production)`; `config/session.ts` and `config/app.ts`'s cookie defaults take them with `app.inProduction`. Production: `__Host-td-session`, `Secure`. Development and tests: `td-session`, not `Secure`. Everything else is the same everywhere: `Path=/`, `HttpOnly`, `SameSite=Lax`, no `Domain`. Why: development runs over plain http, and there Safari refuses `Secure` cookies on `http://localhost`, Chrome refuses `__Host-` names on `http://localhost` (httpwg/http-extensions#2605, 2023; only Firefox accepts both), and no browser keeps either on a phone opening the dev server at its LAN address (TAT-82). The prefix requires `Secure`, and cookie-es (the serializer) throws for a `__Host-` cookie without it, so the two switch together. The switch is the environment, never the request: behind a TLS-terminating proxy the app sees http, and a per-request switch would quietly drop `Secure` in production. Rejected: the prefix in every mode (development sign-in breaks in Chrome, Safari and on phones); `Secure` when `request.secure()`; a setting to turn `Secure` off (a production footgun).
2. **The name is `td-session`.** The `__Host-` prefix renames the cookie anyway, so the base name changes too: it no longer advertises the framework, and it doesn't collide with another AdonisJS app on a developer's `localhost` (cookies ignore ports). Rejected: `__Host-adonis-session`.
3. **Every cookie the app sets, and which can't take the prefix.** Only the session cookie carries authority; the others are safe without the prefix, as the table says. Patching Shield or the session store to rename the rest was rejected: `pnpm patch` edits compiled chunks and is redone on every upgrade (TAT-38 ruling 16's reason), for no gain.

    | Cookie | Set by | Production attributes | Why it keeps its name |
    |---|---|---|---|
    | `__Host-td-session` (`td-session` in development and tests) | the session middleware, on every dashboard response | `Max-Age=7200; Path=/; HttpOnly; Secure; SameSite=Lax`, signed | (it has the prefix) |
    | the session id itself (cookie store only) | `SESSION_DRIVER=cookie`: the session's data, encrypted with `APP_KEY` | the session cookie's options (`stores.cookie()` passes them) | `@adonisjs/session` names it by the session id. It is host-only like the session cookie, encrypted, and its name can't be guessed without the `__Host-` cookie's value. Tests use the memory store, so they never see it. |
    | `XSRF-TOKEN` | Shield's CSRF guard, on every dashboard response | `Max-Age=7200; Path=/; Secure; SameSite=Lax`, not `HttpOnly` (Inertia's client reads it and sends `X-XSRF-TOKEN`) | Shield hard-codes the name (and uses it as the encryption purpose), and Inertia reads it by that name. A token verifies only against its own session's secret, so a planted one fails the check: it can deny service, never forge. |
    | `remember_web` | the auth guard: cleared (`Max-Age=0`) on every login and logout | the defaults: `Path=/; HttpOnly; Secure; SameSite=Lax` | Remember-me is off (ruling 11): it never holds a value. |
    | `app_theme` | the browser (`useTheme`) | `path=/; max-age=1 year; samesite=lax` | Set by script. It carries no authority, and the layout renders it escaped. Unchanged. |
    | flash messages, the CSRF secret, the last tenant | inside the session | | They have no cookie of their own. |
    | anything on `/api/v1` | nothing | | The public API is cookieless (TAT-32). |

4. **"No domain" is enforced, not just configured.** The policy has no `domain` key, and `config/app.ts` loses its `domain: ""`. Tests: the policy for both modes; the real serializer (`ResponseFactory`) writing the production session and `XSRF-TOKEN` lines exactly; a functional guard that every `Set-Cookie` on the login page, login, a dashboard page and logout names a known cookie, has `Path=/` and `SameSite=Lax`, has no `Domain`, has `Secure` exactly in production and `HttpOnly` on everything but `XSRF-TOKEN`; and the resolved session and HTTP configs name no domain. In production a domain added anyway makes the serializer throw for the `__Host-` cookie, so every dashboard request fails loudly instead of quietly widening the cookie; a test pins that too. Rejected: greps of the config source (brittle).
5. **Production is HTTPS-only, refused at boot.** With `NODE_ENV=production`, the web server, the worker and every `ace` command that boots the app refuse to start unless `APP_URL` is an https URL. Why: browsers drop a `Secure` `__Host-` cookie over plain http, so every sign-in would end on "Invalid or expired CSRF token", with nothing in any log. At run time the proxy redirects http to https (checklist), and Shield's HSTS header (on, 180 days) keeps returning browsers on https. Rejected: a run-time warning when `request.secure()` is false (it needs TAT-38's `TRUST_PROXY` to see `X-Forwarded-Proto`, and since nothing else in the app reads the protocol, it would fire for a working setup behind an untrusted proxy); an https redirect in the app (a loop when the proxy's header isn't trusted).
6. **Cookies need no `TRUST_PROXY`.** The app writes `Secure` whatever protocol it sees; the browser judges the cookie against its own https connection to the proxy. So TAT-9 does not depend on TAT-38, and `request.protocol()` stays unused for cookies.
7. **"Separate registrable domain" is a boot check plus the checklist.** In production, `checkAppOrigin` (`#services/app_origin`, called by `start/env.ts` after the environment loads) refuses an `APP_URL` host that is the studio pages' domain, is under it, or has the studio pages under it. The studio pages' domain is the labels two sample studio hosts share (`{tenant}.example.com` and `{tenant}-ink.example.com` both give `example.com`); ports, case and a trailing dot don't count. A sibling under a parent you own (`app.example.com` with `{tenant}.sites.example.com`) is not detected: without the Public Suffix List it can't be told apart from two names under a public suffix (`app.tattoodrip.com.np` with `{tenant}.inkpages.com.np`, which are properly separate), so the checklist covers it, and a test pins the limit. Rejected: the `tldts` package (adding a dependency re-resolves every `latest` specifier in the lockfile, as the TAT-12 build found, and a bundled suffix list goes stale); a hand-kept list of suffixes; refusing every shared parent of two labels or more (it blocks two `.com.np` names); a warning (it would fire forever on a correct `.com.np` pair).
8. **A loopback `APP_URL` skips the domain comparison, never the https rule.** The README's local production trial (installing the PWA) runs the built server behind a local HTTPS proxy at `https://localhost:<port>`, with studio pages on `http://{tenant}.localhost:3000`, which would otherwise fail ruling 7. A real deploy with a loopback `APP_URL` can't go unnoticed: every email link and image URL would point at `localhost`. The https rule stays even on loopback, because Chrome and Safari would refuse the cookie over plain http anyway. Rejected: no exception (the trial could never start); an exception for https too.
9. **The API host.** One process serves the dashboard and `/api/v1`, and it knows only `APP_URL`. The API is served on `APP_URL`'s host or on a sibling of it on the platform's domain (the architecture's `api.`), never under the studio domain. The storefront's `API_URL` must point there (checklist). Rejected: a canonical-host middleware that 404s dashboard routes on any other host (tests and development use `localhost`; TAT-14's proxy can route by host); a storefront boot check (the storefront reads its settings on the first request, and it would be a second copy of this logic in another app).
10. **CSRF unchanged, now pinned.** Shield's CSRF stays on for `POST`, `PUT`, `PATCH` and `DELETE`, with no `exceptRoutes`, the XSRF cookie on, and the API outside it (TAT-32). New tests: a signed-in owner's studio-profile save without a token, and with a token from another session, is refused (302 back, the "Invalid or expired CSRF token" flash) and changes nothing; with a token it saves (positive control); a logout without a token leaves the user signed in; a config guard holds the four values. `SameSite` stays `Lax`. Rejected: `Strict` (a dashboard link opened from an email or WhatsApp would arrive signed out).
11. **Login keeps issuing a new session id; nothing else in auth changes.** `@adonisjs/auth` regenerates the id at login: a test pins that a planted id never carries the login. `__Host-` stops planting from a sibling; regeneration stops every other kind. Remember-me stays off (`useRememberMeTokens: false`: no long-lived cookie, no token table), and the session stays a sliding 2 hours (`age: "2h"`, `clearWithBrowser: false`). Logout forgets the user but keeps the id: no fixation risk, since the next login regenerates. Rejected: remember-me or a longer session for the PWA (a product call and a migration: a ticket of its own if pilots ask).
12. **The production store is the cookie store, as now.** `SESSION_DRIVER=cookie` (`.env.example`'s value). `memory` loses every session on restart and between processes, and `database` needs a `sessions` table that doesn't exist (TAT-36 kept that name free). It goes in the checklist. Rejected: a boot check on `SESSION_DRIVER` (one more check for a value `.env.example` already sets right).
13. **Everyone signs out once.** The new name invalidates every existing session. There are no production users before launch; in development, sign in again. An old `adonis-session` cookie expires by itself within 2 hours, and no code clears it. Rejected: accepting the old name too (an unprefixed session cookie would still be accepted in production: the thing this ticket removes).
14. **Development and tests run as before.** The cookie is `td-session` over http on `localhost`, LAN addresses and `*.localhost`. Japa's session plugin reads the configured name, so `.loginAs()` and `.withCsrfToken()` are untouched. Tests never run in production: its cookie is checked through the real serializer (ruling 4), and its boot through real processes (`node ace.js list:routes` and `bin/server.ts` with `NODE_ENV=production`, TAT-29's `boot`, moved to `#tests/helpers/boot`). The README's local production trial now needs a local HTTPS proxy and an https `APP_URL` (ruling 8).
15. **Carry-forwards, not done here.** TAT-79 must refuse a custom studio domain that is the platform's host, the API's host, or on their registrable domain. TAT-14: TLS for the platform's hosts, an http-to-https redirect at the proxy, DNS for the platform's domain, and the first-deploy cookie check. TAT-13: the wildcard and apex DNS on the studio domain only, and `API_URL` on the platform's domain. If TAT-38 is built after this branch, its builder moves this ticket's checklist bullet from `database/README.md` into `deploy.md`. Out of scope, noted only: clamping `app_theme` to `light` or `dark` on the server (it is typed as one but read raw); a longer session for artists using the PWA.

### Checklist: dashboard cookies and domains (what the user sets in production)

1. Two registrable domains: one for the platform (the dashboard on `app.<platform>`, the API on `api.<platform>` or the same host) and one for the studio pages (the storefront's apex and `*.<studios>` on Vercel). Never the dashboard or the API under the studio domain, the studio pages under the platform's, or both under a parent you own: two domains bought separately (two names under a public suffix such as `com.np` are separate; check a doubtful parent at publicsuffix.org).
2. Platform: `NODE_ENV=production`; `APP_URL=https://app.<platform>` (the boot check refuses http, and refuses an `APP_URL` on, under or above `STOREFRONT_URL`'s domain); `STOREFRONT_URL=https://{tenant}.<studios>`; `SESSION_DRIVER=cookie`. `APP_KEY` signs and encrypts the session and CSRF cookies: rotating it signs everyone out.
3. Storefront: `API_URL=https://api.<platform>` (or `APP_URL`'s host), never a studio domain.
4. Proxy (TAT-14): TLS for the platform's hosts and an http-to-https redirect there; the app itself never redirects. The cookies need no `TRUST_PROXY` (that setting is for client addresses).
5. DNS: the wildcard and the apex of the studio domain go to Vercel only (TAT-13); the platform's names go to the platform. No wildcard on the platform's domain.
6. Custom studio domains (TAT-79) are never the platform's hosts or on its domain.
7. After the first deploy: sign in at `https://app.<platform>`; DevTools, Application, Cookies shows `__Host-td-session` with Secure, HttpOnly, SameSite Lax and no Domain; `curl -sI http://app.<platform>/login` answers a redirect to https.
8. Everyone is signed out once by the rename (no production users yet).

## Not in this ticket
