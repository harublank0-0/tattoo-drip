# Session outcomes and moving a session (TAT-85)

Date: 2026-10-18
Refs: TAT-85 (Session outcomes: mark completed, no-show or cancelled, and move a session). Builds on TAT-36 (`ProjectSession`, `SessionService`: `complete`, `markNoShow`, `cancel`, `reschedule`, the no-overlap constraint, the lock order), TAT-43 (the booking form's time rules: `localDateTime`, quarter hours, today to a year ahead; the project page's Sessions card), TAT-50 (the calendar shows active sessions with a Completed badge), TAT-46 (the "booked, no session" flag, `ProjectService.findFor`), TAT-66 (withdraw from `booked`, the Payments card, `deposit_outcomes.session_id`, `balanceOf`) and TAT-83 (expiry cancels scheduled sessions). Feeds TAT-70 (no-show rate) and TAT-76 (no-show report). Roles are TAT-30; linking an artist's account is TAT-33; the project delete cascade is TAT-42.
Size: **about 5 points.** Part 1 (rulings 1 to 19) is the ticket's 3 points; Part 2 (rulings 20 to 31, scheduling a session on an existing project) was folded in by the run's coordinator as a launch blocker, because without it an inquiry project can never reach `booked`.

## Goal

At the end of a session, or the next day, staff open the project and record what happened: done, no-show or cancelled. A client who asks for another time gets their session moved, and the artist's time can still never be double-booked. The first finished tattoo session moves the project from Booked to In progress. The studio's no-show and cancelled counts can be read for the pilot metrics. And (Part 2) staff schedule a session on a project that already exists: a quoted or deposit-paid project gets its tattoo session and books, a long piece gets its next session, a missed one is rebooked.

**No migration.** No API, SDK, OpenAPI or storefront change. Three dashboard routes. Written without the user (unattended run): every open question is a ruling below.

## Rulings

1. **The smallest slice that meets the acceptance.** Recording an outcome on a scheduled session and moving it, from the project page's Sessions card; the project status move that follows; the authorization; a per-tenant count. Not here: adding a session to an existing project, finishing a project (`in_progress` to `completed`), per-session deposit outcomes, a record-as-done form, changing a session's artist, undoing an outcome (carry-forwards). Why: 3 points, and the ticket puts deposits and completion with TAT-66. Rejected: also building "schedule another session" (the most useful missing piece, but it is a new booking path with its own artist and kind rules). *Amended:* the coordinator brought scheduling on an existing project in as Part 2 (ruling 20); the rest of this ruling stands.
2. **Three outcomes, each final.** A `scheduled` session becomes `completed`, `no_show` or `cancelled`, and nothing changes it afterwards (TAT-36's rule): no undo, no correction, no reopening. A completed session keeps blocking its time; no-show and cancelled ones free it (the generated `active` column). Why: reopening would have to re-run the overlap check against time someone else may have booked meanwhile, and the no-show count would stop being trustworthy for TAT-70. A confirmation step (ruling 15) guards against a mis-tap. Rejected: an undo window; owners correcting an outcome (a carry-forward if the pilot asks for it).
3. **Done and no-show once the session has started; cancelled any time.** `completed` and `no_show` need `starts_at <= now` (server clock, read after the row locks are held), else `SessionRuleError("not_started")`. Cancelling has no time rule. There is no upper limit: an outcome can be recorded days later. Why: the outcomes are final, and a future session can't have been missed or done; a session in the chair right now (started, not ended) can be marked done early. Rejected: waiting for the session's end (an artist finishing early couldn't record it); no time rule (a mis-tap on tomorrow's session would be permanent).
4. **"Already happened" means recording the outcome later; there is no record-as-done form.** A session booked in time can get its outcome at any later moment (ruling 3), so yesterday's session is recorded today. TAT-43's booking form still refuses earlier days, so a walk-in nobody entered on the day can't be recorded after the fact. Why: the pilot studio books at the desk when the client arrives (TAT-43 allows earlier today), so the realistic gap is "nobody marked it", which this covers with no new form. Rejected: a record-as-done form that creates a completed session in the past (a second booking path with its own validation); allowing past days in the booking form (changes TAT-43's ruling 8 and lets a typo book the past).
5. **A tattoo session is marked done only once its project is booked.** Completing a `tattoo` session needs the project in `booked`, `in_progress`, `completed` or `healing_check` (`BOOKED_STATUSES`), else `SessionRuleError("not_booked")`; consultations and touch-ups can be completed in any status (a consultation in `reviewing` is normal), and no-show and cancelled have no status rule. Why: custom work is never booked before its deposit is settled, and a `deposit_pending` project with finished work would later be cancelled by the quote's expiry (TAT-83). The studio first records the deposit (TAT-66's desk payment books the project when a tattoo session is scheduled), then marks the session done. The project page explains it under the session (ruling 15). Rejected: booking the project on completion (skips the deposit rule); allowing it and leaving the project in `deposit_pending`.
6. **The project's status follows its tattoo sessions, whatever the order of events.** After an outcome on a `tattoo` session, a `booked` project that has at least one `completed` tattoo session and no `scheduled` tattoo session moves to `in_progress`; nothing else moves. So: the first finished tattoo session moves `booked` to `in_progress`, unless another tattoo session is still scheduled (the project stays `booked`, where scheduling that next session would put it anyway: TAT-36's `in_progress` to `booked` shortcut); once the work has started, cancelling or missing the next tattoo session puts the project back in `in_progress`; a project whose only tattoo session was missed or cancelled stays `booked` and the board's "booked, no session" flag shows (TAT-46), so staff withdraw it (TAT-66) or rebook. The rule runs in `SessionService.finish`, so it applies to every caller, `ProjectService.cancelScheduledSessions` included: a withdrawal from a booked project whose work started may pass through `in_progress` inside its transaction and still ends `cancelled` (a test pins it). Consultations and touch-ups never move a project. This refines TAT-36's "completing one moves booked to in_progress", which gave a project with a second session scheduled the status `in_progress`, a state the same sessions reach as `booked` in the other order. Rejected: TAT-36's rule unchanged (order-dependent); moving `booked` back to `deposit_pending` after a no-show (the deposit is still settled).
7. **Finishing a project is not in this ticket.** `in_progress` to `completed` needs the last session done and the balance paid (`balanceOf`, TAT-66); TAT-66's carry-forward handed it to TAT-85, and this ruling hands it on to a follow-up ticket: an owner's "Finish project" on the status card, allowed from `in_progress` when no tattoo session is scheduled and the balance due is zero or less, then `healing_check`. Why: it is a new manual move with a payments read (`ProjectService` can't depend on `PaymentService`, which depends on it), a rule for hourly projects whose estimate differs from the actual time, and the board's Closed view; none of it is needed for the acceptance. Rejected: completing the project automatically when its last session is done (the balance may be unpaid).
8. **Moving changes the time only, with the booking form's rules, for any scheduled session.** The new date is a real day from the studio's today to a year ahead (earlier today is fine), the start time must exist that day (a time the clocks skip is a field error; one they pass twice is its first occurrence), the length is 0.25 to 12 hours in quarters, elapsed time, all in `tenant.timezone`. One helper (`readSessionTimes` in `#modules/scheduling/validators/session`) serves both forms; TAT-43's validator moves onto it with the same messages. The artist stays (another artist is a new session). A session whose time has passed and has no outcome can be moved (the client asked to come another day). A move never changes the project's status. Why: the same rules everywhere, and the ticket asks for them. Rejected: moving into an earlier day (it would make a past session out of nothing); changing the artist here (TAT-36's "cancel plus schedule"); drag and drop.
9. **An overlap is a field error and nothing is saved.** The move goes through the existing `reschedule` path: project row lock, then the session's, then the update, whose exclusion constraint settles races; the failed savepoint rolls back and `SessionOverlapError` becomes "{Artist} already has a session at that time. Pick another time." on the start time, the page keeps the form open with the typed values. Its own old time doesn't count (the constraint compares other rows). Rejected: a query for overlaps first (racy; the constraint decides, TAT-36).
10. **Deposits, holds and the quote's expiry: nothing automatic.** Recording a no-show or a cancellation, or moving a session, never touches payments, the deposit link or the quote. A `deposit_pending` project whose held session was moved past the quote's expiry is still cancelled by the expiry if its deposit isn't settled (TAT-83 cancels its scheduled sessions; recorded ones are history and stay). The session rows are never deleted, so `deposit_outcomes.session_id` (TAT-66) can point at a missed or cancelled session later. TAT-66's carry-forward "record a no-show's or cancelled session's deposit through `recordOutcome(…, { sessionId })` and allow `moved`" is declined here and goes to a follow-up ticket. Why: the ticket keeps deposits out "beyond not blocking those paths", a project's deposit isn't per session (what share does one missed session hold?), and it is owners-only money UI on the Payments card. Rejected: a deposit question inside the no-show confirmation.
11. **Who may change a session.** Owners: any session of the studio. An artist member: only a session whose artist is their own linked live profile, on a project assigned to that profile (the project page they can open). Anyone else (another artist's session on their project, their own session on a project reassigned to someone else, an artist without a linked profile) gets a 404, like another studio's id, a deleted session or a session of a deleted project. The rule is `mayChangeSession` (`#modules/scheduling/outcomes`); `SessionService.findChangeable` applies it before the form is read, and `recordOutcome` and `move` apply it again under the row locks, so an owner reassigning the project while the artist's request waited is a 404 too (the `ProjectService.lockFor` precedent). The project page shows the buttons only where the rule allows. Rejected: the session's artist alone (an artist could change a session on a project they can't open, from no screen); the project's artist alone (the assigned artist could record someone else's consultation).

    | Member | Session's artist | Project's artist | May change |
    |---|---|---|---|
    | Owner | any | any or none | yes |
    | Artist linked to profile P | P | P | yes |
    | Artist P | another | P | no (sees it, no buttons; 404) |
    | Artist P | P | another or none | no (calendar row "Not assigned to you"; 404) |
    | Artist without a linked profile | any | any | no (404) |
    | Anyone | another studio's, deleted, or of a deleted project | | 404 |

12. **Two routes in a new `/sessions` group, keyed by the session.** `POST /t/:tenant/sessions/:id/outcome` (`tenant.sessions.outcome`, body `status`) and `POST /t/:tenant/sessions/:id/move` (`tenant.sessions.move`, body `date`, `startTime`, `hours`), with auth, dbContext, tenant and `role({ allow: ["owner", "artist"] })`; both redirect to the project page with a flash. The controller is `ProjectSessionsController` (the name `SessionController` is the login's). One `:id`, so the isolation harness works unchanged (it swaps only the slug and `:id`); this follows TAT-66's `/payments/:id/verify`. The outcome's field is `status`, not `outcome`, because TAT-66's deposit-outcome form on the same page already shows errors for `outcome`. Rejected: `/projects/:id/sessions/:sessionId/…` (two ids); a route per outcome.
13. **No migration, no audit columns.** No `outcome_at`, `outcome_by` or cancel reason; `updated_at` moves. Why: nothing reads them, project moves record no actor either, and the counts (ruling 14) need only the status and the start. Staff can write a reason in the project's notes. Rejected: audit columns now (TAT-30 or TAT-70 can add them with a reader).
14. **Counts for TAT-70 and TAT-76 are a service read.** `SessionService.countByStatus(tenant, { from, to })` counts the tenant's live sessions whose `starts_at` falls in the half-open window, per status, for the studio and per artist (`{ studio, byArtist }`, every status present, 0 when none), in one grouped query served by the `(tenant_id, starts_at)` index; int8 counts are parsed with `Number`. The no-show rate is `no_show / (completed + no_show)`, the caller's to compute. No page. Rejected: counting by `updated_at` (a session recorded late would land in the wrong month); a report screen (TAT-76).
15. **The Sessions card gets the actions.** Each scheduled session the member may change shows, in this order, "Done" and "No-show" (once it has started), "Move", and "Cancel session". An outcome button opens an inline confirmation under the row naming the session and saying it can't be undone, with the confirm button ("Mark done", "Mark no-show", "Cancel session") and "Keep it scheduled"; "Move" opens an inline form (Date, Start time, Length) prefilled with the session's own values (its day, or today when that day can't be chosen any more). One panel is open at a time; Escape closes it and focus returns to its button; after a successful save focus moves to the card's heading. A started tattoo session of a project that isn't booked yet shows "It can be marked done once the project is booked." instead of "Done". The card moves to its own component (`inertia/components/sessions_card.tsx`, like TAT-66's Payments card) so the page diff stays small. Rejected: `window.confirm` (its Cancel and OK buttons read backwards for "Cancel the session?"); a dialog component (none installed, and the inline panel is TAT-66's pattern); swipe actions.
16. **The page decides which buttons show when it loads.** The server computes each row's outcomes with its clock; a page left open past a session's start shows "Done" after a reload. The service checks again on submit. Rejected: a client-side clock for this (one more moving part for a reload's worth of benefit).
17. **The calendar is unchanged.** It shows active sessions (scheduled and completed, with the Completed badge) and hides no-show and cancelled ones (TAT-50 ruling 6); a moved session shows at its new time, and every row still opens the project, where the outcome is recorded. Rejected: an "unrecorded" badge on past scheduled sessions (a carry-forward if outcomes go unrecorded in the pilot).
18. **Words.** The button is "Done" and the status badge "Completed" (TAT-43's labels stay). Flashes: "Session marked done.", "Marked as a no-show. The time is free again.", "Session cancelled. The time is free again.", each followed by " The project is now in progress." when the project moved; "Session moved: {time}." (`sessionTimeText`). Refusals (flash): "This session already has an outcome, and outcomes can't be changed." (and "…, so it can't be moved." for a move), "This session hasn't started yet: mark it done or a no-show once it has.", "This project isn't booked yet, so its tattoo session can't be marked done." Field errors: the booking form's date, time and length messages; "Choose done, no-show or cancelled." for a tampered outcome.
19. **Built on the chain tip; conflicts are textual.** The scheduling code is untouched by the chain, so the service and validator work stands alone; the project page, routes, isolation cases and fixtures are edited next to TAT-65/66's additions, which the plan quotes from 3870788. Rejected: building on 37a612d (the project page there has no Payments card, and the later rebase would conflict on every UI file).

## Part 2: scheduling a session on an existing project

Added by the run's coordinator after the design was accepted. On the built chain (1b535f1) `moveToBooked` needs a scheduled tattoo session and a settled deposit, the payments screen tells staff "Schedule a tattoo session to book the project", and the only caller of `SessionService.schedule` is `BookingService` (a direct booking creates the project and its session together). So an inquiry, quote and deposit project could never reach `booked`. Part 2 reuses Part 1's time validator (`readSessionTimes`), authorization rule (`mayChangeSession`) and Sessions card.

20. **Scheduling on an existing project is in this ticket.** It reverses ruling 1's "not here" for this one item; finishing a project and per-session deposit outcomes stay carry-forwards. The ticket becomes about 5 points. Why: it is the missing step of the core inquiry-to-booking loop, and every piece it needs is built in Part 1. Rejected: a follow-up ticket (the pilot couldn't book an inquiry until it shipped).
21. **One route under the project.** `POST /t/:tenant/projects/:id/sessions`, named `tenant.projects.sessions.store` (the projects group's `.store` convention, like `tenant.projects.payments.store`; outcome and move are under `/sessions` because they act on an existing session's id), action `ProjectSessionsController.store`. The project loads through `ProjectService.findFor` before the body is read, so another studio's project, a deleted one and a project an artist can't open are 404s. Body: `sessionKind`, `sessionArtistId`, `date`, `startTime`, `hours`. Rejected: a `/sessions` route with the project id in the body (the tenant-scoped path id is the access check, and the isolation harness swaps it); `tenant.sessions.store` (the path is a project's).
22. **Which projects take a new session.** `reviewing`, `quoted`, `on_hold`, `deposit_pending`, `booked` and `in_progress` (`SCHEDULABLE_STATUSES`). `completed` and `healing_check` refuse (`SessionRuleError("project_finished")`: nothing reaches them yet, and the finish-project follow-up decides touch-ups after completion); `declined` and `cancelled` refuse (`project_closed`). The refusal is a flash and nothing is saved. TAT-43's direct booking keeps calling the system `schedule` (only `declined` and `cancelled` refuse) unchanged. Rejected: TAT-36's "every status but declined and cancelled" for staff (a finished project would quietly take a tattoo session that books nothing).
23. **Kind and artist.** Any of the model's kinds: Tattoo (the default), Consultation, Touch-up. The artist defaults to the project's artist; owners choose any live artist of the studio, an artist member schedules only with their own linked profile (shown, not chosen), the list being `BookingService.bookableArtists` (TAT-43's rule). An artist outside that list (another artist for an artist member, a deleted or another studio's profile) is the field error "Choose an artist from the list." and nothing is saved. A project without an artist gets the session's (TAT-36). The fields are `sessionKind` and `sessionArtistId` because the page's quote and payment forms own `kind` and the assignment form owns `artistId`, and Inertia shares one error bag per page. Rejected: tattoo only (a consultation in `reviewing` is how many inquiries start); always the project's artist (TAT-36 lets a consultation or touch-up be with someone else).
24. **Time: the booking form's rules.** `readSessionTimes`, as for booking and moving: a day from today to a year ahead in the studio's timezone (a time earlier today is fine), a start that exists that day (a skipped time is a field error, a repeated one its first occurrence), 0.25 to 12 hours in quarters. Past days are refused, like TAT-43's new bookings; something that already happened is recorded through its outcome (ruling 4). An overlap with the artist's other sessions is the field error "{Artist} already has a session at that time. Pick another time." on the start time, and nothing is saved (the project's artist fill rolls back too), as in ruling 9. Rejected: allowing past days here (a second way to invent history).
25. **A project can hold several scheduled sessions.** Yes: a long tattoo's next sittings, a consultation before the work, a touch-up; only one artist's sessions can't overlap (the constraint). The work rule (ruling 6) keeps a booked project `booked` while any tattoo session is scheduled, and scheduling the next tattoo session moves an `in_progress` project back to `booked`. Rejected: one scheduled tattoo session at a time (multi-session pieces are normal).
26. **Scheduling a tattoo session books the project when it can, in the same transaction.** The member-facing `SessionService.scheduleFor` runs the existing rule under the project's row lock, in the transaction that inserts the session (`schedule` already does): `in_progress` becomes `booked`, and a `deposit_pending` project becomes `booked` through `moveToBooked` when its deposit is settled (`DepositService.isSettled`: zero, or covered by verified deposit money). An uncovered deposit leaves it `deposit_pending`, and the flash and the form's hint say what is missing in the payments screen's words ("NPR 1,000 of the deposit is still due"). The later deposit books it (TAT-66's verify and desk deposit call `settleBooking`). Before acceptance (`reviewing`, `quoted`, `on_hold`) a tattoo session holds the date, and accepting the quote books the project at once when the deposit is zero or already settled (`acceptQuote` calls `settleBooking`). So no path dead-ends: see the table below. Rejected: booking on the next deposit event only (a project whose deposit was paid before the session was scheduled would wait for nothing).
27. **Who may schedule.** Owners on any project; an artist member only on a project assigned to their own linked live profile and only with that profile as the session's artist: `mayChangeSession` applied to the new session, under the project's lock, so an owner reassigning the project while the request waited makes it a 404. One isolation case (on `sessionProject`) and an HTTP test with another studio's artist id (a field error, both studios unchanged). Rejected: artists scheduling other artists (TAT-43's "artists book only themselves").
28. **The payments screen points at the new action.** TAT-66's flash after a deposit with no tattoo session scheduled becomes " Schedule a tattoo session under Sessions to book the project." (its test updated). Rejected: leaving it (it named an action with no place on the page).
29. **Words.** Flash: "Session scheduled: {time}." (`sessionTimeText`) plus, for a tattoo session: " The project is booked." when it booked; " NPR 1,000 of the deposit is still due: the project is booked once it's paid." on a `deposit_pending` project with money due (" The project is booked once its deposit is settled." in the rare case of a project with no quote); " It holds the date: the project is booked once the client accepts the quote and the deposit is settled." before acceptance. Refusals: "This project is closed: it takes no new sessions." (`project_closed`), "This project is finished: it takes no new sessions." (`project_finished`). The form's hint (`schedulingHint`): before acceptance "A tattoo session holds the date. The project is booked once the client accepts the quote and the deposit is settled."; `deposit_pending` with money due "A tattoo session holds the date. The project is booked once the deposit is paid: NPR 1,000 still due."; `deposit_pending` covered "Scheduling a tattoo session books the project."; `in_progress` "Scheduling the next tattoo session books the project again."; `booked` none. Field errors: "Choose tattoo, consultation or touch-up." (`sessionKind`), "Choose an artist from the list." (`sessionArtistId`), and the time messages.
30. **The UI: a "Schedule a session" button at the foot of the Sessions card.** It opens an inline form (Kind, Artist, Date with today as default, Start time, Length, the hint, then "Schedule session" and "Close"), one column at 375 px. It shares the card's one-panel-at-a-time rule with the outcome and move panels (opening one closes the others), focus starts on Kind, Escape closes it and returns focus to the button, and after a save focus moves to the card's heading where the new row is. The button shows only when the project takes new sessions and the member has an artist to schedule with (`scheduling` prop null otherwise). Rejected: a separate page (one more navigation for a five-field form); reusing TAT-43's booking page (it creates a project).
31. **The quote's expiry is untouched.** Scheduling neither checks nor extends a quote's expiry: an unaccepted or unpaid project whose quote expires is still cancelled by the expiry with its scheduled sessions (TAT-83), and TAT-66's late-decision spare still applies. Rejected: refusing to schedule on an expired quote (the sweep, not the form, owns expiry; TAT-66's spare can keep such a project alive).

### The project's status, by event

What each event does to a project (TAT-36, TAT-46, TAT-64, TAT-66 and this ticket). "Stays" means no change; the session itself changes as the event says.

| Project status | Schedule a tattoo session | Schedule a consultation or touch-up | Deposit settled (verify, desk deposit) | Tattoo session done | Tattoo session no-show or cancelled | Session moved | Project closed |
|---|---|---|---|---|---|---|---|
| `reviewing`, `quoted`, `on_hold` | stays (holds the date) | stays | n/a (accepting the quote comes first) | refused (`not_booked`) | stays | stays | `declined` (from reviewing) or `cancelled` (withdraw, expiry); scheduled sessions cancelled |
| `deposit_pending` | `booked` if the deposit is settled, else stays | stays | `booked` if a tattoo session is scheduled, else stays | refused (`not_booked`) | stays | stays | `cancelled` (withdraw, expiry); scheduled sessions cancelled |
| `booked` | stays | stays | stays | `in_progress` unless another tattoo session is scheduled | `in_progress` if a tattoo session was done and none is scheduled, else stays (flagged "no session") | stays | `cancelled` (withdraw); scheduled sessions cancelled |
| `in_progress` | `booked` | stays | stays | n/a (scheduling one books the project) | n/a | stays | `cancelled` (withdraw); scheduled sessions cancelled |
| `completed`, `healing_check` | refused (`project_finished`) | refused | stays | stays | stays | stays | n/a |
| `declined`, `cancelled` | refused (`project_closed`) | refused | stays | n/a (no scheduled sessions) | n/a | n/a | n/a |

Accepting the quote moves `quoted` to `deposit_pending` and then, through `settleBooking`, straight to `booked` when the deposit is zero or settled and a tattoo session is scheduled. A direct booking (TAT-43) starts `booked` with its tattoo session and no deposit, then follows the `booked` row.

## Routes and access

| Route | Name | Body | Does |
|---|---|---|---|
| `POST /t/:tenant/sessions/:id/outcome` | `tenant.sessions.outcome` | `status`: `completed`, `no_show` or `cancelled` | Records the outcome; flash; back to the project |
| `POST /t/:tenant/sessions/:id/move` | `tenant.sessions.move` | `date` (yyyy-MM-dd), `startTime` (HH:mm), `hours` | Moves the session; flash or field errors; back to the project |
| `POST /t/:tenant/projects/:id/sessions` | `tenant.projects.sessions.store` | `sessionKind`, `sessionArtistId`, `date`, `startTime`, `hours` | Part 2: schedules a session on the project (and books it when it can); flash or field errors; back to the project |

A new `/sessions` group with `role({ allow: ["owner", "artist"] })`; `tenant_routes.spec.ts` gets the area. The Part 2 route sits in the existing `/projects` group (owners and artists; the area is already guarded). Each route gets an isolation case (owner, 302, snapshot of the studio's sessions and project statuses) against a new `twoStudios` fixture: a booked project assigned to `artistProfile` with a scheduled tattoo session 60 days out (`sessionProject`, `session`), clear of the booking case's day (30 days out); the scheduling case adds a tattoo session to `sessionProject` 62 days out. The controller loads the session with `findChangeable`, or the project with `ProjectService.findFor`, before reading the body.

## Services and helpers

### `#modules/scheduling/outcomes` (pure)

- `SESSION_OUTCOMES = ["completed", "no_show", "cancelled"]`, `SessionOutcome`.
- `outcomeRefusal(session, projectStatus, outcome, now)`: `not_scheduled`, `not_started` (rulings 2, 3), `not_booked` (ruling 5) or null.
- `outcomesFor(session, projectStatus, now)`: the outcomes `outcomeRefusal` allows, in button order.
- `mayChangeSession(member, ownArtistId, session, project)`: ruling 11.

### `SessionService` (scheduling)

| Operation | Rule |
|---|---|
