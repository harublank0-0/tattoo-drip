# Discover frontend

Discover D05 (foundation), D06 (homepage, Studio OS marketing), D06.5 (country-aware discovery), D07 (directories, style and location pages), D08 (public profiles and the storefront booking hand-off), D09 (the tattoo gallery and artwork pages) D10 phase A (technical and international SEO, structured data, sitemaps, robots, indexing and error semantics) and D10 phase B (performance, images, caching, accessibility, security headers; see Performance and caching, Accessibility, Security headers and hardening). The public site at `tattoodrip.app`: `apps/discover`, a TanStack Start app beside the storefront. It reads only the public [Discover API](api.md) and has no database, no auth and no platform imports. D11 (the launch) finishes it.

## Homepage (D06)

The loader prefetches five reads in parallel with `Promise.allSettled(ensureQueryData(...))` and never throws: `homeQueries(client, country)` builds the options (tattoos `limit=24`, studios `limit=8`, artists `limit=8`, each with the page's `country`; styles; locations, kept to the page's country by `placesIn`), and the sections read the same options with `useQuery`, so the server's answers are dehydrated and reused (one request each). The loader returns which reads failed (loader data, so server and browser render the same note). A failed or thin read hides only its section; in the browser a failed read is fetched again on mount and its section appears if it succeeds. A hung read is cut off by the server client's timeout (`SERVER_TIMEOUT_MS`, 5 s; the server test checks it); no extra wait was added. Pages are `Cache-Control: private, no-store` (D06.5; see Country): takedowns propagate and no shared cache keeps one visitor's country for another. A country whose studios read answers empty shows "No studios are listed in India yet." with buttons for the other markets, above the static bands (`EmptyMarket`); it never fills in with another country's listings.

| Section (in order) | Data | Shown when (`HOME_THRESHOLDS`) |
|---|---|---|
| Hero: headline, `DiscoverySearch` (studio names, `?q=` on `/explore/studios`), Explore studios, Find artists, a quiet "For tattoo professionals" | tattoos | Always. A collage of the 4 newest photos when there are ≥4 (first eager, `fetchPriority="high"`, which React 19 turns into a `<link rel="preload">`; fixed frames); else typographic, with the explore links (`PRIMARY_NAV`) set large |

## Directories (D07)

`/explore/studios` and `/explore/artists` share one contract (`src/lib/directory.ts`) and one shell (`DirectoryPage`); their results are distinct (`StudioResults`, `ArtistResults`).

**The API's contract** ([API](api.md)): `q` (2–80 characters, a case-insensitive substring of the name: "Search studios by name", nothing semantic), `country`, `city` (needs `country`), `style` (a slug from `/styles`; an unknown one is a 422), `sort` (`newest`, the default: most recently listed / added; `name`; `-name`; ties by id), `independent` (artists only), `limit` (1–48) and `cursor`: opaque keyset paging, `nextCursor` null on the last page, a cursor valid only with the same filters and sort. There are no totals or page numbers, so Discover shows none.

**The address** (`readDirectorySearch`, the route's `validateSearch`; every key, `undefined` when malformed):

| Parameter | Read as | Sent to the API |
|---|---|---|
| `q` | 2–80 characters, no control character (the API's rule); the router keeps every search value as text (`parseSearchText`), so `?q=true`, `?q=null` and `?q=007` are those searches | as `q` |
| `country` | An assigned ISO code | The address's, else the visitor's (`context.country`): always one country |
| `city` | A place slug, only when `country` is in the address | When the address's country is the page's |
| `style` | A slug, then checked against `/styles` (an unknown one is dropped; so is one that can't be checked while `/styles` fails, and the page says "Styles are unavailable right now, so this list isn't filtered by style.") | as `style` |
| `sort` | `name` or `-name` (an explicit allow-list; `newest` is the default and left out) | as `sort` |
| `independent` | `true` / `false`, artists only | as `independent` |
| `cursor` | base64url, at most 1000 | as `cursor`; a cursor the API refuses (422) redirects to the same filters without it |
| `limit` | not read | always 24 (`DIRECTORY_LIMIT`) |

Anything else (`page`, `limit`, `sort=rating`…) is ignored. Beside the list the loader reads the places, the style list and the page's recent photos (`directoryWorkQuery`: the same country, city and style, 48, the same for every page and sort, so paging reuses it); a row shows its own work from it. Only the list failing is an error (the route's error state with Try again, HTTP 500); the others are optional.

**Changes reset paging.** Every link and control builds its address with `changeSearch`/`applyFilters`: a filter, search, sort or country change drops `cursor`; a new country drops `city` and keeps `q` and `style` (as `switchCountryPath`); choosing a city with an implicit country writes the page's country into the address (a city slug is unique per country only, and a shared link must mean the same for everyone). Chips (search, city, style, who) each remove only themselves; Clear all and Reset keep only the address's own country.

**Paging.** "Next page" is a real link to `?cursor=<nextCursor>` with the same filters (SSR, shareable, back/forward). On a later page "First page" is a link; "Previous page" appears when the tab came by "Next page": the earlier cursors ride in the history entry's state (`directoryTrail`), never the URL, and render after hydration only. Browser back/forward simply revisit the addresses.

**Controls.** From `lg`: a toolbar above the results (Style, City: the page's country's places, Works: artists only, Sort; native selects applied together with a visible Apply, never on change, so arrowing through a closed select doesn't navigate (WCAG 3.2.2); Reset) and the chips. Below `lg`: the search, then "Filters (n)" (n = city, style, who) opening the `Sheet` with the same controls, applied together with Apply or cleared with Reset; Radix traps focus, closes on Escape and returns focus to the button; 48px controls. Without JavaScript the toolbar is the same GET form at every width (`noscript:` variant, `@media (scripting: none)`; the country rides along as a hidden field), and the search form carries the filters as hidden fields. The search is an explicit submit (`DiscoverySearch` with `onSearch`): no routing per keystroke, no autocomplete.

**States.** While the next address loads, the current page stays mounted, its results dimmed and `aria-busy`. The directory routes have no `pendingComponent`: after `pendingMs` it would hide the page (Suspense) and take focus from the control that applied the change. An `<output>` announces "24 studios shown, more on the next page." politely. Empty with a search or filters: what matched nothing, Clear filters, All of <country> (with a city), style pages, other markets (the D06.5 country form). Empty with nothing chosen: `EmptyMarket` ("No studios are listed in India yet."). An empty later page: "No more studios" with First page. Never another country's listings.

**Results.** Rows link to the Discover profiles (D08, through the router: `ProfileLink`). While `PROFILE_PAGES` was off (D07) every link left Discover and told screen readers where it went (`artistSiteNote`); that note now appears only for an external destination. Studios: editorial rows, picture first (a strip of three recent photos, else the cover, else one photo, else the logo, else the name's initial set in type; never stock), name, city and region, styles, "View studio". No description, artist count or figures: the list has none. Artists: work first (one large photo and up to two more, else the portrait, else the initial), name, "at Studio · City" or "Independent · City", styles.

## Style and location pages (D07)

- **`/styles/:slug`** (`paths.style`): the slug must be on `/styles` (unknown or malformed: the 404 page; the list failing: the error page). Country-aware like the directories (`?country=`, else the visitor's), with the country in each query key and, when explicit, in every link the page makes. Reads `styleQueries`: 6 studios, 8 artists, 12 photos with that `style` (the tattoos endpoint filters by style). The intro is generic ("Studios and artists in Nepal who work in blackwork…"): the API has no style descriptions, so none is invented. Sections: recent work (≥3 photos), studios and artists each with "Browse all <style> studios/artists" → the filtered directory, other styles. Nothing listed: an honest empty state, other styles, and `noindex`.
- **`/locations/:country`** and **`/locations/:country/:city`** (`paths.location(code)`, `paths.city(code, slug)`): explicit geography. The country segment is a stable slug of the ISO code (`countrySlug`: a pinned slug for the configured markets, `NP` → `nepal`, `IN` → `india`, else the English name slugified, `US` → `united-states`); `countryFromSlug` maps it back, for configured markets only, by that one spelling (`/locations/np`, `/locations/Nepal` and a non-market are 404s). Add a market's pinned slug when adding a market, so an ICU rename can never move its pages. The city segment is the API's place slug (unique per country).
- **They never change meaning by visitor.** Location loaders pass their own country and city to `locationQueries` and never read `context.country`: the cookie, geolocation and even `?country=` don't change what they list (the header's selector still shows the visitor's country).
- **Policy.** A country page exists only for a configured market (`DISCOVER_MARKETS`), even with nothing listed (then an empty state with the other markets' pages, `noindex`). A city page exists only when `/locations` (places with at least one listed business) has that slug in that country; anything else is a 404, and when `/locations` can't be read the page is the error state, never a guess. A listed place whose rows have gone (a takedown) is an empty state.
- Country page: its places (→ city pages; optional: when `/locations` fails the page has no Cities section, while the city page is the error state), 6 studios, 8 artists, recent work, "All studios/artists in <country>" → `?country=`. City page: studios, artists, the styles their rows name (each → the city's filtered directory), recent work, the country's other places.

## Profile destinations

Every studio and artist link in a list goes through `profileDestination(entity)` (`src/lib/destinations.ts`), and since D08 `PROFILE_PAGES` is true: `href` is Discover's own profile, built from the API's identifiers: a studio's (current) slug; a studio's artist by studio slug and artist slug (unique per studio only, so `maya` at two studios is two profiles, tested); an independent artist by their business's (tenant's) slug, never their own. Since D09 every photo tile (`ArtworkTile`: home, hubs, profiles, the gallery, related work) opens its artwork page (`tattooDestination`, by the photo's id), and its caption links the artist's profile from the photo's own data (`tattooProfile`: `studio.type`, `studio.slug`, `artist.slug`) as a separate link: one primary link per tile, never nested. Directory rows stay whole-row profile links. Internal links go through the router (`ProfileLink`); the storefront stays the profile's booking and "Visit studio site" action. Setting `PROFILE_PAGES` false restores D07's storefront links (kept for a rollback; tests cover both).

## Profiles (D08)

**Data.** One detail read per page, by the address's identifiers, through `discoverQueries` (`src/lib/profiles.ts`), on the server with `ensureQueryData` and in the component with the same options:

| Route | Read | Holds |
|---|---|---|
| `/studios/:studioSlug` | `getDiscoverStudio` | Summary, intro, social links, up to 100 artists, the 12 newest photos, `bookingUrl` |
| `/studios/:studioSlug/artists/:artistSlug` | `getDiscoverStudioArtist` + `listDiscoverStudioArtists` (in parallel; the second optional: its failure hides "More artists") | Artist summary, bio, social links, 12 newest photos, `bookingUrl` (names the artist) |
| `/artists/:tenantSlug` | `getDiscoverIndependentArtist` | The same as a studio's artist; `studio` is their own business |

The detail answers already hold the portfolio (12) and a studio's artists, so no tattoos or artists list is read. No read sends `country`. Since Reviews and Fresh ink (slice 4) each profile also reads its first page of reviews and of Fresh ink, in parallel and optional (see Reviews and Fresh ink).

**Visibility.** A slug the API can't take (studio: 3–63, `[a-z0-9-]`; artist 2–63) is the 404 page without a request. The API's 404 (unknown, never listed, opted out, hidden, taken down, deleted, another studio's artist, an independent under `/studios/:slug/artists/…`, a studio under `/artists/…`) is `notFound()` (`rethrowMissing`): HTTP 404, `noindex`, the generic "Nothing here" page with no title, image or name from the profile. A transient failure is `RouteErrorState` (500). An old slug (the answer names another) is a **301** to the current address; a listed independent's slug under `/studios/` is a 301 to `/artists/:slug` (blueprint H; one more read, only after the 404). The stub (`test/stub-api.ts`) mirrors these rules; the platform's own are in `tests/functional/api/discover.spec.ts`.

**Freshness.** HTML stays `private, no-store` (as every page), so a withdrawn or taken-down profile is a 404 on the next request; the API's own `public, max-age=60, stale-while-revalidate=60` is the only delay (up to 2 minutes), and the browser's query cache keeps a profile 60 s within a tab.

**Country.** Profiles are global: no country is read or sent, nothing is filtered or redirected by it; the place shown is the profile's own (`placeLine`). The header still shows the visitor's country. "Near here" links use the profile's place: for a market its city and country pages, else the directory filtered to that country and city (`nearbyLinks`); "Back to studios" / "Back to artists" go to the directories as they are (the visitor's country).

**Design.** `ProfileHero`: breadcrumbs, eyebrow, the one h1 (with the logo, or the portrait when the hero shows work), the place and style links (→ `/styles/:slug`), then the picture and the booking actions. On a phone they stack identity, picture, booking; from `lg` the picture takes the right column. The picture is the cover (a studio), else the newest photo, else the portrait (an artist), else the name in type on night; it loads first (`fetchPriority="high"`, eager) in a fixed frame (4:5 phone, 3:2, then 4:3), no overlay. Then: About (intro or bio as plain text, paragraphs kept, beside `Facts`: where, artists or studio, https social links) only when there is an intro, bio or link; the portfolio (night, columns at true proportions, lazy; a studio's captions name the artist and link their profile); a studio's artists, work first (`ArtistResults` with the portfolio); an artist's "More artists at <studio>" (compact, optional read); a Booking band; Keep exploring. Empty sections are not rendered. Below `lg` a booking bar is `sticky` at the bottom of the page content (`StickyBooking`): it rests above the footer at the end, so it never covers content or the footer, comes last in the tab order, and `scroll-padding-bottom` (styles.css, only while it exists) keeps a focused control clear of it.

## Reviews and Fresh ink (slice 4)

Clients' reviews and healed tattoos ([spec](../superpowers/specs/2026-11-12-reviews-and-fresh-ink-design.md); API: [Reviews and Fresh ink](api.md#reviews-and-fresh-ink-slice-4)). The platform shows only what both the studio and the client allowed (the client's Discover consent, a listed studio, a shown artist), so Discover never decides visibility itself and an empty answer renders nothing.

- **Profiles.** Each profile's loader starts its first page of reviews (6) and of Fresh ink (8) beside the detail read (`profileReviewQueries`: the same keys as `discoverQueries.studioReviews` and friends), both optional: a failure or an empty page hides the section (no heading, no "no reviews yet"), and neither delays the profile's 404. A studio's page: Portfolio, then **Fresh ink** ("Healed work from <name>'s clients", a night band of tiles, "All Fresh ink" → `/fresh-ink`, with `?country=` of the profile's own place when it is a market, so a visitor from another market doesn't land on an empty feed), then **Reviews**, then its artists. An artist's (studio or independent): Portfolio, Fresh ink, Reviews, then the studio's other artists. "Show more reviews" / "Show more Fresh ink" read the next page in the browser (after hydration only, as "Previous page"): the first page always comes from the loader and only the extra pages are state, and both sections are keyed by the profile (`subjectKey`), so moving to another profile on the same route (an artist to a colleague) never shows the previous one's rows. While loading the button is `aria-disabled` (it keeps focus); afterwards focus moves to the first new item (each item takes focus, `tabIndex={-1}`), also when the button goes away on the last page, and a polite `<output>` says "6 more reviews shown." A failure says so in an alert and keeps what is shown.
- **Ratings** (ruling 10). The average and "from N reviews" only when the API sends `rating` (from 3 reviews; `ratingSummary` refuses fewer too); below that the reviews are listed without an average. The average reads "4.7" (one decimal) with stars that round down, never up (`filledStars`: 4.7 fills 4); every star row is `aria-hidden` and the words carry the meaning: "4 out of 5" beside each review, "Rated 4.7 out of 5, from 12 reviews" for the average. Newest first, never sorted by stars.
- **A review** shows its stars and words, the client's text, the shown name (`<bdi>`), the day (`<time>`), on a studio's page the artist (their profile), and the studio's reply ("Reply from <studio>"). Every user text is plain text with `dir="auto"` (the body, the reply, a caption, a placement) and names are in `<bdi>`, so a right-to-left name never reorders the line around it; each breaks anywhere (`USER_TEXT`: `break-words [overflow-wrap:anywhere]`, with `min-w-0` on its grid and flex parents), so a pasted URL or a 40-character name never overflows a 320 px phone (checked in a browser at 320, 375 and 1440, in the viewer too).
- **Fresh ink tiles** are `ArtworkTile`'s frames (true proportions, lazy, the first 4 of the feed's first page eager); each is a button (`aria-haspopup="dialog"`) that opens the **viewer**: a modal Radix Dialog (focus moves in and is trapped; Escape and Close return it to the tile) with every photo and ready video in the client's order, each framed as `ArtworkImage` frames an artwork (as wide as fits, never taller than 80% of the screen: `min(100%, calc(80svh * ratio))`, `fit="contain"`, so a frame has its size before anything loads and a failed image keeps it), videos with controls, muted, `preload="none"`, never autoplayed, labelled by their alt text or "Video, 0:42"; its description counts only what it shows ("3 photos", "2 photos and a video"); then the caption, the shown name and day, "Tattoo by <artist> at <studio>" (their profiles: following one closes the dialog, `Dialog.Close asChild`, and the page it is already on is plain text), styles, placement, and the booking hand-off by the artwork page's rule (`freshInkBooking`, the post's `artistAcceptingInquiries`): "Request with <artist>"; a studio's artist who isn't taking requests: "<name> isn't taking new requests right now." and the studio's general request ("Request a session at <studio>"); a paused independent: no request. "Visit studio site", or "Visit their site" for an independent, whose note says "a client of <name>", not "of the studio". A post has no page of its own: the viewer is the coherent choice because the feed already holds every angle, and an artwork page per post would need an indexable address for client photos.
- **Alt text** comes from the data: the client's own, else "Healed tattoo by <artist>" ("…, photo 2 of 3" in the viewer).
- **The feed** (`/fresh-ink`, `src/routes/fresh-ink.tsx`) follows the gallery's contract (D09) without search, artist or studio: `country` (the address's, else the visitor's, D06.5, in the query key), `city` (with `country`), `style` (checked against `/styles`), `cursor`; D07's toolbar, sheet, chips and `Pagination` with their own words (`kind="fresh-ink"`: "Filter Fresh ink", "Fresh ink in Nepal"); tiles credit the artist (their profile) and the studio (`profileDestination`, or an independent's profile); empty: "No Fresh ink from <country> yet" with other markets and the gallery, or "No Fresh ink matches these filters" with Clear filters.
- **SEO and navigation.** `/fresh-ink` is in `INDEXABLE_PATTERNS` (not `INDEXABLE_PATHS`): indexable only bare and populated (its loader returns `noindex` for an empty page). The sitemap lists only populated pages, so `/sitemaps/static.xml` lists it only while the default country's feed has a post (one `freshInk.list({ country, limit: 1 })` read, as the style pages are checked; a crawler without a cookie gets the default country). "Fresh ink" is the fourth of `PRIMARY_NAV`'s discovery links (the header, the mobile menu's Discover group, the footer's Explore and the homepage's link list): an empty feed is its own empty state, with other markets and the gallery. Its JSON-LD is its breadcrumbs only: never a rating or review over many studios.

## Booking hand-off (D08)

- **Words.** The storefront takes requests, not instant bookings: "Request a session" (studio), "Request with <artist>", "Request a similar tattoo" (an artwork, D09), secondary "Visit studio site" / "View on studio site" / "Visit their site", and a note: "It's a request, not an instant booking". An artist with `acceptingInquiries` false says "<name> isn't taking new requests right now." and offers the studio's general request (the same link without `artist`); an independent then has none.
- **Destination.** Only the API's `bookingUrl` and `storefrontUrl` (the platform builds both from `STOREFRONT_URL` for that studio: `bookingPageUrl`, `studioPageUrl`). `bookingLinks` (`src/lib/booking.ts`) accepts them only when both are https, or http on `localhost`/`*.localhost`; have no user name or password; share scheme and host (port included); and the booking path is the storefront's `/book`. It then rebuilds the link from those parts: the origin, `/book`, `artist` (only on an artist profile and only that artist's own slug, which is what the storefront's `?artist=` preselects, checked against that studio's artists), `ref` (by shape). `artwork` (D09: only on an artwork page and only that photo's own id, a lowercase uuid: the storefront's "Request a similar tattoo", which checks the photo with the API and names its artist). Nothing else survives, nothing comes from the browser's address, and Discover has no redirect endpoint. Anything else is no link: "Booking isn't available online from Discover right now." Never `flash`: portfolio photos are not flash designs.
- **Custom domains** (TAT-79) are planned, not served: `storefrontUrl` is always the `{tenant}` subdomain. When the platform resolves verified custom domains into it, `bookingLinks` accepts them unchanged (it compares the booking host with the API's own site host, not with a pattern).
- **Referral.** Discover never mints or holds a token or key: the platform signs `ref` into every profile's `bookingUrl` (`linkReferral`, hour-stable, 30 days, studio-bound; [API](api.md#referral)). Discover only carries it. The storefront keeps `?ref=` on `/book` (and through `/request`'s 301) and sends it as the inquiry's `referral`; the platform verifies it for that studio and stores `referral_source = 'discover'` apart from `sourceChannel`. A missing, malformed, expired, forged or other studio's token records nothing and never refuses the request. Nothing is stored in the browser; the token is in the URL only, so navigating elsewhere on the studio site before sending drops it (best-effort attribution by design). `/book` sends `Referrer-Policy: strict-origin-when-cross-origin`, so other sites (the bot challenge, chat links) see the origin only. The token is not secret (it says only "Discover linked to studio X in hour T") and is never logged by Discover.

## Gallery (D09)

`/tattoos` (`src/routes/tattoos/index.tsx`, `src/lib/gallery.ts`) follows the directories' pattern (D07): one URL contract, the loader reads exactly what the address says, every control writes the address.

**The address** (`readGallerySearch`, the route's `validateSearch`; every key, `undefined` when malformed):

| Parameter | Read as | Sent to the API |
|---|---|---|
| `q` | 2–80 characters, no control character | as `q`: alt text, artist, studio and style names ([API](api.md#gallery-search-and-the-artwork-read-d09)) |
| `country` | An assigned ISO code | The address's, else the visitor's (`context.country`), except on one artist's or studio's work (below) |
| `city` | A place slug, only with `country` in the address | When the address's country is the page's |
| `style` | A slug, checked against `/styles` (unknown dropped; unchecked when `/styles` fails, said on the page) | as `style` |
| `artist` | A uuid, lower-cased | as `artist` |
| `studio` | A business's slug | as `studio` |
| `cursor` | base64url, at most 1000 | as `cursor`; one the API refuses redirects to the same filters without it |
| `limit`, `sort`, anything else | not read | always 24, newest first (the API's only order: no sort control) |

- **Country.** One country system (D06.5): `?country=`, else the visitor's. A profile's "All work by …" (`?artist=`) or "All work at …" (`?studio=`) is global like the profile, so the gallery sends no country then unless the address names one (and has no city filter); its chip ("By Sita Rai", "At Black Needle", names from the page's photos) removes it. When no photo on the page names them (nothing listed, or an unknown slug), the page says "this artist" / "this studio" ("Tattoos from this studio", "At this studio"): the address's text is never shown as a name.
- **Search.** `DiscoverySearch`, still a GET form with the other filters as hidden fields (no JavaScript: Enter submits). With JavaScript (`GallerySearchBox`) the results follow the typing: 400 ms (`SEARCH_DEBOUNCE_MS`) after the last keystroke a valid search (`nextSearch`: 2–80 characters, changed) is written to the address; the first update of a burst adds a history entry and later ones replace it, so Back returns to the previous search (or the gallery before it), not through every keystroke. A burst ends with a pause of 1.5 s after the last keystroke (`SEARCH_BURST_GAP_MS`, `startsBurst`), when the box loses focus (a pending search applies then), on Enter or on Clear, so a search typed later is its own history entry; Enter applies at once; Clear (an emptied box) removes the search at once. The box is controlled and never remounted, so focus stays while results load; a search changed elsewhere (a chip, back/forward) refills it. One character keeps the current results. The results' `<output>` announces "12 tattoos shown." politely.
- **Filters.** D07's `FilterToolbar` / `MobileFilters` / `ActiveFilters` with `kind="tattoos"`: style and city (the country's places), applied together with Apply, a sheet below `lg`, the same GET form without JavaScript; no sort and no "who". `Pagination` is D07's ("Next page", "First page", "Previous page" from the history entry): each page is its own SSR address, shareable and back/forward-safe, rather than a "Show more" that accumulates (as D07 decided).
- **Masonry.** CSS columns (2, 3 from `sm`, 4 from `lg`), each photo in a frame of its own proportions (`ArtworkTile`: `ResponsiveImage` with width, height and `aspect-ratio`, so nothing moves as it loads; a failed image keeps a neutral frame with its alt text). The first 4 load eagerly, the first of them with `fetchPriority="high"`, the rest lazily; a later page loads every image lazily. Columns flow top to bottom, as every work section since D07. A card: the image linking to the artwork page (the gallery's cards leave a mark in the history entry, see Back to the gallery) and a caption with the artist (their profile, a separate link), the studio's name or "Independent", the first style. The list has no place per photo, so cards name no city.
- **States.** Loading keeps the current photos mounted, dimmed and `aria-busy` (no `pendingComponent`). Nothing in the market: `EmptyMarket` ("No tattoos are listed in India yet.", the other markets). No match: what matched nothing, Clear filters, All of <country> (with a city), other styles, other markets. An empty later page: "No more tattoos" with First page. The list failing: the route's error state (Try again, 500). A search the API rate-limits (429 with `q`: server renders share one anonymous budget until D11's server key, see Settings, and typing reads often) is not an error: the loader returns `busy` and the page keeps its header, search box (the query in it), filters and chips, with "Searching is busy right now. Try again in a moment." (an `<output>`, announced politely) and Try again (a link to the same address; with JavaScript it re-runs the loader in place), and no results or paging. It answers 200 and is noindex (it has `q`); the failed read isn't cached or sent to the browser as an answer (`private, no-store`, failed queries aren't dehydrated, the browser doesn't retry a 429). A 429 without a search, and every other transient failure, stays the error state.
- **Head.** "Tattoo inspiration from Nepal", "Blackwork tattoos in Pokhara", "Tattoos by Sita Rai", "Tattoos matching "koi"". Any parameter is `noindex`; the bare page is in `INDEXABLE_PATHS` (and so the sitemap) once indexing is on.

## Country

D06.5: Discover is local-first and globally accessible. Each page lists one country's studios, artists, photos and places: the visitor's own by default, any other on request. The country is a relevance filter only. It never hides a public profile, and it has nothing to do with tenants, currency, sign-in or where anyone lives.

**Resolution** (`src/lib/country.ts`), strongest first:

| Source | Taken when |
|---|---|
| `url`: the page's `?country=` | Any assigned ISO 3166-1 alpha-2 code (a static list of the 249; Intl also names `EU`, `UK`, `XK`, `ZZ`…, and Cloudflare sends `XX` and `T1`). A country that isn't a market may be browsed explicitly: it shows the honest empty state |
| `cookie`: `td_country` | It names a market |
| `geo`: the trusted proxy's header | `DISCOVER_GEO_HEADER` is set, and the header names a market |
| `fallback` | `DISCOVER_DEFAULT_COUNTRY` |

A malformed code (`XX1`, `nepal`) is ignored, never a 422 from the API. Names come from `Intl.DisplayNames(["en"])`, a fixed locale, so the server's HTML and the browser's hydration agree.

**Per request, never module state.** `getRouter()`'s server branch (`src/lib/request.ts`) reads this request's `Cookie` and, only when configured, the trusted header (`getRequest()` from `@tanstack/react-start/server`) into `context.preference` (cookie, geo or fallback). The root route's `validateSearch` reads `?country=` for every page, and its `beforeLoad` returns `country` (`pageCountry`: the address's, else the preference), which every loader and component reads as `context.country`. The preference goes to the browser in the dehydrated state beside the settings (checked again on hydrate: a market code and a known source); the root match's `country` is dehydrated with the matches, so the browser hydrates exactly what the server rendered.

**Queries.** Studios, artists and photos send `country` to the API (each accepts it; an unassigned code would be an empty page, a malformed one a 422, which the readers prevent), so it is part of every query key: `discoverKeys.studios({ country: "NP" })` and `({ country: "IN" })` are separate entries, and a late answer for the previous country can never fill the new one's. `/locations` has no country filter: it is small reference data, so pages keep their country's places (`placesIn`). Styles are global. Loaders list `country` in `loaderDeps`.

**The preference cookie.** `td_country=<market>`: host-only (no `Domain`, so it never reaches Studio OS or a studio's site), `Path=/`, `SameSite=Lax`, `HttpOnly` (only the server reads it; the page knows the country from its router context), `Secure` when `DISCOVER_URL` is https, `Max-Age` one year. Only a market is ever stored. No other cookie exists. It is set only by `POST /preferences/country` (`src/lib/preference.ts`), fields `country` and `return`:

- A plain form post (no JavaScript) gets a `303` to `return`, a same-origin path (`safeReturnPath`: one leading `/`, no `//`, backslash, scheme or control character; anything else is `/`), with its `country` replaced and its `city` and `cursor` dropped (`switchCountryPath`: the API ties a cursor to the sort only, so the new country's list would start part-way through).
- The selector's fetch (`Accept: application/json`) gets `{ country }`.
- A code that isn't a market is never saved (`422` for the fetch; the form goes back unchanged). A cross-site post (`Sec-Fetch-Site` other than `same-origin` or `none`) is a `403`.

**Switching** (`country-selector.tsx`). Every control is a real `<form method="post">` of country buttons, so it works without JavaScript. With it, the selector posts by fetch, sets the tab's `preference`, then either navigates to the same address with `country` replaced and `city` and `cursor` dropped (`q`, `style` and the path kept), when the address names a country or has a cursor (`countrySwitchTarget`), or re-runs the loaders (`router.invalidate()`). A failed fetch falls back to the plain post.

- **Desktop** (from `lg`): a disclosure (`<details>`, uncontrolled so a fast Escape and Enter can't be undone by a late render) naming the current country, opening a small panel of country buttons; the current one has `aria-current` and a check. Enter or a click opens it, Escape or a press outside closes it, focus returns to the trigger after a switch. From `lg` to `xl` the trigger drops its icons and cuts a long name, so the header stays on one line at 1024px.
- **Mobile:** a labelled "Country" group in the menu sheet, 48px rows; the sheet closes after a switch and Radix returns focus to the menu button.
- **One market:** the country is shown as text (and in the sheet, "Discover lists studios in Nepal for now."): a picker with one choice is noise. A page with an explicit non-market `?country=` still offers the market.

**Empty market.** Home, `/explore/studios` and `/explore/artists` (no `q` or filters) say "No studios are listed in India yet." (or artists) with buttons for the other markets. They never borrow another country's listings.

**Trusted header and nginx.** Discover never reads `CF-IPCountry` (the setting refuses it): a visitor can send it. In the split layout (`deploy/nginx/hosts.split.conf`), nginx makes `$discover_country` from `CF-IPCountry` only on a connection from cloudflared (`172.30.42.20`, matched on `$realip_remote_addr`, the same trust as the visitor's address in `common.conf`) and only as two letters. Discover's location always sets `X-Discover-Country` from it, empty (not sent) for anyone else, so a visitor's own header never passes. The tunnel is the only way in, so no Cloudflare IP list is needed. `deploy/test/nginx/run.sh` checks it. Geolocation stays off (`DISCOVER_GEO_HEADER` unset) until D11 has verified that Cloudflare overwrites a visitor's own `CF-IPCountry` and that Discover's port is not published ([domain migration](domain-migration.md), step 15). The compose service publishes no port; only the stack's network reaches it.

**Caching.** Every HTML response (the root route's `headers`) is `Cache-Control: private, no-store` with `Vary: Cookie`, because the header and the lists depend on the cookie and the geolocation header. `Vary` is only a second line. Before D06.5 pages set no `Cache-Control`. `/robots.txt` (`public, max-age=300`), the sitemaps (`public, max-age=3600`, D10) and the static files keep their own headers (D10 phase B: see Performance and caching). Cloudflare doesn't cache HTML by default; no cache rule may cover Discover's pages until D10/D11 design a keyed strategy.

**SEO.** The canonical stays the path alone, so `?country=` variants never canonicalise as separate pages, and a page with an explicit `?country=` is `noindex` (meta and `X-Robots-Tag`; `noindex, follow` while indexing is on, D10) whatever `DISCOVER_INDEXING` says. Nothing ever redirects by country. A crawler without a cookie or header gets the default country, deterministically; a crawler that comes through Cloudflare with geolocation on gets its own country. Crawlable geographic entry points are D07's location pages (`/locations/nepal`, `/locations/nepal/kathmandu`), which never depend on the visitor's country. `DISCOVER_INDEXING` behaves as before.

**Directories vs location pages.** Directories and style pages follow the page's country (explicit `?country=`, else the visitor's); location pages always list their own. A crawler without a cookie sees the default country on a directory or style page, deterministically.

**Profiles (D08).** Global: no profile is hidden, filtered or redirected by country, and profile links never carry `country` (see Profiles).

**Local development.**

- Add a market: `DISCOVER_MARKETS=NP,IN` in `.env.local` (restart `pnpm dev`). A market with no listed studio shows the empty state.
- Simulate geolocation: `DISCOVER_GEO_HEADER=X-Discover-Country`, then `curl -H 'X-Discover-Country: IN' http://localhost:3100/`, or a browser extension that sets the header. Without the setting the header is ignored.
- Try a country without the selector: `/?country=IN`; clear the preference by deleting the `td_country` cookie.

## Data loading pattern

`/explore/studios` is the pattern every data page follows (D07: the loader is shared, `loadDirectory` in `src/lib/directory-loader.ts`):

```ts
export const Route = createFileRoute("/explore/studios")({
	validateSearch: (search) => readDirectorySearch(search, "studios"), // every key
	loaderDeps: ({ search }) => search,
	loader: ({ context, deps }) => loadDirectory("studios", context, deps), // ensureQueryData + rethrowUnavailable
	head: ({ match }) => directoryHead("studios", match),
	component: Studios, // useSuspenseQuery(discoverQueries.studios(client, directoryQuery(filters, "studios")))
});
```

- The loader runs on the server for the first page and in the browser after; the server's result is streamed into the browser's cache, so the component's `useSuspenseQuery` doesn't fetch again.
- Use `discoverQueries` / `discoverKeys` from `@tattoo-drip/react` (D03); never a second client or a hand-made key. Each query forwards TanStack Query's `signal`: a component's query is cancelled when nothing observes it any more (a loader's prefetch is not tied to the navigation).
- Validate search params before they reach the API (`readQuery`: 2–80 characters, no control character, as the API requires). The router parses search values as text, never JSON (`parseSearchText`/`stringifySearchText` in `src/router.tsx`); readers take strings (`readIndependent` reads `"true"`). `validateSearch` must return every key it owns, `undefined` when malformed: the router merges its result over the raw search, so a key left out keeps the raw value.
- A loader ends with `.catch(rethrowUnavailable)` (`src/lib/api-errors.ts`): the server's error reaches the browser as a plain `Error`, so a transient failure (no answer, timeout, 5xx, 429) is rethrown with a marked message that `RouteErrorState` recognises on both sides ("Discover is unavailable for a moment", Try again; HTTP 500). An empty answer shows `EmptyState`. Never invent rows, figures or reviews.
- The root layout reads no API data, so the shell, `/robots.txt` and the health check never wait on the API.

| `DISCOVER_SERVER_KEY` | in production | The key the platform lists in `DISCOVER_SERVER_KEYS` (D11): 32 to 256 token68 characters (`openssl rand -hex 32`). Required when `NODE_ENV=production`; unset in development, reads are anonymous |

Origins are https, or http on localhost. All but `DISCOVER_GEO_HEADER`, `DISCOVER_SITEMAP_CACHE_SECONDS` and `DISCOVER_SERVER_KEY` (server only; the key is a secret) are public: the browser receives them in the router's dehydrated state. `publicSettings` leaves the server-only ones out. `pnpm build` ends with a check that the browser bundle holds no server-only text (`scripts/check-client-bundle.mjs`). The built server checks every setting when it starts (`src/server/startup.ts`): a missing or malformed one stops it with the setting's name and rule (never a value), so a bad deploy restarts in a loop instead of answering 500; a good start logs one line of what it serves (origins, indexing, markets, geolocation on or off, "server key set").

**Server key and visitor (D11).** Every server-side API read, page renders and sitemaps alike, carries `Authorization: Bearer <DISCOVER_SERVER_KEY>` and the visitor's address as `X-Visitor-IP` (`serverFetch`, `src/lib/server-fetch.ts`): the first `X-Forwarded-For` value, which nginx sets, never appends (`deploy/nginx/proxy.conf`). The platform (`DISCOVER_SERVER_KEYS`, `#services/api_caller`) then counts each visitor in Discover's own buckets instead of all of Discover as one client; without a usable address it uses Discover's one shared budget and logs a warning at most every 10 minutes. The key grants no data, route or field. A sitemap build, shared between requests, counts against the request that started it. Browser reads (the gallery's search as you type) carry no key and count by the browser's own address.

**Health and logs (D11).** `/healthz` answers `ok` (`no-store`, `noindex`) without reading the API: the container's health check, so an API outage doesn't restart Discover and checking spends no API budget. Each failed API read (a 5xx or 429, or no answer: refused, reset, timed out) logs one line, `Discover API read failed: GET /api/v1/discover/studios answered 503 (120 ms)`, with the method and path only (never the query, which holds a search, or a header, which holds the key); 404s are not failures. Pages that fail answer 500 with the error state, which nginx's access log shows. `SIGTERM` closes the server gracefully (about a second; the container runs under `init`).

## SEO and indexing

D05 built the foundation; D10 phase A finished it (blueprint C.12). Everything here is server-rendered and the same after a client navigation (the router recomputes the head from the same matches).

**Architecture.** The root route (`__root.tsx`) renders the shared head of every page from `headTags`: title, description, canonical, Open Graph (`og:site_name`, `og:type`, `og:title`, `og:description`, `og:url`, `og:image` with its width, height and alt), `twitter:card` and robots. A page adds its own title, description and picture with `pageMeta` (the deepest match wins per name or property, so each tag appears once) and its JSON-LD with `structuredData`. Titles are `Page | Tattoo Drip`, or the default on the home page. Pages without a picture share the brand mark (`/brand/tattoo-drip-512.png`: Studio OS's interim mark, TAT-67, copied from `apps/platform/public/icons/icon-512.png`; square, so `twitter:card` is `summary`); a page's own photo is `summary_large_image`.

**Robots: one decision, in the root** (`pageState`, `robotsValue` in `src/lib/seo.ts`), from every match, and the same value in `<meta name="robots">` and the `X-Robots-Tag` header:

| | Indexing off (default) | Indexing on (`DISCOVER_INDEXING=on`) |
|---|---|---|
| An indexable page: a path in `INDEXABLE_PATHS` (`/`, `/for-studios`, the bare `/explore/studios`, `/explore/artists` and `/tattoos`) or matching `INDEXABLE_PATTERNS` (style, market, city, the three profile shapes, an artwork at its lowercase id), with no query, not opted out | `noindex, nofollow` | no tag (index, follow) |
| Anything else: any query string (filters, searches, sorts, cursors, `?country=`, tracking parameters: every canonical is the bare path), a route's `staticData: { noindex: true }` (`/pricing`), a loader's `noindex: true` (an empty style, market or city page), a 404, an error page | `noindex, nofollow` | `noindex, follow` |

**Why `noindex, follow`** (blueprint H; before D10 these pages said `noindex, nofollow`): a filtered, paged or empty page is no search result of its own, but its links lead to profiles, artwork and hubs that are, so crawlers may follow them; a later directory or gallery page keeps its Next, First and Previous links. While indexing is off nothing may be crawled, so `nofollow` stays there. A page never writes its own robots tag: an unfinished page sets `staticData: { noindex: true }` or returns `noindex: true` from its loader.

**Canonical policy** (`canonicalUrl`): `DISCOVER_URL`'s origin (never the request's host; `https://tattoodrip.app` in production, tested) plus the page's own path as the router matched it (already percent-encoded), with no query and no fragment, and no trailing slash but the root's (an index route's `/locations/nepal/` is `/locations/nepal`). Identifiers are lower case where the API's are: an upper-case or readable artwork slug is a 301 to the lowercase id, an old studio slug a 301, and a profile slug in another case a 404 (the API's slugs are lower case), so only one spelling answers 200. A filter or query URL canonicalises to its bare path and is noindex. A 404 or an error page has no canonical (and no `og:url`). Profiles (D08) and artwork pages (D09) are self-canonical, never the storefront's.

**Country and international.** Location pages (`/locations/:country`, `/locations/:country/:city`) are distinct country content: they never change with the visitor's country, are self-canonical, indexable when populated and `noindex, follow` when nothing is listed (an empty market's page, a city whose rows have gone: thin content); they are the crawlable geographic entry points and are in the sitemap only when populated. Pages that follow the visitor's country (home, directories, style pages, the gallery) are one URL each; a crawler without a cookie gets `DISCOVER_DEFAULT_COUNTRY` deterministically, and an explicit `?country=` variant is `noindex, follow` with its canonical on the bare path. A country page is never canonicalised to a global page, and nothing redirects by country. **No hreflang:** Discover has one language and no translated or per-locale equivalents, and hreflang only links equivalent pages in different languages or regions; `?country=` changes the listings, not the language, so it isn't a locale variant (and it is noindex). It needs, first, real localized pages (a message catalog, translated copy and place names, blueprint H's `/{locale}/…` prefix kept free), then reciprocal `hreflang` links between them with an `x-default`, generated from one locale setting with `lang` and `og:locale` (neither is set beyond `lang="en"` today).

**Structured data** (`src/lib/structured-data.ts`): schema.org JSON-LD, one `<script type="application/ld+json">` per page holding a `@graph`, through the head's `"script:ld+json"` entry (the router serialises it with `<`, `>`, `&`, U+2028 and U+2029 escaped, so text from the API can't close the script). Only on an indexable 200 page (the same decision as robots): never while indexing is off, on a variant, an empty hub, a 404 or an error.

| Page | Nodes |
|---|---|
| `/` | `WebSite` (name, url, publisher, a `SearchAction` on `/explore/studios?q={search_term_string}`: the hero's own search box submits exactly that GET, a page any crawler can load; it searches studio names, as the box says), `Organization` (name, url, the brand mark as `logo`; no `sameAs`: Tattoo Drip has no public social accounts yet) |
| Studio profile | `TattooParlor` (a `LocalBusiness`): name, `url` = the Discover profile, `image` (cover, else newest photo), `logo`, `address` with only the listing's place (`addressLocality`, `addressRegion`, `addressCountry`; no street), `sameAs` = its https social links; since Reviews and Fresh ink (slice 4), only from 3 reviews, `aggregateRating` (`ratingValue` to one decimal, `reviewCount`, best 5, worst 1) and `review` (the reviews the page shows: `reviewRating`, `author` the shown name, `datePublished`, `reviewBody`; `reviewsLd`); `BreadcrumbList` |
| Artist profiles | `Person`: name, url, `jobTitle`, `image` (portrait), `worksFor` the studio's Discover profile (a studio's artist; an independent works for no one), `workLocation` (the place), `sameAs`; `BreadcrumbList` |
| Artwork page | `ImageObject`: `url` (the page), `contentUrl`, `width`, `height`, `name` (the page's heading), `caption` (the alt text, else the data's "Blackwork tattoo by …"), `creator` (`Person`, their profile); `BreadcrumbList` |
| Style, market, city, bare directories and gallery | `BreadcrumbList` |

Breadcrumbs come from one list per page (`crumbs` in `src/lib/breadcrumbs.ts`) that both `Breadcrumbs` and `BreadcrumbList` use, so they match exactly; every item is an absolute URL, the last the page itself. Never prices, opening hours, contact details, booking links or anything the page doesn't show; ratings and reviews only on a studio's profile from 3 reviews, as the page shows them (ruling 10: a third party about the business), never on an artist's (schema.org gives a `Person` no `aggregateRating`), the Fresh ink feed or anywhere else. Validation is by tests that parse the scripts and compare them with the visible page; Google's Rich Results Test needs a deployed URL (phase B).

**Sitemaps** (`src/lib/sitemap.ts`, `sitemap-route.ts`). Only while indexing is on; otherwise `/sitemap.xml` and every child are 404s. `/sitemap.xml` is a sitemap index of:

| Child | Lists | From |
|---|---|---|
| `/sitemaps/static.xml` | `INDEXABLE_PATHS`, and `/fresh-ink` while the default country's feed has a post (an empty feed is noindex) | one `fresh-ink?country=&limit=1` |
| `/sitemaps/styles.xml` | Style pages with an artist in the default country (a crawler gets that country; an empty style page is noindex; a studio matches a style only through its artists) | `/styles`, then one `artists?style=&country=&limit=1` per style, 4 at a time |
| `/sitemaps/locations.xml` | Each market with a studio or artist listed, and its cities (`/locations`: places with a listed business) | `/locations`, two `limit=1` reads per market |
| `/sitemaps/studios.xml`, `artists.xml`, `tattoos.xml` (`?after=<cursor>` for later pages) | Studio profiles; studio artists and independents' profiles; artwork pages | The API's sitemap lists ([API](api.md#sitemap-lists-d10)): 5,000 identifiers a page, keyset by id |

A paged child is exactly one API page (5,000 URLs, far under the protocol's 50,000 URLs and 50 MB); the index walks each list's cursors once (the three lists in parallel, each sequential, at most 1,000 pages) to name its pages. Ids only grow, so new rows land on the last page and earlier `?after=` addresses stay stable. A wrong child, or `?after=` that isn't a cursor or is on an unpaged child, is a 404. A list longer than the 1,000-page guard makes the index a 503, never a truncated index; a failed build is logged (`console.error`) before its 503. Everything is XML-escaped (`xmlText`), `Content-Type: application/xml; charset=utf-8`, `X-Robots-Tag: noindex` (the files aren't search results), `Cache-Control: public, max-age=3600`. No `lastmod`: the API exposes no modification time, and a listing or creation time isn't one. **Freshness:** the server keeps each built sitemap for `DISCOVER_SITEMAP_CACHE_SECONDS` (10 minutes by default; one build is shared between concurrent requests, at most 64 are kept, a failed build is never kept), because a sitemap costs up to twenty API reads on a budget every page shares; a browser or shared cache may then serve it for up to an hour more (plus the API's 2 minutes), so a removed profile or photo leaves the sitemaps within that, while its page is a 404 on the next request (`private, no-store`). An API failure is a `503` with `Retry-After: 300` and `no-store`, never a partial sitemap. Generation reads the API anonymously and shares Discover's server budget until D11's server key: an index costs about one read per 5,000 rows of each list, a child one read (and `discoverSitemap` caps them, [API](api.md)).

**robots.txt** (`public, max-age=300`). Indexing off: `Disallow: /` for everyone. On: `Allow: /` and `Sitemap: <DISCOVER_URL>/sitemap.xml`, and nothing disallowed: not the filtered or `?country=` URLs either, because a crawler must fetch a page to see its `noindex`, and a disallowed URL can still be indexed from links, without its content. robots.txt is never a security measure: everything on Discover is public.

**Status semantics** (server and client navigation alike, tested on the built server and checked in a browser):

| Case | Status | Robots (indexing on) |
|---|---|---|
| A shown page | 200 | none, or `noindex, follow` with a query |
| Unknown or unpublished entity, malformed id or slug, a style or market that doesn't exist | 404, "Page not found", no canonical | `noindex, follow` |
| An old slug, a non-canonical artwork spelling, `/explore/tattoos` | 301 to the canonical address | — |
| The API down or slow (a required read) | 500, "Discover is unavailable for a moment", no canonical | `noindex, follow` |
| An empty filtered directory or gallery, a rate-limited gallery search | 200 | `noindex, follow` |
| An empty market, city or style page | 200 | `noindex, follow` |
| A later directory or gallery page (`?cursor=`) | 200, paging links kept | `noindex, follow` |

**Titles and descriptions** come from real public data and say what the page lists: "Black Needle — Tattoo studio in Kathmandu, Nepal", "Maya — Tattoo artist at Black Needle in Kathmandu", "Asha — Independent tattoo artist in Pokhara, Nepal", "Blackwork tattoo studios and artists in Nepal", "Tattoo studios and artists in Kathmandu, Nepal", "Tattoo inspiration from Nepal". `fitTitle` keeps a title within 60 characters (before the site name) by dropping whole trailing parts (country, then city, then studio), never cutting a name; descriptions are cut at a word at 155 (`summary`).

## Performance and caching (D10 phase B)

**Measurement** (lab only: no field data exists before launch). Lighthouse 12.8 (mobile preset: Moto G-class CPU ×4, slow 4G simulated; one desktop check) against the built server, the stub API with 20 of everything (`test/stub-api.ts`, with the platform's real copy widths) and synthetic JPEGs served locally. Two network modes: *origin* (the Node server as it answers) and *edge* (a gzip proxy in front, standing in for Cloudflare's compression). Synthetic photos are larger than real ones (a line pattern compresses badly), so image-led LCPs are pessimistic; Lantern's simulated LCP also varies by up to ±1.5 s between identical runs on image pages, so results are medians of three runs. The harness and its notes live outside the repo (the D10 session's scratchpad: `perf/run.mts`, `perf/journey.mts`, `perf/axe.mjs`, `perf/keyboard.mjs`); to rerun, build (`pnpm build`), then run Lighthouse against `pnpm start` with a stub or a staging API, keeping Chrome's `--host-resolver-rules` for the media host and running Lighthouse *asynchronously* when the stub lives in the same process (a synchronous child process blocks the stub, and every page but `/` then times out into a 500: the "Lighthouse gets 500" seen at the start of D10 phase B was that, not a server bug).

|---|---|---|---|
| `/` | 3.0 → 3.0 → 3.1 | 3.8 → 3.8 → 3.9 | 5.3 → 5.3 → 3.2 |
| `/explore/studios` | 2.6 → 2.7 → 4.0 | 10.2 → 10.1 → 9.6 | 5.8 → 6.7 → 4.2 |
| studio profile | 3.9 → 5.6 → 5.6 | 7.3 → 7.4 → 7.4 | 6.7 → 7.6 → 5.6 |

Desktop (edge): `/` 0.7 s, an artwork page 0.9 s, performance 99–100, unchanged. Lighthouse accessibility 100 on every page in every state. Reading it: precompression cut 1.5–3.7 s from every page at the origin (FCP 4.1–4.6 → 2.2–2.6 s), which is what visitors get if the edge doesn't compress; with compression at the edge, phase B is neutral except the directories. The studios directory's now-eager LCP photo is faster in real Chrome (10.1 → 9.6 s) but slower in Lantern (2.7 → 4.0 s): Lantern doesn't model request priority, so an early high-priority photo just shares the link with the JS. Where a photo is the LCP the real-Chrome times stay long because the lab's media host is HTTP/1.1 without prioritisation and Chrome loads every lazy photo within its slow-network lazy-load distance (about 2,500 px, six rows of a directory) alongside the LCP photo; R2 behind Cloudflare (HTTP/2 and 3, priorities) and real photos (smaller than the synthetic ones) should do better, which only field data can confirm.

**What the traces show.** No layout shift anywhere (every image has its frame: width, height and `aspect-ratio`), no long tasks (TBT 0–30 ms), the server answers in ~20 ms. The bottleneck on a phone is bytes before LCP on a slow link: the render-blocking stylesheet (9 KB gz), the two preloaded fonts (Geist 29 KB, Eczar 16 KB, Latin subsets, `font-display: swap`), the JS that is requested from the head (the entry is 122 KB gz / 107 KB brotli) and the LCP photo. The entry is framework code: react-dom 52%, TanStack Router 13%, seroval (SSR hydration) 6%, TanStack Query 3%, Radix Dialog with its scroll lock about 6% (the menu sheet, on every page), app code a few KB; no devtools, one copy of each package (`pnpm why`: the second router-core belongs to the route generator CLI only), lucide icons tree-shaken. Splitting it further (a lazily loaded menu sheet, dropping `tailwind-merge`, 9 KB gz) would save under 10% of the JS for real complexity, with TBT already near zero: not done.

**Changes.**

- Static files are stored pre-compressed (`compressPublicAssets`: brotli and gzip, chosen by `Accept-Encoding`, `Vary: Accept-Encoding`), so the origin sends the entry as 107 KB brotli instead of 393 KB raw whether or not a proxy compresses. HTML stays uncompressed at the origin (it streams): Cloudflare compresses it on the way out (D11: verify `content-encoding` on a deployed page).
- The directories' first result is the page's lead image: the first image of `/explore/studios`' first row and of `/explore/artists`' first card loads at once with `fetchPriority="high"` (React 19 turns it into a `<link rel="preload">` in the head); the rest stay lazy so nothing competes with it. Before, every directory image was lazy, including the LCP (Lighthouse's "LCP image was lazily loaded").
- Thumbnails never offer the stored original (up to 2048 px): tiles, cards and strips offer the API's copies up to 1280 px (`THUMBNAIL_MAX_WIDTH`), an image stored before the copies existed its original alone; only the artwork page and a profile's hero (`large`) offer the original, and "View full size" links it. Logos and portrait badges (`BadgeImage`) load the smallest copy for their 48–112 px tile instead of the original.
- `sizes` checked against every layout: studio strips are 14vw between `sm` and `lg` (was 33vw: up to three times the bytes), a profile's compact artist cards 22vw from `lg` (was 30vw). One deliberate exception, measured: artist cards are one column below 26rem but keep `50vw` there, which caps them at the 640 px copy (about 1.7x density on a 380 px card); the exact `100vw` picked the 1280 px copy, doubled `/explore/artists`' photo bytes and its LCP (4.6 → 8.4 s in Chrome with slow-4G throttling).

**Images, the rules.** Only the API's public URLs and copies (`variants`: 320, 640, 1280 px for photos, 640–1600 for covers; JPEG or PNG: the platform makes no WebP or AVIF and Discover adds no image proxy, so modern formats wait for the media pipeline). `srcset` from the copies (plus the original only where shown large), `sizes` per layout, width and height always (no CLS), one `fetchPriority="high"` eager image per page (home: the collage's first; directories: the first result; gallery: the first of 4 eager tiles; profiles: the hero; artwork: the artwork), everything below lazy with `decoding="async"`. A photo that fails shows a neutral frame with its alt text, also when it failed before hydration (`ResponsiveImage` checks `complete` and `naturalWidth` on mount; React can't see an error that fired before it attached).

**Budgets** (lab, mobile, edge mode; a regression past them needs a reason): JS transferred by a page ≤ 200 KiB (now 177–182 KiB), the entry ≤ 130 KB gzip (122), CSS ≤ 15 KB gzip (9), CLS 0, TBT ≤ 100 ms, FCP ≤ 2.5 s (2.2), Lantern LCP ≤ 6 s with the synthetic photos (now 3.1–5.6 s). The launch targets are field values (D11, p75 from CrUX or RUM): LCP ≤ 2.5 s, CLS ≤ 0.1, INP ≤ 200 ms.

**Network.** Every page's reads run on the server, in parallel, and are dehydrated: the browser makes no API request on load (checked in a browser on every route type) and none on focus (`refetchOnWindowFocus: false`, 60 s fresh). The browser retries a transient failure twice (no 4xx, no 429: `shouldRetry`), the server never; `SERVER_TIMEOUT_MS` (5 s) bounds a hung read. Loaders have no waterfalls but the deliberate ones (a profile's 301 check after a 404, an artwork's related reads after the photo). The sitemap index walks its three lists in parallel, each sequentially (bounded: three requests at a time, style counts four at a time). The API's list and detail queries batch their places and styles per page (no N+1); its tattoo search and sitemap plans are in [API](api.md).

**Cache lifetimes and invalidation.**

| What | `Cache-Control` | Invalidation |
|---|---|---|
| Every page (200, 301, 404, 500) | `private, no-store`, `Vary: Cookie` | None needed: rebuilt per request, so a takedown is a 404 on the next request (plus the API's cache, below) |
| `/assets/*` (hashed JS, CSS, fonts) | `public, max-age=31536000, immutable`; brotli/gzip by `Accept-Encoding` | A new build has new names; old names keep working until the next deploy removes them |
| `/favicon.svg`, `/brand/*` | `public, max-age=86400` | Same names across deploys: a change shows within a day |
| `/robots.txt` | `public, max-age=300` | 5 minutes |
| Sitemaps | `public, max-age=3600` (errors `no-store`) | An hour, plus the API's 2 minutes |
| API reads (the platform) | `public, max-age=60, stale-while-revalidate=60`, `Vary: Origin`, ETag | Up to 2 minutes for a takedown; no purge exists ([API](api.md#limits-and-caching)) |
| The browser's query cache | 60 s fresh per tab | A reload |

**Why HTML is never cached at the edge.** Every page shows the visitor's country (the header and the country-aware lists), resolved from the `td_country` cookie and, once enabled, the trusted geolocation header. No page type is provably free of that: even a profile or artwork page (global content) renders the header's country. Caching HTML at Cloudflare would need the country in the cache key (a Cache Rule keyed on the cookie and the geolocation header, with bypass for anything else), `Vary` that Cloudflare honours, and a purge on takedown; until D11 designs that, no cache rule may cover Discover's pages, and `/assets/*` (cacheable by extension) is what the edge caches.

## Accessibility (D10 phase B)

- **Contrast:** no new colour or token in phase B; the measured ratios in `src/styles.css` stand.

## Security headers and hardening (D10 phase B)

**Headers** (`src/lib/headers.ts`), on every response: pages and their 404/500/301s and the server routes through Start's request middleware (`src/start.ts`), static files through Nitro's route rules (`vite.config.ts`), and anything answered before either (Start's 308 for a protocol-relative `//host/x`) through the Nitro plugin's `withSecurityHeaders` (`src/server/malformed-path.ts`), which adds them only to a response without them. Tested on the built server for each kind (`server-d10b.test.ts`).

| Header | Value |
|---|---|
| `X-Content-Type-Options` | `nosniff` |
| `Referrer-Policy` | `strict-origin-when-cross-origin`: a studio's site sees `https://tattoodrip.app`, never the page's path or search |
| `X-Frame-Options` | `DENY` |
| `Content-Security-Policy` | `base-uri 'self'; object-src 'none'; frame-ancestors 'none'; form-action 'self'` |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=(), payment=(), usb=(), browsing-topics=()` (Web Share and the Clipboard keep their defaults) |

**CSP, the follow-up (D11).** The policy sets no `script-src`, `style-src`, `img-src` or `connect-src`: TanStack Start's hydration data, its scroll restoration and the JSON-LD are inline scripts, and React adds inline styles (image frames), so a useful script policy needs a per-request nonce passed to the router (`ssr.nonce`) and to every inline script, `'strict-dynamic'`, and `img-src` limited to `MEDIA_URL`'s origin, `connect-src` to `API_URL`'s. Roll it out as `Content-Security-Policy-Report-Only` with a report endpoint first, watch a week of reports, then enforce. **HSTS** is left to the domain (Cloudflare ends TLS; the max-age and `includeSubDomains` across the studio subdomains are a D11 decision).

**Hardening checked.**

- **Undecodable paths** (`/%ff`, `/tattoos/%E0%A4`, `/%`): h3 decodes the path while it creates the request's event, before any middleware, and threw: the request was never answered and held its connection until the client or nginx (130 s) gave up, on every build before phase B. Now a 400 at once (`src/server/malformed-path.ts`, a Nitro plugin wrapping the app's fetch), tested on the built server (`pnpm dev` answers such a path with Vite's own immediate 500).
- **Search parameters and slugs:** 1,700 hostile requests (every parameter and path segment with empty, over-long (5,000), control, NUL, bidi, emoji, encoded traversal, prototype keys, JSON-ish, script and URL values; duplicated keys): no 5xx, no hang, nothing reflected unescaped. A malformed value is dropped (the router 307s to the same path without it) or a 404; a refused cursor redirects to the same filters.
- **Redirects:** every 301/303/307/308 target is a same-origin path (`/explore/tattoos`, old slugs, artwork spellings, the cursor drop, `/preferences/country`'s `return`, which refuses `//`, schemes and backslashes); `//host/` is normalised by the server to a same-origin path.
- **Error pages** never show a stack, an API message or an error code (`RouteErrorState` shows only its own words; the server logs the error); tested with every read failing.
- **Dehydrated state** holds only the public settings, the preference and the API's public answers (scanned on every route type: no e-mail, phone, token, key or tenant id; the booking `ref` appears only inside the API's `bookingUrl`, as intended); hidden, unpublished and taken-down entities are absent from lists and 404 by address (the journey below).
- **Media** only from the API's URLs; "View full size" links only an http(s) URL.
- **Retries:** at most two in the browser, transient errors only, none on the server; a client navigation that fails shows the error state with Try again.

**Critical journey** (Playwright, built server, markets NP and IN, with a hidden studio, artist and photo): home → country switch to India (the httpOnly cookie) → studios → a studio profile → artists → an artist profile → the gallery → an artwork → its artist → back → its studio, and the booking links (the studio's `/book?ref=`, the artist's `/book?artist=<slug>&ref=`, the artwork's `/book?artwork=<id>&ref=`): no console error or hydration warning, the country kept on every page, one valid canonical and one h1 per page, the hidden entities absent and 404 by address. Run in both markets.

## Design system

All tokens are in `src/styles.css`; components use them, never hex values.

- **Semantic tokens** are a plain `@theme`, not `@theme inline` (D06 fix): the utilities read `var(--color-muted-foreground)` and friends, so `.night` really redefines them. Inlined, `text-muted-foreground` stayed paper's ink-muted on night (about 2.6:1).
- **Palette:** paper `#f5f2ec` (page), paper-raised and paper-sunk, ink `#111111`, ink-muted, line and line-strong, accent red `#b4232c` (small accents and focus; text only on paper), and the night set for dark sections (`.night`: `#111111`, night-ink, night-muted, accent-bright `#e5484f` for text and focus there, 4.8:1). Contrast is measured and noted in the file (body text ≥ 6.3:1, control borders ≥ 3:1). shadcn's semantic names (`background`, `foreground`, `muted-foreground`, `border`, `ring`, `primary`) map onto them, and `.night` redefines them for its section.
- **Type:** Eczar 700 (display) and Geist variable (UI and text), vendored from Studio OS with their OFL licences; Latin preloaded, `font-display: swap`. Fluid display sizes `text-display-xl/lg/md` (clamp, phone first); `eyebrow` for small uppercase labels.
- **Layout:** `PageContainer` (90rem wide, or a 48rem reading width) with `page-gutter` (16, 24 then 40px); `EditorialSection` for full-bleed bands with the vertical rhythm (64px, 96px from `lg`), `tone="night"` for a dark one. Breakpoints are Tailwind's (`sm` 40rem, `lg` 64rem: where the header shows every link).
- **Interaction:** 2px-radius buttons (no pills), 44px targets below `lg`, one focus ring (2px accent, 3px offset; accent-bright on night), subtle transitions only, and everything instant under `prefers-reduced-motion`. No animation library.
- **Brand:** the "Tattoo Drip" wordmark in Eczar, as in Studio OS; the favicon is Studio OS's interim mark (TAT-67). No new logo.
