# Testing and code generation

Read before changing tests or routes, pages and controllers whose generated types must be refreshed. Commands below run from `apps/platform`; the [root README](../../../README.md) covers local environment, PostgreSQL and Mailpit setup.

## Development and focused checks

- `pnpm dev` runs `node ace serve --hmr` on port 3333.
- `pnpm worker` runs `node ace queue:work` for queued jobs and mail; see [jobs and email](jobs-and-email.md) for restart and delivery rules.
- `pnpm typecheck` checks the server and `inertia/`.
- `pnpm test` runs `node ace test`; narrow to a suite and filename with `pnpm test functional --files=tenant_routes.spec.ts`, or use `node ace test unit --files=queue_config.spec.ts`. Suites are defined in `adonisrc.ts` (`unit`, `functional`, `browser`). `--files` is a suffix match on the file name: use the full name (`cross_tenant.spec.ts`) or the bare stem (`cross_tenant`). The half form `cross_tenant.spec` matches nothing. Do not insert `--` after the script name: pnpm forwards it verbatim and it ends Ace flag parsing. Wrap runs in `timeout -s KILL <seconds>`: a spec that fails to import hangs `node ace test` instead of failing.
- Run relevant tests for changed behavior, including tenant-isolation tests for tenant-owned endpoints. Preserve validation and security coverage; broader checks are justified for shared behavior or new failures.

## Environment and test conventions

Ace commands that boot the app validate its environment. Prepare the platform `.env` following the root setup guide; every test run needs a reachable PostgreSQL, and functional tests need it migrated (`pnpm migrate`). The `.env` must have the `DB_USER` / `DB_MIGRATION_USER` variables from `.env.example`, or pass them inline: the runner refuses to boot as a role that bypasses row-level security.

Functional tests run inside `testUtils.db().wrapInGlobalTransaction()` (Lucid 22's name; `withGlobalTransaction` is deprecated), so they leave no data behind. HTTP tests use `client` with `.loginAs(user)` and `.withCsrfToken()`. Check form errors with `assertValidationError(response, field)` from `#tests/helpers/validation`: Adonis 7 flashes them under `inputErrorsBag`, while the session plugin's `assertHasValidationError` reads `errors`.

Slugs are permanent (TAT-24): every slug a tenant has held stays in `tenant_slugs`, and only an owner-role `DELETE` releases it ([database conventions](../database/README.md#row-level-security)). Tests roll back, so they never reserve anything, but they share the dev database. If you try the "Page link" form in `pnpm dev` with a slug the fixtures use (`black-needle`, `red-ink`, `studio-a`, `ink-1` and so on), that slug stays reserved there and `studioWithOwner(...)` or `changeSlug(...)` with it fails with `SlugTakenError` (`tenant_slugs_slug_unique`). Pick other names in dev, and in new tests give slugs a prefix or suffix specific to the test. To release one, delete its row from `tenant_slugs` as the owner role.

Rate limits (TAT-8) use the memory store under test (`config/limiter.ts`). `tests/bootstrap.ts` empties it before every functional and browser test, so counts never carry over. Test requests come from loopback, which is trusted as a proxy, so `.header("x-forwarded-for", "203.0.113.1")` picks the client address. `rate_limit_store.spec.ts` covers the Postgres store outside a global transaction. The store keeps the client it was created with, so never call `limiter.use("database", …)` inside `wrapInGlobalTransaction`. The intake's bot challenge is off in tests: `.env.test` sets `TURNSTILE_SECRET_KEY` empty, so a developer's `.env` never turns it on. A `TURNSTILE_SECRET_KEY` exported in the shell or in a CI job's environment still wins over that empty value (the process environment is read first), and the tests that expect the check off then fail loudly: unset it for the test run. A test turns it on with `enableChallenge(siteverify(answer))` from `#tests/helpers/challenge` (the real `BotChallenge` with `TEST_SECRET`, a fake `fetch` and the host and action checks) and undoes it in teardown with `app.container.restore(BotChallenge)`; `verdict(slug, over?)` is Cloudflare's answer for a good token made on that studio's page (`<slug>.localhost`, from `.env.test`'s `STOREFRONT_URL`). The intake's limits (20 per address and 60 per studio an hour, 10 per phone a day) apply in every test: a test that sends more than 20 intakes to one studio gives them different `x-forwarded-for` values.

Cookies (TAT-9): the session cookie is `td-session` in tests; read its name from `sessionCookieName(app.inProduction)` (`#services/cookie_policy`), never a literal. `setCookieLines` and `parseSetCookie` (`#tests/helpers/cookies`) read `Set-Cookie` lines, from `response.headers()["set-cookie"]` or a `ResponseFactory` response. Tests never run in production, so production's `__Host-` cookie is checked through the real serializer (`cookie_policy.spec.ts`), the real `config/session.ts` and `config/app.ts` in one production boot (`production_boot.spec.ts` runs `tests/helpers/print_cookie_config.ts`, which prints the resolved cookie configs and the `Set-Cookie` lines they produce; no database) and its startup through real processes (`boot` from `#tests/helpers/boot`, which TAT-29's role-guard boots use too). Cookies ignore ports: two dev servers on `localhost` share `XSRF-TOKEN` and fail each other's CSRF checks, so open the second on `127.0.0.1`.

The public API counts every request per caller (TAT-38): 300 reads per 5 minutes and 60 writes per hour per address. A test that sends more from one address gives its requests distinct `x-forwarded-for` values. `fillApiLimit(name, caller, tenantId?)` (`#tests/helpers/api_limits`) spends a budget so the next request is refused, and `testServerKeys()` gives the two `STOREFRONT_SERVER_KEYS` of `.env.test` for keyed requests (`authorization: Bearer …` and `x-visitor-ip`). `#tests/helpers/raw_http` (`rawRequest`, `readResponse`, `closedWithin`, `waitFor`) drives a raw socket, for answers that must come before a body is sent. A variable exported in your shell or CI wins over `.env.test`: an exported `STOREFRONT_SERVER_KEYS` or `TRUST_PROXY` (like `TURNSTILE_SECRET_KEY`) changes what the tests see, so unset them before a run.

Storage written to `tmp/storage/` is cleared before and after test runs by `tests/bootstrap.ts`. Uploads in tests: `receiveUploads` writes them to `tmp/storage/uploads` (`config/bodyparser.ts`; `tests/bootstrap.ts` makes it). `tempUploads()` / `newTempUploads(before)` from `#tests/helpers/uploads` check that a request left no temp file (a positive control in `inquiry_refusals.spec.ts` shows that a half-sent upload really appears in that folder, so "no temp file left" cannot pass for lack of looking; wait a moment before asserting, because a write stream can still be closing when the response is out), and `storedReferenceImages(tenant)` lists a studio's stored reference files. `tests/functional/http/multipart.spec.ts` sends file parts named like `Object.prototype` properties to login, signup, a dashboard form and the public upload routes with an `unhandledRejection` listener and a client timeout: a crash there fails the test instead of ending the run. `#tests/helpers/intake` builds intake requests (`intakeFields`, `png`, `postInquiry`) and reads what an intake can change (`intakeRows`). Run the suite on the Node version in `.nvmrc`: on Node 26.9 the multipart parser stalls on a text field over about 130 KB and the "more than 2 MB of text" test hangs the runner. Queue fake and direct execution conventions are in [jobs and email](jobs-and-email.md#jobs).

Staff alert emails (TAT-52) are on in tests: `.env.test` sets `ALERT_EMAILS=true` (an exported `ALERT_EMAILS` still wins: unset it). No test sends real mail: a queued email is a `SendMailJob` payload on `queue.fake()` (`fake.getPushedJobs()`), or a row in the test's transaction; through `processQueued()`, `mail.fake()` with `emitter.fake(["mail:sent"])` catches it. Render a mail class itself with `buildWithContents()` and its `message.assert*` helpers.

Accounts (TAT-18): `User.create` leaves the address unconfirmed (like the accounts from before TAT-18); a test that opens or posts `/onboarding` creates its user with `emailVerifiedAt: DateTime.now()`. The session's `auth_web` holds `<user id>.<session version>`, which `loginAs(user)` writes from the instance you pass: an instance loaded before the version changed is a signed-out session (the reset's sign-out is tested that way), and a user built without the column fails with "its session version is missing". `#tests/helpers/accounts` reads the emails a faked queue holds (`queuedMails`), the token in a link (`tokenOf`), expires a token (`expireToken`), alters one (`altered`) and reads its row's flow id (`flowOf`, `NO_FLOW` for a well-formed id no row has): the reset and confirmation POSTs must send the `flow` field their page rendered, so a direct post carries `flow: await flowOf(token)`. Put a link's token in a request with `.withSession({ [SESSION_TOKEN_KEYS.reset_password]: token })`, as the link's GET leaves it. The link routes count 30 requests per client address per 15 minutes and the reset request 3 per address named: a test that sends more gives them distinct `x-forwarded-for` values or addresses. Invitations (TAT-33): `#tests/helpers/invitations` has `invite`, `confirmedUser`, `invitationFlow` (the page's flow id for a token: pure, `invitationFlowId` of its hash) and `expireInvitation`; `invitation_race.spec.ts` is the one spec that races two real connections: it runs outside the global transaction, commits its studios (random slugs) and deletes them in its teardown through the `owner` connection (`session_replication_role = replica`), and holds one side open at a known point (the accepting side at `membershipOf`, protected for that; or a whole `invite` / `renew` / removal / demotion left uncommitted with `heldOpen`) until the other request, on a connection of its own (`onItsOwnConnection` gives its `pg_backend_pid`), waits on a lock: `waitUntilBlocked` watches that backend in `pg_stat_activity`, never the whole database, so unrelated contention can't release the test early. The flash that carries a new link is tested with stand-in objects in `tests/unit/middleware/inertia_flash.spec.ts` (only the Members page emits it, always `no-store`); stage a link's token with `.withSession({ [INVITATION_TOKEN_KEY]: token })`.

## Generated files and scaffolding

- `node ace codegen` after adding or renaming routes, pages or controllers regenerates `.adonisjs/` types (route names, pages, controllers) that `pnpm typecheck` reads. Keep the regenerated result with the change. This command refreshes types without starting the HTTP server.
- Scaffold with one concrete command, such as `node ace make:controller <name>`, `node ace make:model <name>`, `node ace make:migration <name>` or `node ace make:validator <name>`.
- `pnpm migrate` applies migrations (as the owner role) and regenerates `database/schema.ts`. Read [database conventions](../database/README.md) before writing migrations. Never edit generated files manually.

For broader CI requirements, consult the [workflow](../../../.github/workflows/ci.yml). Relevant design docs are [architecture](../../../docs/architecture.md), [data model](../../../docs/data-model.md) and [requirements](../../../docs/requirements.md); read only the part the task needs.

## Tenant isolation tests

Tests run as the restricted app role, so row-level security applies to them. A direct model read or write of tenant-owned rows needs a context: `inTenant(tenant, fn)`, `inUser(user, fn)` or `inTenantAs(tenant, user, fn)` from `#tests/helpers/tenants`. A negative check ("nothing was created") must run in the context that would have seen the row, or it passes vacuously.

- `twoStudios()` gives studios A and B, each with an owner, an artist (a user with the artist role), two payment methods, an artist profile (`artistProfile`), a visible artist who takes no inquiries with a slug only that studio has (`closedArtist`, `<slug>-mira`: the public artist route's isolation case needs a slug B has and A hasn't) and one of each pipeline record (`pipeline`: client, accepted inquiry, project, reference image, quote and a submitted payment), a deposit_pending project with its deposit link (`depositProject`, `depositToken`, `depositReferenceCode`) and the eSewa method its page shows (`depositMethod`), a project booked without a price (`pricelessProject`), a booked project holding a verified deposit (`paidProject`, `verifiedPayment`) and a cancelled one whose deposit needs its outcome (`closedPaidProject`); `payment` is the pipeline's submitted payment; a booked project assigned to `artistProfile` with a scheduled tattoo session 60 days out (`sessionProject`, `session`) is the session routes' resource (TAT-85); an unread alert of the owner about the new inquiry (`alert`) is the alerts routes' (TAT-52), and the studio's own aftercare text (`messageTemplate`) is what the messages settings routes' snapshot reads; a pending invitation (`invitation`) and the artist's membership row (`artistMembership`) are the members routes' (TAT-33). Seed data for a new table goes there.
- Every `/t/:tenant` route needs an entry in `tests/isolation/cases.ts` (method, pattern, actor, valid body, own status, a snapshot of what it could change) or a reasoned exemption. `cross_tenant.spec.ts` runs each as studio A against studio B: a positive control first, then B's slug and, with an `:id`, B's resource id. Each attack must be a 404 with B unchanged. `tenant_routes.spec.ts` fails for a route without an entry. A write case's positive control must change studio A's snapshot, so an invalid body, a CSRF failure or a logged-out 302 cannot pass it.
- Roles (TAT-30): every `/t/:tenant` route also needs an entry in `TENANT_ROUTE_ROLES` (`#modules/tenancy/access`); `tenant_routes.spec.ts` fails for a route without one and for a route without the role check after tenant. `role_access.spec.ts` seeds one studio with `seededStudio` and sends every isolation case as that studio's artist, linked to its artist profile with every project assigned to it and an alert of their own: an owner-only route must be a 404 with the case's snapshot unchanged, any other route the case's own status (and a write must change the snapshot). It pins `ARTIST_ROUTES`, the routes open to artists: opening one is an edit of the table and of that list. `seededStudio(slug, name)` (`#tests/helpers/tenants`) seeds one studio like `twoStudios`' and `caseRequest` (`#tests/helpers/isolation`) sends one case.
- Public API routes (TAT-32) are not in `cases.ts`: there is no signed-in actor, and another studio's slug is simply another tenant. Each `/api/v1/tenants/:tenant` route needs an entry in `tests/isolation/public_cases.ts` (method, pattern, valid body, own status, `ownMarkers`, snapshot); `public_api.spec.ts` requests it under studio A's slug and fails if the answer mentions studio B (`publicMarkers`: ids, slug and names) or B changed. A write case that takes multipart sets `encoding: "multipart"`, and its body is sent as form fields. A route with parameters besides `:tenant` needs `params` (the harness also sends B's values under A's slug and A's values under B's slug, a route can fail in one direction only; each must be the 404 and leave the owner of the values unchanged); a multipart write sends `body` as fields and `files` as parts (TAT-65). `api_routes.spec.ts` fails for a route without a case, for an API route without `publicApi` first or with web middleware, and for an API GET route without `publicCache()` or a written reason. Assert API responses with `assertApiData`, `assertApiError` and `assertNoCookies` from `#tests/helpers/api` (TAT-47's schema check goes there). Test-only API routes live under `/api/v1/__test` and `/api/v1/tenants/:tenant/__test`; the guards skip `__test` patterns. Artist fixtures for public tests: `artistInput` and `addArtist` from `#tests/helpers/artists` (TAT-44).
- The limit of that table: with RLS on, a service query that forgot its tenant filter still gives a 404 here (RLS hides the row), so it proves the system as a whole. The app-level filters are covered by service specs that run from the OTHER tenant's context (`inTenant` / `inTenantAs`), e.g. `payment_method_service.spec.ts` "list and findFor only see the tenant's live methods".
- Deposit tests build their services with `depositServices()` and a studio ready for a link with `depositReady()` (`#tests/helpers/deposits`); `postProof`, `proofPart` and `storedProofs` drive the public endpoints. `.env.test` sets `STOREFRONT_URL` so link URLs never depend on a developer's `.env`.
- Payment tests build their services with `paymentServices()` and a waiting screenshot with `proofFor()` (`#tests/helpers/payments`); a member's writes record `verified_by_user_id`, a key to `users`, so pass a real user's id (`ownerMember(owner)`).
- Tests that drive the queue use `processQueued()` from `#tests/helpers/worker` (the real worker). Jobs that touch tenant data extend `TenantJob`. Locally the tests share the dev database, where `pnpm dev` keeps its schedules, so `processQueued()` deletes `queue_schedules` rows inside the test's transaction before draining: a test runs only what it queued.
- A SECURITY DEFINER function such as `expired_quote_candidates()` sees every tenant's committed rows, the dev database's included (so does `tenant_for_slug()`: an 'unknown slug' test must use a slug no dev studio has): filter its output to the test's own tenants, and assert a sweep's queued jobs by payload, never by count. To run a sweep's jobs through the worker, run the sweep against `queue.fake()`, keep the payloads of your own tenants and dispatch only those: the worker would otherwise run a job for every committed candidate and stop after `MAX_CYCLES` (100), so the test would depend on the data in the dev database.
- Test-only routes live in `tests/support/test_routes.ts`; the functional suite registers them.
