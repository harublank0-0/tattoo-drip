# Backend conventions

Read the relevant section before changing backend behavior. For module boundaries or tenancy design, consult [architecture](../../../docs/architecture.md); for schema changes read [database conventions](../database/README.md) and the relevant [data-model](../../../docs/data-model.md) section. Those contain the canonical schema rules.


## Layout

- `app/controllers`, `app/models`, `app/validators`, `app/transformers`, `app/middleware`, `app/exceptions`
- `app/modules/<module>/`: one folder per backend module from [architecture](../../../docs/architecture.md), owning its `models/`, `services/`, `controllers/`, `validators/` and `emails/`. Import with `#modules/*`. New module code goes here; code still in the flat `app/*` folders moves when its module is built. Controllers and transformers stay in `app/controllers` and `app/transformers` for now: `indexEntities` in `adonisrc.ts` only scans those folders to generate `#generated/*`, so it has to be pointed at the module folders first.
- `start/routes.ts` (routes reference controllers through `#generated/controllers`), `start/kernel.ts` (middleware), `start/env.ts`
- `config/`, `database/migrations/`
- `inertia/pages`, `inertia/layouts`, `inertia/components` (shadcn components in `inertia/components/ui`), `inertia/hooks`, `inertia/css/app.css` (Tailwind entry and theme tokens)
- `tests/unit`, `tests/functional`, `tests/browser` (suites are defined in `adonisrc.ts`)

Import with the subpath aliases from `package.json` (`#controllers/*`, `#models/*`, `#services/*`, `#validators/*`, …), never with long relative paths.

## Dependency injection and module boundaries

- Controllers and services that use `@inject()` must import their dependencies as values, not `import type`: the container reads the class from decorator metadata at runtime. Biome's `useImportType` fix gets this wrong, so mark those imports with `// biome-ignore lint/style/useImportType: @inject() reads the class at runtime`.
- Each backend module owns its models and services; other modules call its services instead of querying its tables. Inertia controllers, API controllers and jobs stay thin and call the same services. See the module table in [architecture](../../../docs/architecture.md).

## API contract and migrations

- The REST API implements the contract in [OpenAPI contract](../../../packages/types/openapi.yaml). Change the contract first, regenerate the types, then implement.
- `database/schema.ts` and `.adonisjs/` are generated. Change the schema with a new migration, never by editing an existing migration that has been run.
- Read [database conventions](../database/README.md) before writing a migration; it owns the UUIDv7, timestamp, ownership, indexing and soft-delete rules.

## Soft deletes

- Soft delete: models of business records use `compose(XSchema, withSoftDeletes)` from `#models/mixins/soft_deletes`. Delete with `record.softDelete(trx?)`, undo with `restore()`; model queries skip deleted rows unless they start from `Model.withTrashed()` or `Model.onlyTrashed()`. The hooks don't reach `whereHas` subqueries or raw `db.from(...)` queries, so add `whereNull("<table>.deleted_at")` there. The hooks append `deleted_at IS NULL` to the end of the query, so a top-level `.orWhere(...)` would let deleted rows through (`a OR (b AND deleted_at IS NULL)`): group your own conditions in `.where((q) => q.where(a).orWhere(b))`. Update queries skip the hooks too; filter `deleted_at` yourself there. Soft-deleting a parent soft-deletes its children in the same transaction (the database's `ON DELETE CASCADE` only covers real purges).

## Tenancy and route access

- The tenant always comes from the URL (`/t/:slug/…` for the dashboard, `/api/v1/tenants/:slug/…` for the API). Services scope every query by tenant; never trust a tenant ID from a request body. Every tenant-owned endpoint needs a test proving tenant A can't reach tenant B's data.
- Tenancy: the `tenancy` module (`app/modules/tenancy/`) owns tenants and memberships. Other modules read them through `TenancyService` (`#modules/tenancy/services/tenancy_service`): `createTenant`, `tenantsFor`, `hasTenant` (one cheap yes/no query), and `assertKeepsAnOwner`, which every remove or demote of a member must call inside its transaction. New users create their first tenant at `/onboarding` (only while they have none: one tenant per account for now), once their email address is confirmed (`middleware.verifiedEmail()`, see [Accounts](#accounts)). Login and onboarding land on `/dashboard`, which redirects to the tenant the user opened last, else their oldest, else `/onboarding`; a tenant's own address (`/t/:tenant`) then redirects every member to Today (`/t/:tenant/today`, TAT-107; joining a studio lands there too). Login and logout forget the last tenant (`LAST_TENANT_KEY`), so a shared browser doesn't carry it over. `createTenant` also gives an independent artist their own artist profile (`ArtistService.createOwnerProfile`) in the same transaction; a studio gets none. The studio's cover photo (TAT-116) is three columns of `tenants` (`cover_image_key`, `_width`, `_height`, all or none: `tenants_cover_all_or_none`): `TenancyService.setCover(tenant, upload)` stores the public `studio_cover` image with `afterRollback` right after, locks the tenant row, swaps the columns and deletes the replaced cover after the commit; `removeCover(tenant)` deletes the files first (`deleteOrThrow`) and then clears them; a file that cannot be deleted throws `ImageDeleteError`, the cover stays and the flash says "Couldn't remove the cover photo, try again." (nothing to remove is not an error). Owners only (`PUT` and `DELETE /t/:tenant/settings/cover`, `StudioCoverController`). The studio page's look (TAT-56, Settings, Page look) is more columns of `tenants`, not a table (the row is already loaded, so the public read and the settings page cost no query): `storefront_theme`, `storefront_sections` (the visible sections in order, as `artists,inquiry`; always holds `inquiry`), `brand_accent` and `brand_accent_dark` (lowercase `#rrggbb` or null), `brand_font`, and the logo's `logo_image_key`, `_width`, `_height` (all or none, `tenants_logo_all_or_none`). The database checks only the shapes (`tenants_storefront_theme_format`, `_sections_format`, `_brand_accent_format`, `_brand_accent_dark_format`, `_brand_font_format`); which theme, font and section keys exist is the app's list in `#modules/storefront/look`, so a new theme needs no migration. That module is pure and holds the lists, the storefront's two papers, the theme's violets and the 4.5:1 contrast rule; `tests/unit/modules/storefront/look.spec.ts` reads the storefront's own files and fails when a copy drifts (apps never import each other). The validator (`updateLookValidator`) refuses an unknown key, a colour that is not `#rrggbb` (any letter case, stored lowercase) and an accent under 4.5:1 on `#f7f3ee` or a dark-mode colour under 4.5:1 on `#14110f`; `lookOf(tenant)` filters again on read, so a stored value off today's list is served as that value's default alone. `TenancyService.updateLook(tenant, input)` reads the row under its lock (another studio's context finds no row, `E_ROW_NOT_FOUND`) and writes only the five look columns; `setLogo` and `removeLogo` are the cover's rules through one private pair shared with the cover (a slot table names the purpose and the three columns), with the flash "Couldn't remove the logo, try again." when a file cannot be deleted. Owners only (`GET` and `PUT /t/:tenant/settings/look`, `PageLookController`; `PUT` and `DELETE /t/:tenant/settings/logo`, `StudioLogoController`); the page's props are the stored look as served, the server's lists, `swatches`, the logo's 640 px preview (never the key) and `hasCover`. Soft-deleting a tenant (`tenant.softDelete(trx?)`) also soft-deletes its live memberships, payment methods, artists, clients, inquiries, projects, reference images and sessions (quotes and payments have no `deleted_at` and stay).
- Members and invitations (TAT-33): an owner invites an address as an owner or an artist, optionally offering a live, unlinked artist profile, from Settings, Members (`/t/:tenant/settings/members`, `OWNERS`). `InvitationService` (`#modules/tenancy/services/invitation_service`) owns `tenant_invitations` (`TenantInvitation`; RLS; one per studio and canonical address, replaced by a new invitation; not soft-deleted): `invite` / `renew` return the raw token once (TAT-18's `newAccountToken`; only `hashAccountToken` is stored, and only in this table: the raw token also sits in the session store from the flash until the next request, and a staged one until sign-in, sign-out, accept or the 2-hour session age, like TAT-18's) and the controller flashes the link a single time (`INVITATION_LINK_FLASH`), which `InertiaMiddleware.flash()` puts in the page object's `flash` field next to the toasts: Inertia strips that field from history state, so Back and reload never show the link again, which a prop (`encryptHistory` keeps props) would not guarantee; the middleware emits the link only on the Members page (`INVITATION_LINK_PAGE`; the flash is read once by whichever request comes next, another tab's included) and sets `Cache-Control: no-store` whenever it emits one; `revoke` deletes; `pending` lists (`expired` by the database's clock). An expired invitation is not purged (it stays, address included, until renewed or cancelled; pruning is a follow-up). The link (`/invitations/<token>`, `ACCOUNT_TOKEN`, `throttleAccountLinks`) only stages the token in the session (`INVITATION_TOKEN_KEY`, forgotten at sign-in and sign-out) and opens `/invitations`; `preview(token, viewer)` finds the studio through the `invitation_tenant()` SECURITY DEFINER lookup and works in that studio's context; `accept(user, token, flow)` (`POST /invitations`: `auth`, `dbContext`, `verifiedEmail`, `throttleAccountLinks`) takes the (studio, address) advisory lock, then locks the row, requires the flow id (`invitationFlowId`, a fingerprint of the staged token's hash: the page renders it and a replaced or renewed invitation has a new one, so an old tab's form can't accept terms it never showed; the row's id would not do, since an upsert keeps it), a live invitation, a confirmed account with the same canonical address and no live membership, then creates the membership, claims the profile (`ArtistService.claim`: still live and unlinked, else the person joins without it) and deletes the invitation. `invite` takes the same transaction-scoped advisory lock (`pg_advisory_xact_lock` on the studio and canonical address) before any row lock and checks membership after it, so a re-sent invitation can't be inserted after an accept made its address a member (a link left for a member would restore them after a removal); keep that order (advisory lock, then rows) in any new path that changes an invitation or the membership of an address. `invite` and `renew` then lock the inviter's live owner membership `FOR SHARE` (`lockInviter`, a 404 when it is gone): removing or demoting an owner deletes the owner invitations they sent, and that DELETE cannot see an invitation another transaction has not committed, so `MemberService` must wait for the inviter through its owner locks (`FOR UPDATE`) and delete what committed, or find the membership gone first. The lock order is the address lock, the inviter's membership, the invitation row; `MemberService` takes the owner memberships, the target's, then the invitation rows and never the address lock, so the two cannot wait for each other in a cycle. `revoke` is a single statement on one existing row and needs no lock. No email is sent: the owner copies the link (`CopyLinkButton`, Share on WhatsApp). `MemberService` (`#modules/tenancy/services/member_service`) removes members (`assertKeepsAnOwner`, `ArtistService.unlinkUser`, `membership.softDelete`) and changes roles (`assertKeepsAnOwner` when demoting an owner); neither acts on the actor's own membership (`MemberRuleError`). A removal, and the demotion of an owner, also delete the studio's pending invitations for the member's address and the owner-role invitations they sent (so nothing they or a lost race left behind brings them, or a departing owner's chosen address, back as an owner); their artist invitations stay. A member removed between the unlocked read and the last-owner check is a 404 (`MembershipNotLiveError` becomes `E_ROW_NOT_FOUND`), not a 500.
- Tenant pages live in the `/t/:tenant` route group with `[middleware.auth(), middleware.dbContext(), middleware.tenant(), middleware.role()]`. The tenant middleware calls `TenancyService.membershipFor(user, slug)` on every request (never cache it) and turns `null` into the same 404 as an unknown URL (after redirecting a GET or HEAD on an old slug of the user's tenant, see the Slugs bullet below), never a 403, so a URL doesn't reveal that a tenant exists. Every tenant route goes in that group; a test fails for a `/t/:tenant` route without the middleware. Read the result with `tenantContext(ctx)` from `#middleware/tenant_middleware`, which returns `{ tenant, membership }` and throws outside the group (`ctx.tenant` is optional for that reason; the role is `membership.role`). Who may use each tenant route is one table, `TENANT_ROUTE_ROLES` in `#modules/tenancy/access` (TAT-30): route name → the roles that may use it (`OWNERS` or `MEMBERS`; owners are in every entry). The role middleware (`middleware.role()`, last in the `/t/:tenant` group after `tenant()`) reads it on every request and gives any other role the same 404; a route the table doesn't name throws. A new tenant route needs a name, an entry there (`tenant_routes.spec.ts` fails otherwise), an isolation case, and, if artists may use it, an edit of `ARTIST_ROUTES` in `role_access.spec.ts`, which sends every route as an artist. The table decides routes; which records an artist reaches stays with each module's service (its comments name them: `ProjectService.findFor` / `lockFor`, `BookingService.bookableArtists`, `mayChangeSession`, `CalendarService.load`, `AlertService`, `paymentsCard`, `ArtistService.findEditable`). Never add a role check to a route group. `:id` route params use `.where("id", router.matchers.uuid())`, so a malformed id is a 404 rather than a database error. Controllers pass the tenant to services explicitly; never read a tenant id from the body, query string or headers, and keep `tenant_id` out of validators. Every page gets the `tenant` and `tenants` props from `InertiaMiddleware.share()`; nav items for tenant pages pass `params: { tenant: slug }`.
- Slugs (TAT-24): `checkSlug(input)` in `#modules/tenancy/slugs` is the one rule for a new tenant slug: ASCII letters, digits and hyphens only (Unicode is refused, never case-folded), lowercased, 3 to 63 characters, no hyphen at either end, no `--` (so no `xn--` punycode), at least one letter, not in `RESERVED_SLUGS` and not containing `tattoodrip`. It does not trim; the `tenantSlug()` Vine rule in the tenancy validators trims and wraps it for `createTenantValidator` and `changeSlugValidator`. Never copy the reserved list or `STORED_SLUG`. `checkSlug` is for slugs someone chooses only: a slug taken from a path is pre-filtered with `STORED_SLUG` (the shape `tenant_slugs_slug_format` enforces), because legacy slugs such as `12345`, `a--b` or `www` stay valid and reachable. Existing slugs are kept as they are. Every slug a tenant has held, its current one included, is a row of `tenant_slugs`, written by the `tenants_register_slug` trigger, never by app code; its unique index keeps a slug from ever reaching another tenant (see [database conventions](../database/README.md#row-level-security)). `TenancyService.changeSlug(tenant, slug)` (owners, Settings → Page link, `PUT /t/:tenant/settings/slug`) locks the tenant row, allows `MAX_TENANT_SLUGS` (5) slugs in total (switching back to an own old slug is allowed if it still passes `checkSlug`; a kept slug that fails the rules, such as `a--b` or `www`, keeps redirecting but cannot be chosen again, so a reserved name never comes back) and throws `SlugTakenError` or `SlugLimitError` after its savepoint rolls back; `createTenant` maps both slug indexes to `SlugTakenError`. `currentSlugFor(user, slug)` resolves an old slug for a live member; the tenant middleware uses it to send GET and HEAD to the same path and query under the current slug (`withTenantSlug`) with a 302, never a 301 (a studio can switch back). The redirect turns the app's query-string forwarding off (`withQs(false)`) because the URL it builds already has the query. Writes on an old slug are a 404. Lookups match exactly: never case-fold a path parameter. The public API resolves slugs through `tenant_slugs` too: `STORED_SLUG` pre-filters a path slug (never `checkSlug`), then an exact lookup (see [Public API](#public-api)).
- Studio names (TAT-70): the onboarding and profile validators share `studioName()` in `#modules/tenancy/validators/tenant`: 2 to 120 characters after trimming and no control characters or line and paragraph separators (the message says so plainly), so a name can't carry an escape sequence into an email, a terminal or a log. It only judges new input: names already stored are covered where they are printed (`terminalText`, see Pilot metrics).
- Database context: every authenticated request runs in one transaction (the `dbContext` middleware, right after `auth`) with `app.user_id` set, and the tenant middleware adds `app.tenant_id` (`setRequestContext`, which only the outermost level may call). Row-level security reads them, so a query outside that transaction sees no tenant rows. Nested work uses `withTransaction` from `#services/db_context`, never `db.transaction`: inside a request it is a savepoint, so a caught unique violation leaves the request usable. `withDbContext({ tenantId }, fn)` runs `fn` as a tenant (jobs, tests, `createTenant`). The database settings belong to the connection, so overlapping `withDbContext` calls under one parent throw: await one before starting the next (`Promise.all` over `withDbContext`, or over the tests' `inTenant`, throws; plain `withTransaction` siblings are fine). A plain query made while a child context is open sees that context's settings, so don't mix them in a fan-out. Model queries, preloads and relations join the request transaction automatically; raw `db.from()` and `db.rawQuery()` do not, so use `dbClient()`. Tests will not reveal a query that escapes the request transaction on its own (the request is a savepoint on the test's single connection), which is why a tripwire fails the test run and Biome forbids importing the db service under `app/`. A failed request is rolled back by the exception handler, so a handler must throw to fail a request: one that returns a status of 400 or more without throwing still commits its writes. Never catch a database error outside `withTransaction`: after a failed statement the request transaction is aborted, and committing it silently rolls everything back (the response still says success). Work outside the database (deleting a file, sending an email) goes in `afterCommit` / `afterRollback`, never right after `withTransaction` returns: inside a request that is only a savepoint. Details: [database conventions](../database/README.md#row-level-security).
- Cross-tenant reads: the app role sees one tenant at a time, and nothing in a request ever needs more. Three SECURITY DEFINER functions look across tenants, and all return ids only: the expiry sweep (TAT-83) reads `expired_quote_candidates()` and acts on each row through a `TenantJob` in that row's tenant, never directly; the public API (TAT-32) turns a path slug into one tenant id with `tenant_for_slug()` and runs the request in that tenant; the invitation page (TAT-33) turns a token's hash into one tenant id with `invitation_tenant()`, then reads the invitation in that tenant's context. Rules for such functions: [database conventions](../database/README.md#row-level-security). The operator command `metrics:pilot` (TAT-70) is the one other cross-tenant read: it lists the live tenants (ids, slugs, names) through the `owner` connection and computes each one's numbers as the app role in that tenant's context; it runs from a shell, never in the web or worker process.
- Page history (TAT-82): Inertia encrypts the page props it keeps in browser history (`encryptHistory: true` in `config/inertia.ts`), and the guest middleware (the `guest` route group: login, signup and the password reset pages) calls `ctx.inertia.clearHistory()`, which drops the tab's key. After logout, an expired session or a change of user, Back can't decrypt the old pages and asks the server again, which sends a guest to `/login`. The flag travels only with a rendered page, so `clearHistory()` before a redirect does nothing. A flow that signs a user in without passing through a guest page must clear history on the first page it renders. A signed-in visitor of a guest page goes to `/dashboard`. The email confirmation page (`/verify-email`) and the invitation page (`/invitations`, TAT-33) are outside the group on purpose: their usual visitor is signed in, and they sign nobody in or out. In development, a plain-HTTP request from a non-loopback host (a phone on the LAN) is not encrypted (`encryptsHistory` in `#services/history_encryption`): browsers have no `crypto.subtle` there, and Inertia's visits would hang. Production always encrypts. Every Inertia page rendered for a signed-in user also answers `Cache-Control: private, no-store` (TAT-16): `InertiaMiddleware.share()` sets it with `response.safeHeader`, so a controller's own value stays (the invitation, password reset and confirmation pages set `no-store` themselves). `share()` is the one hook that runs exactly when a page is rendered, a full load or an Inertia visit alike; `handle()` can't do it, because it is a server middleware that runs before the session and auth middleware and can't tell a page from a `/files` or `/uploads` stream. What it adds to TAT-82 is the document navigation: it keeps the page out of shared and HTTP caches and, in current browsers, out of the back/forward cache after the session cookie changes, so Back after the sign-in page was reloaded or the tab restored asks the server again. Public `/uploads` files stay cacheable, private `/files` answer their own `private, no-store`, and the API is unchanged. Guest pages and an error page for a path no route matches (no user is known there) don't get it.
- Cookies and domains (TAT-9): `#services/cookie_policy` is the one policy. `sessionCookieName(app.inProduction)` is `__Host-td-session` in production and `td-session` elsewhere; `cookieAttributes(app.inProduction)` is `Path=/`, `HttpOnly`, `SameSite=Lax`, `Secure` in production and never a `Domain`. `config/session.ts` uses both, and `config/app.ts`'s cookie defaults use the attributes, so Shield's `XSRF-TOKEN` (not `HttpOnly`: Inertia sends it back as `X-XSRF-TOKEN`), the auth guard's `remember_web` (only ever cleared: remember-me is off), the cookie store's data cookie (named by the session id) and every `clearCookie` follow it; the browser-set `app_theme` is the only other cookie. A new cookie goes through the policy and into `KNOWN` in `tests/functional/auth/cookies.spec.ts`. Never add a `domain`, never decide `Secure` per request (behind the proxy the app sees http), and never give a cookie the `__Host-` prefix outside the production switch: the serializer throws without `Secure`. `checkAppOrigin` (`#services/app_origin`, run by `start/env.ts` once the environment is read) stops every process in production when `APP_URL` is not https or shares the studio pages' domain (on, under or above it; a loopback `APP_URL` skips that comparison). Production uses `SESSION_DRIVER=cookie`.

## Public API

- **One group, no session.** Every public endpoint lives in the `/api/v1` group at the end of `start/routes.ts`, whose `publicApi` middleware runs first (TAT-32; `api_routes.spec.ts` checks). `isApiRequest(ctx)` (`#services/public_api`) is true for a route under `/api`, or before routing for a URL under it. The session and shield wrappers in `router.use` (`#middleware/web_session_middleware`, `#middleware/web_shield_middleware`), silent auth and Inertia skip such requests, so the API reads no session, needs no CSRF token and never sets a cookie. Never add `auth`, `guest`, `dbContext`, `tenant` or `role` to an API route. Platform-wide endpoints go in the outer group, tenant endpoints in the inner `/tenants/:tenant` group.
- **Tenant from the path.** `publicTenant` gives a slug that fails `STORED_SLUG` (`#modules/tenancy/slugs`, the registry CHECK's shape; never `checkSlug`, so grandfathered slugs such as `12345` or `www` keep working) a 404 without a query, then asks `TenancyService.tenantIdForSlug`, the only caller of the `tenant_for_slug()` SECURITY DEFINER function, and runs the rest of the request in one transaction with `app.tenant_id` set and no `app.user_id`: every model query is RLS-scoped to that tenant. Read it with `publicTenantContext(ctx)`. An old slug serves GET and HEAD as the same tenant; any other method under it is the same 404 as an unknown slug, before validators, handlers and writes. The bodyparser is a `router.use` middleware, so it runs before `publicTenant` (and before anything in the group's `use` list): a body that cannot be read is a 400, 413 or 415 under any slug, which is no oracle because an old slug, a current one and an unknown one answer alike. RLS scoping is not authorization: a public endpoint returns only studio-page data, through a transformer that picks public fields ([requirements](../../../docs/requirements.md#tenant-isolation), rule 6).
- **Responses.** Return `ctx.serialize(SomeTransformer.transform(record))` for `{ data }`. To fail, throw `ApiException.notFound()`, or `ApiException.of(code)` (`#services/public_api_errors`) for a code of `API_ERRORS` (`#services/public_api`: the shared codes and each endpoint's own, with its status and its one message), or `new ApiException(status, code, message)` for a one-off, listed in `openapi.yaml` (`fields` belong to `validation_failed` only: a fourth argument is a type error with any other code and throws at construction). The exception handler turns every error on an `/api` request into `{ error: { code, message, fields? } }` (`renderApiError`): VineJS errors are `validation_failed` with `fields`, a known path with another method is a 405 with `Allow`, bodyparser and limiter errors get their codes, anything else is `internal_error`. Shared codes have fixed messages: an error's own message, stack or details never reach a response. API 4xx are not logged. A URL the server cannot decode (`/api/v1/%`, invalid UTF-8) is refused before routing and middleware; `onBadUrl` in `config/app.ts` (`#services/public_api`) answers one under `/api` with the `bad_request` envelope and the API headers, and any other URL keeps the plain-text 400.
- **CORS and caching.** `config/cors.ts` only serves `/api`: any origin, no credentials, GET, HEAD and POST, the `Accept`, `Content-Type` and `X-Challenge-Token` request headers, `Retry-After` exposed, preflights cached for 10 minutes. `publicApi` also sends `Access-Control-Allow-Origin: *` without an `Origin`, for CDN copies. Every API response is `Cache-Control: no-store` unless its route uses `middleware.publicCache()`: a 200 GET or HEAD then gets `public, max-age=60, stale-while-revalidate=600` and an ETag, and a matching `If-None-Match` a 304 (pass `{ maxAge, staleWhileRevalidate }` for other seconds). The middleware serializes an object body itself before it marks anything public, so a body that cannot be serialized (a throwing getter or `toJSON`, a circular reference) is an `internal_error` with `no-store`, never a cacheable 500. Never cache a response that isn't the same for everyone (the deposit page, TAT-65); a test makes every API GET route choose.
- **A new endpoint.** Contract first (`openapi.yaml`, then `pnpm --filter @tattoo-drip/types generate`), then a case in `tests/isolation/public_cases.ts`, the caching decision, and tests with `assertApiData` / `assertApiError` (`#tests/helpers/api`). Limits (TAT-38) need nothing per endpoint: `PublicGateMiddleware` (first in `router.use`) counts every API request per caller before its body, and the tenant group's `apiLimit({ name: "tenantReads" })` counts a studio's reads after `publicTenant`. A route that needs its own limit adds an `API_LIMITS` entry (`#services/api_limits`) and `.use(middleware.apiLimit({ name }))`, or a throttle of its own that counts `callerIp(ctx)` (`#services/api_caller`), never `request.ip()`. Limits call `consume()`, never `limiter.define` middleware, which puts `X-RateLimit-*` on every success: a cacheable response carries no per-caller header. The body parser reads no multipart body itself (`multipart.autoProcess: false`, `api_routes.spec.ts` checks; TAT-38): auto-processing would stream every file to the temp directory before `publicTenant` and the limits answer, and its handler table crashes the process on a part named like an `Object.prototype` property. A route that accepts uploads (TAT-51, TAT-65) reads its body in the handler with `receiveUploads(request)` (`#services/uploads`, the parser's own limits and errors: 413, 400; a client that hangs up is a 400 `E_REQUEST_ABORTED`, not a logged 500) and ends with `discardUploads(request)` in a `finally`; it validates files with `imageFile()` and stores them through `ImageService`. Its public isolation case sets `encoding: "multipart"`. A route with parameters besides `:tenant` (the deposit page's `:token`) gives its isolation case `params`, and a multipart write with files gives `files` (TAT-65). An endpoint's own error codes go in `API_ERRORS` (`#services/public_api`), are thrown with `ApiException.of(code)`, and are listed in the operation and in `ErrorResponse`. The cost of reading in the handler: the request holds its pooled connection and transaction while the upload streams. `receiveUploads` registers its handler under every `Object.prototype` name (`constructor`, `toString`, `__proto__`...), so no part name reaches the parser's flawed lookup (@adonisjs/bodyparser 11.0.4 keeps that table in a plain object; report it upstream before relying on a fix).
- **Bot challenge (TAT-55).** `BotChallenge` (`#services/bot_challenge`) asks Cloudflare Turnstile's siteverify whether the token in the `X-Challenge-Token` header is good: one form-encoded POST with the secret and the token, at most `CHALLENGE_TIMEOUT_MS` (3 s), no retry, inside the pooled request transaction `publicTenant` opened (so a slow Cloudflare holds a database connection for up to 3 s: the pool and write-slot numbers in [deploy](deploy.md) count on it). `passed` needs `success: true`, and in production also the studio page's host (`studioHostname(storefrontTemplate(), slug)`, `#services/storefront_url`) and the form's action (`CHALLENGE_ACTIONS.inquiry`); a missing, blank or over-2048-character token fails without a call. `failed` is 403 `challenge_failed`; no answer in time, an answer that isn't a verdict, Cloudflare's `internal-error` or a refused secret is `unavailable`, 503 `challenge_unavailable` (it fails closed: the widget needs Cloudflare too). It logs a fixed cause, never the token, the secret or Cloudflare's body. `TURNSTILE_SECRET_KEY` (a `Secret`, checked at boot by `checkChallengeSecret` in `#services/challenge_secret`) is required in production; unset elsewhere the check is off. The `intakeGuard` middleware runs it on `api.v1.inquiries.store`, after `publicTenant`, between the address and the studio counts, before the multipart body is read (nothing is written to disk for a refusal). The global body parser is the exception: it still reads a JSON, urlencoded or `text/*` body (1 MB at most) before any route middleware (TAT-32, ruling 6), so such a request is parsed first and then refused by the guard (counted) or the controller's 415, and an unreadable one by the parser itself (not counted by the guard, but by the gate: TAT-38's per-caller limit in front of the parser bounds that cost). Another form that needs a challenge gets its own entry in `CHALLENGE_ACTIONS` and the same middleware shape.
- **Studio page reads (TAT-44).** `GET /api/v1/tenants/:tenant` (`api.v1.studio`), `…/artists` (`api.v1.artists.index`) and `…/artists/:artist` (`api.v1.artists.show`; the `ARTIST_SLUG` matcher makes a malformed or uppercase slug the router's 404 without a query) are cached with `publicCache()`. `StudioPageService` (`#modules/storefront/services/studio_page_service`) builds them from the tenant row `publicTenant` loaded and from `ArtistService`, one query per request: `studio(tenant)` (the `TenantProfile` that the settings page says is shown on the booking page, the current slug, the type, and `acceptingInquiries` from `studioTakesInquiries` in `#modules/artists/accepting`, which intake's `studio_not_accepting` uses too), `visibleArtists(tenant)` and `visibleArtist(tenant, slug)` (null for a hidden, deleted or unknown artist: the 404). `socialLinks` (`#modules/storefront/studio_page`) keeps only https links, in a fixed order. A closed message shows only while the artist is closed; a photo is `ImageService.shownImage` of the public `artist_photo` key: its URL, its size and its `variants` (smaller copies, TAT-112; `[]` for a photo with none), built from the key without I/O. The transformers write each field out: a new public field needs the contract, a ruling and the exact-fields tests. The studio's cover (TAT-116) is `Studio.cover`, an `Image` with `alt` always null (the name over it says what the page is), from the tenant row `publicTenant` already loaded: `getStudio` costs no new query. So is the page look (TAT-56), `Studio.storefront`: `{ theme, branding: { logo, colors: { accent, accentDark }, font }, sections: [{ type }] }`, built by `lookOf(tenant)` and the logo's `shownImage` (`alt` always null) and written field by field by the transformer: the theme key, the logo's public URL, size and copies, the two colours (null: the theme's own violet, and for dark a lighter shade of `accent`), the font key and the shown sections in order. A studio that set nothing gets the defaults (`stencil-and-ink`, no colours, `eczar`, artists then the form, no logo). Never the logo's key or columns. The enums say to treat an unknown value as the default, because the lists will grow (TAT-120). Each listed artist carries up to six `workPhotos` (`url`, `width`, `height`, `alt` or null, `variants`: no id, key, position or timestamp), read for the visible artists only in one more query (`WorkPhotoService.forArtists`): `listArtists` and `getArtist` cost two queries (one when no artist is visible), and a visible artist who is closed for inquiries still shows their work. Hidden and deleted artists' photos are in no answer (no endpoint lists photos on their own). Never in these answers: the tenant id (except inside a photo's or its copies' URL path), the deposit policy or percentage, payment methods, members, clients, inquiries, projects, quotes, payments, hidden or deleted artists.

## Rate limits

- Login and signup are rate-limited (TAT-8) with `@adonisjs/limiter`, whose counts live in Postgres (`rate_limits`; no Redis in V1; `config/limiter.ts`). Login: per client address, 10 attempts that don't sign in per 15 minutes; per email, from any address, 25 failures per 15 minutes (`throttleLogin` in `#modules/identity/services/auth_limits`, around `User.verifyCredentials`). Signup: 10 requests per address per hour (the `throttleSignup` middleware from `start/limiter.ts`), then 3 per typed email address per hour (`throttleSignupEmail`, TAT-18: `+tags` and dots are different addresses, so the real cap on mail to one mailbox is the 10 signups per client address per hour). Windows are fixed, and a lockout ends with its window: no extra block, nothing stored on the user, and the right password is refused too until then. A sign-in gives back only the two attempts it took, and only while their window is still open (a slow password check can end after the window did); failures already counted for the email stay (a sign-in proves the password, not who made the earlier guesses; since TAT-18 emails are canonical, so look-alike accounts no longer exist). The email limit is above twice the address limit, so one address can't lock an account. Any email is counted, registered or not, so a lockout reveals nothing about accounts. The per-email lockout is an accepted pilot cost (TAT-16): someone who knows an owner's sign-in email can keep that account out of sign-in until each window ends, and a completed password reset ends it early; the shared-address intake and write limits are accepted the same way. The owner-facing advice is in [deploy](deploy.md#accepted-denial-costs).
- Keys are `digest(…)` (HMAC-SHA256 with `APP_KEY`) of the lower-cased email or of `clientAddress(ip)` (IPv4, or the IPv6 /64), from `#services/rate_limits`, so the table holds no email or IP address. `request.ip()` trusts `X-Forwarded-For` only from a loopback peer (the framework default). Behind another proxy, set `TRUST_PROXY` ([deploy](deploy.md#public-api-production-checklist)). The store writes on the `limiter` connection (`config/database.ts`: the app role, a pool of at most 4 of its own), outside the request transaction, so a failed request's count survives the rollback. It must stay off the `pg` pool: the public deposit routes count inside a request that already holds a `pg` connection, and on a shared pool enough concurrent requests would each wait for a second connection and stall the app (a test holds every `pg` connection and counts anyway).
- A refused dashboard form goes back with the error toast "Too many attempts. Try again in N minutes." (`app/exceptions/handler.ts`, for every `E_TOO_MANY_REQUESTS`); a JSON request gets the limiter's 429 with `Retry-After`. The three account links a person opens from an email or a chat (`ACCOUNT_LINK_ROUTES` in `#services/rate_limits`: confirm email, reset password, invitation; TAT-119) are the exception, since a GET that only stages a token has no form to go back to and `back()` would end at `/`, whose redirect uses up the flash: over the limit they flash `LINK_THROTTLED_MESSAGE` ("Too many tries. Wait a few minutes and open the link again.", the same words for a live, expired or unknown token, no minutes) and redirect straight to the final page, `/login` for a guest and `/dashboard` for a signed-in person; every redirect on the way keeps the flash with `reflash()` (`DashboardController.show` and `tenantHome`, which end on Today or `/onboarding`, and `VerifiedEmailMiddleware`, which sends an unconfirmed account on to `/confirm-email`; the guest middleware does the same for `/dashboard`), where the layout shows it as a toast; a new redirect in that chain must reflash too, and `throttled_links.spec.ts` walks the chain for every state (no studio, unconfirmed with and without a studio, one studio, several, an artist member). Nothing of the link is staged. A new throttled GET link goes in that list. Adding a limit: put its numbers in `AUTH_LIMITS`, then use either a `limiter.define` middleware in `start/limiter.ts` (counts every request, unknown emails too; `perAddress`, `perEmail` and `perAccount` build the keys) or a wrapper like `throttleLogin` (counts failures). TAT-18's: 3 reset requests per typed email address (a `+tag` or dotted variant is another address; only registered ones are mailed) and 10 per client address an hour, 30 opens or uses of an account link per client address per 15 minutes, and one new confirmation link a minute and five an hour per account. A completed reset clears the login failures of the account's stored address (`clearLoginFailures`). Give `limiter.use()` a copy of the limits object, because it parses the durations in place. Never call `limiter.clear()` in app code: on Postgres it truncates the table, which the app role may not do.
- The deposit endpoints (TAT-65) count every request per client address and per link token, reads and uploads apart (`DEPOSIT_LIMITS` in `#modules/payments/deposit_limits`: GET 120 per address and 60 per token per 10 minutes, POST 20 and 10 per hour), in the `depositThrottle` middleware after `publicTenant`, with `limiter.multi` (the address first). Keys are digests of `clientAddress(ip)` and of the token. The upload route reads its body with `receiveUploads` after the link check (the body parser reads none itself), so a refused or dead-link upload never reaches the disk; the gate's per-caller count runs ahead of the tenant lookup (TAT-38); these per-address and per-token counts stay here.
- The public API (TAT-38): `PublicGateMiddleware` (first in `router.use`, API requests only) works out the caller with `callerOf(ctx)` (`#services/api_caller`): a request with a valid server key (`Authorization: Bearer`, one of `STOREFRONT_SERVER_KEYS`, compared as SHA-256 digests in constant time) is the hosted storefront's server and counts by its visitor (`X-Visitor-IP`: one public IP literal, else the storefront's one shared budget, with a warning at most every 10 minutes); anything else, an unknown key included (also warned about, never a 401), is anonymous and counts by `request.ip()`. The key grants nothing else; the dashboard never reads it. Budgets (`API_LIMITS`): 300 reads per 5 minutes and 60 writes per hour per caller, each kind apart; 3000 per 5 minutes shared by keyed calls without a visitor; per studio 6000 storefront reads and 1500 anonymous reads per 5 minutes (`apiLimit`). `request.ip()` believes `X-Forwarded-For` only from `TRUST_PROXY` (required in production). Keys are `digest(clientAddress(ip))` or a tenant id. Writes also take one of 4 write slots per process (2 per address) before their body (`#services/write_slots`): over is 503 `service_busy` or 429, `Retry-After: 10`. A slot is freed when the response closes or the connection does (a pipelined request queued behind another gets no socket, so its response never closes); a client that hung up while the gate counted its request takes none. Anything added to the gate that waits before the slot must keep that check right before `take()`, with no await after it. Upload bodies must arrive within 90 s (`receiveUploads`, 408 `request_timeout`; 120 s on the dashboard). A pool timeout (10 s, `#services/db_pool`) on the API is a logged 503 `service_busy`.
- The intake (TAT-55) counts per studio, in `INTAKE_LIMITS` (`#modules/inquiries/intake_limits`) with `countIntake`: 20 tries per client address and 60 passed challenges per studio an hour (the `intakeGuard` middleware, before the multipart body is read; the address first, so a refused address never reaches Cloudflare, and the studio only after a passed challenge, so no one can close a studio's form without solving challenges), and 10 validated tries per phone a day (the controller, before `IntakeService.submit`). Keys come from `intakeLimitKeys(tenantId, ip)` and `intakePhoneKey(tenantId, phone)`: digests of the tenant id with `clientAddress(ip)` or the E.164 phone, and the tenant id for the studio, so one studio's counts never touch another's and the table holds no address or number. Every attempt that reaches a count counts, later refusals included. The 3-open cap (`OPEN_INQUIRY_LIMIT`) is separate and checked in `submit` under the lock. An unknown or old slug is the 404 before any count; TAT-38's generic limits come on top.

## Images

- Images: the `media` module (`app/modules/media/`) owns uploads. Every upload field uses `imageFile()` (`#modules/media/validators/image_file`: 10 MB; jpg, jpeg, png, webp), and every upload is stored with `ImageService.store(file, { tenant, purpose })` (`#modules/media/services/image_service`), never written to a disk directly.
  - Processing: `store()` checks the real format by its first bytes, rejects images over 40 MP, applies the EXIF orientation, fits the image in 2048 px and re-encodes it with no metadata; anything else throws `InvalidImageError`, whose message is meant for the user (show it as a field error). Decoding is the costly part: at most `MAX_CONCURRENT_DECODES` (2) images decode at once per process (`limitConcurrency` in `#modules/media/concurrency`; the format sniff runs before the wait), and sharp's cache is off (TAT-51: the first anonymous uploads).
  - Purposes and keys: the purpose (`IMAGE_PURPOSES`) decides the disk: add one per new kind of image, public only if anyone may see it. The owning record keeps the returned key in a column (e.g. `qr_image_key`). Drive disks (`config/drive.ts`): `public` served at `/uploads`, `private` at `/files` (signed only). Files live in `storage/` in dev and `tmp/storage/` in tests (cleared each run); production moves to R2 (TAT-27).
  - Transactions: store the upload inside the `withTransaction` callback that saves the record, and register `afterRollback(() => images.delete(purpose, key))` right after `store()` resolves (no `await` in between), so a transaction that cannot open stores nothing and no failure can fall between the store and its cleanup; do it before any row lock in that callback. Delete a replaced key with `afterCommit`. The cost: outside a request, the image is processed with a transaction open. Soft-deleted records keep their files.
  - URLs: `url(purpose, key, tenant)` gives the public URL, or a 5-minute signed URL for a private purpose that answers with `Cache-Control: private, no-store` (signed in, so it can't be stripped): load the owning record scoped to the tenant first, which is the access check; `url` also refuses a key outside `tenants/<id>/<purpose>/` (TAT-66).
  - Copies (TAT-112): `IMAGE_PURPOSES` gives each purpose its visibility and its copies, `variants`. Artist photos and reference images get 320, 640 and 1280 px copies (only those narrower than the image, never enlarged); QR codes and payment screenshots keep one size (a QR must stay scannable and an owner reads small print on a screenshot). A new purpose picks its copies in `IMAGE_PURPOSES`.
  - Making them: in the request, from the cleaned image only, inside a decode slot and one width at a time (`makeVariants` in `#modules/media/services/image_processor`, one sharp source cloned per width; an input over 2048 x 2048 px is refused), in the image's format (JPEG at quality 80, a PNG stays PNG), with no metadata, then written beside the image on its disk. The key names them, so the owning record keeps one key and no query or disk read finds them: `<id>.jpg` has none (every key before TAT-112), `<id>.320-640-1280.jpg` has copies `<id>.320w.jpg`, `<id>.640w.jpg` and `<id>.1280w.jpg` (`#modules/media/variants`: `variantsOfKey`, `originalKey`; a copy's own key and any malformed key name none).
  - Failure and cleanup: if any copy cannot be made or written, the copies already written are deleted, a warning is logged and the image is stored under a key of the old form, so a key only ever names copies that exist; if the cleanup of those copies fails too, a copy stays on the disk under a key nothing names, and `storeVariants` logs it at error level with the purpose, the base and the stray keys (every file `delete` and `deleteOrThrow` remove includes the copies the purpose could have made for the key's base, so removing the image finds it, TAT-116); if the image's own write fails its copies are deleted before the error is thrown. The copies are written before the image, and nothing names them until the image is: a process killed in between leaves unreferenced copies that `delete()` cannot reach (it finds copies through the image's key). That needs an R2 lifecycle rule or a sweeper for objects without an original (TAT-27). The same sweep must cover the unreferenced files a failed best-effort delete leaves (the old files of a replaced image after the commit: `ImageService.delete` logs each failure with its purpose and key and counts it in `deleteFailures`, and never throws). `delete(purpose, key)` removes the image and every copy its key names, each best effort, so every caller's `afterRollback` and `afterCommit` cleanup covers the copies; ids are random, so a replaced image's copies never collide with the new image's.
  - Reading them: `variants(purpose, key, tenant)`, `urlFor(purpose, key, tenant, width)` and `shownImage(purpose, key, tenant, { width, height })` follow `url()`'s rules (the same key check; a private copy is signed for 5 minutes with `private, no-store`, never `getUrl`). `variants` is `[{ url, width }]` narrowest first, `urlFor` is the narrowest copy at least `width` wide else the image itself, `shownImage` is the shape of the contract's `Image` and `Photo`. Images stored before TAT-112 have no copies and work as before (no backfill; a re-upload gives them copies).
  - Limits: public copies carry no `Cache-Control` of their own (the drive's file server sends an ETag and `Last-Modified` only, so a browser revalidates each one; keys never change, so `max-age, immutable` is safe once TAT-27 or a CDN serves them). `THUMBNAIL_WIDTH` (320) is the one copy dashboard lists and grids show, with no `srcset`: soft on a 3x screen, accepted for a thumbnail that opens the full image.
  - Cover and work photos (TAT-116): two more public purposes with fixed names, never taken from a request. `studio_cover` has copies 640, 960, 1280 and 1600 px (`COVER_WIDTHS` in `#modules/media/variants`: a phone at 2x to 2.75x takes the 960 copy, a 4:3 photo at 3x the 1280 one, and a 16:9 photo, which the phone's 4:3 box enlarges until it is as tall as the box, needs about 1320 px at 3x, so the 1600 copy keeps it off the stored 2048 px image) and `artist_work_photo` has the photos' 320, 640 and 1280 px. Both go through `ImageService.store`, so the format sniff, the 40 MP limit and the metadata strip apply unchanged. Removal and freshness: removing a photo or the cover deletes its files first (`ImageService.deleteOrThrow`: the image, the copies its key names and every copy its purpose could have made for the same base name, a missing file counts as deleted, every file is tried even after one fails; the last set is for the fallback state below, where a key names no copy but one is on the disk) and only then the row, inside the transaction under the owner's lock; if any file cannot be deleted the request fails visibly ("Couldn't remove the photo, try again.", the row stays and is still listed, the retry finishes the job), so a photo a client asked to take down is never reported removed while its URL still answers. The files are really gone before the commit, so a later failure in the same request restores the row without them (a retry removes it). Replacing a cover is best effort: the old files are deleted after the commit by `ImageService.delete`, which tries every file and logs each failure at error level with its purpose and key (`deleteFailures` counts them for tests); a file that fails stays unreferenced until the orphan sweep of TAT-27. Once the files are gone nobody can fetch them; a studio page or API answer cached before can still name the old URL for up to about 12 minutes (the API's `max-age=60, stale-while-revalidate=600`, the page's `s-maxage=60, stale-while-revalidate=600`) and shows an empty box (the cover's dark placeholder, a photo's alt text) there, and a visitor's browser that already downloaded the file may keep its copy (the file server sends `Last-Modified` and no `Cache-Control`, so browsers may cache heuristically). TAT-27 must purge a deleted key from any CDN, or keep a short `max-age` on these two purposes, and sweep the unreferenced files a failed replacement cleanup leaves (it already owes a sweep for the orphan copies above). Measured first-screen cover bytes, a detailed (grainy) photo, cache off: at 375 x 812 a 16:9 cover is 16 KB at 1x (640w), 39 KB at 2x (960w) and 153 KB at 3x (1600w; it was 428 KB, the stored image, before the 1600 copy); a 4:3 cover is 20, 51 and 110 KB (1280w at 3x). At 1280 x 800 it is 82 to 110 KB at 1x (1280w), but a 2x screen needs 2292 px, more than any copy, and takes the stored 2048 px image (428 to 570 KB for a detailed photo): that is the cap on stored images, not a missing copy.
  - Studio logo (TAT-56): one more public purpose, `studio_logo`, with the photos' 320, 640 and 1280 px copies (`VARIANT_WIDTHS`), set and removed through `TenancyService.setLogo` and `removeLogo` exactly as the cover is (same ordering, same removal rule, same freshness note above). The image processor keeps a PNG a PNG, in its copies too, so only a PNG logo keeps a see-through background; a JPEG or WebP is flattened on white. An SVG is refused by its bytes.
  - Dashboard uploads are read by `WebMultipartMiddleware` (last in `router.use`, TAT-38): only for a signed-in user (a signed-out multipart body is a 415, never read), through `receiveUploads`, and every temp file goes at the end of the request. A multipart form sends its CSRF token in the `X-XSRF-TOKEN` header (Inertia does), never as a `_csrf` field: shield checks it before the body is read.
  - Public API uploads: a route reads its body itself with `receiveUploads(request)` and ends with `discardUploads(request)` (`#services/uploads`) in a `finally` (Public API section): `receiveUploads` records every temp path it allocates and every file handler still running, so `discardUploads` waits for those handlers and removes every path, whatever the part names or failures (a malformed or cut-off part after a good one, `junk` then `junk.extra`, `x.__proto__.y`).
  - Reference images: the private `reference_image` purpose (TAT-37) holds a client's reference images: load the owning inquiry or project scoped to the tenant first, then ask for the signed URL. The inquiry, project and client pages build each reference with `referenceView` (`#modules/inquiries/reference_view`): `url` (the full image, what a tap opens) and `thumbnailUrl` (the signed 320 px copy, or the image when it has none), both after the same scoped reads (TAT-112); TAT-109's Projects list calls `urlFor("reference_image", key, tenant, THUMBNAIL_WIDTH)`.

## Payments

- Payments: the `payments` module (`app/modules/payments/`) owns payment methods. Read and change them through `PaymentMethodService` (`#modules/payments/services/payment_method_service`): `list(tenant)`, `findFor(tenant, id)` (throws a 404 for an unknown, deleted or other tenant's id), `create`, `update`, `move` and `delete`. The rules for each kind (which details it needs, QR or not, deposit page or not) live in `checkPaymentMethod` (`#modules/payments/rules`). Validators check only the shape. The service throws `PaymentMethodRuleError`; controllers turn it into field errors. eSewa and Khalti wallet IDs are stored in `account_number`. The deposit page (TAT-65) shows `listForDepositPage(tenant)` (shown on the deposit page, never cash) and the tenant's `depositPolicy`. `Payment` (`#modules/payments/models/payment`, TAT-37) is the append-only ledger of money received; see Clients, inquiries and projects below.

- Deposit links and the deposit page (TAT-65): one `DepositLink` per project (`deposit_links`, tenant-owned, not soft-deleted: a credential replaced in place). The token (43 base64url characters) is `tokenFor(nonce)`, an HMAC of the row's random nonce with a key of its own (HKDF of `APP_KEY`, never the raw key that `digest()` uses); the row keeps the nonce and `token_hash` (SHA-256), which a request is looked up by, never the token, so the owner's page can show the link again (`DepositLinkService.forProject`) and rotating `APP_KEY` kills every link (`resolve` and `forProject` both need the nonce to still derive the stored hash). A link works for 30 days; "New link" replaces the token at once and keeps the 6-character reference code (`23456789ABCDEFGHJKMNPQRSTVWXYZ`, unique per tenant), which the client writes in the payment remark and which grants nothing. Owners make links (`DepositLinkService.issue`: deposit_pending, a live quote, a deposit not covered, a method on the deposit page). `DepositPageService.show` gives the page (`depositState` in `#modules/payments/deposit_page`: cancelled, paid, submitted, due or expired, updating) and `submitProof` takes one screenshot at a time: pre-check, `ImageService.store` with `payment_proof` and `afterRollback`, lock the project (`ProjectService.lockLive`), check again, then `DepositService.recordProof` inserts the `submitted` payment with its proof in one INSERT and `DepositProofAlertJob` is queued. Every dead link is `DepositPageNotFoundError` (the API's one 404). The link's URL is `STOREFRONT_URL` (`{tenant}` for the slug; checked at boot by `checkStorefrontUrl` in `#services/storefront_url`, required in production, the dev host in development with a warning on the owner's panel) plus `/deposit#<token>`: the token rides in the fragment. `DepositPageService.show` reads the quote before the project, so a revision that commits between the two reads gives `updating`, never `due` with the revised quote. Once the page is `paid` it also gives `nextSession` (TAT-110, `SessionService.nextScheduled`: the project's earliest live `scheduled` session that hasn't ended, of any kind; only its start and its own artist, named from the one artists read the page already makes, hidden profiles included, a deleted one `null`); every other state makes no session query, `cancelled` wins over `paid`, and the transformer sends the start as a UTC instant. The extra query is one on the `(tenant_id, project_id)` index, under the public request's RLS context. `DepositService` (this ticket's) also gives `remaining`, `pendingProof` and `lastDecisionRejected`. (`countPendingProofs`, the old Projects badge, is gone: TAT-107's Today counts screenshots through `depositStates`.) TAT-107 adds batch reads for many projects at once, one query each, all tenant-scoped: `DepositService.depositStates(tenant, projectIds, quotes)` (per project whether a deposit screenshot waits, since when (the oldest one's submitted time, `proofSince`) and whether the current quote's deposit is covered, by the pure `depositSettled(quote, payments)` in the ledger, which `isSettled` agrees with; a test pins that; it selects only the columns the rules read) and `DepositService.pendingProofProjects(tenant)` (a subquery of the project ids with a waiting screenshot, for `ProjectService.listActive` to nest), `DepositLinkService.statesFor(tenant, projectIds)` (per project with a link, when it was made, `updated_at`, and whether it still opens; never the token, nonce, hash or URL) and `ProjectService.listActive` (live projects: every non-closed one, plus, for owners only, a closed one that still holds a waiting deposit screenshot, because a client can withdraw while it waits and the money stays the owner's to decide; rows carry only the columns the waiting rules and Today's rows read).

- Artists: the `artists` module (`app/modules/artists/`) owns the public profiles of a tenant's artists. ## Clients, inquiries and projects

- Clients, inquiries and projects (TAT-37, data layer only): `app/modules/clients/` owns `Client` (one live client per normalized phone per tenant; `anonymized_at` is for the privacy deletion, TAT-42), `app/modules/inquiries/` owns `Inquiry` (a frozen record of what was submitted) and `ReferenceImage`, `app/modules/projects/` owns `TattooProject` and `Quote`, and `Payment` lives in `app/modules/payments/`. Projects and quotes go through the services in the next bullet; clients go through `ClientService` (the Clients bullet below), inquiries go through `InquiryService` (the Inquiries and Intake bullets below), and payments go through `DepositService` (TAT-65) and `PaymentService` (TAT-66), so touch those models only in tests and inside a tenant context. The allowed values are const arrays in the model files (`INQUIRY_STATUSES`, `SOURCE_CHANNELS`, `PROJECT_STATUSES`, `QUOTE_KINDS`, `PAYMENT_KINDS`, `PAYMENT_STATUSES`). Links between these tables are composite `(tenant_id, id)` foreign keys with `NO ACTION`. A project has no `inquiry` status (the inquiry is its own record) and its status moves are in `ProjectService` (the quote moves, TAT-64; the manual moves, TAT-46). Soft-deleting a client, inquiry or project does NOT cascade to its children yet, sessions included (only `Tenant.softDelete` does, across the whole tenant); TAT-42 (client deletion) defines those cascades, so do not call `softDelete()` on these models elsewhere before then (the dashboard never deletes a project: declined and withdrawn ones are Closed). The inquiry privacy scrub is one-shot: the contact snapshot and free text change only in the UPDATE that first sets `anonymized_at` (TAT-42 must scrub in that same update), and a decided payment's verifier becomes null only when the verifier's account is gone. A quote revision is a new row with the next `version`, the current quote is the project's highest version, time is whole minutes (`estimated_minutes`) and money is paisa. Quotes have no trigger: "history is never deleted" and "price, deposit and expiry never change after insert" are conventions that `QuoteService` keeps (it only inserts), and the only database protection is the `NO ACTION` key from a quote to its project. Quotes and payments have no `deleted_at`, so those of a soft-deleted project stay visible to direct queries: list them through a live project. `fixed_price`, `deposit_amount`, `hourly_rate` and `amount` are integer (int4) paisa, so one value tops out at 2,147,483,647 paisa (about NPR 21.47 million); a quote's hourly total (rate × minutes / 60) is not stored and is not capped by int4, and the largest possible one (about 7.7e16 paisa) is above `Number.MAX_SAFE_INTEGER` (about 9.0e15). Code that computes totals (`quoteTotal` in `#modules/projects/quotes` does, in bigint; TAT-66's balance due must too) must compute them in bigint, or in JavaScript numbers only after the validator caps the rate and the minutes so that rate × minutes stays below 2^53, and never in int4 arithmetic in SQL (the `quotes_deposit_within_total` check itself casts to bigint for this reason). That check rounds half away from zero (Postgres `round` on numeric), so a total computed in application code should round the same way (`Math.round` matches for positive values). Aggregates such as `sum(amount)` and `count(*)` return int8, which node-pg returns as a string, so parse them with `Number` or `BigInt` (`count(*)::int` is fine, but `sum(amount)::int` raises "integer out of range" once a total passes 2,147,483,647 paisa); TAT-65's balance due will hit this. A payment is never edited or deleted, except that its decision (status, verifier, decision time) is recorded once, `updated_at` moves, its proof can be cleared (privacy deletion, TAT-42) and its verifier becomes null when that user's account is deleted: a refund is a negative `refund` payment, a reversal of a mistaken verification is a `correction`, and a decided payment (`verified` or `rejected`) is final, so if a customer paid a different amount than shown, reject the payment and record a new one (it may reuse the proof key, so delete a proof file only when no other payment references its key). Balance due (the current quote's total minus verified payments) is computed, never stored (`balanceOf`, TAT-66). A `correction` names the payment it reverses (`corrects_payment_id`, same project, once).

## Scheduling

- Scheduling (TAT-36): `app/modules/scheduling/` owns `ProjectSession` (table `project_sessions`, not `sessions`: the database session store's default name) and `SessionService` (`#modules/scheduling/services/session_service`): `schedule`, `reschedule` (time only), `complete`, `markNoShow`, `cancel`, `settleBooking`, `findFor`, `listForProject`, `nextScheduled` (TAT-110: the paid deposit page's next session, one query), `nextScheduledFor` (the first scheduled session that has not started, any kind, of each of many projects, in one query: the Projects list's "Next session", TAT-109) and `listInRange` (the calendar's read: active sessions overlapping a half-open window, for one artist or all, written as the no-overlap constraint's own `tstzrange(starts_at, ends_at) &&` expression so its gist index serves one artist's window; no index was added for it). A session is `active` while it is `scheduled` or `completed` and not deleted: `active` is a stored generated column and the one definition of "blocks time", so never write it and use `where active` for anything that asks whether time is taken. `project_sessions_artist_no_overlap` (a gist exclusion on the artist and the half-open time range) settles every race; `schedule` and `reschedule` turn its SQLSTATE 23P01 into `SessionOverlapError`, and `SessionRuleError` carries a `reason` (`project_closed`, `not_scheduled`, `invalid_range`, TAT-85's `not_started`, `not_booked` and `project_finished`, and TAT-111's `touch_ups_only`). Controllers write their own messages. `completed`, `no_show` and `cancelled` are final; a mistake is a new session. Only `tattoo` sessions move the project: scheduling one moves `in_progress` to `booked` and, through `settleBooking`, `deposit_pending` to `booked` once a scheduled tattoo session exists and `DepositService.isSettled` is true (the current quote's deposit is 0, or verified deposits and the corrections of deposits reach it); an outcome on one moves a `booked` project to `in_progress` when the project has a completed tattoo session and no scheduled one (TAT-85: a second scheduled tattoo session keeps it `booked`, and cancelling or missing the next one once the work started puts it back), in `finish`, so every caller gets it. Whatever verifies or records a deposit (`PaymentService`, TAT-66) calls `settleBooking` afterwards, and so must whatever moves a project into `deposit_pending` (`ProjectService.acceptQuote` does; TAT-46's moves must too): a tattoo session held earlier is only re-checked when something calls it. Cancelling or no-showing the only tattoo session of a project whose work hasn't started leaves it `booked`, and the projects list flags "booked with no scheduled session" (TAT-46). Every write locks the project row `FOR UPDATE` first and then the session row, in that order. `DepositService` (payments module) reads the current quote through `QuoteService`. A session's artist can be any live artist of the tenant; the first session fills an empty project artist. Lucid reads nothing back after an insert or update, so the service `refresh()`es every session it returns and `status` and `active` are the database's; a session you create outside the service (a test factory) has neither until you `refresh()` it.
- Direct bookings (TAT-43): `BookingService` (`#modules/projects/services/booking_service`) books a walk-in, phone or DM client in one step. `bookableArtists(tenant, member)`: every live artist for an owner, only the live profile linked to them for an artist. `book(tenant, member, booking)` refuses any other artist (`BookingRuleError` `artist_unavailable`) and then, in one `withTransaction`, takes the client (`ClientService.findFor` for a found one, which the booking never changes; `client_unavailable` for an anonymized one; `ClientService.create` for a new one), creates a `booked` project with no inquiry, its artist set and `last_contacted_at` now, inserts the optional quick quote with `QuoteService.create` (version 1, deposit 0, valid through the session's day) and schedules one `tattoo` session through `SessionService.schedule`. An overlap (`SessionOverlapError`), a number taken meanwhile (`ClientRuleError` `phone_taken`) or another tenant's client (E_ROW_NOT_FOUND) rolls the whole booking back; `BookingsController` turns them into field errors (a 404 for the foreign client). The quick quote does not go through `issueQuote` and queues no `ExpireQuoteJob`: expiry only acts on `quoted`, `on_hold` and `deposit_pending`, which a booked project never returns to. From `booked` on (`BOOKED_STATUSES` in `#modules/projects/quotes`) the project page hides the quote's expiry, and a booked project's price can't change (quotes are locked from `booked`; a booking made without a price gets one once through `ProjectService.setPrice`, TAT-66). The page is `/t/:tenant/projects/new` (`?phone=` looks the number up in the tenant, only for a member who has an artist to book with; owners get the client's name, an artist gets `client.name: null` (TAT-16: the client list is the owners', so an artist learns only that the number is a client's, and keeps the `id` the form posts to book them), and the refusal for a number added meanwhile reads "This number now belongs to another client of the studio. Look the number up again to book them." for an artist, without the name or the lookup query; the success flash after booking still names the client, since the project is then the artist's) and posts to `/t/:tenant/projects`. Session times are the studio's: `localDateTime` (a time the clocks skip is null, one they pass twice is its first occurrence) and `sessionTimeText` in `#modules/scheduling/times`; the project page lists its sessions with them.
- Calendar (TAT-50): `CalendarService` (`#modules/scheduling/services/calendar_service`) `load(tenant, member, { artistId, from, to })` decides whose sessions a member sees and reads them with one query per module (`ArtistService.list`, `SessionService.listInRange`, `ProjectService.findManyFor`, `ClientService.findMany`). Owners see the whole studio, or one live artist with `artistId`; an artist member sees only the live profile linked to them (none: `scope` `unlinked`, an explanation on the page). Any other `artistId` is E_ROW_NOT_FOUND (a 404), compared with the artist list in memory so a malformed id never reaches the database; the controller makes a repeated `?artist=` a 404 too. A session's client and brief are shown only when the member may open its project (`findManyFor`, the `findFor` rule): an artist's session on a project assigned to someone else shows its time and kind only. Only active sessions show. - Session outcomes and moves (TAT-85): staff record a scheduled session's outcome and move it from the project page's Sessions card (`inertia/components/sessions_card.tsx`), through `POST /t/:tenant/sessions/:id/outcome` (`status`: `completed`, `no_show` or `cancelled`) and `POST /t/:tenant/sessions/:id/move` (`date`, `startTime`, `hours`) in the `/sessions` group (owners and artists; `ProjectSessionsController`). - Scheduling on a project (TAT-85): `POST /t/:tenant/projects/:id/sessions` (`tenant.projects.sessions.store`, the projects group; `sessionKind`, `sessionArtistId`, `date`, `startTime`, `hours`) adds a session to an existing project through `SessionService.scheduleFor(tenant, member, project, input)`, which shares `schedule`'s body: under the project's lock `mayChangeSession` for the new session (an artist only with their own profile on their own project; the controller first offers only `BookingService.bookableArtists`, else the field error on `sessionArtistId`), then `scheduleRefusal(status, kind)` (`#modules/scheduling/schedule_rules`: `reviewing` to `in_progress` take every kind, `healing_check` touch-ups only (`touch_ups_only`, TAT-111), `completed` is `project_finished`, `declined` and `cancelled` `project_closed`; `schedulableKinds` is the Sessions card's kind list), then the insert and, for a tattoo session, the booking rule in the same transaction (`in_progress` to `booked`; `deposit_pending` to `booked` through `moveToBooked` when the deposit is settled). - Projects and quotes (TAT-64): `app/modules/projects/` has two services, layered so that no class depends on itself through another module. `QuoteService` (`#modules/projects/services/quote_service`) depends on nothing outside the module: `current` (the highest version), `history` (newest first) and `create(trx, …)` (the next version, under the caller's project lock). `ProjectService` (`#modules/projects/services/project_service`) depends on it, `DepositService` and `SessionService`: `findFor(tenant, member, id)` (owners see every live project, an artist only those assigned to their own live artist profile, anyone else a 404), `findManyFor(tenant, member, ids)` (the same rule for many ids at once, no order: the calendar's project details, TAT-50), `issueQuote(tenant, project, input, baseQuoteId)` (allowed in `reviewing`, `quoted`, `on_hold`, `deposit_pending`; `baseQuoteId` is the quote the form showed, null for a first quote, and a mismatch with the current quote is refused so a stale form can't restore old terms; moves to `quoted`; queues `ExpireQuoteJob` in the same transaction, delayed to `expires_at`), `acceptQuote` (only `quoted`, only the current unexpired quote; moves to `deposit_pending`, then `settleBooking`) and `expireQuote` (what the job runs: cancels `quoted`, `on_hold` and unsettled `deposit_pending` projects and their scheduled sessions, but never one whose non-zero deposit was paid; anything else, including a revised quote's old job, is a no-op; a run before the expiry queues the job again for the rest of the time, and `SweepExpiredQuotesJob` catches a job that failed or never ran, see [jobs and email](jobs-and-email.md#jobs)). Nothing records who made the contact, and never the text, a link or a token.

## Reports

- Pilot metrics (TAT-70): the `reports` module (`app/modules/reports/`) has no table. `PilotMetricsService.forStudio(tenant, window, now?)` (`#modules/reports/services/pilot_metrics_service`) gathers `PilotFacts` from the owning modules: `InquiryService.countReceived` and `receivedAt`, `ProjectService.countBookedAtDesk` and `inquiryIdsFor`, `DepositService.firstVerifiedDeposits` (per project, the first `verified` deposit no correction reverses, from the deposit page or the desk) and `SessionService.countByStatus`; a window may reach past `now` (a calendar month): `noOutcome` counts only scheduled sessions that started before `now`, through a second, narrower `countByStatus` read made only then. `#modules/reports/pilot_metrics` holds the arithmetic and the words (`linkShare`, `median`, `noShowRate`, `durationText`, `pilotCard`, `pilotLines`); windows are rolling instants (`lastDays`), so no time zone is involved. Today (owners only, `TodayController`, TAT-107) renders `pilotCard(…, CARD_DAYS)` as `pilotMetrics`; it used to sit on the Inbox. `node ace metrics:pilot [--days=42]` (`commands/pilot_metrics.ts`) prints every live studio's block and one for all studios; see Cross-tenant reads above for its one owner-role query. It prints each studio's name and slug through `terminalText` (`#services/terminal_text`): a studio owner chooses the name, so control characters (escapes, CR, LF, TAB, DEL, C1, line and paragraph separators, bidi overrides) are shown as `\xNN` or `\u{NNNN}` and never reach the operator's terminal as themselves; letters of any script stay. Use it for any other command that prints text a tenant typed. TAT-76's reports extend the service.

## Accounts

- Email addresses (TAT-18): `canonicalEmail` (`#modules/identity/email_address`) is the one form an address is stored and looked up in: spaces (U+0020) removed at both ends and the ASCII letters A to Z in lower case, nothing else (dots, `+tags`, other whitespace and other scripts stay). That is exactly what the `users_email_canonical` check computes (`translate(btrim(email), …)`); the validator's `trim()` cleans other typed whitespace before it, and `typedEmail` does both for a raw value (the rate-limit keys use it). The `accountEmail()` rule in `#validators/user` applies it to signup, login and the reset request, the `User` model's `beforeSave` hook to every write, and the check to the table, so `users_email_unique` means one account per address whatever its ASCII case. Never use Vine's `normalizeEmail()` for accounts. ASCII-only on purpose, and two consequences are accepted: an address whose non-ASCII letters differ in case (`Éva@…`, `bob@Éxample.com`, an internationalised domain) is a different account from its lower-case twin, and `+tags` and Gmail dots are different addresses.
- Account links (TAT-18): `AccountTokenService` (`#modules/identity/services/account_token_service`) owns `account_tokens`: one live token per account and purpose (`verify_email` for 24 hours, `reset_password` for 60 minutes), stored as its SHA-256 only, bound to the address it was sent to, replaced by the next one and deleted when used (`consume`, one `delete … returning`). The emailed link (`/verify-email/<token>`, `/reset-password/<token>`) only puts the token in the session (`SESSION_TOKEN_KEYS`) and redirects to a page without it (`Referrer-Policy: no-referrer`, `Cache-Control: no-store`); the change is that page's POST, so a mail scanner that opens links changes nothing. Never put a token in a page's URL, its props or a log. A link's page renders the token row's id, which is not a secret, in a hidden `flow` field and its POST must send it back (`consume` matches `id` too), so a form acts only on the link it showed, not on another one staged in the same session since (two tabs); a missing or foreign id is a dead link. An invitation's page renders the same kind of id derived from the stored token hash instead (`invitationFlowId`), because the invitation's row, and so its id, survives a replacement or renewal; the rendered-link invariant is the same: the POST's flow must be the one of the very link that is staged. Sign-in and sign-out forget the staged tokens (`forgetStagedTokens`), since regenerating the session keeps its data. `AccountService` takes its locks in one order, the reset token's row, the confirmation token's row, then the user's (comment on the class): keep it when adding a method.
- `AccountService` (`#modules/identity/services/account_service`) has the flows. `signUp` never says whether an address has an account: a new one gets an unconfirmed account and a confirmation email, a taken one an "already have an account" email with a reset link, and nobody is signed in. `requestPasswordReset` emails only an address an account uses; the page says the same either way (the found path adds a token upsert, one template render and a queue insert to the unknown one's single select: accepted, with 3 requests per address per hour). `resetPassword` sets the password (signup's rule), raises `session_version`, confirms the address, emails a notice and clears the stored address's login failures after the commit; it signs nobody in. `confirmEmail` confirms the account the link was sent to, whoever is signed in. Account emails print nothing the signup form took (no name). Accepted for the pilot, a carry-forward: signing up and then signing in tells whether an address already had an account (a new address's account takes the typed password and signs in, a taken one answers invalid credentials), because accounts that exist today must keep signing in unconfirmed (ruling 18); it costs one signup, which emails the probed address and is limited to 10 per client address per hour. The strict fix is to refuse sign-in for accounts created after TAT-18 until confirmed (a column set false for the rows that exist at migration time) with a resend from the login page, ideally once TAT-20 gives reliable mail, or a pending-signup table. Related: someone who signs up with another person's address can have them click "Confirm" on an email they didn't ask for, which confirms an account whose password the signer chose (ruling 16).
- Sessions (TAT-18): the session stores `<user id>.<session version>` (`SessionVersionUserProvider` in `#modules/identity/session_user_provider`, used by `config/auth.ts`), and a session whose version isn't the account's is signed out on its next request. Anything that should end every session of an account (a password change, a later "sign out everywhere") raises `users.session_version`.
- The confirmed-email gate (TAT-18): `middleware.verifiedEmail()`, after `auth`, sends an account whose address isn't confirmed to `/confirm-email`. It guards `/onboarding`; `POST /invitations` (TAT-33) uses it too, and `tests/functional/identity/account_routes.spec.ts` lists the gated routes. Unconfirmed accounts keep every page of the tenants they already belong to; `TenancyService.createTenant` itself isn't gated. The shared `user` prop has `emailVerified` (the confirmation bar).
- The front door and form messages (TAT-100): `/` has no page of its own. It redirects a signed-in user to `/dashboard` (which picks their studio) and anyone else to `/login` (`start/routes.ts`, named `home`, which the wordmark links to); the AdonisJS starter page is gone. The account forms (signup, login, both reset steps) share one VineJS messages provider, `accountMessages` in `#validators/account_messages`, attached in `#validators/user`. Its keys are `field.rule` (VineJS rule names) with short, kind sentences that say what to do and name no field ("Enter your email.", "Use 8 to 32 characters.", "Type the same password again."), so a Nepali file can mirror it key for key; the fallback text still writes the field the way the page labels it. A new field or rule on these forms needs its key there: `tests/unit/validators/account_messages.spec.ts` sweeps odd bodies and fails on any message with a field name or validator wording. The confirmation box only has to match the password (`sameAs`), so a short password gets one message, not two. The name is optional on the form, and a blank one is `null`.
- Operator confirmation: `node ace account:verify <email>` (`node build/ace.js …` in production) confirms an existing account's address without a link, after you checked the person yourself; it prints no token, id or link. It is the pilot's way in until the sending domain exists ([deploy](deploy.md#account-email)).
