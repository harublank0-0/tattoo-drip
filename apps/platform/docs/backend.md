# Backend conventions

Read the relevant section before changing backend behavior. For module boundaries or tenancy design, consult [architecture](../../../docs/architecture.md); for schema changes read [database conventions](../database/README.md) and the relevant [data-model](../../../docs/data-model.md) section. Those contain the canonical schema rules.


## Layout

- `app/controllers`, `app/models`, `app/validators`, `app/transformers`, `app/middleware`, `app/exceptions`
- `app/modules/<module>/`: one folder per backend module from [architecture](../../../docs/architecture.md), owning its `models/`, `services/`, `controllers/`, `validators/` and `emails/`. Import with `#modules/*`. New module code goes here; code still in the flat `app/*` folders moves when its module is built. Controllers and transformers stay in `app/controllers` and `app/transformers` for now: `indexEntities` in `adonisrc.ts` only scans those folders to generate `#generated/*`, so it has to be pointed at the module folders first.
- `start/routes.ts` (routes reference controllers through `#generated/controllers`), `start/kernel.ts` (middleware), `start/env.ts`
- `config/`, `database/migrations/`
- `inertia/pages`, `inertia/layouts`, `inertia/components` (shadcn components in `inertia/components/ui`), `inertia/hooks`, `inertia/css/app.css` (Tailwind entry and theme tokens)
- `tests/unit`, `tests/functional`, `tests/browser` (suites are defined in `adonisrc.ts`)

Import with the subpath aliases from `package.json` (`#controllers/*`, `#models/*`, `#services/*`, `#validators/*`, …), never with long relative paths.

## Dependency injection and module boundaries

- Controllers and services that use `@inject()` must import their dependencies as values, not `import type`: the container reads the class from decorator metadata at runtime. Biome's `useImportType` fix gets this wrong, so mark those imports with `// biome-ignore lint/style/useImportType: @inject() reads the class at runtime`.
- Each backend module owns its models and services; other modules call its services instead of querying its tables. Inertia controllers, API controllers and jobs stay thin and call the same services. See the module table in [architecture](../../../docs/architecture.md).

## API contract and migrations

- The REST API implements the contract in [OpenAPI contract](../../../packages/types/openapi.yaml). Change the contract first, regenerate the types, then implement.
- `database/schema.ts` and `.adonisjs/` are generated. Change the schema with a new migration, never by editing an existing migration that has been run.
- Read [database conventions](../database/README.md) before writing a migration; it owns the UUIDv7, timestamp, ownership, indexing and soft-delete rules.

## Soft deletes

- Soft delete: models of business records use `compose(XSchema, withSoftDeletes)` from `#models/mixins/soft_deletes`. Delete with `record.softDelete(trx?)`, undo with `restore()`; model queries skip deleted rows unless they start from `Model.withTrashed()` or `Model.onlyTrashed()`. The hooks don't reach `whereHas` subqueries or raw `db.from(...)` queries, so add `whereNull("<table>.deleted_at")` there. The hooks append `deleted_at IS NULL` to the end of the query, so a top-level `.orWhere(...)` would let deleted rows through (`a OR (b AND deleted_at IS NULL)`): group your own conditions in `.where((q) => q.where(a).orWhere(b))`. Update queries skip the hooks too; filter `deleted_at` yourself there. Soft-deleting a parent soft-deletes its children in the same transaction (the database's `ON DELETE CASCADE` only covers real purges).

## Tenancy and route access

- The tenant always comes from the URL (`/t/:slug/…` for the dashboard, `/api/v1/tenants/:slug/…` for the API). Services scope every query by tenant; never trust a tenant ID from a request body. Every tenant-owned endpoint needs a test proving tenant A can't reach tenant B's data.
- Tenancy: the `tenancy` module (`app/modules/tenancy/`) owns tenants and memberships. Other modules read them through `TenancyService` (`#modules/tenancy/services/tenancy_service`): `createTenant`, `tenantsFor`, `hasTenant` (one cheap yes/no query), and `assertKeepsAnOwner`, which every remove or demote of a member must call inside its transaction. New users create their first tenant at `/onboarding` (only while they have none: one tenant per account for now). Login, signup and onboarding land on `/dashboard`, which redirects to the tenant the user opened last, else their oldest, else `/onboarding`. Login and logout forget the last tenant (`LAST_TENANT_KEY`), so a shared browser doesn't carry it over. `createTenant` also gives an independent artist their own artist profile (`ArtistService.createOwnerProfile`) in the same transaction; a studio gets none. Soft-deleting a tenant (`tenant.softDelete(trx?)`) also soft-deletes its live memberships, payment methods, artists, clients, inquiries, projects and reference images (quotes and payments have no `deleted_at` and stay).
- Tenant pages live in the `/t/:tenant` route group with `[middleware.auth(), middleware.dbContext(), middleware.tenant()]`. The tenant middleware calls `TenancyService.membershipFor(user, slug)` on every request (never cache it) and turns `null` into the same 404 as an unknown URL, never a 403, so a URL doesn't reveal that a tenant exists. Every tenant route goes in that group; a test fails for a `/t/:tenant` route without the middleware. Read the result with `tenantContext(ctx)` from `#middleware/tenant_middleware`, which returns `{ tenant, membership }` and throws outside the group (`ctx.tenant` is optional for that reason; the role is `membership.role`). Limit a route to some roles with `middleware.role({ allow: ["owner"] })` after `tenant()`: other members get the same 404. Studio settings (`/t/:tenant/settings/…`) and the artists area (`/t/:tenant/artists/…`) are owners only. They go in their nested groups, and a test fails for a route in either area without the role check. `:id` route params use `.where("id", router.matchers.uuid())`, so a malformed id is a 404 rather than a database error. Controllers pass the tenant to services explicitly; never read a tenant id from the body, query string or headers, and keep `tenant_id` out of validators. Every page gets the `tenant` and `tenants` props from `InertiaMiddleware.share()`; nav items for tenant pages pass `params: { tenant: slug }`.
- Database context: every authenticated request runs in one transaction (the `dbContext` middleware, right after `auth`) with `app.user_id` set, and the tenant middleware adds `app.tenant_id` (`setRequestContext`, which only the outermost level may call). Row-level security reads them, so a query outside that transaction sees no tenant rows. Nested work uses `withTransaction` from `#services/db_context`, never `db.transaction`: inside a request it is a savepoint, so a caught unique violation leaves the request usable. `withDbContext({ tenantId }, fn)` runs `fn` as a tenant (jobs, tests, `createTenant`). The database settings belong to the connection, so overlapping `withDbContext` calls under one parent throw: await one before starting the next (`Promise.all` over `withDbContext`, or over the tests' `inTenant`, throws; plain `withTransaction` siblings are fine). A plain query made while a child context is open sees that context's settings, so don't mix them in a fan-out. Model queries, preloads and relations join the request transaction automatically; raw `db.from()` and `db.rawQuery()` do not, so use `dbClient()`. Tests will not reveal a query that escapes the request transaction on its own (the request is a savepoint on the test's single connection), which is why a tripwire fails the test run and Biome forbids importing the db service under `app/`. A failed request is rolled back by the exception handler, so a handler must throw to fail a request: one that returns a status of 400 or more without throwing still commits its writes. Never catch a database error outside `withTransaction`: after a failed statement the request transaction is aborted, and committing it silently rolls everything back (the response still says success). Work outside the database (deleting a file, sending an email) goes in `afterCommit` / `afterRollback`, never right after `withTransaction` returns: inside a request that is only a savepoint. Details: [database conventions](../database/README.md#row-level-security).

## Images

- Images: the `media` module (`app/modules/media/`) owns uploads. Every upload field uses `imageFile()` (`#modules/media/validators/image_file`: 10 MB; jpg, jpeg, png, webp), and every upload is stored with `ImageService.store(file, { tenant, purpose })` (`#modules/media/services/image_service`), never written to a disk directly. `store()` checks the real format by its first bytes, rejects images over 40 MP, applies the EXIF orientation, fits the image in 2048 px and re-encodes it with no metadata; anything else throws `InvalidImageError`, whose message is meant for the user (show it as a field error). The purpose (`IMAGE_PURPOSES`) decides the disk: add one per new kind of image, public only if anyone may see it. The owning record keeps the returned key in a column (e.g. `qr_image_key`). Store the upload inside the `withTransaction` callback that saves the record, and register `afterRollback(() => images.delete(purpose, key))` right after `store()` resolves (no `await` in between), so a transaction that cannot open stores nothing and no failure can fall between the store and its cleanup; do it before any row lock in that callback. Delete a replaced key with `afterCommit`. The cost: outside a request, the image is processed with a transaction open. Soft-deleted records keep their files. `url(purpose, key)` gives the public URL, or a 5-minute signed URL for a private purpose: load the owning record scoped to the tenant first, which is the access check. Drive disks (`config/drive.ts`): `public` served at `/uploads`, `private` at `/files` (signed only). Files live in `storage/` in dev and `tmp/storage/` in tests (cleared each run); production moves to R2 (TAT-27). The private `reference_image` purpose (TAT-37) holds a client's reference images: load the owning inquiry or project scoped to the tenant first, then ask for the signed URL.

## Payments

- Payments: the `payments` module (`app/modules/payments/`) owns payment methods. Read and change them through `PaymentMethodService` (`#modules/payments/services/payment_method_service`): `list(tenant)`, `findFor(tenant, id)` (throws a 404 for an unknown, deleted or other tenant's id), `create`, `update`, `move` and `delete`. The rules for each kind (which details it needs, QR or not, deposit page or not) live in `checkPaymentMethod` (`#modules/payments/rules`). Validators check only the shape. The service throws `PaymentMethodRuleError`; controllers turn it into field errors. eSewa and Khalti wallet IDs are stored in `account_number`. The deposit page (TAT-65) shows `list(tenant)` filtered to `showOnDepositPage`, with the tenant's `defaultDepositPercent` and `depositPolicy`. `Payment` (`#modules/payments/models/payment`, TAT-37) is the append-only ledger of money received; see Clients, inquiries and projects below.

## Artists

- Artists: the `artists` module (`app/modules/artists/`) owns the public profiles of a tenant's artists. Read and change them through `ArtistService` (`#modules/artists/services/artist_service`): `list(tenant)` (by name), `findFor(tenant, id)` (a 404 for an unknown, deleted or other tenant's id), `create`, `update`, `delete` (soft) and `createOwnerProfile`. `create` and `update` take the signed-in member: `linkToMe` links the profile to them, never takes over a profile that is linked to someone else, and unchecking it unlinks only them, so a profile is only ever linked to a proven member (TAT-33's claim path adds its own check before linking anyone else). They throw `ArtistSlugTakenError` or `ArtistProfileExistsError` after rolling back their own savepoint; the controller turns them into field errors. A slug is unique among a tenant's live artists, so a deleted profile frees it. The photo is the `artist_photo` image purpose (public) with the usual `store` / `afterRollback` / `afterCommit` lifecycle. `user_id` is optional and `ON DELETE SET NULL`: deleting an account keeps the public profile, and TAT-33 must unlink, not delete, a removed member's profile. The dashboard area is owners only for now; TAT-30 opens it to artists by changing the allow list. Public reads (visible profiles only) are TAT-44.

## Clients, inquiries and projects

- Clients, inquiries and projects (TAT-37, data layer only): `app/modules/clients/` owns `Client` (one live client per normalized phone per tenant; `anonymized_at` is for the privacy deletion, TAT-42), `app/modules/inquiries/` owns `Inquiry` (a frozen record of what was submitted) and `ReferenceImage`, `app/modules/projects/` owns `TattooProject` and `Quote`, and `Payment` lives in `app/modules/payments/`. There are no services yet: TAT-51 (intake and client matching), TAT-46 (inbox and lifecycle), TAT-64 (quotes) and TAT-65 (deposit page and proofs) add them, so until then touch these models only in tests and inside a tenant context. The allowed values are const arrays in the model files (`INQUIRY_STATUSES`, `SOURCE_CHANNELS`, `PROJECT_STATUSES`, `QUOTE_KINDS`, `PAYMENT_KINDS`, `PAYMENT_STATUSES`). Links between these tables are composite `(tenant_id, id)` foreign keys with `NO ACTION`. A project has no `inquiry` status (the inquiry is its own record) and its transition rules are TAT-46's. Soft-deleting a client, inquiry or project does NOT cascade to its children yet (only `Tenant.softDelete` does, across the whole tenant); TAT-42 (client deletion) and TAT-46 (project lifecycle) define those cascades, so do not call `softDelete()` on these models elsewhere before then. The inquiry privacy scrub is one-shot: the contact snapshot and free text change only in the UPDATE that first sets `anonymized_at` (TAT-42 must scrub in that same update), and a decided payment's verifier becomes null only when the verifier's account is gone. A quote revision is a new row with the next `version`, the current quote is the project's highest version, time is whole minutes (`estimated_minutes`) and money is paisa. Quotes have no trigger: "history is never deleted" and "price, deposit and expiry never change after insert" are conventions for TAT-64 to keep, and the only database protection is the `NO ACTION` key from a quote to its project. Quotes and payments have no `deleted_at`, so those of a soft-deleted project stay visible to direct queries: list them through a live project. `fixed_price`, `deposit_amount`, `hourly_rate` and `amount` are integer (int4) paisa, so one value tops out at 2,147,483,647 paisa (about NPR 21.47 million); a quote's hourly total (rate × minutes / 60) is not stored and is not capped by int4, and the largest possible one (about 7.7e16 paisa) is above `Number.MAX_SAFE_INTEGER` (about 9.0e15). Code that computes totals (TAT-64, balance due) must compute them in bigint, or in JavaScript numbers only after the validator caps the rate and the minutes so that rate × minutes stays below 2^53, and never in int4 arithmetic in SQL (the `quotes_deposit_within_total` check itself casts to bigint for this reason). That check rounds half away from zero (Postgres `round` on numeric), so a total computed in application code should round the same way (`Math.round` matches for positive values). Aggregates such as `sum(amount)` and `count(*)` return int8, which node-pg returns as a string, so parse them with `Number` or `BigInt` (`count(*)::int` is fine, but `sum(amount)::int` raises "integer out of range" once a total passes 2,147,483,647 paisa); TAT-65's balance due will hit this. A payment is never edited or deleted, except that its decision (status, verifier, decision time) is recorded once, `updated_at` moves, its proof can be cleared (privacy deletion, TAT-42) and its verifier becomes null when that user's account is deleted: a refund is a negative `refund` payment, a reversal of a mistaken verification is a `correction`, and a decided payment (`verified` or `rejected`) is final, so if a customer paid a different amount than shown, reject the payment and record a new one (it may reuse the proof key, so delete a proof file only when no other payment references its key). Balance due (the current quote's total minus verified payments) is computed, never stored.

## Phone numbers

- Phone numbers: validate with `phoneNumber()` from `#validators/phone`, which stores E.164 (+977 when no country code is given).
