# Backend conventions

Read the relevant section before changing backend behavior. For module boundaries or tenancy design, consult [architecture](../../../docs/architecture.md); for schema changes read [database conventions](../database/README.md) and the relevant [data-model](../../../docs/data-model.md) section. Those contain the canonical schema rules.


## Layout

- `app/controllers`, `app/models`, `app/validators`, `app/transformers`, `app/middleware`, `app/exceptions`
- `app/modules/<module>/`: one folder per backend module from [architecture](../../../docs/architecture.md), owning its `models/`, `services/`, `controllers/`, `validators/` and `emails/`. Import with `#modules/*`. New module code goes here; code still in the flat `app/*` folders moves when its module is built. Controllers and transformers stay in `app/controllers` and `app/transformers` for now: `indexEntities` in `adonisrc.ts` only scans those folders to generate `#generated/*`, so it has to be pointed at the module folders first.
- `start/routes.ts` (routes reference controllers through `#generated/controllers`), `start/kernel.ts` (middleware), `start/env.ts`
- `config/`, `database/migrations/`
- `inertia/pages`, `inertia/layouts`, `inertia/components` (shadcn components in `inertia/components/ui`), `inertia/hooks`, `inertia/css/app.css` (Tailwind entry and theme tokens)
- `tests/unit`, `tests/functional`, `tests/browser` (suites are defined in `adonisrc.ts`)

Import with the subpath aliases from `package.json` (`#controllers/*`, `#models/*`, `#services/*`, `#validators/*`, …), never with long relative paths.

## Dependency injection and module boundaries

- Controllers and services that use `@inject()` must import their dependencies as values, not `import type`: the container reads the class from decorator metadata at runtime. Biome's `useImportType` fix gets this wrong, so mark those imports with `// biome-ignore lint/style/useImportType: @inject() reads the class at runtime`.
- Each backend module owns its models and services; other modules call its services instead of querying its tables. Inertia controllers, API controllers and jobs stay thin and call the same services. See the module table in [architecture](../../../docs/architecture.md).

## API contract and migrations

- The REST API implements the contract in [OpenAPI contract](../../../packages/types/openapi.yaml). Change the contract first, regenerate the types, then implement.
- `database/schema.ts` and `.adonisjs/` are generated. Change the schema with a new migration, never by editing an existing migration that has been run.
- Read [database conventions](../database/README.md) before writing a migration; it owns the UUIDv7, timestamp, ownership, indexing and soft-delete rules.

## Soft deletes

- Soft delete: models of business records use `compose(XSchema, withSoftDeletes)` from `#models/mixins/soft_deletes`. Delete with `record.softDelete(trx?)`, undo with `restore()`; model queries skip deleted rows unless they start from `Model.withTrashed()` or `Model.onlyTrashed()`. The hooks don't reach `whereHas` subqueries or raw `db.from(...)` queries, so add `whereNull("<table>.deleted_at")` there. The hooks append `deleted_at IS NULL` to the end of the query, so a top-level `.orWhere(...)` would let deleted rows through (`a OR (b AND deleted_at IS NULL)`): group your own conditions in `.where((q) => q.where(a).orWhere(b))`. Update queries skip the hooks too; filter `deleted_at` yourself there. Soft-deleting a parent soft-deletes its children in the same transaction (the database's `ON DELETE CASCADE` only covers real purges).

## Tenancy and route access

- The tenant always comes from the URL (`/t/:slug/…` for the dashboard, `/api/v1/tenants/:slug/…` for the API). Services scope every query by tenant; never trust a tenant ID from a request body. Every tenant-owned endpoint needs a test proving tenant A can't reach tenant B's data.
- Tenancy: the `tenancy` module (`app/modules/tenancy/`) owns tenants and memberships. Other modules read them through `TenancyService` (`#modules/tenancy/services/tenancy_service`): `createTenant`, `tenantsFor`, `hasTenant` (one cheap yes/no query), and `assertKeepsAnOwner`, which every remove or demote of a member must call inside its transaction. New users create their first tenant at `/onboarding` (only while they have none: one tenant per account for now). Login, signup and onboarding land on `/dashboard`, which redirects to the tenant the user opened last, else their oldest, else `/onboarding`; a tenant's own address (`/t/:tenant`) then redirects owners to the Inbox and artists to Projects. Login and logout forget the last tenant (`LAST_TENANT_KEY`), so a shared browser doesn't carry it over. `createTenant` also gives an independent artist their own artist profile (`ArtistService.createOwnerProfile`) in the same transaction; a studio gets none. Soft-deleting a tenant (`tenant.softDelete(trx?)`) also soft-deletes its live memberships, payment methods, artists, clients, inquiries, projects, reference images and sessions (quotes and payments have no `deleted_at` and stay).
- Tenant pages live in the `/t/:tenant` route group with `[middleware.auth(), middleware.dbContext(), middleware.tenant()]`. The tenant middleware calls `TenancyService.membershipFor(user, slug)` on every request (never cache it) and turns `null` into the same 404 as an unknown URL (after redirecting a GET or HEAD on an old slug of the user's tenant, see the Slugs bullet below), never a 403, so a URL doesn't reveal that a tenant exists. Every tenant route goes in that group; a test fails for a `/t/:tenant` route without the middleware. Read the result with `tenantContext(ctx)` from `#middleware/tenant_middleware`, which returns `{ tenant, membership }` and throws outside the group (`ctx.tenant` is optional for that reason; the role is `membership.role`). Limit a route to some roles with `middleware.role({ allow: ["owner"] })` after `tenant()`: other members get the same 404. Studio settings (`/t/:tenant/settings/…`) and the artists area (`/t/:tenant/artists/…`) are owners only. They go in their nested groups, and a test fails for a route in either area without the role check. `:id` route params use `.where("id", router.matchers.uuid())`, so a malformed id is a 404 rather than a database error. Controllers pass the tenant to services explicitly; never read a tenant id from the body, query string or headers, and keep `tenant_id` out of validators. Every page gets the `tenant` and `tenants` props from `InertiaMiddleware.share()`; nav items for tenant pages pass `params: { tenant: slug }`.
- Slugs (TAT-24): `checkSlug(input)` in `#modules/tenancy/slugs` is the one rule for a new tenant slug: ASCII letters, digits and hyphens only (Unicode is refused, never case-folded), lowercased, 3 to 63 characters, no hyphen at either end, no `--` (so no `xn--` punycode), at least one letter, not in `RESERVED_SLUGS` and not containing `tattoodrip`. It does not trim; the `tenantSlug()` Vine rule in the tenancy validators trims and wraps it for `createTenantValidator` and `changeSlugValidator`. Never copy the reserved list or `STORED_SLUG`. `checkSlug` is for slugs someone chooses only: a slug taken from a path is pre-filtered with `STORED_SLUG` (the shape `tenant_slugs_slug_format` enforces), because legacy slugs such as `12345`, `a--b` or `www` stay valid and reachable. Existing slugs are kept as they are. Every slug a tenant has held, its current one included, is a row of `tenant_slugs`, written by the `tenants_register_slug` trigger, never by app code; its unique index keeps a slug from ever reaching another tenant (see [database conventions](../database/README.md#row-level-security)). `TenancyService.changeSlug(tenant, slug)` (owners, Settings → Web address, `PUT /t/:tenant/settings/slug`) locks the tenant row, allows `MAX_TENANT_SLUGS` (5) slugs in total (switching back to an own old slug is allowed if it still passes `checkSlug`; a kept slug that fails the rules, such as `a--b` or `www`, keeps redirecting but cannot be chosen again, so a reserved name never comes back) and throws `SlugTakenError` or `SlugLimitError` after its savepoint rolls back; `createTenant` maps both slug indexes to `SlugTakenError`. `currentSlugFor(user, slug)` resolves an old slug for a live member; the tenant middleware uses it to send GET and HEAD to the same path and query under the current slug (`withTenantSlug`) with a 302, never a 301 (a studio can switch back). The redirect turns the app's query-string forwarding off (`withQs(false)`) because the URL it builds already has the query. Writes on an old slug are a 404. Lookups match exactly: never case-fold a path parameter. The public API resolves slugs through `tenant_slugs` too: `STORED_SLUG` pre-filters a path slug (never `checkSlug`), then an exact lookup (see [Public API](#public-api)).
- Database context: every authenticated request runs in one transaction (the `dbContext` middleware, right after `auth`) with `app.user_id` set, and the tenant middleware adds `app.tenant_id` (`setRequestContext`, which only the outermost level may call). Row-level security reads them, so a query outside that transaction sees no tenant rows. Nested work uses `withTransaction` from `#services/db_context`, never `db.transaction`: inside a request it is a savepoint, so a caught unique violation leaves the request usable. `withDbContext({ tenantId }, fn)` runs `fn` as a tenant (jobs, tests, `createTenant`). The database settings belong to the connection, so overlapping `withDbContext` calls under one parent throw: await one before starting the next (`Promise.all` over `withDbContext`, or over the tests' `inTenant`, throws; plain `withTransaction` siblings are fine). A plain query made while a child context is open sees that context's settings, so don't mix them in a fan-out. Model queries, preloads and relations join the request transaction automatically; raw `db.from()` and `db.rawQuery()` do not, so use `dbClient()`. Tests will not reveal a query that escapes the request transaction on its own (the request is a savepoint on the test's single connection), which is why a tripwire fails the test run and Biome forbids importing the db service under `app/`. A failed request is rolled back by the exception handler, so a handler must throw to fail a request: one that returns a status of 400 or more without throwing still commits its writes. Never catch a database error outside `withTransaction`: after a failed statement the request transaction is aborted, and committing it silently rolls everything back (the response still says success). Work outside the database (deleting a file, sending an email) goes in `afterCommit` / `afterRollback`, never right after `withTransaction` returns: inside a request that is only a savepoint. Details: [database conventions](../database/README.md#row-level-security).
- Cross-tenant reads: the app role sees one tenant at a time, and nothing in a request ever needs more. Two SECURITY DEFINER functions look across tenants, and both return ids only: the expiry sweep (TAT-83) reads `expired_quote_candidates()` and acts on each row through a `TenantJob` in that row's tenant, never directly; the public API (TAT-32) turns a path slug into one tenant id with `tenant_for_slug()` and runs the request in that tenant. Rules for such functions: [database conventions](../database/README.md#row-level-security).
- Page history (TAT-82): Inertia encrypts the page props it keeps in browser history (`encryptHistory: true` in `config/inertia.ts`), and the guest middleware (the `guest` route group: login, signup) calls `ctx.inertia.clearHistory()`, which drops the tab's key. After logout, an expired session or a change of user, Back can't decrypt the old pages and asks the server again, which sends a guest to `/login`. The flag travels only with a rendered page, so `clearHistory()` before a redirect does nothing. A new page where someone new may start (password reset, invitations) goes in the `guest` group, and a flow that signs a user in without passing through a guest page must clear history on the first page it renders. In development, a plain-HTTP request from a non-loopback host (a phone on the LAN) is not encrypted (`encryptsHistory` in `#services/history_encryption`): browsers have no `crypto.subtle` there, and Inertia's visits would hang. Production always encrypts.

## Public API

- **One group, no session.** Every public endpoint lives in the `/api/v1` group at the end of `start/routes.ts`, whose `publicApi` middleware runs first (TAT-32; `api_routes.spec.ts` checks). `isApiRequest(ctx)` (`#services/public_api`) is true for a route under `/api`, or before routing for a URL under it. The session and shield wrappers in `router.use` (`#middleware/web_session_middleware`, `#middleware/web_shield_middleware`), silent auth and Inertia skip such requests, so the API reads no session, needs no CSRF token and never sets a cookie. Never add `auth`, `guest`, `dbContext`, `tenant` or `role` to an API route. Platform-wide endpoints go in the outer group, tenant endpoints in the inner `/tenants/:tenant` group.
- **Tenant from the path.** `publicTenant` gives a slug that fails `STORED_SLUG` (`#modules/tenancy/slugs`, the registry CHECK's shape; never `checkSlug`, so grandfathered slugs such as `12345` or `www` keep working) a 404 without a query, then asks `TenancyService.tenantIdForSlug`, the only caller of the `tenant_for_slug()` SECURITY DEFINER function, and runs the rest of the request in one transaction with `app.tenant_id` set and no `app.user_id`: every model query is RLS-scoped to that tenant. Read it with `publicTenantContext(ctx)`. An old slug serves GET and HEAD as the same tenant; any other method under it is the same 404 as an unknown slug, before validators, handlers and writes. The bodyparser is a `router.use` middleware, so it runs before `publicTenant` (and before anything in the group's `use` list): a body that cannot be read is a 400, 413 or 415 under any slug, which is no oracle because an old slug, a current one and an unknown one answer alike. RLS scoping is not authorization: a public endpoint returns only studio-page data, through a transformer that picks public fields ([requirements](../../../docs/requirements.md#tenant-isolation), rule 6).
- **Responses.** Return `ctx.serialize(SomeTransformer.transform(record))` for `{ data }`. To fail, throw `ApiException.notFound()`, or `ApiException.of(code)` (`#services/public_api_errors`) for a code of `API_ERRORS` (`#services/public_api`: the shared codes and each endpoint's own, with its status and its one message), or `new ApiException(status, code, message)` for a one-off, listed in `openapi.yaml` (`fields` belong to `validation_failed` only: a fourth argument is a type error with any other code and throws at construction). The exception handler turns every error on an `/api` request into `{ error: { code, message, fields? } }` (`renderApiError`): VineJS errors are `validation_failed` with `fields`, a known path with another method is a 405 with `Allow`, bodyparser and limiter errors get their codes, anything else is `internal_error`. Shared codes have fixed messages: an error's own message, stack or details never reach a response. API 4xx are not logged. A URL the server cannot decode (`/api/v1/%`, invalid UTF-8) is refused before routing and middleware; `onBadUrl` in `config/app.ts` (`#services/public_api`) answers one under `/api` with the `bad_request` envelope and the API headers, and any other URL keeps the plain-text 400.
- **CORS and caching.** `config/cors.ts` only serves `/api`: any origin, no credentials, GET, HEAD and POST, the `Accept` and `Content-Type` request headers, `Retry-After` exposed, preflights cached for 10 minutes. `publicApi` also sends `Access-Control-Allow-Origin: *` without an `Origin`, for CDN copies. Every API response is `Cache-Control: no-store` unless its route uses `middleware.publicCache()`: a 200 GET or HEAD then gets `public, max-age=60, stale-while-revalidate=600` and an ETag, and a matching `If-None-Match` a 304 (pass `{ maxAge, staleWhileRevalidate }` for other seconds). The middleware serializes an object body itself before it marks anything public, so a body that cannot be serialized (a throwing getter or `toJSON`, a circular reference) is an `internal_error` with `no-store`, never a cacheable 500. Never cache a response that isn't the same for everyone (the deposit page, TAT-65); a test makes every API GET route choose.
- **A new endpoint.** Contract first (`openapi.yaml`, then `pnpm --filter @tattoo-drip/types generate`), then a case in `tests/isolation/public_cases.ts`, the caching decision, and tests with `assertApiData` / `assertApiError` (`#tests/helpers/api`). TAT-38 adds its rate limits to the group's `use` lists (per IP before `publicTenant`, per tenant after) and must keep per-caller headers off cacheable responses. Those lists run after the bodyparser, so a limit that must refuse a request before its body is read has to sit in `server.use` or `router.use`, guarded by `isApiRequest(ctx)`. Every API route that takes a body is listed in `multipart.processManually` (`config/bodyparser.ts`; `api_routes.spec.ts` checks), so the body parser never reads a multipart body before `publicTenant` and the limits have answered: auto-processing streams every file to the temp directory (and the parser never removes them), even for an unknown slug. A route that accepts uploads (TAT-51, TAT-65) reads its body in the handler with `receiveUploads(request)` (`#services/uploads`, the parser's own limits and errors: 413, 400; a client that hangs up is a 400 `E_REQUEST_ABORTED`, not a logged 500) and ends with `discardUploads(request)` in a `finally`; it validates files with `imageFile()` and stores them through `ImageService`. Its public isolation case sets `encoding: "multipart"`. A route with parameters besides `:tenant` (the deposit page's `:token`) gives its isolation case `params`, and a multipart write with files gives `files` (TAT-65). An endpoint's own error codes go in `API_ERRORS` (`#services/public_api`), are thrown with `ApiException.of(code)`, and are listed in the operation and in `ErrorResponse`. The cost of reading in the handler: the request holds its pooled connection and transaction while the upload streams. `receiveUploads` also registers its handler under every `Object.prototype` name (`constructor`, `toString`, `__proto__`...): @adonisjs/bodyparser 11.0.4 (the latest, with @poppinss/multiparty 3.0.0) keeps its handler table in a plain object, so a file part with such a name throws inside the parser's async listener, an unhandled rejection that ends the process (the app registers no handler). The routes whose multipart body the parser auto-processes (login, signup, the dashboard forms) still have that flaw: see the production checklist in [database conventions](../database/README.md).
- **Studio page reads (TAT-44).** `GET /api/v1/tenants/:tenant` (`api.v1.studio`), `…/artists` (`api.v1.artists.index`) and `…/artists/:artist` (`api.v1.artists.show`; the `ARTIST_SLUG` matcher makes a malformed or uppercase slug the router's 404 without a query) are cached with `publicCache()`. `StudioPageService` (`#modules/storefront/services/studio_page_service`) builds them from the tenant row `publicTenant` loaded and from `ArtistService`, one query per request: `studio(tenant)` (the `TenantProfile` that the settings page says is shown on the booking page, the current slug, the type, and `acceptingInquiries` from `studioTakesInquiries` in `#modules/artists/accepting`, which intake's `studio_not_accepting` uses too), `visibleArtists(tenant)` and `visibleArtist(tenant, slug)` (null for a hidden, deleted or unknown artist: the 404). `socialLinks` (`#modules/storefront/studio_page`) keeps only https links, in a fixed order. A closed message shows only while the artist is closed; a photo is `ImageService.url` of the public `artist_photo` key with its size. The transformers write each field out: a new public field needs the contract, a ruling and the exact-fields tests. Never in these answers: the tenant id (except inside a photo URL's path), the deposit policy or percentage, payment methods, members, clients, inquiries, projects, quotes, payments, hidden or deleted artists.

## Rate limits

- Login and signup are rate-limited (TAT-8) with `@adonisjs/limiter`, whose counts live in Postgres (`rate_limits`; no Redis in V1; `config/limiter.ts`). Login: per client address, 10 attempts that don't sign in per 15 minutes; per email, from any address, 25 failures per 15 minutes (`throttleLogin` in `#modules/identity/services/auth_limits`, around `User.verifyCredentials`). Signup: 10 requests per address per hour (the `throttleSignup` middleware from `start/limiter.ts`). Windows are fixed, and a lockout ends with its window: no extra block, nothing stored on the user, and the right password is refused too until then. A sign-in gives back only the two attempts it took, and only while their window is still open (a slow password check can end after the window did); failures already counted for the email stay, because look-alike accounts (`users.email` is case-sensitive) share one count and one account's sign-in must not wipe another's. The email limit is above twice the address limit, so one address can't lock an account. Any email is counted, registered or not, so a lockout reveals nothing about accounts.
- Keys are `digest(…)` (HMAC-SHA256 with `APP_KEY`) of the lower-cased email or of `clientAddress(ip)` (IPv4, or the IPv6 /64), from `#services/rate_limits`, so the table holds no email or IP address. `request.ip()` trusts `X-Forwarded-For` only from a loopback peer (the framework default). Read the production checklist in [database conventions](../database/README.md) before deploying behind another proxy. The store writes on the `limiter` connection (`config/database.ts`: the app role, a pool of at most 4 of its own), outside the request transaction, so a failed request's count survives the rollback. It must stay off the `pg` pool: the public deposit routes count inside a request that already holds a `pg` connection, and on a shared pool enough concurrent requests would each wait for a second connection and stall the app (a test holds every `pg` connection and counts anyway).
- A refused dashboard form goes back with the error toast "Too many attempts. Try again in N minutes." (`app/exceptions/handler.ts`, for every `E_TOO_MANY_REQUESTS`); a JSON request gets the limiter's 429 with `Retry-After`. Adding a limit (password reset, TAT-18): put its numbers in `AUTH_LIMITS`, then use either a `limiter.define` middleware in `start/limiter.ts` (counts every request; a reset request must count unknown emails too) or a wrapper like `throttleLogin` (counts failures). Give `limiter.use()` a copy of the limits object, because it parses the durations in place. Never call `limiter.clear()` in app code: on Postgres it truncates the table, which the app role may not do.
- The deposit endpoints (TAT-65) count every request per client address and per link token, reads and uploads apart (`DEPOSIT_LIMITS` in `#modules/payments/deposit_limits`: GET 120 per address and 60 per token per 10 minutes, POST 20 and 10 per hour), in the `depositThrottle` middleware after `publicTenant`, with `limiter.multi` (the address first). Keys are digests of `clientAddress(ip)` and of the token. The upload route is in `multipart.processManually` and reads its body with `receiveUploads` after the link check, so a refused or dead-link upload never reaches the disk; TAT-38 may move the per-address part ahead of the tenant lookup.

## Images

- Images: the `media` module (`app/modules/media/`) owns uploads. Every upload field uses `imageFile()` (`#modules/media/validators/image_file`: 10 MB; jpg, jpeg, png, webp), and every upload is stored with `ImageService.store(file, { tenant, purpose })` (`#modules/media/services/image_service`), never written to a disk directly. `store()` checks the real format by its first bytes, rejects images over 40 MP, applies the EXIF orientation, fits the image in 2048 px and re-encodes it with no metadata; anything else throws `InvalidImageError`, whose message is meant for the user (show it as a field error). The purpose (`IMAGE_PURPOSES`) decides the disk: add one per new kind of image, public only if anyone may see it. The owning record keeps the returned key in a column (e.g. `qr_image_key`). Store the upload inside the `withTransaction` callback that saves the record, and register `afterRollback(() => images.delete(purpose, key))` right after `store()` resolves (no `await` in between), so a transaction that cannot open stores nothing and no failure can fall between the store and its cleanup; do it before any row lock in that callback. Delete a replaced key with `afterCommit`. The cost: outside a request, the image is processed with a transaction open. Soft-deleted records keep their files. `url(purpose, key, tenant)` gives the public URL, or a 5-minute signed URL for a private purpose that answers with `Cache-Control: private, no-store` (signed in, so it can't be stripped): load the owning record scoped to the tenant first, which is the access check; `url` also refuses a key outside `tenants/<id>/<purpose>/` (TAT-66). Drive disks (`config/drive.ts`): `public` served at `/uploads`, `private` at `/files` (signed only). Files live in `storage/` in dev and `tmp/storage/` in tests (cleared each run); production moves to R2 (TAT-27). Decoding is the costly part: at most `MAX_CONCURRENT_DECODES` (2) images decode at once per process (`limitConcurrency` in `#modules/media/concurrency`; the format sniff runs before the wait), and sharp's cache is off (TAT-51: the first anonymous uploads). Where the body parser auto-processes multipart (the dashboard forms), it writes every uploaded file to a temp file and nothing removes the ones that aren't stored; the artist-photo and payment-QR forms still leave a rejected upload's temp file in the OS temp folder (signed-in users only, not yet fixed). A public API route reads its body itself with `receiveUploads(request)` and ends with `discardUploads(request)` (`#services/uploads`) in a `finally` (Public API section): `receiveUploads` records every temp path it allocates and every file handler still running, so `discardUploads` waits for those handlers and removes every path, whatever the part names or failures (a malformed or cut-off part after a good one, `junk` then `junk.extra`, `x.__proto__.y`). The private `reference_image` purpose (TAT-37) holds a client's reference images: load the owning inquiry or project scoped to the tenant first, then ask for the signed URL.

## Payments

- Payments: the `payments` module (`app/modules/payments/`) owns payment methods. Read and change them through `PaymentMethodService` (`#modules/payments/services/payment_method_service`): `list(tenant)`, `findFor(tenant, id)` (throws a 404 for an unknown, deleted or other tenant's id), `create`, `update`, `move` and `delete`. The rules for each kind (which details it needs, QR or not, deposit page or not) live in `checkPaymentMethod` (`#modules/payments/rules`). Validators check only the shape. The service throws `PaymentMethodRuleError`; controllers turn it into field errors. eSewa and Khalti wallet IDs are stored in `account_number`. The deposit page (TAT-65) shows `listForDepositPage(tenant)` (shown on the deposit page, never cash) and the tenant's `depositPolicy`. `Payment` (`#modules/payments/models/payment`, TAT-37) is the append-only ledger of money received; see Clients, inquiries and projects below.

- Deposit links and the deposit page (TAT-65): one `DepositLink` per project (`deposit_links`, tenant-owned, not soft-deleted: a credential replaced in place). The token (43 base64url characters) is `tokenFor(nonce)`, an HMAC of the row's random nonce with a key of its own (HKDF of `APP_KEY`, never the raw key that `digest()` uses); the row keeps the nonce and `token_hash` (SHA-256), which a request is looked up by, never the token, so the owner's page can show the link again (`DepositLinkService.forProject`) and rotating `APP_KEY` kills every link (`resolve` and `forProject` both need the nonce to still derive the stored hash). A link works for 30 days; "New link" replaces the token at once and keeps the 6-character reference code (`23456789ABCDEFGHJKMNPQRSTVWXYZ`, unique per tenant), which the client writes in the payment remark and which grants nothing. Owners make links (`DepositLinkService.issue`: deposit_pending, a live quote, a deposit not covered, a method on the deposit page). `DepositPageService.show` gives the page (`depositState` in `#modules/payments/deposit_page`: cancelled, paid, submitted, due or expired, updating) and `submitProof` takes one screenshot at a time: pre-check, `ImageService.store` with `payment_proof` and `afterRollback`, lock the project (`ProjectService.lockLive`), check again, then `DepositService.recordProof` inserts the `submitted` payment with its proof in one INSERT and `DepositProofAlertJob` is queued. Every dead link is `DepositPageNotFoundError` (the API's one 404). The link's URL is `STOREFRONT_URL` (`{tenant}` for the slug; checked at boot by `checkStorefrontUrl` in `#services/storefront_url`, required in production, the dev host in development with a warning on the owner's panel) plus `/deposit#<token>`: the token rides in the fragment. `DepositPageService.show` reads the quote before the project, so a revision that commits between the two reads gives `updating`, never `due` with the revised quote. `DepositService` (this ticket's) also gives `remaining`, `pendingProof`, `lastDecisionRejected` and `countPendingProofs` (the Projects badge).

- Payment decisions, desk payments and balance due (TAT-66): `PaymentService` (`#modules/payments/services/payment_service`) does every owner write under the project's row lock (`ProjectService.lockLive`) and then the payment's, and refuses anyone but an owner with a 404: `verify` / `reject` (a `submitted` payment only, else `PaymentRuleError` `already_decided`; a verified deposit goes through `SessionService.settleBooking`), `record` (desk money, verified at once: a deposit only in `deposit_pending`, session and balance payments in any status but `declined`), `refund` (a negative `refund` up to what the project holds; `outcome_first` on a closed project that still needs its deposit outcome), `reverse` (a full `correction` of a verified payment that isn't one, once: `corrects_payment_id` names it) and `recordOutcome` (a closed project that still holds deposit money, `settleableDeposit` in the ledger: the smaller of the deposit money and what the project holds after any refund, so a deposit already refunded at the desk needs no outcome and can't be refunded twice; kept, or refunded with a refund payment up to that amount, which is also what the outcome stores). Reads: `forProject` (quote, payments, balance, deposit money and what is due of it, outcome), `forProjects`, `balancesFor`, `listFlags` (the projects list's "screenshot to check", "deposit to settle" and "quote expired": a deposit_pending project the sweep spares because of a late decision on its deposit), `memberNames`. The money maths is pure, in `#modules/payments/ledger`: `depositMoney` (verified deposits plus only the corrections of deposits), `settleableDeposit`, `netPaid`, `balanceOf` (the current quote's `quoteTotal` minus every verified payment in its currency, bigint, never stored), `decidedLate` and `formatSignedMoney`. A decision or entry may carry a staff `note` (500 characters, written once, then only cleared). The project page's Payments card props come from the pure `paymentsCard` (`#modules/payments/payments_card`): owners get the screenshots (signed in `ProjectsController` after the tenant-scoped read), the Reverse buttons and the forms; the assigned artist gets the balance and the list only. The three project payment routes ask `PaymentService.requireOwner` before the body is validated, so an artist always gets the 404. A deposit outcome's `amount` is a bigint column (a sum of deposits can pass int4) that `DepositOutcome` reads back as a number. The client profile reads payments through `forProjects` and `balancesFor`.

## Artists

- Artists: the `artists` module (`app/modules/artists/`) owns the public profiles of a tenant's artists. Read and change them through `ArtistService` (`#modules/artists/services/artist_service`): `list(tenant)` (by name), `listVisible(tenant)` (live and visible, by name: what an inquiry may name, TAT-51), `findFor(tenant, id)` (a 404 for an unknown, deleted or other tenant's id), `create`, `update`, `delete` (soft) and `createOwnerProfile`. `create` and `update` take the signed-in member: `linkToMe` links the profile to them, never takes over a profile that is linked to someone else, and unchecking it unlinks only them, so a profile is only ever linked to a proven member (TAT-33's claim path adds its own check before linking anyone else). They throw `ArtistSlugTakenError` or `ArtistProfileExistsError` after rolling back their own savepoint; the controller turns them into field errors. A slug is unique among a tenant's live artists, so a deleted profile frees it. The photo is the `artist_photo` image purpose (public) with the usual `store` / `afterRollback` / `afterCommit` lifecycle. `user_id` is optional and `ON DELETE SET NULL`: deleting an account keeps the public profile, and TAT-33 must unlink, not delete, a removed member's profile. The dashboard area is owners only for now; TAT-30 opens it to artists by changing the allow list. Public reads (TAT-44) use `listVisible` and `findVisibleBySlug(tenant, slug)` (live, visible, the exact slug; null otherwise), through `StudioPageService` (Public API section). Artist slugs have no aliases: a renamed artist's old slug is a 404, and a deleted profile's slug can be taken by a new one. An independent artist's own profile starts with the studio's slug (`createOwnerProfile` copies it once, when the studio is created) and keeps it when the studio is renamed: `getStudio` then names the new slug while `getArtist` still answers at the slug the profile was created with, until the owner edits the profile's slug.

## Clients, inquiries and projects

- Clients, inquiries and projects (TAT-37, data layer only): `app/modules/clients/` owns `Client` (one live client per normalized phone per tenant; `anonymized_at` is for the privacy deletion, TAT-42), `app/modules/inquiries/` owns `Inquiry` (a frozen record of what was submitted) and `ReferenceImage`, `app/modules/projects/` owns `TattooProject` and `Quote`, and `Payment` lives in `app/modules/payments/`. Projects and quotes go through the services in the next bullet; clients go through `ClientService` (the Clients bullet below), inquiries go through `InquiryService` (the Inquiries and Intake bullets below), and payments go through `DepositService` (TAT-65) and `PaymentService` (TAT-66), so touch those models only in tests and inside a tenant context. The allowed values are const arrays in the model files (`INQUIRY_STATUSES`, `SOURCE_CHANNELS`, `PROJECT_STATUSES`, `QUOTE_KINDS`, `PAYMENT_KINDS`, `PAYMENT_STATUSES`). Links between these tables are composite `(tenant_id, id)` foreign keys with `NO ACTION`. A project has no `inquiry` status (the inquiry is its own record) and its status moves are in `ProjectService` (the quote moves, TAT-64; the manual moves, TAT-46). Soft-deleting a client, inquiry or project does NOT cascade to its children yet, sessions included (only `Tenant.softDelete` does, across the whole tenant); TAT-42 (client deletion) defines those cascades, so do not call `softDelete()` on these models elsewhere before then (the dashboard never deletes a project: declined and withdrawn ones are Closed). The inquiry privacy scrub is one-shot: the contact snapshot and free text change only in the UPDATE that first sets `anonymized_at` (TAT-42 must scrub in that same update), and a decided payment's verifier becomes null only when the verifier's account is gone. A quote revision is a new row with the next `version`, the current quote is the project's highest version, time is whole minutes (`estimated_minutes`) and money is paisa. Quotes have no trigger: "history is never deleted" and "price, deposit and expiry never change after insert" are conventions that `QuoteService` keeps (it only inserts), and the only database protection is the `NO ACTION` key from a quote to its project. Quotes and payments have no `deleted_at`, so those of a soft-deleted project stay visible to direct queries: list them through a live project. `fixed_price`, `deposit_amount`, `hourly_rate` and `amount` are integer (int4) paisa, so one value tops out at 2,147,483,647 paisa (about NPR 21.47 million); a quote's hourly total (rate × minutes / 60) is not stored and is not capped by int4, and the largest possible one (about 7.7e16 paisa) is above `Number.MAX_SAFE_INTEGER` (about 9.0e15). Code that computes totals (`quoteTotal` in `#modules/projects/quotes` does, in bigint; TAT-66's balance due must too) must compute them in bigint, or in JavaScript numbers only after the validator caps the rate and the minutes so that rate × minutes stays below 2^53, and never in int4 arithmetic in SQL (the `quotes_deposit_within_total` check itself casts to bigint for this reason). That check rounds half away from zero (Postgres `round` on numeric), so a total computed in application code should round the same way (`Math.round` matches for positive values). Aggregates such as `sum(amount)` and `count(*)` return int8, which node-pg returns as a string, so parse them with `Number` or `BigInt` (`count(*)::int` is fine, but `sum(amount)::int` raises "integer out of range" once a total passes 2,147,483,647 paisa); TAT-65's balance due will hit this. A payment is never edited or deleted, except that its decision (status, verifier, decision time) is recorded once, `updated_at` moves, its proof can be cleared (privacy deletion, TAT-42) and its verifier becomes null when that user's account is deleted: a refund is a negative `refund` payment, a reversal of a mistaken verification is a `correction`, and a decided payment (`verified` or `rejected`) is final, so if a customer paid a different amount than shown, reject the payment and record a new one (it may reuse the proof key, so delete a proof file only when no other payment references its key). Balance due (the current quote's total minus verified payments) is computed, never stored (`balanceOf`, TAT-66). A `correction` names the payment it reverses (`corrects_payment_id`, same project, once).

## Scheduling

- Scheduling (TAT-36): `app/modules/scheduling/` owns `ProjectSession` (table `project_sessions`, not `sessions`: the database session store's default name) and `SessionService` (`#modules/scheduling/services/session_service`): `schedule`, `reschedule` (time only), `complete`, `markNoShow`, `cancel`, `settleBooking`, `findFor`, `listForProject` and `listInRange` (the calendar's read: active sessions overlapping a half-open window, for one artist or all, written as the no-overlap constraint's own `tstzrange(starts_at, ends_at) &&` expression so its gist index serves one artist's window; no index was added for it). A session is `active` while it is `scheduled` or `completed` and not deleted: `active` is a stored generated column and the one definition of "blocks time", so never write it and use `where active` for anything that asks whether time is taken. `project_sessions_artist_no_overlap` (a gist exclusion on the artist and the half-open time range) settles every race; `schedule` and `reschedule` turn its SQLSTATE 23P01 into `SessionOverlapError`, and `SessionRuleError` carries a `reason` (`project_closed`, `not_scheduled`, `invalid_range`). Controllers write their own messages. `completed`, `no_show` and `cancelled` are final; a mistake is a new session. Only `tattoo` sessions move the project: scheduling one moves `in_progress` to `booked` and, through `settleBooking`, `deposit_pending` to `booked` once a scheduled tattoo session exists and `DepositService.isSettled` is true (the current quote's deposit is 0, or verified deposits and the corrections of deposits reach it); completing one moves `booked` to `in_progress`. Whatever verifies or records a deposit (`PaymentService`, TAT-66) calls `settleBooking` afterwards, and so must whatever moves a project into `deposit_pending` (`ProjectService.acceptQuote` does; TAT-46's moves must too): a tattoo session held earlier is only re-checked when something calls it. Cancelling or no-showing the last live session leaves a `booked` project `booked`: TAT-46 owns any rollback and can flag "booked with no scheduled session". Every write locks the project row `FOR UPDATE` first and then the session row, in that order. `DepositService` (payments module) reads the current quote through `QuoteService`. A session's artist can be any live artist of the tenant; the first session fills an empty project artist. Lucid reads nothing back after an insert or update, so the service `refresh()`es every session it returns and `status` and `active` are the database's; a session you create outside the service (a test factory) has neither until you `refresh()` it.
- Direct bookings (TAT-43): `BookingService` (`#modules/projects/services/booking_service`) books a walk-in, phone or DM client in one step. `bookableArtists(tenant, member)`: every live artist for an owner, only the live profile linked to them for an artist. `book(tenant, member, booking)` refuses any other artist (`BookingRuleError` `artist_unavailable`) and then, in one `withTransaction`, takes the client (`ClientService.findFor` for a found one, which the booking never changes; `client_unavailable` for an anonymized one; `ClientService.create` for a new one), creates a `booked` project with no inquiry, its artist set and `last_contacted_at` now, inserts the optional quick quote with `QuoteService.create` (version 1, deposit 0, valid through the session's day) and schedules one `tattoo` session through `SessionService.schedule`. An overlap (`SessionOverlapError`), a number taken meanwhile (`ClientRuleError` `phone_taken`) or another tenant's client (E_ROW_NOT_FOUND) rolls the whole booking back; `BookingsController` turns them into field errors (a 404 for the foreign client). The quick quote does not go through `issueQuote` and queues no `ExpireQuoteJob`: expiry only acts on `quoted`, `on_hold` and `deposit_pending`, which a booked project never returns to. From `booked` on (`BOOKED_STATUSES` in `#modules/projects/quotes`) the project page hides the quote's expiry, and a booked project's price can't change (quotes are locked from `booked`; a booking made without a price gets one once through `ProjectService.setPrice`, TAT-66). The page is `/t/:tenant/projects/new` (`?phone=` looks the number up in the tenant, only for a member who has an artist to book with; only the name is shown, since artists use it too) and posts to `/t/:tenant/projects`. Session times are the studio's: `localDateTime` (a time the clocks skip is null, one they pass twice is its first occurrence) and `sessionTimeText` in `#modules/scheduling/times`; the project page lists its sessions with them.
- Calendar (TAT-50): `CalendarService` (`#modules/scheduling/services/calendar_service`) `load(tenant, member, { artistId, from, to })` decides whose sessions a member sees and reads them with one query per module (`ArtistService.list`, `SessionService.listInRange`, `ProjectService.findManyFor`, `ClientService.findMany`). Owners see the whole studio, or one live artist with `artistId`; an artist member sees only the live profile linked to them (none: `scope` `unlinked`, an explanation on the page). Any other `artistId` is E_ROW_NOT_FOUND (a 404), compared with the artist list in memory so a malformed id never reaches the database; the controller makes a repeated `?artist=` a 404 too. A session's client and brief are shown only when the member may open its project (`findManyFor`, the `findFor` rule): an artist's session on a project assigned to someone else shows its time and kind only. Only active sessions show. Days are the studio's local days (`#modules/scheduling/calendar`: `dayBounds` runs from local midnight to the next, 23 or 25 hours on clock-change days, and takes the first of a midnight the clocks pass twice (Havana, the Azores), like `localDateTime`; dates are plain yyyy-MM-dd computed in UTC and only the years 1900 to 2100 count, anything else is today; weeks run Sunday to Saturday; a session shows on every day it overlaps). The page is `/t/:tenant/calendar?view=day|week&date=yyyy-MM-dd&artist=` (owners and artists), read-only; its "Book session" (owners of a studio with an artist, and artists with a profile) opens `/t/:tenant/projects/new?date=`, which preselects that day when it is bookable. The page follows the browser's clock for "today" (the Today badge, the Today link, the Now marker), so a tab left open past the studio's midnight stays right.
- Projects and quotes (TAT-64): `app/modules/projects/` has two services, layered so that no class depends on itself through another module. `QuoteService` (`#modules/projects/services/quote_service`) depends on nothing outside the module: `current` (the highest version), `history` (newest first) and `create(trx, …)` (the next version, under the caller's project lock). `ProjectService` (`#modules/projects/services/project_service`) depends on it, `DepositService` and `SessionService`: `findFor(tenant, member, id)` (owners see every live project, an artist only those assigned to their own live artist profile, anyone else a 404), `findManyFor(tenant, member, ids)` (the same rule for many ids at once, no order: the calendar's project details, TAT-50), `issueQuote(tenant, project, input, baseQuoteId)` (allowed in `reviewing`, `quoted`, `on_hold`, `deposit_pending`; `baseQuoteId` is the quote the form showed, null for a first quote, and a mismatch with the current quote is refused so a stale form can't restore old terms; moves to `quoted`; queues `ExpireQuoteJob` in the same transaction, delayed to `expires_at`), `acceptQuote` (only `quoted`, only the current unexpired quote; moves to `deposit_pending`, then `settleBooking`) and `expireQuote` (what the job runs: cancels `quoted`, `on_hold` and unsettled `deposit_pending` projects and their scheduled sessions, but never one whose non-zero deposit was paid; anything else, including a revised quote's old job, is a no-op; a run before the expiry queues the job again for the rest of the time, and `SweepExpiredQuotesJob` catches a job that failed or never ran, see [jobs and email](jobs-and-email.md#jobs)). It also spares a project while a deposit screenshot waits and once the studio verified, recorded at the desk, rejected or reversed a deposit at or after the expiry (`DepositService.expirySpared`, TAT-66), so a late decision is never undone by a sweep. `setPrice` gives a project booked without a price its quote version 1 (fixed, no deposit), once (`QuoteRuleError` `price_locked` otherwise; TAT-66). Every member-facing mutation (`issueQuote`, `acceptQuote`, `move`, `updateNotes`, `markContacted`) takes the acting `member` and locks through `lockFor`, which re-checks under the lock that a non-owner still has the project assigned to their own live artist profile (a 404 otherwise): `findFor` runs before the lock, so a request that waited while an owner reassigned the project must not write to it. TAT-46 adds the manual moves (`app/modules/projects/moves.ts`: `hold`, `resume`, `decline`, `withdraw`, the table the page's buttons come from) through `ProjectService.move` (`ProjectRuleError` `move_not_allowed`; a client may withdraw up to `in_progress`, and when the project holds deposit money the owner then records its outcome, TAT-66; declining and withdrawing cancel scheduled sessions), `assignArtist` (owners only, a 404 for anyone else), `updateNotes`, `markContacted` (the chat links call it in the background), and `list` / `countByStatus` for the projects list: Active is every status but `declined`, `cancelled` and `completed`, 25 per page, the same visibility as `findFor`. The list reads only `tattoo_projects`; client names, artist names and the "booked, no session" flag come from `ClientService.findMany`, `ArtistService.list` and `SessionService.projectsWithScheduledTattoo`. Projects are never deleted from the dashboard: declined and withdrawn ones are Closed. They throw `QuoteRuleError` with a reason (`project_closed`, `not_quoted`, `quote_changed`, `expired`). There are no drafts: saving issues the next version. `ExpireQuoteJob` imports `ProjectService` inside `handle()`, because `ProjectService` imports the job. Pure helpers (totals in bigint, money and date formatting, `expiresAtFor`: the start of the day after the chosen date in the tenant's timezone, the chat message and links) are in `#modules/projects/quotes`. The dashboard has the projects list (`/t/:tenant/projects`), the project page and its routes under `/t/:tenant/projects/:id` for owners and the assigned artist. `pnpm seed:dev` (development only, run as the owner role) gives each tenant without a project a demo project to open.
- Inquiries (TAT-46): `InquiryService` (`#modules/inquiries/services/inquiry_service`) reads the inbox (`listNew` oldest first, `listDecided` latest decision first, 25 per page; `countNew` for the Inbox badge, shared as `inboxCount` for owners; `findFor` / `find`; `images` by inquiry or project; `imageCounts`) and decides inquiries: `accept(tenant, inquiry, artistId)` locks the inquiry, refuses one that is no longer `new` (`InquiryRuleError` `already_decided`) or a non-live artist (`artist_unavailable`), creates a `reviewing` project through `ProjectService.createFromInquiry` (brief = the idea), sets `project_id` on the inquiry's live reference images (they keep `inquiry_id`) and records `accepted` with `decided_at`; `decline` records `declined`. Both are final. The `/inbox` routes are owners only (reference images are private to owners until a project is assigned; the project page then shows them to its assigned artist too, in its Request section). `ImageService.storeBytes` stores in-memory bytes like an upload (the dev seeder's generated references). `pnpm seed:dev` gives each tenant without inquiries three new demo ones with generated references.
- Intake (TAT-51): `POST /api/v1/tenants/:tenant/inquiries` (`PublicInquiriesController.store`, `api.v1.inquiries.store`) takes `multipart/form-data` only (anything else is 415), reads the body itself (`receiveUploads`, below), validates with `intakeValidator` (`#modules/inquiries/validators/intake`: the inquiry columns' lengths, NUL refused, the phone to E.164, up to `MAX_REFERENCE_IMAGES` (5) `imageFile()` uploads from `request.files("referenceImages")`; `challengeToken` is taken and ignored until TAT-55) and calls `IntakeService.submit(tenant, submission)` (`#modules/inquiries/services/intake_service`). In one transaction it checks the artist (one of `listVisible`, else `InquiryRuleError` `artist_unavailable`, answered as a `preferredArtistId` field error; closed: `artist_not_accepting`; no artist chosen while every visible one is closed: `studio_not_accepting`), matches the client (`ClientService.matchByPhone`), refuses a phone that already has `OPEN_INQUIRY_LIMIT` (3) open inquiries (live, `new`, that `contact_phone`) with `too_many_open_inquiries`, counted under the client's lock, stores each image (`reference_image`, its `afterRollback` cleanup right after; a bad one is `InvalidReferenceImageError` with its index, answered on `referenceImages.<index>`), inserts the inquiry with the submitted contact copy and its reference rows by `position`, and queues `NewInquiryAlertJob` ([jobs](jobs-and-email.md)). Every refusal comes before any image is decoded. The answer is `{ data: { id } }` whatever the phone, so it never tells whether the phone was known; only the cap's 409 depends on it. TAT-55's per-phone limit goes in the controller where its comment says; its challenge and honeypot are route middleware on `api.v1.inquiries.store`. The request keeps its pooled database connection while the upload streams and while an image waits for a decode slot (`publicTenant` opens the transaction first), so TAT-38's limits must land before any public deploy.
- Clients (TAT-41): `ClientService` (`#modules/clients/services/client_service`) has `find` / `findMany` (other modules' lookups), `findFor` (a 404), `findByPhone` (E.164; what intake, TAT-51, and direct bookings, TAT-43, match on), `create` (a booking's new client, TAT-43; `ClientRuleError` `phone_taken` from the same index), `matchByPhone(tenant, contact)` (intake, TAT-51: the live client with that phone, locked until the transaction ends, else a new one; never changes a found client, an anonymized one included; the loser of a race for a new phone gets the winner's client), `list` (newest first, 25 per page; a search matches part of the name in any case, literally, or with at least 3 digits part of the phone's digits) and `update` (owners' edits under the row lock: `ClientRuleError` `phone_taken` from the one-live-client-per-phone index, `anonymized` for a client whose details were deleted). Only an owner's edit changes a client: intake records what was submitted on the inquiry's frozen copy. TAT-42 must null an anonymized client's phone, or intake keeps attaching new inquiries to it. The clients pages (`/t/:tenant/clients`) are owners only; the profile's history comes from `ProjectService.forClient` / `countsForClients` / `lastChangeForClients` and `InquiryService.forClient` / `latestForClients` / `imagesFor`, so the clients module reads no other module's table. Chat and call links are in `#modules/clients/contact_links`.
