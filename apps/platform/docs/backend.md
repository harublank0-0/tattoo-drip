# Backend conventions

Read the relevant section before changing backend behavior. For module boundaries or tenancy design, consult [architecture](../../../docs/architecture.md); for schema changes read [database conventions](../database/README.md) and the relevant [data-model](../../../docs/data-model.md) section. Those contain the canonical schema rules.


## Layout

- `app/controllers`, `app/models`, `app/validators`, `app/transformers`, `app/middleware`, `app/exceptions`
- `app/modules/<module>/`: one folder per backend module from [architecture](../../../docs/architecture.md), owning its `models/`, `services/`, `controllers/`, `validators/` and `emails/`. Import with `#modules/*`. New module code goes here; code still in the flat `app/*` folders moves when its module is built. Controllers and transformers stay in `app/controllers` and `app/transformers` for now: `indexEntities` in `adonisrc.ts` only scans those folders to generate `#generated/*`, so it has to be pointed at the module folders first.
- `start/routes.ts` (routes reference controllers through `#generated/controllers`), `start/kernel.ts` (middleware), `start/env.ts`
- `config/`, `database/migrations/`
- `inertia/pages`, `inertia/layouts`, `inertia/components` (shadcn components in `inertia/components/ui`), `inertia/hooks`, `inertia/css/app.css` (Tailwind entry and theme tokens)
- `tests/unit`, `tests/functional`, `tests/browser` (suites are defined in `adonisrc.ts`)

Import with the subpath aliases from `package.json` (`#controllers/*`, `#models/*`, `#services/*`, `#validators/*`, …), never with long relative paths.

## Dependency injection and module boundaries

- Controllers and services that use `@inject()` must import their dependencies as values, not `import type`: the container reads the class from decorator metadata at runtime. Biome's `useImportType` fix gets this wrong, so mark those imports with `// biome-ignore lint/style/useImportType: @inject() reads the class at runtime`.
- Each backend module owns its models and services; other modules call its services instead of querying its tables. Inertia controllers, API controllers and jobs stay thin and call the same services. See the module table in [architecture](../../../docs/architecture.md).

## API contract and migrations

- The REST API implements the contract in [OpenAPI contract](../../../packages/types/openapi.yaml). Change the contract first, regenerate the types, then implement.
- `database/schema.ts` and `.adonisjs/` are generated. Change the schema with a new migration, never by editing an existing migration that has been run.
- Read [database conventions](../database/README.md) before writing a migration; it owns the UUIDv7, timestamp, ownership, indexing and soft-delete rules.

## Soft deletes

- Soft delete: models of business records use `compose(XSchema, withSoftDeletes)` from `#models/mixins/soft_deletes`. Delete with `record.softDelete(trx?)`, undo with `restore()`; model queries skip deleted rows unless they start from `Model.withTrashed()` or `Model.onlyTrashed()`. The hooks don't reach `whereHas` subqueries or raw `db.from(...)` queries, so add `whereNull("<table>.deleted_at")` there. The hooks append `deleted_at IS NULL` to the end of the query, so a top-level `.orWhere(...)` would let deleted rows through (`a OR (b AND deleted_at IS NULL)`): group your own conditions in `.where((q) => q.where(a).orWhere(b))`. Update queries skip the hooks too; filter `deleted_at` yourself there. Soft-deleting a parent soft-deletes its children in the same transaction (the database's `ON DELETE CASCADE` only covers real purges).

## Tenancy and route access

- The tenant always comes from the URL (`/t/:slug/…` for the dashboard, `/api/v1/tenants/:slug/…` for the API). Services scope every query by tenant; never trust a tenant ID from a request body. Every tenant-owned endpoint needs a test proving tenant A can't reach tenant B's data.
- Tenancy: the `tenancy` module (`app/modules/tenancy/`) owns tenants and memberships. Other modules read them through `TenancyService` (`#modules/tenancy/services/tenancy_service`): `createTenant`, `tenantsFor`, `hasTenant` (one cheap yes/no query), and `assertKeepsAnOwner`, which every remove or demote of a member must call inside its transaction. New users create their first tenant at `/onboarding` (only while they have none: one tenant per account for now). Login, signup and onboarding land on `/dashboard`, which redirects to the tenant the user opened last, else their oldest, else `/onboarding`; a tenant's own address (`/t/:tenant`) then redirects owners to the Inbox and artists to Projects. Login and logout forget the last tenant (`LAST_TENANT_KEY`), so a shared browser doesn't carry it over. `createTenant` also gives an independent artist their own artist profile (`ArtistService.createOwnerProfile`) in the same transaction; a studio gets none. Soft-deleting a tenant (`tenant.softDelete(trx?)`) also soft-deletes its live memberships, payment methods, artists, clients, inquiries, projects, reference images and sessions (quotes and payments have no `deleted_at` and stay).
- Tenant pages live in the `/t/:tenant` route group with `[middleware.auth(), middleware.dbContext(), middleware.tenant()]`. The tenant middleware calls `TenancyService.membershipFor(user, slug)` on every request (never cache it) and turns `null` into the same 404 as an unknown URL, never a 403, so a URL doesn't reveal that a tenant exists. Every tenant route goes in that group; a test fails for a `/t/:tenant` route without the middleware. Read the result with `tenantContext(ctx)` from `#middleware/tenant_middleware`, which returns `{ tenant, membership }` and throws outside the group (`ctx.tenant` is optional for that reason; the role is `membership.role`). Limit a route to some roles with `middleware.role({ allow: ["owner"] })` after `tenant()`: other members get the same 404. Studio settings (`/t/:tenant/settings/…`) and the artists area (`/t/:tenant/artists/…`) are owners only. They go in their nested groups, and a test fails for a route in either area without the role check. `:id` route params use `.where("id", router.matchers.uuid())`, so a malformed id is a 404 rather than a database error. Controllers pass the tenant to services explicitly; never read a tenant id from the body, query string or headers, and keep `tenant_id` out of validators. Every page gets the `tenant` and `tenants` props from `InertiaMiddleware.share()`; nav items for tenant pages pass `params: { tenant: slug }`.
- Database context: every authenticated request runs in one transaction (the `dbContext` middleware, right after `auth`) with `app.user_id` set, and the tenant middleware adds `app.tenant_id` (`setRequestContext`, which only the outermost level may call). Row-level security reads them, so a query outside that transaction sees no tenant rows. Nested work uses `withTransaction` from `#services/db_context`, never `db.transaction`: inside a request it is a savepoint, so a caught unique violation leaves the request usable. `withDbContext({ tenantId }, fn)` runs `fn` as a tenant (jobs, tests, `createTenant`). The database settings belong to the connection, so overlapping `withDbContext` calls under one parent throw: await one before starting the next (`Promise.all` over `withDbContext`, or over the tests' `inTenant`, throws; plain `withTransaction` siblings are fine). A plain query made while a child context is open sees that context's settings, so don't mix them in a fan-out. Model queries, preloads and relations join the request transaction automatically; raw `db.from()` and `db.rawQuery()` do not, so use `dbClient()`. Tests will not reveal a query that escapes the request transaction on its own (the request is a savepoint on the test's single connection), which is why a tripwire fails the test run and Biome forbids importing the db service under `app/`. A failed request is rolled back by the exception handler, so a handler must throw to fail a request: one that returns a status of 400 or more without throwing still commits its writes. Never catch a database error outside `withTransaction`: after a failed statement the request transaction is aborted, and committing it silently rolls everything back (the response still says success). Work outside the database (deleting a file, sending an email) goes in `afterCommit` / `afterRollback`, never right after `withTransaction` returns: inside a request that is only a savepoint. Details: [database conventions](../database/README.md#row-level-security).
- Cross-tenant reads: the app role sees one tenant at a time, and nothing in a request ever needs more. A system task that must look across tenants (only the expiry sweep, TAT-83) reads ids through a SECURITY DEFINER function, then acts on each row through a `TenantJob` in that row's tenant, never directly. Rules for such functions: [database conventions](../database/README.md#row-level-security).
- Page history (TAT-82): Inertia encrypts the page props it keeps in browser history (`encryptHistory: true` in `config/inertia.ts`), and the guest middleware (the `guest` route group: login, signup) calls `ctx.inertia.clearHistory()`, which drops the tab's key. After logout, an expired session or a change of user, Back can't decrypt the old pages and asks the server again, which sends a guest to `/login`. The flag travels only with a rendered page, so `clearHistory()` before a redirect does nothing. A new page where someone new may start (password reset, invitations) goes in the `guest` group, and a flow that signs a user in without passing through a guest page must clear history on the first page it renders. In development, a plain-HTTP request from a non-loopback host (a phone on the LAN) is not encrypted (`encryptsHistory` in `#services/history_encryption`): browsers have no `crypto.subtle` there, and Inertia's visits would hang. Production always encrypts.

## Rate limits

- Login and signup are rate-limited (TAT-8) with `@adonisjs/limiter`, whose counts live in Postgres (`rate_limits`; no Redis in V1; `config/limiter.ts`). Login: per client address, 10 attempts that don't sign in per 15 minutes; per email, from any address, 25 failures per 15 minutes (`throttleLogin` in `#modules/identity/services/auth_limits`, around `User.verifyCredentials`). Signup: 10 requests per address per hour (the `throttleSignup` middleware from `start/limiter.ts`). Windows are fixed, and a lockout ends with its window: no extra block, nothing stored on the user, and the right password is refused too until then. A sign-in gives back only the two attempts it took, and only while their window is still open (a slow password check can end after the window did); failures already counted for the email stay, because look-alike accounts (`users.email` is case-sensitive) share one count and one account's sign-in must not wipe another's. The email limit is above twice the address limit, so one address can't lock an account. Any email is counted, registered or not, so a lockout reveals nothing about accounts.
- Keys are `digest(…)` (HMAC-SHA256 with `APP_KEY`) of the lower-cased email or of `clientAddress(ip)` (IPv4, or the IPv6 /64), from `#services/rate_limits`, so the table holds no email or IP address. `request.ip()` trusts `X-Forwarded-For` only from a loopback peer (the framework default). Read the production checklist in [database conventions](../database/README.md) before deploying behind another proxy. The store writes on its own pooled connection, outside the request transaction, so a failed request's count survives the rollback.
- A refused dashboard form goes back with the error toast "Too many attempts. Try again in N minutes." (`app/exceptions/handler.ts`, for every `E_TOO_MANY_REQUESTS`); a JSON request gets the limiter's 429 with `Retry-After`. Adding a limit (password reset, TAT-18): put its numbers in `AUTH_LIMITS`, then use either a `limiter.define` middleware in `start/limiter.ts` (counts every request; a reset request must count unknown emails too) or a wrapper like `throttleLogin` (counts failures). Give `limiter.use()` a copy of the limits object, because it parses the durations in place. Never call `limiter.clear()` in app code: on Postgres it truncates the table, which the app role may not do.

## Images

- Images: the `media` module (`app/modules/media/`) owns uploads. Every upload field uses `imageFile()` (`#modules/media/validators/image_file`: 10 MB; jpg, jpeg, png, webp), and every upload is stored with `ImageService.store(file, { tenant, purpose })` (`#modules/media/services/image_service`), never written to a disk directly. `store()` checks the real format by its first bytes, rejects images over 40 MP, applies the EXIF orientation, fits the image in 2048 px and re-encodes it with no metadata; anything else throws `InvalidImageError`, whose message is meant for the user (show it as a field error). The purpose (`IMAGE_PURPOSES`) decides the disk: add one per new kind of image, public only if anyone may see it. The owning record keeps the returned key in a column (e.g. `qr_image_key`). Store the upload inside the `withTransaction` callback that saves the record, and register `afterRollback(() => images.delete(purpose, key))` right after `store()` resolves (no `await` in between), so a transaction that cannot open stores nothing and no failure can fall between the store and its cleanup; do it before any row lock in that callback. Delete a replaced key with `afterCommit`. The cost: outside a request, the image is processed with a transaction open. Soft-deleted records keep their files. `url(purpose, key)` gives the public URL, or a 5-minute signed URL for a private purpose: load the owning record scoped to the tenant first, which is the access check. Drive disks (`config/drive.ts`): `public` served at `/uploads`, `private` at `/files` (signed only). Files live in `storage/` in dev and `tmp/storage/` in tests (cleared each run); production moves to R2 (TAT-27). The private `reference_image` purpose (TAT-37) holds a client's reference images: load the owning inquiry or project scoped to the tenant first, then ask for the signed URL.

## Payments

- Payments: the `payments` module (`app/modules/payments/`) owns payment methods. Read and change them through `PaymentMethodService` (`#modules/payments/services/payment_method_service`): `list(tenant)`, `findFor(tenant, id)` (throws a 404 for an unknown, deleted or other tenant's id), `create`, `update`, `move` and `delete`. The rules for each kind (which details it needs, QR or not, deposit page or not) live in `checkPaymentMethod` (`#modules/payments/rules`). Validators check only the shape. The service throws `PaymentMethodRuleError`; controllers turn it into field errors. eSewa and Khalti wallet IDs are stored in `account_number`. The deposit page (TAT-65) shows `list(tenant)` filtered to `showOnDepositPage`, with the tenant's `defaultDepositPercent` and `depositPolicy`. `Payment` (`#modules/payments/models/payment`, TAT-37) is the append-only ledger of money received; see Clients, inquiries and projects below.

## Artists

- Artists: the `artists` module (`app/modules/artists/`) owns the public profiles of a tenant's artists. Read and change them through `ArtistService` (`#modules/artists/services/artist_service`): `list(tenant)` (by name), `findFor(tenant, id)` (a 404 for an unknown, deleted or other tenant's id), `create`, `update`, `delete` (soft) and `createOwnerProfile`. `create` and `update` take the signed-in member: `linkToMe` links the profile to them, never takes over a profile that is linked to someone else, and unchecking it unlinks only them, so a profile is only ever linked to a proven member (TAT-33's claim path adds its own check before linking anyone else). They throw `ArtistSlugTakenError` or `ArtistProfileExistsError` after rolling back their own savepoint; the controller turns them into field errors. A slug is unique among a tenant's live artists, so a deleted profile frees it. The photo is the `artist_photo` image purpose (public) with the usual `store` / `afterRollback` / `afterCommit` lifecycle. `user_id` is optional and `ON DELETE SET NULL`: deleting an account keeps the public profile, and TAT-33 must unlink, not delete, a removed member's profile. The dashboard area is owners only for now; TAT-30 opens it to artists by changing the allow list. Public reads (visible profiles only) are TAT-44.

## Clients, inquiries and projects

- Clients, inquiries and projects (TAT-37, data layer only): `app/modules/clients/` owns `Client` (one live client per normalized phone per tenant; `anonymized_at` is for the privacy deletion, TAT-42), `app/modules/inquiries/` owns `Inquiry` (a frozen record of what was submitted) and `ReferenceImage`, `app/modules/projects/` owns `TattooProject` and `Quote`, and `Payment` lives in `app/modules/payments/`. Projects and quotes go through the services in the next bullet; clients go through `ClientService` (the Clients bullet below), inquiries go through `InquiryService` (the Inquiries bullet below; intake is TAT-51), and payments have no service yet (TAT-65), so touch those models only in tests and inside a tenant context. The allowed values are const arrays in the model files (`INQUIRY_STATUSES`, `SOURCE_CHANNELS`, `PROJECT_STATUSES`, `QUOTE_KINDS`, `PAYMENT_KINDS`, `PAYMENT_STATUSES`). Links between these tables are composite `(tenant_id, id)` foreign keys with `NO ACTION`. A project has no `inquiry` status (the inquiry is its own record) and its status moves are in `ProjectService` (the quote moves, TAT-64; the manual moves, TAT-46). Soft-deleting a client, inquiry or project does NOT cascade to its children yet, sessions included (only `Tenant.softDelete` does, across the whole tenant); TAT-42 (client deletion) defines those cascades, so do not call `softDelete()` on these models elsewhere before then (the dashboard never deletes a project: declined and withdrawn ones are Closed). The inquiry privacy scrub is one-shot: the contact snapshot and free text change only in the UPDATE that first sets `anonymized_at` (TAT-42 must scrub in that same update), and a decided payment's verifier becomes null only when the verifier's account is gone. A quote revision is a new row with the next `version`, the current quote is the project's highest version, time is whole minutes (`estimated_minutes`) and money is paisa. Quotes have no trigger: "history is never deleted" and "price, deposit and expiry never change after insert" are conventions that `QuoteService` keeps (it only inserts), and the only database protection is the `NO ACTION` key from a quote to its project. Quotes and payments have no `deleted_at`, so those of a soft-deleted project stay visible to direct queries: list them through a live project. `fixed_price`, `deposit_amount`, `hourly_rate` and `amount` are integer (int4) paisa, so one value tops out at 2,147,483,647 paisa (about NPR 21.47 million); a quote's hourly total (rate × minutes / 60) is not stored and is not capped by int4, and the largest possible one (about 7.7e16 paisa) is above `Number.MAX_SAFE_INTEGER` (about 9.0e15). Code that computes totals (`quoteTotal` in `#modules/projects/quotes` does, in bigint; TAT-66's balance due must too) must compute them in bigint, or in JavaScript numbers only after the validator caps the rate and the minutes so that rate × minutes stays below 2^53, and never in int4 arithmetic in SQL (the `quotes_deposit_within_total` check itself casts to bigint for this reason). That check rounds half away from zero (Postgres `round` on numeric), so a total computed in application code should round the same way (`Math.round` matches for positive values). Aggregates such as `sum(amount)` and `count(*)` return int8, which node-pg returns as a string, so parse them with `Number` or `BigInt` (`count(*)::int` is fine, but `sum(amount)::int` raises "integer out of range" once a total passes 2,147,483,647 paisa); TAT-65's balance due will hit this. A payment is never edited or deleted, except that its decision (status, verifier, decision time) is recorded once, `updated_at` moves, its proof can be cleared (privacy deletion, TAT-42) and its verifier becomes null when that user's account is deleted: a refund is a negative `refund` payment, a reversal of a mistaken verification is a `correction`, and a decided payment (`verified` or `rejected`) is final, so if a customer paid a different amount than shown, reject the payment and record a new one (it may reuse the proof key, so delete a proof file only when no other payment references its key). Balance due (the current quote's total minus verified payments) is computed, never stored.

## Scheduling

- Scheduling (TAT-36): `app/modules/scheduling/` owns `ProjectSession` (table `project_sessions`, not `sessions`: the database session store's default name) and `SessionService` (`#modules/scheduling/services/session_service`): `schedule`, `reschedule` (time only), `complete`, `markNoShow`, `cancel`, `settleBooking`, `findFor` and `listForProject`; calendar range queries are TAT-50's. A session is `active` while it is `scheduled` or `completed` and not deleted: `active` is a stored generated column and the one definition of "blocks time", so never write it and use `where active` for anything that asks whether time is taken. `project_sessions_artist_no_overlap` (a gist exclusion on the artist and the half-open time range) settles every race; `schedule` and `reschedule` turn its SQLSTATE 23P01 into `SessionOverlapError`, and `SessionRuleError` carries a `reason` (`project_closed`, `not_scheduled`, `invalid_range`). Controllers write their own messages. `completed`, `no_show` and `cancelled` are final; a mistake is a new session. Only `tattoo` sessions move the project: scheduling one moves `in_progress` to `booked` and, through `settleBooking`, `deposit_pending` to `booked` once a scheduled tattoo session exists and `DepositService.isSettled` is true (the current quote's deposit is 0, or verified `deposit` and `correction` payments reach it); completing one moves `booked` to `in_progress`. Whatever verifies a deposit (TAT-65) must call `settleBooking` afterwards, and so must whatever moves a project into `deposit_pending` (`ProjectService.acceptQuote` does; TAT-46's moves must too): a tattoo session held earlier is only re-checked when something calls it. Cancelling or no-showing the last live session leaves a `booked` project `booked`: TAT-46 owns any rollback and can flag "booked with no scheduled session". Every write locks the project row `FOR UPDATE` first and then the session row, in that order. `DepositService` (payments module) reads the current quote through `QuoteService`. A session's artist can be any live artist of the tenant; the first session fills an empty project artist. Lucid reads nothing back after an insert or update, so the service `refresh()`es every session it returns and `status` and `active` are the database's; a session you create outside the service (a test factory) has neither until you `refresh()` it.
- Direct bookings (TAT-43): `BookingService` (`#modules/projects/services/booking_service`) books a walk-in, phone or DM client in one step. `bookableArtists(tenant, member)`: every live artist for an owner, only the live profile linked to them for an artist. `book(tenant, member, booking)` refuses any other artist (`BookingRuleError` `artist_unavailable`) and then, in one `withTransaction`, takes the client (`ClientService.findFor` for a found one, which the booking never changes; `client_unavailable` for an anonymized one; `ClientService.create` for a new one), creates a `booked` project with no inquiry, its artist set and `last_contacted_at` now, inserts the optional quick quote with `QuoteService.create` (version 1, deposit 0, valid through the session's day) and schedules one `tattoo` session through `SessionService.schedule`. An overlap (`SessionOverlapError`), a number taken meanwhile (`ClientRuleError` `phone_taken`) or another tenant's client (E_ROW_NOT_FOUND) rolls the whole booking back; `BookingsController` turns them into field errors (a 404 for the foreign client). The quick quote does not go through `issueQuote` and queues no `ExpireQuoteJob`: expiry only acts on `quoted`, `on_hold` and `deposit_pending`, which a booked project never returns to. From `booked` on (`BOOKED_STATUSES` in `#modules/projects/quotes`) the project page hides the quote's expiry, and a booked project's price can't change (quotes are locked from `booked`; recording a final price is TAT-66's). The page is `/t/:tenant/projects/new` (`?phone=` looks the number up in the tenant, only for a member who has an artist to book with; only the name is shown, since artists use it too) and posts to `/t/:tenant/projects`. Session times are the studio's: `localDateTime` (a time the clocks skip is null, one they pass twice is its first occurrence) and `sessionTimeText` in `#modules/scheduling/times`; the project page lists its sessions with them.
- Projects and quotes (TAT-64): `app/modules/projects/` has two services, layered so that no class depends on itself through another module. `QuoteService` (`#modules/projects/services/quote_service`) depends on nothing outside the module: `current` (the highest version), `history` (newest first) and `create(trx, …)` (the next version, under the caller's project lock). `ProjectService` (`#modules/projects/services/project_service`) depends on it, `DepositService` and `SessionService`: `findFor(tenant, member, id)` (owners see every live project, an artist only those assigned to their own live artist profile, anyone else a 404), `issueQuote(tenant, project, input, baseQuoteId)` (allowed in `reviewing`, `quoted`, `on_hold`, `deposit_pending`; `baseQuoteId` is the quote the form showed, null for a first quote, and a mismatch with the current quote is refused so a stale form can't restore old terms; moves to `quoted`; queues `ExpireQuoteJob` in the same transaction, delayed to `expires_at`), `acceptQuote` (only `quoted`, only the current unexpired quote; moves to `deposit_pending`, then `settleBooking`) and `expireQuote` (what the job runs: cancels `quoted`, `on_hold` and unsettled `deposit_pending` projects and their scheduled sessions, but never one whose non-zero deposit was paid; anything else, including a revised quote's old job, is a no-op; a run before the expiry queues the job again for the rest of the time, and `SweepExpiredQuotesJob` catches a job that failed or never ran, see [jobs and email](jobs-and-email.md#jobs)). Every member-facing mutation (`issueQuote`, `acceptQuote`, `move`, `updateNotes`, `markContacted`) takes the acting `member` and locks through `lockFor`, which re-checks under the lock that a non-owner still has the project assigned to their own live artist profile (a 404 otherwise): `findFor` runs before the lock, so a request that waited while an owner reassigned the project must not write to it. TAT-46 adds the manual moves (`app/modules/projects/moves.ts`: `hold`, `resume`, `decline`, `withdraw`, the table the page's buttons come from) through `ProjectService.move` (`ProjectRuleError` `move_not_allowed`, or `deposit_paid` when a withdrawal would close a project that holds verified deposit money: `depositHeld`, from `DepositService.verifiedPaid`; declining and withdrawing cancel scheduled sessions), `assignArtist` (owners only, a 404 for anyone else), `updateNotes`, `markContacted` (the chat links call it in the background), and `list` / `countByStatus` for the projects list: Active is every status but `declined`, `cancelled` and `completed`, 25 per page, the same visibility as `findFor`. The list reads only `tattoo_projects`; client names, artist names and the "booked, no session" flag come from `ClientService.findMany`, `ArtistService.list` and `SessionService.projectsWithScheduledTattoo`. Projects are never deleted from the dashboard: declined and withdrawn ones are Closed. They throw `QuoteRuleError` with a reason (`project_closed`, `not_quoted`, `quote_changed`, `expired`). There are no drafts: saving issues the next version. `ExpireQuoteJob` imports `ProjectService` inside `handle()`, because `ProjectService` imports the job. Pure helpers (totals in bigint, money and date formatting, `expiresAtFor`: the start of the day after the chosen date in the tenant's timezone, the chat message and links) are in `#modules/projects/quotes`. The dashboard has the projects list (`/t/:tenant/projects`), the project page and its routes under `/t/:tenant/projects/:id` for owners and the assigned artist. `pnpm seed:dev` (development only, run as the owner role) gives each tenant without a project a demo project to open.
- Inquiries (TAT-46): `InquiryService` (`#modules/inquiries/services/inquiry_service`) reads the inbox (`listNew` oldest first, `listDecided` latest decision first, 25 per page; `countNew` for the Inbox badge, shared as `inboxCount` for owners; `findFor` / `find`; `images` by inquiry or project; `imageCounts`) and decides inquiries: `accept(tenant, inquiry, artistId)` locks the inquiry, refuses one that is no longer `new` (`InquiryRuleError` `already_decided`) or a non-live artist (`artist_unavailable`), creates a `reviewing` project through `ProjectService.createFromInquiry` (brief = the idea), sets `project_id` on the inquiry's live reference images (they keep `inquiry_id`) and records `accepted` with `decided_at`; `decline` records `declined`. Both are final. The `/inbox` routes are owners only (reference images are private to owners until a project is assigned; the project page then shows them to its assigned artist too, in its Request section). `ImageService.storeBytes` stores in-memory bytes like an upload (the dev seeder's generated references). `pnpm seed:dev` gives each tenant without inquiries three new demo ones with generated references.
- Clients (TAT-41): `ClientService` (`#modules/clients/services/client_service`) has `find` / `findMany` (other modules' lookups), `findFor` (a 404), `findByPhone` (E.164; what intake, TAT-51, and direct bookings, TAT-43, match on), `create` (a booking's new client, TAT-43; `ClientRuleError` `phone_taken` from the same index), `list` (newest first, 25 per page; a search matches part of the name in any case, literally, or with at least 3 digits part of the phone's digits) and `update` (owners' edits under the row lock: `ClientRuleError` `phone_taken` from the one-live-client-per-phone index, `anonymized` for a client whose details were deleted). Only an owner's edit changes a client: intake records what was submitted on the inquiry's frozen copy. The clients pages (`/t/:tenant/clients`) are owners only; the profile's history comes from `ProjectService.forClient` / `countsForClients` / `lastChangeForClients` and `InquiryService.forClient` / `latestForClients` / `imagesFor`, so the clients module reads no other module's table. Chat and call links are in `#modules/clients/contact_links`.
