# Dashboard UI conventions

Read before changing dashboard components, forms, styling or SSR. Dashboard UI lives in `inertia/pages`, `inertia/layouts`, `inertia/components`, `inertia/hooks` and `inertia/css/app.css` (Tailwind entry and theme tokens). Backend and test guidance is separate: [backend](backend.md), [testing](testing.md).

## Stack and rendering

- Inertia + React. The SSR entry exists in `inertia/ssr.tsx`, but SSR is disabled in `config/inertia.ts`.
- Tailwind CSS v4 and shadcn/ui (new-york style, Radix, lucide icons; same `components.json` settings as the storefront). The theme is Stencil & Ink (TAT-97; [direction C](../../../docs/superpowers/specs/2026-10-20-ux-stencil-and-ink-design.md)): the tokens live in `inertia/css/app.css`, see [Theme](#theme-stencil--ink).

## Components, forms and theme

- Build UI from shadcn components in `inertia/components/ui` and semantic tokens (`bg-background`, `text-muted-foreground`); don't add custom CSS classes. Use `cn` from the `cn` package.
- Add components from `apps/platform` with `pnpm dlx shadcn@latest add <component>`, then run a focused Biome check on those files from the root (see [validation](../../../docs/agent-workflow.md#validation)). Don't edit generated components just to satisfy Biome; it relaxes a few lint rules for `**/components/ui/**`.
- Forms post with `Form` from `@adonisjs/inertia/react` and are validated server-side with VineJS. Lay fields out with shadcn's `FieldGroup` / `Field` / `FieldLabel` / `FieldError`, setting `data-invalid` on `Field` and `aria-invalid` on the control (see `inertia/pages/auth/login.tsx`).
- Dark mode follows `data-theme` on `<html>`, rendered from the `app_theme` cookie, and Tailwind's `dark:` variant is keyed to it. Use `useTheme` from `~/hooks/use-theme`, not `next-themes`. A first visit has no cookie, so the layout renders `data-theme="system"` and a small inline script in `resources/views/inertia_layout.edge` resolves it to the phone's light or dark setting before the first paint (no flash), and keeps following it until the toggle writes the cookie; from then on the toggle's choice wins. If a Content-Security-Policy is ever enabled (`config/shield.ts`), that script needs a nonce or a hash.
- Import frontend code with the `~/` alias (`~/components/ui/button`).
- Chat links (TAT-52, TAT-104): `ChatMessage` and `ChatLinks` (`inertia/components/chat_message.tsx`) are the one way to draw a WhatsApp, Viber or Call link; each tap calls back with its channel so the page records the last contact. Hand an `onClick` a wrapper (`() => markContacted()`), never the recording function itself, or the click event becomes the request body. The "Message the client" card is `inertia/components/message_card.tsx`.
- A message and its ways (TAT-104): `ChatMessage` draws the text folded to two lines, one leading button and one "Other ways" row, in the Message card, the Quote card and the Deposit card alike. The preview is the one place a line clamp is allowed on text that can hold a client's name (`line-clamp-2`, with `leading-normal` so Devanagari isn't cut): a "Show message" / "Hide message" `Button` above it carries `aria-expanded` and `aria-controls`. `useFold` (`components/fold.ts`, React only, so a unit test loads it) shows the toggle only when the folded text really overflows, so a short message has none: it measures when the preview mounts, when the text changes (a preserved Inertia update can need a third line while the clamped box keeps its size and no resize fires) and on resize; when the toggle goes with nothing left to fold, focus moves to the text (`tabIndex={-1}`) instead of falling to `<body>`; a failed copy opens the text so it can be selected. The leading button is "Send on WhatsApp", or "Copy and open Viber" when the last contact was a message on Viber: `primaryChannel` (`components/messages.ts`, a call or a copied text doesn't count) reads the page's `lastChannel`, and `primary` is a required prop of `ChatMessage`, so the type checker finds a call site that forgets it. The "Other ways" row is `otherWays`, in order: the channel that doesn't lead, Call, Copy text, "Chat without a message" (a chat on the leading channel, no text); the Message card passes `plain` (its links and a callback that records without a message kind), the Quote and Deposit cards don't, so their row is the other channel and Copy text. Viber's link can't carry text, so its click handler (`tapViber` in `messages.ts`) starts the copy and records `viber` inside the tap and returns: the anchor opens the chat by its own default action in the same tick, as the link did before TAT-104. An `await` before the navigation can lose the user gesture that iOS Safari requires for a custom scheme, so no handler in the block may wait for the copy or call `preventDefault` (`tests/unit/inertia/message_block_source.spec.ts` scans for the latter). The one toast (`VIBER_HINT`, besides the page's own "Marked as contacted.") comes when the copy settles, which can be after Viber has opened, so staff may see it on coming back; a refused copy (no clipboard on a LAN `http` page, or a denied write) still opens the chat, records `viber`, and opens the text to select. Below `sm` the card is compact (`max-sm:gap-3 max-sm:py-4`, the last-contact note on the title's line when it fits, the leading button full width); from `sm` the leading button keeps its own width and the kind chooser is 18rem wide. No message to offer (a decided inquiry, a quoted project whose message is in the Quote card) keeps the three plain links under "Open a chat with the client:".
- Tap targets (TAT-103): below Tailwind's `lg` (1024px) every `Button` size, `Input`, `SelectTrigger`, `SelectItem` (the rows of an open list, such as the time zones) and every dropdown menu row is at least 44px, and from `lg` the compact shadcn sizes apply (default 36px, `sm` 32px, icon 36px), so the desktop keeps its density. The rule lives in the components as `max-lg:min-h-11` (`max-lg:size-11` for icon sizes): a minimum, not a fixed height, so a call site's `h-auto` (a studio name that wraps) still grows. A call site needs no `h-11` of its own; the older ones stay and are 44px at every width, so don't strip them without checking the desktop. A raw `<select>` or `<input>` adds `max-lg:min-h-11` itself, and a `SelectTrigger` ignores a plain `h-*` class (its `data-[size]` height wins). `Checkbox` and `RadioGroupItem` keep their 16px mark and gain an invisible 44px hit area below `lg` (an `after:` box, pulled out 15px because the mark's border sits inside it); keep a row at least 44px tall around each so two areas never overlap. A bare text link that is a control (the list pages' Previous and Next) is padded to 44px with `-my-3 flex min-h-11 items-center`, which keeps the row's text height; a link inside a sentence (the "check it under Payments" note) stays inline. `tests/unit/inertia/tap_targets.spec.ts` pins the component rules; heights themselves are measured in a browser at 375px. The Projects status chips are one row that scrolls sideways below `lg` (it bleeds to the screen edge, snaps, hides its scrollbar and scrolls the current chip into view on load) and wrap from `lg`; the Calendar's artist filter applies on change, with no button: a pick with the mouse or a finger is one `router.get` (view and date kept, `preserveState` so the select stays mounted and keeps focus), while a change made with the arrow keys on the closed select waits for Enter, Tab or blur, because the browser changes the value at every key press and loading the calendar at each one would be a change of context nobody asked for. Chromium opens the picker on Enter, so the handler takes the key itself when a change is waiting.
- Finishing (TAT-111): the project page's Finish panel (`FinishPanel`, `inertia/components/finish_card.tsx`, its words in `components/finish.ts`) is the body of the Next step card on an in-progress project (owners) and a healing check (owners, and the assigned artist without a button); the card's title is the same phrase (`FINISH_TITLES`, pinned against the server's `nextStepOf` by `finish_copy.spec.ts`). Its step is confirmed in an inline panel (focus starts on "Not yet", Escape closes it and returns focus), never `window.confirm`; a refused amount (the `confirmedDue` field error, only a hand-edited request can send one) shows under the buttons as a `FieldError` that the confirm button points to with `aria-describedby`, and the panel stays open. When a step is done the focused button is gone (the panel is replaced or removed), so `show.tsx` moves focus to the page's `h1` through `Page`'s `titleRef` (the heading gets `tabIndex={-1}`, like the Payments card's); a keyboard or screen-reader user then lands on the client's name, not on `<body>`. Closed projects (the `closed` prop) show no artist picker and no "Mark contacted".
- Project page (TAT-108): `inertia/pages/projects/show.tsx`. The header says who it is for (`h1`, the client's name), the piece (the start of the brief, `project.piece`, as the Projects list words it), the status badge, "With Asha" or "No artist yet" and "View client" (owners), then `ProgressLine` (`components/progress_line.tsx`: Review, Quote, Deposit, Sessions, Done as five dots; `progressOf` in `components/project_page.ts` decides which are done, a completed project has all five and a declined or cancelled one none, because we don't store how far a withdrawn project got; `aria-current="step"` on the current step and an `sr-only` ", done" or ", now" after a label) and, below `lg` only, `payments.summary`. `Page` has an optional `details` slot for this. Then ONE Next step card (`components/next_step_card.tsx`): the server chooses it (`nextStep`, see [backend](backend.md#clients-inquiries-and-projects)) by the same rules as Today and the Projects list, and sends its words, a primary action, secondary actions (names from `NEXT_STEP_ACTIONS`) and an `anchor`; the page draws each name with the component that already does it (the screenshot's `PendingProof` blocks, the first quote's `QuoteForm`, the quote's `ChatMessage`, `AcceptQuote`, the Revise, Record payment and Schedule sheet triggers, `DepositPanel`, `FinishPanel`, the deposit's `OutcomeForm`, Resume, a link to `#sessions`), so there is one place to look and no rule in the browser (`layoutOf` only sorts blocks from buttons). A marigold dot and an `sr-only` "Needs you:" mark a step that waits on the studio. Anchors: `WAITING_HASH` (the cards Today's rows and the Projects list's lines open), the screenshot alert's `#payments` and the day agenda's `#sessions` all land on this page. The Next step card carries the id of its `anchor` (`id={nextStep.anchor}`) and the card that normally owns that id gives it up (`cardId` in `project_page.ts`), so each of `payments`, `quote`, `quote-form` (also on the Revise trigger wherever it is drawn), `deposit` (also on the deposit panel wherever it is drawn) and `sessions` appears at most once (`idsOnPage` says which; the agreement test checks every link Today's rows carry, and a browser run compares the DOM) and a link lands on the card that holds the action (Today's "Deposit screenshot to check" opens Verify and Reject; "Price sent" opens Client accepted); each carries the top-bar `scroll-mt` rule. `placementsOf` (`components/project_page.ts`, pure; `tests/functional/projects/page_affordances.spec.ts` pins it against what the pre-TAT-108 page offered, per status) says where every control is drawn: in the Next step card when it names the action (and then not again in its own card), else in the card that owns it. So nothing the page offers vanishes where the Next step table does not name it: the Quote card draws the quote's message (a held project's), Client accepted and the first quote; a Deposit card (`DepositCard`, right column) draws the deposit panel while a screenshot to check or a price that ended is the step; the Sessions, Payments and Quote cards draw Schedule, the money buttons, the screenshots, the outcome form, Set price and Revise. The Finish panel follows the same rule: the Next step card holds it when it names the step, and while something else is the step (a deposit screenshot nobody decided after the money was recorded at the desk) a Finish card (`FinishCard`, left column under the Next step) draws it, so finishing and the healing check's close stay reachable. The one control dropped on purpose is an owner's Finish panel while a session is scheduled or under way (the step is that session, finishing is refused, and the old panel held no button either). Below that, in DOM order (a phone reads it, and Tab follows it): Sessions, Message the client (its "Mark contacted" button lives here, with the contact line), the Request (the whole brief, the details and the references; "About the piece" for a direct booking), Notes, and "Change this project" (`components/change_card.tsx`: the owner's artist picker, Put on hold or Resume, Client withdrew, Decline; the last two ask inline; Resume is left out when the Next step offers it). Payments and Quote form the right column from `lg` (`lg:col-span-5`, `lg:sticky lg:top-6`, scrolling inside itself when an opened ledger is taller than the screen) beside the left one (`lg:col-span-7`); below `lg` they follow the left column. The Payments card leads with the server's one-line summary (`payments.summary`: "Paid NPR 5,000 of NPR 20,000 · Balance NPR 15,000"; the assigned artist gets it read-only too), the deposit line and the recorded outcome; the ledger is behind "Show payments (N)" (`aria-expanded`, `aria-controls`; closed on load, Reverse still confirms inline), waiting screenshots are never behind it, and Record payment and Record a refund are sheets. The assigned artist sees the card READ-ONLY, as the requirements give them (docs/requirements.md:87, TAT-30): the summary line, the balance and the ledger, with no screenshot, no deposit link, no Reverse and no form, button or sheet (`pending` is empty, `actions` and `outcome.needed` are null, so `placementsOf` places no money control). The Quote card shows the current quote, Set price (a sheet) for a booking made without one, Revise the quote (a sheet) and "Earlier versions (N)" behind a button. A closed project (declined, cancelled, completed) offers no change to the project itself and keeps money settlement and notes: see the table under [Closed projects](#closed-projects). On a phone the first screen holds the Next step title, and for the usual cases its action (a waiting screenshot's Verify and Reject, the first quote's price field, Client accepted): the screenshot is a thumbnail beside its facts in that card (`PendingProof compact`), and the first quote's Fixed price and Hourly choices sit side by side. The deposit's outcome form in the Next step card (`OutcomeForm embedded`) has no box or heading of its own, because the card's title already asks the question. An artist's quote form (TAT-16, `form.depositFloor`): the Deposit field's note is the studio's minimum (`depositFloorHint`: "At least NPR 3,000, your studio's 20% deposit. Only an owner can quote less or no deposit.", or "Only an owner can quote without a deposit." when the studio has no default) in place of the owner's three lines, and the server's refusal shows under the field instead of the note (the same sentence, with "Enter at least"); an untouched Deposit field is filled in by `depositAutofill` and is never under the minimum, in a first quote or a revision, so keeping it is never refused (an owner's is the plain suggestion, as before); in a studio whose default is 0% an artist sees the owner's lines, since they may offer none. On a quoted project whose deposit is under what an artist can offer (`ownerAccepts`) there is no "Client accepted" anywhere on the page, and the Quote card says "An owner confirms this quote when the client agrees: its deposit is below what an artist can offer."
- Book a session (TAT-43, TAT-16): `inertia/pages/projects/new.tsx`, step 2 for a number already in the studio. An owner sees the client's name and "View client"; an artist sees "A client with this number is already in the studio." in its place (`lookup.client.name` is null for them), then the phone, the "Returning client" badge and "Their saved name, email and notes stay as they are." The form still posts the client's id. The sentence wraps like the name did (`text-sm break-words`), and the badge wraps under it on a phone.
- Sheets and inline confirms (TAT-108): the five forms the page uses rarely open in a bottom sheet (`components/ui/sheet.tsx`, the shadcn sheet on Radix Dialog from `radix-ui`; it slides up on every width, at most 90% of the screen high and scrolling inside, clear of the safe area, and from `lg` centred and 36rem wide; its overlay is the `bg-background/80` token; its close "x" is the shared icon `Button`, 44px below `lg`, and motion respects `prefers-reduced-motion`): Revise the quote, Record payment, Record a refund, Set price and Schedule a session (`usePageSheets`, `FormSheetTrigger`, `FormSheetPanel` and `FormSheetActions` in `components/form_sheet.tsx`). Each sheet is ONE instance held by the page and mounted once (`show.tsx` renders the five panels; the cards only draw triggers), because the Next step can move a trigger to another card while its sheet is open (a stale Revise whose refusal returns the project in another status) and a sheet that lived in its trigger's card would unmount with the refusal; a panel whose data is gone closes and can't reopen by itself, and the page's toast is dismissed only while a sheet shows its message. Radix does the focus (into the sheet on open, trapped inside, Escape, the close button, Cancel and a tap outside all close it) and focus goes back to the trigger, or to the page `h1` when a save removed the trigger (`focusBack`). Every form keeps its fields, route and validation; each stays a controlled form that mounts when the sheet opens, so it starts fresh each time. A sheet that has just saved is inert at once and its form's submit is refused (`maySubmit`, applied to a ref mirror of the state): Radix keeps a closing sheet and its filled-in form on the page for its exit animation, and a held Enter would otherwise send a refund twice. The close button stays on screen while the form scrolls (the sheet scrolls in an inner box) and is disabled with `aria-busy` and a title while a save is out. A sheet closes only after a save that went through: `sheetStep` (`components/sheets.ts`, pure and unit-tested, with `sheetAfterSave`) keeps it open when the rules refuse the save (an error flash comes back as a successful visit, so its message is shown inside the sheet in a `role="alert"` paragraph, because the toast's live region is hidden from screen readers while a modal is open) and while a request is out (nothing is dismissed, so an answer is never lost), and a field error leaves it open under its field with what was typed, because the page stays mounted (Inertia keeps a form's page mounted); the Revise form is keyed by the quote it was built from, so a refusal because someone revised the quote meanwhile remounts it with the new terms while the sheet stays open. Refund and Set price confirm by naming the amount on the submit button ("Record refund of NPR 2,000", "Set the price to NPR 15,000": `refundLabel`, `priceLabel`) with the consequence in the sheet's description; nothing asks a second time. One-tap actions ask in the page with `InlineConfirm` (`components/inline_confirm.tsx`; the state is `confirmStep` in `components/confirm.ts`, pure and unit-tested): Decline and Client withdrew (project), New deposit link and Decline (inquiry). The question, the confirm button and the safe button show under the trigger (`aria-expanded`, `aria-controls`), focus starts on the safe one so Enter right away changes nothing, Escape or the safe button closes it and returns focus, nothing closes it while the request is out, and the answer (whatever it was) closes it and moves focus to the trigger or, when the answer removed it, the page `h1`. Never put an inline confirm inside a sheet (Escape would close the sheet). `tests/unit/inertia/inline_confirms_source.spec.ts` fails for a `window.confirm`, a `confirm(` call or an `onBefore=` on the project and inquiry pages and in `components/*.tsx`, and for a sheet's state living in a card; Settings (members, payment methods) and Artists still ask with the browser's box, a follow-up.

- Inquiry page (TAT-100): the page reads top to bottom as the artist thinks (status of a decided request, Idea, References, Details, Message the client, then Decide); the artist picker and the Accept and Decline buttons are 44px, the picker full width; the Details list is `grid-cols-[auto_minmax(0,1fr)]` with `min-w-0 wrap-anywhere` values, so an unbroken email or placement wraps inside the card instead of widening the page; the client's phone is a `tel:` link built from the server's `contact.callUrl` (the same link as the Message card's Call button) that never wraps, with its 44px tap target pulled back by a negative margin so the row keeps its text height. Tapping it records the contact as a call (`() => markContacted({ channel: "call" })`, the wrapper rule of Chat links above), and a tap on the Call button is a separate record. `/` has no page: it redirects (see [backend](backend.md#accounts)).
- Studio link and setup checklist (TAT-101): `StudioLinkCard` (`components/studio_link_card.tsx`) is the one way to show the studio page link: the URL as selectable text, "Copy link", "Open" and "Share on WhatsApp", all using the same `studioPage.url` from the server (`studioLinks`), never a URL built in the browser. `CopyLinkButton` copies exactly the text it is given and says "Couldn't copy: select the link instead." where there is no clipboard (plain http on a LAN). While `studioPage.devHost` is true (STOREFRONT_URL unset in development), the card shows `DevHostWarning`, the same warning as the deposit panel. It lives on Settings, Profile (always) and in the empty New view of the Inbox; artist cards on the Artists page show their own `pageUrl` with Copy (none while hidden). `SetupChecklist` (`components/setup_checklist.tsx`) draws the server's `setup` prop on Today (TAT-107; owners, until all four steps are done; it used to sit on the Inbox): the first open step is highlighted and marked "Next", done steps carry a check icon and read "done" to a screen reader, and each step links to where it is done (the last opens the studio page). The slug boxes on onboarding and Settings use the real host from the `addressHost` prop (`prefix` and `suffix` around the slug), never a hard-coded domain, and are labelled "Your page link".
- Pilot numbers (TAT-70): `PilotMetricsCard` (`inertia/components/pilot_metrics_card.tsx`) shows the server's worded `pilotMetrics` at the bottom of Today (TAT-107; owners only, `null` for artists): three label, value and detail tiles in a `dl` (stacked on phones with a rule between them, three columns from `sm`), text tokens only, no chart. It sits last so what needs the owner stays on the first screen of a phone.
- Today (TAT-107): `inertia/pages/today/index.tsx`, every member's home (`/t/:tenant` redirects there; so does joining a studio). The server decides every group, row, count, word and target (`TodayController`, `WaitingService`, see [backend](backend.md#clients-inquiries-and-projects)); the page only lays them out, so its words are in `components/today.ts` (`GROUP_TITLES`, `moreText`, `emptyText`, `setupFirst`, unit-tested). Sections, top to bottom on a phone: the setup checklist first only when nothing needs the owner (`setupFirst`), "Needs you" (one card; per non-empty group an `h3` with a marigold dot, its count at the right, then rows, then a "See all N in the Inbox" / "See all N on Projects" link (violet, the `link` button variant, 44px below `lg`) when the group has more rows than the five shown; on Projects it opens `?waiting=<group>`, that group's rows and no others, TAT-109; the owner's "Payment screenshots to check" group is the exception and shows every row with no link, because an unresolved payment is never hidden behind one), "Today's sessions" (the day agenda with the Now marker, an "Open the calendar" link), "Waiting on clients" (rows without dots, the last contact on each), the checklist otherwise, and the pilot numbers last (owners). From `lg` they are a 12-column grid: Needs you and Waiting on clients (and the late checklist) in the left 7 columns, Today's sessions in the right 5 beside them, so there is no empty third. A row is one `Link` (name `wrap-anywhere`, detail, muted meta, a chevron; 44px tall below `lg`) to the page and the card where the member acts: the server sends `{ route, id, hash }` and the page appends `#hash`. The project page carries the ids `payments`, `quote`, `quote-form`, `deposit` and `sessions` (each once, on the Next step card when it holds the action, else on the card that owns it; see the Project page bullet above), each with the top-bar `scroll-mt` rule; keep them or change `WAITING_HASH` in `#modules/projects/waiting` with them, because a missing id only scrolls to the top. Empty states are plain sentences that say what shows up there. The day agenda (`DayAgenda`, `NowMarker`, `SessionItem` and `useNow` in `components/day_agenda.tsx`) is shared with the calendar; its client name wraps and a session opens its project at `#sessions`. An owner's Today also keeps a withdrawn project whose deposit screenshot nobody decided (its row opens the project's Payments card, where the Verify and Reject buttons are) until it is decided, and a paid project whose quote expired stays under "Sessions to book". An artist's Today holds only their own projects and sessions (no requests, screenshots, deposit links, setup, studio link or pilot numbers; a project of theirs with a screenshot waiting shows as one waiting for the deposit). The page follows the browser's clock for the Now marker, but the date and the groups are as of the page load: a tab left open past the studio's midnight is stale until it reloads.
- Projects list (TAT-109): `inertia/pages/projects/index.tsx`. The server decides the rows, their order and every word of a row (`ProjectsController.index`, `#modules/projects/project_list`, see [backend](backend.md#clients-inquiries-and-projects)); the page lays them out, with its links, the card's fallback line, the empty sentences and the table caption in `components/project_list.ts` (unit-tested). Chips, in one row that scrolls below `lg`: Active, Needs you (a marigold dot, `aria-hidden`; its number is the Today badge's), the seven open statuses, Closed. Today's "See all" opens `?waiting=<group>` (or `on_client`): the same rows in the same order under the parent chip, which is `aria-current="true"` there (`"page"` in a plain view), with an `h2` naming the group and its count and a "Show all that needs you" / "Show all active projects" link back. Below `lg` each project is a card, one `Link` (to the page, plus `#hash` when its line names the card to act on): the client's name and `StatusBadge`, the piece (the start of the brief until TAT-115 gives it a title), one line, and the owner's artist ("With Asha", "No artist yet"). The line is what waits (words from `WaitingService`, with the marigold dot and an `sr-only` "Needs you:" when it needs the member), else an owner's one plain money line ("NPR 15,000 still due" or "Record whether the deposit was kept or refunded", never marked as needing you; a waiting screenshot and a price the sweep spares are always WaitingService's, so the list words neither itself), else the next session that has not started ("Next session Sat 24 Oct, 11:00"; one already under way is not named). The money line wins over the session on a card (a healing check with a balance due and a touch-up booked says what is due); the table's Next session column still names the session. A two-option "Sort: What needs you / Last contact" switch (`lg:hidden`; both choices are links kept mounted and the chosen one carries `aria-current="true"`, so activating one keeps keyboard focus on it; the chips, the back link and Previous / Next keep the page's state too, with `preserveState`, for the same reason) appears in the Active and single-status views; in the contact sort a card's last line also gives the contact ("Contacted 2 days ago on WhatsApp (Quote)", or "No contact yet"). "Never contacted" is not shown on the list's rows (Today's "Waiting on clients" rows and the project page still say it). From `lg` the list is a shadcn `Table` (`components/ui/table.tsx`) with Client and piece, Status, Waiting, Next session, Artist (owners only) and Last contact; shadcn's cells are `whitespace-nowrap`, so the text columns and their heads are `whitespace-normal`, every cell `align-top` and names `wrap-anywhere`, so a long Devanagari name wraps instead of widening the table. "Waiting" and "Last contact" sort: each head holds a real `Link` (sorting is a visit; Enter works, and the link has `preserveState` so Inertia keeps the page mounted and focus stays on it, where a plain visit remounts the page and drops focus to `<body>`), `aria-sort` is on the sorted column's `th` only (`other` on Waiting, which is a rank, not an order of its words, and `ascending` on Last contact) and the heads are plain text in waiting and closed views, which keep their own order. The pager's Previous, from a page past the last (a stale address), goes to the last real page. An empty cell is `–` with an `sr-only` "None"; an `sr-only` caption says the order. A client's name is the row's link (no clickable `tr`). ### Closed projects

A declined, cancelled or completed project is read-only for the project itself: no status move, no artist picker, no quote form, no message to send for the quote or the deposit, no scheduling, no finish step, no "Mark contacted". Money settlement and notes stay possible, because a studio must be able to settle what a closed project holds. `tests/functional/projects/page_affordances.spec.ts` pins every row below (and that an artist's card is read-only). The writes the server still accepts are in [backend](backend.md#clients-inquiries-and-projects).

| Status and condition | Offered to an owner | Not offered |
|---|---|---|
| Completed, a fixed price still owed | The Next step: "NPR 15,000 still due" with Record payment; Record a refund, Reverse, Show payments; Notes; the chat links (aftercare) | Moves, artist, quote, scheduling, Mark contacted |
| Completed, paid in full | Record payment and Record a refund (Money card), Reverse, Notes, the chat links | the same |
| Completed, booked without a price | Set price (Quote card), Record payment, Notes, the chat links | the same |
| Declined, no deposit | Notes, the chat links, an undecided screenshot's Verify and Reject | Record payment (declined takes none), everything above |
| Declined, holding a deposit | The Next step: record whether the deposit was kept or refunded; Reverse; Notes; the chat links | the same |
| Cancelled (withdrew), holding a deposit | The Next step: the deposit's outcome; Record payment (session and balance), Reverse; Notes; the chat links | the same |
| Cancelled, a screenshot nobody decided | The Next step: Verify and Reject (the outcome follows in the Payments card); Record payment; Notes; the chat links | the same |

An artist on a closed project sees the same page with the Payments card read-only (the balance and the ledger, nothing to record, refund, reverse or verify; docs/requirements.md:87) and nothing to change except Notes and the chat links (and Set price on a completed project booked without one).

## Phones and slow connections

Check every page against these:

- Open-ended lists are paginated (25 per page); a view bounded by a range (the calendar's day or week) lists the whole range instead. Props carry only what the screen shows.
- Images in lists and grids are lazy-loaded thumbnails, never the full-size file. Reference grids use `thumbnailUrl` and artist photos `photoUrl`, both the 320 px copy (`ImageService.urlFor` with `THUMBNAIL_WIDTH`, TAT-112); the link opens the full image. It is one fixed copy, with no `srcset`: soft on a 3x screen, accepted for a thumbnail.
- Forms disable their button and say "Saving…" while a request is in flight.
- Optimistic UI only for reversible single-field changes (notes, "Mark contacted"); never for money, quotes, status moves, or accepting and declining.
- Touch targets are at least 44px below `lg` (see Tap targets under Components), and nothing is wider than 375px.

## Theme (Stencil & Ink)

- One vocabulary with the storefront (`apps/storefront/src/styles.css` carries a copy of the palette: packages can't import from apps, so change both together): `--paper --surface --ink --ink-muted --line --line-strong --stencil --stencil-strong --stencil-wash --on-stencil --marigold --destructive --on-destructive --paper-shade`, plus `--display-face`, `--body-face` and `--radius` (4px). shadcn's names are mapped onto them in `app.css` (`--background` is paper, `--card` is the surface, `--primary` is the stencil violet, `--input` is `--line-strong`, `--accent` and `--secondary` are the violet wash, `--muted` is `--paper-shade`), so components keep using `bg-primary`, `text-muted-foreground` and so on. Never write a hex value or a Tailwind palette colour (`zinc-500`, `text-white`) in a component: use a token; `--on-destructive` is the text on a destructive fill (`text-destructive-foreground`).
- Light and dark values, their measured contrast and the one place dark `--line-strong` departs from the spec are in the comment at the top of `app.css`. Body text is at least 7:1, muted text 4.5:1 and input borders 3:1 on the surface they sit on; measure again after changing a token.
- Violet is for actions, focus and the selected state; marigold is a dot or a bar ("needs you", today), never text. Radius is 4px everywhere (`rounded-md`, `rounded-lg` and `rounded-xl` all resolve to it); `rounded-full` stays for dots and counts.
- Fonts are vendored in `inertia/assets/fonts/eczar/` with their OFL licence: Eczar 700 (Latin, Latin Extended, Devanagari; `font-display: optional`, each subset downloads only when a page holds its characters). Use it (`font-display` class) only for the page `h1` (`components/page.tsx`), the studio name and the wordmark (`components/logo.tsx`); everything else is the system stack. There is no preload: the first view of a session may show the system serif, and the font is used from the next view. Never add letter-spacing, uppercase, an ellipsis (`truncate`) or a line clamp to text that can hold a client's name (Devanagari; the message preview's two-line fold, which has a visible toggle, is the one exception); the studio name in the switcher and the person's name and email in the account menu wrap (`wrap-anywhere`; the sidebar's name button grows with `h-auto min-h-9`); keep line height at 1.35 or more in headings and 1.5 in body text.
- Status colours (TAT-98): show a project's, an inquiry's or the "Screenshot to check" flag with `StatusBadge` (`components/status_badge.tsx`), never a plain `Badge`. `STATUS_GROUPS` in `components/projects.ts` puts every status in exactly one group, which sets the colour, the mark and the tooltip: waiting on the studio (marigold dot, new request, reviewing, screenshot to check), waiting on the client (clock; quoted, on hold, deposit pending), booked (calendar tick), in the chair (pen; in progress, healing check) and closed (archive; completed, accepted, declined, cancelled). The word is always shown, so nothing relies on colour alone. A new status goes in `STATUS_LABELS` and `STATUS_GROUPS` together; `tests/unit/inertia/status_groups.spec.ts` fails until it does, and a status nobody mapped reads as closed. The colours are the `--status-{studio,client,booked,chair,closed}-{fg,bg}` tokens (text on its wash, 4.5:1 or better in both themes, measured in the comment above them in `app.css`).
