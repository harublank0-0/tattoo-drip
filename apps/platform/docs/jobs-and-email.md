# Jobs and email conventions

Read before changing workers, queued jobs, delivery or mail templates. For jobs that change tenant-owned data, also read the relevant [backend](backend.md) section; for new tests consult [testing](testing.md).

## Emails

- Emails are Edge templates with inline styles and table layout: no `<style>` blocks, CSS inliner or MJML.
- Shared parts are components in `resources/views/components/email/`. Wrap every email in `@email.layout({ title, preheader })` and use `@!email.button({ href, text })` for calls to action.
- Each email is a `BaseMail` class in `app/modules/<module>/emails/`, next to an HTML template and a `_text` template. HTML templates print with `{{ }}`; text templates print with `{{{ }}}` so URLs keep their `&`. Guard optional values: Edge prints `undefined` and `null` literally.
- Mail classes never set `from`; `config/mail.ts` always sends from the platform's domain.
- A module with templates needs one `edge.mount("<module>", …)` line in `start/view.ts`; its templates are then `<module>::emails/<name>`. `metaFiles` in `adonisrc.ts` copies `app/modules/**/*.edge` into the build.
- Send with `mail.sendLater(...)`: the messenger in `start/mail.ts` queues a `SendMailJob` that the worker sends. Use `mail.send(...)` only inside a job. An email that must go out only if a transaction commits is sent from a domain job queued with `dispatchInTransaction`.
- To send an email only if a job's transaction commits, use `sendMailInTransaction(email, trx)` (`#services/mail_in_transaction`, TAT-52): it builds the mail and queues its `SendMailJob` with `dispatchInTransaction`, where `mail.sendLater` queues outside the transaction. Tie each email to the row that records it, and a retried job never sends twice.
- Template data is stored as JSON until the worker renders it: templates see serialized fields only (`user.fullName` works; getters and methods don't, and dates become strings). Pass plain values for anything computed.
- Queued mail can't carry `Buffer` or stream attachments; they don't survive JSON. Attach by file `path` or URL, or build the email inside a job and use `mail.send`.
- In development, run `pnpm worker` next to `pnpm dev`, or queued emails never reach Mailpit.

## Jobs

- `@adonisjs/queue` with the `database` driver: jobs are rows in `queue_jobs` in the app's own Postgres, run by a separate worker (`pnpm worker`, i.e. `node ace queue:work`). It doesn't reload on code changes; restart it after editing a job.
- Shared plumbing such as `SendMailJob` lives in `app/jobs/` (`#jobs/*`). Domain jobs live in `app/modules/<module>/jobs/`. The worker loads every file in those folders as a job, so put nothing else there.
- Defaults in `config/queue.ts`: 3 retries with exponential backoff (5s up to 5m); completed jobs are deleted, failed jobs stay 7 days with their error. Retries must be the top-level `retry` key: a `retry` inside `defaultJobOptions` is silently ignored (`tests/unit/jobs/queue_config.spec.ts` pins this). `SendMailJob` keeps failed rows for 1 day only, because its payload holds links that work like passwords. Delivery is at-least-once: a worker stopped mid-job reruns it, so make jobs safe to repeat. A job's `failed()` hook runs once retries are used up; log identifying fields under named keys (`err` for the error), never whole objects or secrets.
- Queue a job that belongs to a database write with `dispatchInTransaction(Job.dispatch(payload), trx)` from `#services/queue`, so it commits or rolls back with the data. Inside a request or a `TenantJob`, `trx` comes from `withTransaction((trx) => dispatchInTransaction(job, trx))`, never from `db.transaction` (in production that is a second connection outside the request's transaction; tests will not show it). Don't call `.with()` on that dispatcher; the helper picks the adapter, and it throws if two copies of `@boringnode/queue` are installed.
- Jobs that touch tenant-owned data extend `TenantJob` (`#services/tenant_job`, not in `app/jobs`: the worker registers every file there as a job), implement `handle()` instead of `execute()`, and carry `tenantId` in the payload. `handle()` runs in that tenant's context and one transaction: a throw rolls every write back before the retry, and the worker acknowledges the job only after the commit. A missing or malformed `tenantId` fails the job. Jobs that touch no tenant data (`SendMailJob`; `SweepExpiredQuotesJob`, which reads only ids) extend `Job` and are listed in the allowlist in `tests/unit/jobs/job_classes.spec.ts`.
- Recurring jobs: `start/scheduler.ts`, a preload for the `web` environment only, upserts each schedule into `queue_schedules` by a fixed id when the web server boots (`Job.schedule(payload).id(…).cron(…).run()`; a restart or a second server changes nothing). It does nothing unless the app runs (`app.getMode() === "run"`): `node ace codegen` boots the web environment in warmup mode, where nothing closes the database, so a connection opened there would keep the command from exiting. The worker claims due schedules on every cycle, once per due time with no catch-up after downtime, and runs the job. `node ace queue:scheduler:list` shows them. A new recurring job is one more line there.
- Quote expiry (TAT-64, TAT-83): `ExpireQuoteJob` runs at a quote's `expires_at`. A run that comes early (the worker's clock behind the issuer's) is queued again for the rest of the time by `ProjectService.expireQuote`. `SweepExpiredQuotesJob` runs every 5 minutes as the safety net for a job that used up its retries or was never queued: it lists the current quotes that expired between 24 hours and 2 minutes ago on `quoted`, `on_hold` or `deposit_pending` projects through the SECURITY DEFINER function `expired_quote_candidates()` (ids only, see [database conventions](../database/README.md#row-level-security)) and queues one `ExpireQuoteJob` per row with that row's `tenantId`; `expireQuote` decides each under the project lock. A project is therefore cancelled at most about 7 minutes after its quote expired. A quote whose expiry keeps failing gets a new job every sweep for 24 hours (at most 288 failed rows, each logged by `failed()`); a project stuck longer than that is withdrawn by hand. The sweep itself has a `failed()` hook too ("Sweeping expired quotes failed."): a sweep that keeps failing, such as a runtime role without `EXECUTE` on the function, shows in the logs.
- New-inquiry alerts (TAT-51, TAT-52): `IntakeService.submit` queues `NewInquiryAlertJob { tenantId, inquiryId }` (`#modules/inquiries/jobs/new_inquiry_alert_job`) in the inquiry's transaction, so it exists exactly when the inquiry does. For an inquiry still `new` it logs "New inquiry received." with the two ids and calls `AlertService.newInquiry` (`#modules/notifications/services/alert_service`): every live owner, and the member linked to the inquiry's live preferred artist, gets one `staff_alerts` row and one `NewInquiryMail`, once (unique `(user_id, inquiry_id)`, `insert … on conflict do nothing returning user_id`, and each email queued with `sendMailInTransaction` in the same transaction, so a rerun adds nothing and sends nothing again; a rollback leaves neither). The email holds the client's first name, 140 characters of the idea, the asked-for artist and, for owners, the inquiry's dashboard link (`APP_URL`); never the phone, the email address, the budget or the references, and its subject has no client data (`SendMailJob.failed()` logs it). `ALERT_EMAILS=false` keeps the in-app alerts and queues no email; `start/mail.ts` logs one warning at boot.
- Fresh ink alerts (Reviews and Fresh ink, slice 2): `ClientPostService` queues `FreshInkAlertJob { tenantId, postId, round }` (`#modules/reviews/jobs/fresh_ink_alert_job`, a TenantJob) with `dispatchInTransaction` in the transaction that puts a post in the studio's queue: the client's submit (round 1) and a client's change of an approved post (`backToQueue`, the next round; a change of a post already waiting queues nothing). For a post still submitted, `waiting`, not taken down and still in that round it logs "Fresh ink waiting for approval." with the ids and the round, reads the live project (none: no alert) and calls `AlertService.freshInk`: every live owner, and the member linked to the project's live artist profile, gets one `staff_alerts` row (`kind = 'fresh_ink'`, `post_id`, `post_round`) and one `FreshInkMail`, once per post per round (unique `(user_id, post_id, post_round)`, `on conflict do nothing`, `sendMailInTransaction`). The email names the client only by the name they chose to show, through `emailShownName` (`#modules/notifications/alerts`: each word of name characters, an initial's final dot allowed, else "A client", so "evil.com" is never a link), says whether it is a change ("It is off your page until you approve it again."), and links to the Reviews page (`APP_URL` + `/t/<slug>/reviews`); never the full name, phone, email, caption, photos or a signed URL, and its subject has no client data ("Fresh ink to approve for <studio>"). `ALERT_EMAILS=false` keeps the in-app alerts and queues no email.
- Account emails (TAT-18): `VerifyEmailMail`, `AccountExistsMail`, `ResetPasswordMail` and `PasswordChangedMail` (`#modules/identity/emails/`) take plain data (`to` and the links), print no name, and are queued by `AccountService` with `sendMailInTransaction`. `ALERT_EMAILS` doesn't apply to them: an account can't be confirmed or recovered without them. `PasswordChangedMail` takes `signedOut` (TAT-95): `"everywhere"` for a reset, which signs every device out, and `"elsewhere"` for a change made from the account page, which keeps the device that made it ("…signed out except the one used to change it"); the queued data holds that clause as text (`signedOut`) and what to check if it wasn't them (`checkWho`: "who else can read this mailbox" after a reset, "who else knows your password" after a change, since the person had the password and a session, not the mailbox); a job queued before TAT-95 has neither field, so both templates default them to the first wording (`{{ signedOut || '…' }}`), never "undefined": a new view field on any queued mail needs the same default until the old rows are gone. It links only to `/forgot-password` (a page to ask for a new link, never a token) and goes to the stored address. "Sign out of other devices" sends no email. Their links work like passwords, which is why `SendMailJob` keeps failed rows one day; a failed send leaves the account as it was, and the person asks for a new link.
- Deposit proofs (TAT-65, TAT-88): `DepositPageService.submitProof` queues `DepositProofAlertJob { tenantId, paymentId }` in the payment's transaction, so it exists exactly when the payment does. For a payment still `submitted` it logs "Deposit proof received." with the tenant, project and payment ids (never the link, the token, a URL or the amount), reads the live project (none: no alert) and its client's name, and calls `AlertService.depositProof`: every live owner, and the member linked to the project's live artist profile, gets one `staff_alerts` row (`kind = 'deposit_proof'`, `project_id`, `payment_id`) and one `DepositProofMail`, once per payment (unique `(user_id, payment_id)`, the same `on conflict do nothing` and `sendMailInTransaction` as new inquiries). A client's next screenshot is a new payment (possible only after a rejection) and alerts again. The email holds the client's first name and the project's Payments card link (`APP_URL` + `/t/<slug>/projects/<id>#payments`); never the amount, the method, the reference code, the deposit link or the phone, and its subject has no client data. `ALERT_EMAILS=false` keeps the in-app alerts and queues no email. Today's badge (`todayCount`, TAT-107) counts the projects whose screenshots wait, among others; the owner's bell counts no deposit-proof alert (`bellKinds`).
- Video angles: `ProcessWorkVideoJob { tenantId, photoId }` (`#modules/artists/jobs/process_work_video_job`), on its own queue, `video` (its `static options.queue`), is queued by `WorkPhotoService.addVideo` with `dispatchInTransaction` in the transaction that creates the video's row. It is a plain `Job`, not a `TenantJob`, on purpose, and on the allowlist in `tests/unit/jobs/job_classes.spec.ts`: a `TenantJob` runs `handle()` in one transaction, a transcode takes minutes, and production ends a transaction idle for 3 minutes (`idle_in_transaction_session_timeout`). `WorkPhotoService.processVideo` opens none around the slow part: one short `withDbContext({ tenantId })` reads the row (only a video still `processing` is worked on), then `VideoService.process` runs ffprobe and ffmpeg with no transaction open (it throws if called inside one; `work_video_angles.spec.ts` checks it sees no client), then one more short transaction writes the outcome with one conditional UPDATE (still `processing`, the same staging key). It is safe to repeat: a second delivery, or one that finds the row removed or settled meanwhile, writes nothing and deletes the files it made. A refusal (not a video, over 60 s, over 4K, a missing upload, and ffmpeg that exits non-zero, times out or is stopped) is stored as `failed` with its reason and never retried; only a storage error or a missing ffmpeg throws and retries (3, the queue's defaults). `failed()` logs the ids and, once the retries are used up, marks a still-processing video `failed` (`VIDEO_GAVE_UP`) and deletes its upload. `static options.timeout` is 30 minutes for the whole job (waiting for the one transcode slot included); each ffmpeg run has its own limit and is killed on it, or when the job's signal aborts ([backend](backend.md), Images, Video angles). The worker refuses to start without `ffmpeg` and `ffprobe` on its PATH (`providers/video_tools_provider.ts`, `queue:work` only), naming the one missing; the web server and the tests never need them to boot. **Queues and workers**: the default worker (`queue:work`, the `default` queue only) never runs a transcode, so mail and alerts never wait behind one; the video worker runs `queue:work --queue=video --concurrency=1` (deploy/compose.yml's `video-worker`, with a memory and CPU limit and `stop_grace_period: 5m`), and `QUEUE_MAX_STALLED_COUNT=3` there (config/queue.ts's `maxStalledCount`, 1 by default) puts a job it lost back up to three times. In development run `pnpm worker` and `node ace queue:work --queue=video` beside it, or the videos stay processing. Tests run the video queue with `processQueued(["video"])`. **Stuck videos**: `SweepStuckVideosJob` (`start/scheduler.ts`, every 10 minutes, `*/10 * * * *`; a plain Job on the allowlist) lists the videos still `processing` an hour after they were added, across tenants, through the SECURITY DEFINER `stuck_video_candidates()` (ids only, at most 500; [database conventions](../database/README.md)) and queues one `FailStuckVideoJob { tenantId, photoId }` (a TenantJob) per row, which fails it under the row's lock with "Took too long to process. Upload it again." (`VIDEO_STUCK`) and deletes its upload after the commit (`WorkPhotoService.failStuckVideo`; a video that finished, was removed or is younger is left alone; `stuck_videos.spec.ts`). Restart the workers after changing the job, the processor or the limits. **Client videos** (Reviews and Fresh ink): `ProcessClientPostVideoJob { tenantId, mediaId }` (`#modules/reviews/jobs/process_client_post_video_job`) runs on a queue of its own, `client_video`, in the same video worker (`--queue=video,client_video`: the worker asks its queues in that order, so work videos go first; in development `node ace queue:work --queue=video,client_video`; tests `processQueued(["client_video"])`), by the same model (a plain Job on the allowlist; `ClientPostService.processVideo` reads and writes its item only in short transactions and calls `VideoService.process` with the private `client_post_video` purpose; safe to repeat; `failed()` marks a still-processing item failed with `VIDEO_GAVE_UP`). The stuck-video sweep covers them too: `SweepStuckVideosJob` also reads the SECURITY DEFINER `stuck_client_video_candidates()` (ids only, at most 500, migration `1791930000000`, with the partial index `client_post_media_processing_videos`) and queues one `FailStuckClientVideoJob { tenantId, mediaId }` (a TenantJob) per row, which fails it under its lock with `VIDEO_STUCK` and deletes its upload after the commit (`ClientPostService.failStuckVideo`). The review page also shows such a video as failed when it reads it, as a fallback until the sweep has run (`client_post_video.spec.ts` runs the real ffmpeg). **Disputes record**: `SweepStaleSubmittersJob` (daily) lists the tenants holding a review or post submitter digest older than 90 days through the SECURITY DEFINER `stale_submitter_tenants()` and queues one `ClearSubmittersJob { tenantId }` (a TenantJob) per tenant, which clears them (`clearStaleSubmitters` in its module), deleted rows included.
- Payment reconciliation (docs/payments-paybridgenp.md): `ReconcilePaymentsJob` runs every 15 minutes (`start/scheduler.ts`, one of its schedules): it reads only ids from `gateway_checkouts_to_reconcile()` and queues one `SyncGatewayCheckoutJob { tenantId, checkoutId }` per online checkout still open 10 minutes to 2 days on and not checked in 10 minutes (one PayBridgeNP read each), and at 03:00 to 03:15 UTC one `SyncBillingJob { tenantId }` per studio from `billing_tenants()`. Both are `TenantJob`s and safe to repeat: recording is idempotent by PayBridgeNP's ids. It is a safety net for missed webhooks, never a polling loop.
- `@adonisjs/queue` (0.6.2) and `@boringnode/queue` (0.6.0) are pinned to exact versions, and `overrides` in `pnpm-workspace.yaml` forces a single copy of `@boringnode/queue`. Upgrade all three together, then check `pnpm why @boringnode/queue` shows one version.
- The only driver is `database`; there is no `sync` driver, because it would run jobs inside the request, before a transaction commits and without the JSON round trip.
- Tests: fake the queue with `queue.fake()` and assert with `fake.assertPushed(Job, { payload })`; run a job directly with `new Job()`, `$hydrate(payload, context)` and `execute()`. Restore fakes in `group.each.teardown`. To run queued jobs through the real worker, see `processQueued()` in [testing](testing.md#tenant-isolation-tests); it never runs persisted schedules. A queued email is a `SendMailJob` payload: read it from `fake.getPushedJobs()` (`job.name`, `job.payload.mailMessage`). Through the real worker, use `mail.fake()` with `emitter.fake(["mail:sent"])`: the fake mailer doesn't track `sendCompiled`.
