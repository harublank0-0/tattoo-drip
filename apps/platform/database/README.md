# Database conventions

PostgreSQL 18. Every migration follows these rules; the reasoning is in `docs/data-model.md` (Tenant ownership).

- **Primary keys are UUIDv7, generated by Postgres.** They are time-ordered, so inserts stay index-friendly, and they are safe to expose in URLs and the API. `uuidv7()` is built into Postgres 18. The first migration (`ensure_uuidv7`) does nothing there. On older Postgres it enables the `pg_uuidv7` extension and adds a `uuidv7()` wrapper, or fails with a clear error if the extension isn't available.

  ```ts
  table.uuid("id").primary().defaultTo(this.raw("uuidv7()"));
  ```

- **Instants are `timestamptz`, stored in UTC.** Pass `{ useTz: true }` explicitly. App code works with Luxon `DateTime` in UTC and converts to the studio's time zone only for display.

  ```ts
  table.timestamp("created_at", { useTz: true }).notNullable();
  ```

- **Every tenant-owned table has `tenant_id`.** That is every table except `users` and platform reference lists. The column is `uuid not null`, references `tenants`, and is indexed. References between tenant-owned rows include `tenant_id` in a composite foreign key, so the database rejects cross-tenant links. Row-level security is on for every tenant-owned table (see below).
- **Foreign keys are `uuid` columns with an index.**
- **Phone numbers are E.164,** defaulting to +977. **Money is an integer in minor units** (paisa) with a currency, `NPR` by default.
- **Business records are soft-deleted.** Tenant-owned tables (and `tenants` itself) get a nullable `deleted_at timestamptz`, and their models use the `withSoftDeletes` mixin (`#models/mixins/soft_deletes`). Unique rules that a deleted row must not block become partial indexes, `... WHERE deleted_at IS NULL` (for example, a removed member can be invited back). Keep a plain unique index when a deleted row should keep its value forever: tenant slugs stay reserved so a deleted studio's subdomain is never reused (and `tenant_slugs` keeps every slug a tenant ever held, below). Not soft-deleted: `users` (account and personal-data deletion must really erase), payments (never deleted at all), quotes (versioned history), and queue tables.

  ```ts
  table.timestamp("deleted_at", { useTz: true }).nullable();
  ```

- **Exception: `rate_limits`.** `@adonisjs/limiter`'s Postgres store fixes its shape: a string `key` primary key, integer `points` and `expire` in epoch milliseconds, in that column order (the store inserts positional values). It holds short-lived counts keyed by HMAC digests, isn't tenant-owned and is exempt from row-level security. The store deletes rows that expired over an hour ago every 5 minutes.

`database/schema.ts` is generated by `pnpm migrate`; never edit it by hand. Never edit a migration that has run anywhere; add a new one instead.

## Row-level security

- **Two roles.** The owner (`DB_MIGRATION_USER`, `postgres` in dev and CI) owns the tables and runs migrations through the `owner` connection: `pnpm migrate` and `pnpm migrate:rollback` (plain `node ace migration:run` would run as the app role). The app (`DB_USER`, `tattoo_drip_app`) is `NOSUPERUSER NOBYPASSRLS` with data access only. `database/setup_roles.sql` creates it and runs once per database (compose, through `docker/postgres/init`, and CI do it). The server, the worker and the tests refuse to start as a role that bypasses RLS.
- **Context.** Each authenticated request and each `TenantJob` runs in one transaction that sets `app.user_id` and `app.tenant_id` (`app/services/db_context.ts`). Policies read them through `app_tenant_id()` and `app_user_id()`; with nothing set, queries return no rows. Raw `db` queries and Vine's `unique` and `exists` rules run outside that transaction, so they see nothing: use models, or `dbClient()`. Tests will not reveal a query that escapes the request transaction on its own (the request is a savepoint on the test's single connection), which is why a tripwire fails the test run and Biome forbids importing the db service under `app/`.
- **A new tenant-owned table.** In its migration, `for (const sql of enableTenantRls("quotes")) this.schema.raw(sql);` from `#database/helpers/tenant_rls` (RLS on, `UNIQUE (tenant_id, id)`, the `tenant_isolation` policy), and `tenantReference(table, "client_id", "clients")` for references to other tenant-owned tables. `tests/functional/rls/catalog_guard.spec.ts` fails for a table without them, and until you add the table's `tenant_isolation:ALL` entry to `EXPECTED_POLICIES` in that spec.
- **`ENABLE`, not `FORCE`.** The owner bypasses RLS, so data migrations behave the same on any Postgres. `users` is outside RLS: login and the session guard read it before any context exists.
- **SECURITY DEFINER functions** are the only way across tenants. There are two: `expired_quote_candidates()` (TAT-83, the expiry sweep) and `tenant_for_slug(requested_slug)` (TAT-32, the public API's tenant lookup). Such a function runs as its owner, which bypasses RLS, so it returns ids only, takes no arguments (the one exception is an exact lookup: one text argument compared with `=` against a unique column, returning at most one id, as `tenant_for_slug` does; name the argument so no column shadows it), has an SQL-standard body (`begin atomic … end`: names are bound when it is created, no dynamic SQL), pins `set search_path = pg_catalog, pg_temp` and schema-qualifies every table. Postgres grants `EXECUTE` on a new function to `PUBLIC`, so its migration runs `revoke all on function … from public` and grants `EXECUTE` to the app role named by `DB_USER` (quoted as an identifier). Callers act on the rows only through tenant-scoped code (a `TenantJob`, or the public API's request transaction). `tests/functional/rls/catalog_guard.spec.ts` fails for a definer function in any non-system schema (not only `public`) missing from `DEFINER_FUNCTIONS` (keys are `schema.name`, with the expected argument list), without the pinned `search_path`, or executable by `PUBLIC`; a new one also needs a spec of its properties, like `expired_quote_candidates.spec.ts`. The body depends on the columns it reads: a migration that drops or retypes `quotes.expires_at`, `quotes.version`, `tattoo_projects.status` or `tattoo_projects.deleted_at` must replace the function in the same migration. `tenant_for_slug` reads `tenant_slugs.slug`, `tenant_slugs.tenant_id`, `tenants.id` and `tenants.deleted_at`; a migration that drops or retypes one of them must replace it in the same migration.
- **Slug registry (TAT-24).** `tenant_slugs` holds every slug a tenant has held, its current one included. `tenant_slugs_slug_unique` is one namespace for the platform, so a slug, once used, never reaches another tenant, and no cross-tenant read is needed to enforce it. The `tenants_register_slug` trigger (`AFTER INSERT OR UPDATE OF slug` on `tenants`, plpgsql, invoker rights, pinned `search_path`) writes the rows; app code never does. Policies: `tenant_slugs_select` (the current tenant, or a tenant the user is a live member of, like `tenants_select`) and `tenant_slugs_insert` (the current tenant); there is no UPDATE or DELETE policy, so the app role changes nothing. `tenant_slugs_slug_format` checks the lowercase DNS label shape; the stricter rules for new slugs are in `#modules/tenancy/slugs`, and the migration copied every existing slug without applying them. Releasing a slug is a deliberate operations step: delete its row as the owner role, never the tenant's current slug. The key to `tenants` is `NO ACTION`, so a hard purge of a tenant releases its slugs first.
- **Guard triggers.** `inquiries_guard_update` (the submitted fields are frozen) and `payments_guard` (append-only) are `FOR EACH ROW` plpgsql triggers that fail closed: they name the columns that may change and freeze every other column, so a column added later is frozen until its migration allows it. `inquiries_guard_update` covers UPDATE only, so an inquiry with no children can still be hard-deleted (nothing in the product does); `payments_guard` covers UPDATE and DELETE. Both functions pin `search_path = pg_catalog, pg_temp`, so a session cannot shadow the built-ins they call; keep the pin in any replacement function. Errors read `<trigger>: <column> cannot change`, so the prefix is `inquiries_guard_update:` or `payments_guard:` (a payment DELETE reads `payments_guard: payments are never deleted`, and putting a new value in the proof reads `payments_guard: proof can only be cleared`). The privacy deletion (TAT-42) must scrub an inquiry in the one UPDATE that first sets `anonymized_at`: the contact snapshot and the free-text fields (`idea`, `placement`, `approximate_size`, `preferred_dates`, `budget`) may change only in that update, after which they are frozen again and `anonymized_at` never changes. TAT-42 must therefore scrub each inquiry in ONE UPDATE restricted to rows with `anonymized_at is null`: a bulk update that includes an already-anonymized row fails the whole statement, and so does setting the marker and scrubbing in two statements. A later re-scrub is an explicit operations step: disable the trigger around it, as for a backfill. The same ticket may only clear a payment's proof columns. Once a payment is decided its `status` and `verified_at` are final, and its verifier can never change to another user: the only change allowed is to null, and only when that user's row no longer exists, which is what the `ON DELETE SET NULL` action finds after the account is deleted (the guard reads `public.users`, schema-qualified because of the pinned `search_path`); clearing it by hand while the account exists is refused. Because the check reads `public.users`, if `users` ever gets row-level security the check must read it through a SECURITY DEFINER helper, otherwise a hidden row would make it fail open. The app role holds UPDATE on every table, so these exceptions are enforced inside the triggers, not by privileges. A migration that backfills a frozen column on these tables must `ALTER TABLE … DISABLE TRIGGER <name>` around the backfill: the owner bypasses RLS but not triggers. A hard purge of a tenant that has payments is refused by the payments trigger's DELETE rule (the `tenants` cascade deletes payment rows), so purging such a tenant is an explicit operations step: disable the trigger around it, as for a backfill (a design claim, not something the suite tests). A trigger's `down()` must drop its function as well as the trigger.
- **Exclusion constraints and `btree_gist`.** `project_sessions` keeps one artist from being in two places with `EXCLUDE USING gist (artist_id WITH =, tstzrange(starts_at, ends_at) WITH &&) WHERE (active)`. Comparing a uuid with `=` in a gist index needs the `btree_gist` extension, which the migration creates with `create extension if not exists btree_gist` (the owner role runs migrations; on a managed Postgres check the provider allows the extension). `down()` leaves the extension in place. `active` is a stored generated column, so the definition of "blocks time" lives in one place; the half-open range makes back-to-back sessions legal. The error is SQLSTATE 23P01 with the constraint name `project_sessions_artist_no_overlap`: recognize it with `isExclusionViolation` (`#services/db_errors`), the way unique indexes use `isUniqueViolation`.
- **Operations.**
  - Every test-runner start needs a reachable Postgres, even `node ace test unit` (the boot guard queries the role), and the web and worker processes exit 1 if Postgres is down at boot. The functional suite needs `psql` on PATH (`setup_roles.spec.ts`).
  - Always migrate with `pnpm migrate`. The app role can write the migration bookkeeping tables, so a pure-DML migration run by mistake as the app role would be recorded as done.
  - In production keep `DB_MIGRATION_PASSWORD` out of the web and worker environment (`start/env.ts` requires only `DB_MIGRATION_USER`).
  - Creating the app role: run `setup_roles.sql` as a superuser, as compose and CI do. Its one `ALTER ROLE` names `NOSUPERUSER`, `NOBYPASSRLS`, `NOCREATEDB` and `NOREPLICATION`, and PostgreSQL 18 (checked on 18.6) refuses `NOSUPERUSER` to every non-superuser, even one holding `CREATEROLE`, `CREATEDB`, `REPLICATION` and `BYPASSRLS`; a `CREATEROLE`-only admin is also refused `NOBYPASSRLS`, `NOCREATEDB` and `NOREPLICATION` ("Only roles with the X attribute may change the X attribute"). On a managed Postgres without superuser access, create the role with the provider's tooling and run the script with that `ALTER ROLE` cut down to `LOGIN` and `PASSWORD` (a new role has none of those powers; the grants were not tried as a non-superuser). The app password appears in psql's argv, in the server log if the statement errors, and on success under `log_statement = ddl` or `all`, so use a throwaway or secret-managed value in production.
  - If an initdb script fails, Postgres can restart "healthy" without the app role. After fixing the script, recreate the volume (`podman-compose down -v`).
- **Production checklist.** None of this is covered by the test suite; check it against your deploy.
  - Migrate from the build as the owner: `node build/ace.js migration:run --connection=owner --force` (`pnpm build` writes `build/ace.js`; `--force` is required when `NODE_ENV=production`; the owner's `DB_MIGRATION_USER` and `DB_MIGRATION_PASSWORD` must be in that process's environment). `migration:rollback`, `migration:fresh`, `migration:status` and `db:seed` take the same `--connection=owner`; without it they use the app role (a seeder's models still do). Even with it, a seeder's model writes must pass `{ connection: client.connectionName }` (`client` is `this.client`): a model instance keeps only a transaction client, so `Model.create(values, { client })` quietly writes as the app role and fails row-level security, while `Model.query({ client })` is honored. Run a new seeder once to find out, since neither the type checker nor the suite covers seeders.
  - A model imported in a migration uses the app role, so RLS applies: with no context its data changes silently affect 0 rows or fail the policy check. Use the migration's own client instead, `this.defer((db) => ...)`.
  - Set the pool size explicitly (`pool: { min, max }` on the `pg` connection in `config/database.ts`). It is not set today, so knex's default applies (maximum 10), and every authenticated request holds one connection for its whole length.
  - Consider `ALTER ROLE tattoo_drip_app SET idle_in_transaction_session_timeout = '...'` (`setup_roles.sql` does not set it), so a request that stalls mid-transaction cannot hold its connection and locks indefinitely. Pick a value above your slowest legitimate request.
  - Run production and CI on the Node version in `.nvmrc` (24.3.0). On Node 26.9 the multipart parser (`@poppinss/multiparty` 3.0.0) stalls on any text field over about 130 KB, with no error and no response, so one request holds its connection and transaction until Node's request timeout. Before a Node upgrade, re-run `inquiry_refusals.spec.ts` ("more than 2 MB of text is 413") on the new version.
  - The multipart parser crashes the process on a file part named like an `Object.prototype` property (`constructor`, `toString`, `__proto__`...): `@adonisjs/bodyparser` 11.0.4 (the latest, no fix published) keeps its handler table in a plain object, so `new PartHandler(part, handler.options)` throws inside an async listener, an unhandled rejection, and the app registers no `unhandledRejection` handler. `receiveUploads` guards only the public API routes that use it (the intake). The routes the parser auto-processes (login, signup, the dashboard forms; reproduced on the login route) are still open to one anonymous request that stops the web process. This must be fixed before any public deploy: patch the parser (`pnpm patch @adonisjs/bodyparser`: make its `#handlers` table `Object.create(null)`) or move to a release that does, and report it upstream; do not rely on a process-level handler.
  - Uploads hold a pooled database connection and an open transaction for as long as they stream (the intake reads its body after `publicTenant` opens the transaction), and only bytes are bounded, not time: ten slow uploads can drain a pool of 10 that the dashboard shares. The public deploy needs a per-request time bound for uploads (reverse proxy body and read timeouts, such as nginx `client_body_timeout`, and/or an in-process concurrency cap before `publicTenant`) and the explicit pool size above (TAT-38, TAT-14), not only request-count limits.
  - Behind a proxy that isn't on loopback (a platform load balancer), set `trustProxy` in the `http` config of `config/app.ts` to that proxy's addresses as a proxy-addr string (for example `trustProxy: "loopback, 10.0.0.0/8"`), never `true`. Without it every visitor shares the proxy's address, so one person's failed logins refuse login and signup to everyone for up to an hour (TAT-8). With `true`, any client picks its own address through `X-Forwarded-For`.
