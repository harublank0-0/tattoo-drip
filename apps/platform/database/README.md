# Database conventions

PostgreSQL 18. Every migration follows these rules; the reasoning is in `docs/data-model.md` (Tenant ownership).

- **Primary keys are UUIDv7, generated by Postgres.** They are time-ordered, so inserts stay index-friendly, and they are safe to expose in URLs and the API. `uuidv7()` is built into Postgres 18. The first migration (`ensure_uuidv7`) does nothing there. On older Postgres it enables the `pg_uuidv7` extension and adds a `uuidv7()` wrapper, or fails with a clear error if the extension isn't available.

  ```ts
  table.uuid("id").primary().defaultTo(this.raw("uuidv7()"));
  ```

- **Instants are `timestamptz`, stored in UTC.** Pass `{ useTz: true }` explicitly. App code works with Luxon `DateTime` in UTC and converts to the studio's time zone only for display.

  ```ts
  table.timestamp("created_at", { useTz: true }).notNullable();
  ```

- **Every tenant-owned table has `tenant_id`.** That is every table except `users` and platform reference lists. The column is `uuid not null`, references `tenants`, and is indexed. References between tenant-owned rows include `tenant_id` in a composite foreign key, so the database rejects cross-tenant links. Row-level security is on for every tenant-owned table (see below).
- **Foreign keys are `uuid` columns with an index.**
- **Phone numbers are E.164,** defaulting to +977. **Money is an integer in minor units** (paisa) with a currency, `NPR` by default.
- **Business records are soft-deleted.** Tenant-owned tables (and `tenants` itself) get a nullable `deleted_at timestamptz`, and their models use the `withSoftDeletes` mixin (`#models/mixins/soft_deletes`). Unique rules that a deleted row must not block become partial indexes, `... WHERE deleted_at IS NULL` (for example, a removed member can be invited back). Keep a plain unique index when a deleted row should keep its value forever: tenant slugs stay reserved so a deleted studio's subdomain is never reused (and `tenant_slugs` keeps every slug a tenant ever held, below). Not soft-deleted: `users` (account and personal-data deletion must really erase), payments (never deleted at all), deposit outcomes (history; append-only by convention, `PaymentService` only inserts), quotes (versioned history), deposit links (a credential replaced in place; a deleted project's link is dead because the deposit page loads only live projects), reference codes (`reference_codes`: every code a studio has used, an inquiry's or a deposit link's, one row each with a unique `(tenant_id, code)`, so one code runs from a request to its deposit and is never handed out twice; written only by `ReferenceCodeService.claim`, never updated or deleted), message templates (a studio setting replaced in place: a row only for a changed text), studio hours and studio closures (TAT-128: settings replaced in place; a removed closed day is deleted), studio FAQ entries and policy sections (`studio_faq_entries`, `studio_policy_sections`: each list replaced whole under the studio's row lock, positions 0..n-1 unique per studio), artist work photos (TAT-116: a removed photo must stop being reachable at once, and soft-deleted records keep their files, so removing one deletes its files first and then its row), staff alerts (ids only, kept read or unread), account tokens (single-use credentials, deleted when used), tenant invitations (credentials, deleted when accepted or cancelled), and queue tables. Not soft-deleted, on purpose: `artist_work_photos` and `flash_designs` (TAT-129), which are deleted with their files. Both have `hidden` (a work photo's since Studio OS, `1791860000000_add_hidden_to_artist_work_photos`, default false): a hidden row stays in the dashboard and is in no public read, which asks `not hidden` in its own query. `flash_designs` is kept alive by what names it: `inquiries.flash_design_id` and `tattoo_projects.flash_design_id` reference it through `(tenant_id, flash_design_id)` keys with `NO ACTION` (`inquiries_flash_design_fk`, `tattoo_projects_flash_design_fk`), so a design a request or a project names cannot be deleted and the studio hides it (`hidden`) instead. A one-of-a-kind design (`one_of_a_kind`) is claimed by `claimed_at`, with `claimed_project_id` naming the project whose first verified deposit or booking claimed it (null for a claim by hand): `flash_designs_claim_one_of_a_kind` (`claimed_at is null or one_of_a_kind`) and `flash_designs_claim_project_needs_time` (`claimed_project_id is null or claimed_at is not null`) are checks, and `flash_designs_claimed_project_fk` is a composite `NO ACTION` key `(tenant_id, claimed_project_id)` to `tattoo_projects (tenant_id, id)` (projects are never purged), so another tenant's project cannot claim a design; the claim is one conditional `UPDATE` and nothing but "Make available" or saving the design as repeatable clears it. `tenants.storefront_claimed_flash` (`show` or `hide`) has only a shape check, like the other look columns.

  ```ts
  table.timestamp("deleted_at", { useTz: true }).nullable();
  ```

- **A swap or a compaction in one UPDATE: a deferrable unique (TAT-116).** A plain unique is checked row by row, so swapping two positions in one UPDATE fails half way; a deferrable one (`unique (tenant_id, artist_id, position) deferrable initially immediate`) is checked at the end of the statement, so a list kept in order with a `position` column can swap two rows, or close the gap after a removal (`position = position - 1`), in one statement each. `artist_work_photos` used this pattern with `position` from 0 to 5 until TAT-126, which dropped the column: the portfolio is now newest first by `created_at desc, id desc` with no manual order, and the limit of 100 per artist is not a database rule (the count under the artist's row lock in `WorkPhotoService.add` is its only guard). The migration (`1791700000001_work_photos_newest_first_with_styles`) first rewrote the dates so the studio's order survived: position 0 got the artist's newest date and each later position one second less. Use the deferrable-unique pattern for the next list that is reordered in place. Angles are that list: `artist_work_photos_angle_place`, `unique (tenant_id, lead_photo_id, angle_position) deferrable initially immediate` (below).
- **Angles: a tattoo's photos (`1791900000000_add_angles_to_artist_work_photos`).** A tattoo is a lead photo and up to seven angles: `artist_work_photos.lead_photo_id uuid null` (the lead) and `angle_position smallint null` (1 to 7), additive with no backfill. Constraints: `artist_work_photos_angle_lead_fk`, a composite key `(tenant_id, lead_photo_id)` to the table's own `(tenant_id, id)` with `NO ACTION` (checked at the end of the statement, so a lead and its angles go in one DELETE and a lead is never deleted alone); `artist_work_photos_angle_complete` (`(lead_photo_id is null) = (angle_position is null)`); `artist_work_photos_angle_not_self` (`lead_photo_id <> id`); `artist_work_photos_angle_position` (`angle_position between 1 and 7`); and `artist_work_photos_angle_place` (the deferrable unique above), whose index also serves the key and the angle reads (`(tenant_id, lead_photo_id)` is its prefix), so there is no second index. The guard is `artist_work_photos_angles_guard`, an ordinary plpgsql `AFTER INSERT OR UPDATE … FOR EACH ROW` trigger (function `public.artist_work_photos_angles_guard()`, invoker rights, `search_path = pg_catalog, pg_temp`, the table schema-qualified): an angle's lead must be a lead itself (no chains), a photo that has angles cannot become one, and a lead and its angles must have the same tenant and artist. AFTER row triggers run once their statement has finished, so one UPDATE that hands a tattoo to a new lead, or moves a whole tattoo to another artist, is judged on its outcome (a BEFORE trigger sees a statement's rows in no set order and would refuse it half way). It is deliberately not deferrable: a check deferred to the commit would run in whatever context the session has left by then, and with the tenant context cleared RLS would hide every row it reads (`tests/functional/rls/artist_work_photo_angles.spec.ts` defers every constraint and clears the context to prove nothing gets through). It fires on every insert and update whatever the columns and fails closed: a row or a lead it cannot read is an error. In the angle branch it reads the lead `FOR SHARE`, so a concurrent change of that lead (moving it to another artist, making it an angle) waits for this transaction or makes this one wait, and the second sees the first's outcome; the spec pins that on two real connections. Errors read `artist_work_photos_angles_guard: …`. Its `down()` drops the trigger and the function. Rules the app keeps (the lead's `styles` and `healed` copied onto the angles, the 100 per artist counting angles) are in [backend conventions](../docs/backend.md) (Angles).
- **Video angles (`1791910000000_add_video_angles_to_artist_work_photos`).** A video is an angle row of `artist_work_photos`, chosen over a table of its own so the angles' constraints and guard hold for it unchanged (a second table could not share the deferrable unique place). Additive: `kind varchar(8) not null default 'photo'` and nullable `video_state`, `video_failure`, `video_staging_key`, `video_duration_ms`, `video_keys varchar(255)[]`; `image_key`, `width` and `height` lose `not null` (a video's poster and size come once it is processed). Checks: `artist_work_photos_kind` (`photo` or `video`), `artist_work_photos_video_is_angle` (a video always has a lead, so it is never one), `artist_work_photos_photo_shape` (a photo has its image and size and no video column), `artist_work_photos_video_shape` (a state and a staging key), `artist_work_photos_video_ready` (ready: the poster, the size, 1 to 60000 ms, one or two keys, no failure), `artist_work_photos_video_unfinished` (processing or failed: no poster, no keys) and `artist_work_photos_video_failed` (a failure exactly when failed); `artist_work_photos_video_staging_key` is unique on `(tenant_id, video_staging_key)`, so an upload finishes once (the key stays on the row for good). The migration replaces `artist_work_photos_angles_guard()` (`create or replace`, the same pin and invoker rights) to refuse a video as a lead in both directions: a lead whose `kind` is not `photo` (`… the lead of % is a video`) and a row with no lead that is a video. `down()` refuses while any video exists, puts the original function back and drops the rest. `1791910000001` grants the discovery role `kind` and replaces `discovery.artwork_angles` (same columns) to map photos only; `discovery.artworks` lists leads, so it never held a video. Schema rule: `video_keys` is typed `string[]` in `database/schema_rules.ts`.
- **Exception: `rate_limits`.** `@adonisjs/limiter`'s Postgres store fixes its shape: a string `key` primary key, integer `points` and `expire` in epoch milliseconds, in that column order (the store inserts positional values). It holds short-lived counts keyed by HMAC digests, isn't tenant-owned and is exempt from row-level security. The store deletes rows that expired over an hour ago every 5 minutes.
- **Exception: `account_tokens`** (TAT-18) isn't tenant-owned and has no row-level security, like `users`: a confirmation or reset link is read before any context exists. It holds SHA-256 digests of single-use tokens, one per account and purpose, deleted when used and by `on delete cascade` with the account.
- **Canonical emails (TAT-18).** `users_email_canonical` keeps every address trimmed, with its ASCII letters in lower case (`translate()`, never `lower()`, so the database's locale doesn't matter): the rule of `canonicalEmail` in `#modules/identity/email_address`. Migration `1791680000000` rewrote existing addresses and refuses to apply while two accounts would end up with one address. To resolve it, list them as the owner role with `select id, email, created_at from users where translate(btrim(email), 'ABCDEFGHIJKLMNOPQRSTUVWXYZ', 'abcdefghijklmnopqrstuvwxyz') in (select translate(btrim(email), 'ABCDEFGHIJKLMNOPQRSTUVWXYZ', 'abcdefghijklmnopqrstuvwxyz') from users group by 1 having count(*) > 1) order by email, created_at;`, decide with the people concerned which account keeps each address, give each other account an address of its own (for example `update users set email = 'duplicate-<id>@invalid' where id = '<id>'`: `.invalid` never receives mail), then migrate again. Write a canonical value in that `update`: the check (and `canonicalEmail`) strips only U+0020 at both ends and lower-cases A to Z, so a tab, a line break or a no-break space in an address is kept as typed. Never merge or delete the rows.

`database/schema.ts` is generated by `pnpm migrate`; never edit it by hand. Never edit a migration that has run anywhere; add a new one instead.

## Row-level security

- **Two roles.** The owner (`DB_MIGRATION_USER`, `postgres` in dev and CI) owns the tables and runs migrations through the `owner` connection: `pnpm migrate` and `pnpm migrate:rollback` (plain `node ace migration:run` would run as the app role). The app (`DB_USER`, `tattoo_drip_app`) is `NOSUPERUSER NOBYPASSRLS` with data access only. `database/setup_roles.sql` creates it and runs once per database (compose, through `docker/postgres/init`, and CI do it). The server, the worker and the tests refuse to start as a role that bypasses RLS.
- **Context.** Each authenticated request and each `TenantJob` runs in one transaction that sets `app.user_id` and `app.tenant_id` (`app/services/db_context.ts`). Policies read them through `app_tenant_id()` and `app_user_id()`; with nothing set, queries return no rows. Raw `db` queries and Vine's `unique` and `exists` rules run outside that transaction, so they see nothing: use models, or `dbClient()`. Tests will not reveal a query that escapes the request transaction on its own (the request is a savepoint on the test's single connection), which is why a tripwire fails the test run and Biome forbids importing the db service under `app/`.
- **A new tenant-owned table.** In its migration, `for (const sql of enableTenantRls("quotes")) this.schema.raw(sql);` from `#database/helpers/tenant_rls` (RLS on, `UNIQUE (tenant_id, id)`, the `tenant_isolation` policy), and `tenantReference(table, "client_id", "clients")` for references to other tenant-owned tables. `tests/functional/rls/catalog_guard.spec.ts` fails for a table without them, and until you add the table's `tenant_isolation:ALL` entry to `EXPECTED_POLICIES` in that spec.
- **`ENABLE`, not `FORCE`.** The owner bypasses RLS, so data migrations behave the same on any Postgres. `users` is outside RLS: login and the session guard read it before any context exists.
- **SECURITY DEFINER functions** are one of the app role's two ways across tenants (the other is the discovery views, next bullet). There are three: `expired_quote_candidates()` (TAT-83, the expiry sweep), `tenant_for_slug(requested_slug)` (TAT-32, the public API's tenant lookup) and `invitation_tenant(requested_hash)` (TAT-33, the invitation page's lookup: the live tenant holding the invitation whose `token_hash` is exactly the argument). Such a function runs as its owner, which bypasses RLS, so it returns ids only, takes no arguments (the one exception is an exact lookup: one text argument compared with `=` against a unique column, returning at most one id, as `tenant_for_slug` does; name the argument so no column shadows it), has an SQL-standard body (`begin atomic … end`: names are bound when it is created, no dynamic SQL), pins `set search_path = pg_catalog, pg_temp` and schema-qualifies every table. Postgres grants `EXECUTE` on a new function to `PUBLIC`, so its migration runs `revoke all on function … from public` and grants `EXECUTE` to the app role named by `DB_USER` (quoted as an identifier). Callers act on the rows only through tenant-scoped code (a `TenantJob`, or the public API's request transaction). `tests/functional/rls/catalog_guard.spec.ts` fails for a definer function in any non-system schema (not only `public`) missing from `DEFINER_FUNCTIONS` (keys are `schema.name`, with the expected argument list), without the pinned `search_path`, or executable by `PUBLIC`; a new one also needs a spec of its properties, like `expired_quote_candidates.spec.ts`. The body depends on the columns it reads: a migration that drops or retypes `quotes.expires_at`, `quotes.version`, `tattoo_projects.status` or `tattoo_projects.deleted_at` must replace the function in the same migration. `tenant_for_slug` reads `tenant_slugs.slug`, `tenant_slugs.tenant_id`, `tenants.id` and `tenants.deleted_at`; a migration that drops or retypes one of them must replace it in the same migration. `invitation_tenant` reads `tenant_invitations.token_hash`, `tenant_invitations.tenant_id`, `tenants.id` and `tenants.deleted_at`; a migration that drops or retypes one of them must replace it in the same migration.
- **Discovery views (Discover D02).** The app role's other way across tenants, read-only: the views in schema `discovery` (`studios`, `artists`, `artworks`, migration `1791870000001_create_discovery_views`) list only what Discover may show. They are owned by `tattoo_drip_discovery` (setup_roles.sql: NOLOGIN, no superuser, no BYPASSRLS, NOINHERIT, no memberships) and are not `security_invoker`, so their tables are read as that role, under RLS, never as the owner. That role has column-level SELECT on public columns only and its own policies (`TO tattoo_drip_discovery`): a restrictive `discovery_only` with the full rule (AND-ed with the tables' policies, which apply to every role) and a permissive `discovery_select` on the row's own columns; `discovery_none` keeps it from every membership. The app role gets SELECT on the views and nothing new on any table. A new public column or view is a conscious edit in a migration: grant the column to the role, select it in the view, and update `tests/functional/rls/discovery.spec.ts`, which pins the role, its grants, the policies and the views' columns. `discovery.artworks` lists tattoos' leads only since angles (`1791900000001_discovery_artworks_leads_only`: `create or replace view`, the same columns, so its owner, options and grants stay; the role reads `lead_photo_id` for that rule and selects nothing new), and a fourth view, `discovery.artwork_angles` (`1791900000002`), maps a tattoo's other photos to it, ids only, for the artwork lookup. Both need the view owner or a superuser to apply ([Discover database security](../../../docs/discover/database-security.md), "Setup"). Never `select *`, never `security_invoker`, never a policy for the role that is not restrictive about eligibility. Rules: [Discover database security](../../../docs/discover/database-security.md).
- **The owner connection outside migrations: `metrics:pilot` only (TAT-70).** The operator command lists the live tenants (ids, slugs, names) as the owner role and nothing else; every number it prints is computed as the app role inside each tenant's context, and it refuses to start when the default connection is a role that bypasses RLS (the `ace.loaded` hook in `db_context_provider.ts`, as for `queue:work`). No other app code, and never the web or worker process, uses the `owner` connection.
- **Slug registry (TAT-24).** `tenant_slugs` holds every slug a tenant has held, its current one included. `tenant_slugs_slug_unique` is one namespace for the platform, so a slug, once used, never reaches another tenant, and no cross-tenant read is needed to enforce it. The `tenants_register_slug` trigger (`AFTER INSERT OR UPDATE OF slug` on `tenants`, plpgsql, invoker rights, pinned `search_path`) writes the rows; app code never does. Policies: `tenant_slugs_select` (the current tenant, or a tenant the user is a live member of, like `tenants_select`) and `tenant_slugs_insert` (the current tenant); there is no UPDATE or DELETE policy, so the app role changes nothing. `tenant_slugs_slug_format` checks the lowercase DNS label shape; the stricter rules for new slugs are in `#modules/tenancy/slugs`, and the migration copied every existing slug without applying them. Releasing a slug is a deliberate operations step: delete its row as the owner role, never the tenant's current slug. The key to `tenants` is `NO ACTION`, so a hard purge of a tenant releases its slugs first.
- **Guard triggers.** `inquiries_guard_update` (the submitted fields are frozen; besides the decision, `deleted_at`, `updated_at` and `anonymized_at`, TAT-52 frees the last contact: `last_contacted_at`, `last_contact_channel` and `last_contact_kind`; the anonymising update may also clear the client's free text, `notes` included, and `style`, `colour` and `reference_code` stay frozen) and `payments_guard` (append-only) are `FOR EACH ROW` plpgsql triggers that fail closed: they name the columns that may change and freeze every other column, so a column added later is frozen until its migration allows it. Angles' `artist_work_photos_angles_guard` (above) is the third guard trigger, about the rows a tattoo links, not about frozen columns. `inquiries_guard_update` covers UPDATE only, so an inquiry with no children can still be hard-deleted (nothing in the product does); `payments_guard` covers UPDATE and DELETE. Both functions pin `search_path = pg_catalog, pg_temp`, so a session cannot shadow the built-ins they call; keep the pin in any replacement function. Errors read `<trigger>: <column> cannot change`, so the prefix is `inquiries_guard_update:` or `payments_guard:` (a payment DELETE reads `payments_guard: payments are never deleted`, and putting a new value in the proof reads `payments_guard: proof can only be cleared`). The privacy deletion (TAT-42) must scrub an inquiry in the one UPDATE that first sets `anonymized_at`: the contact snapshot and the free-text fields (`idea`, `placement`, `approximate_size`, `preferred_dates`, `budget`) may change only in that update, after which they are frozen again and `anonymized_at` never changes. TAT-42 must therefore scrub each inquiry in ONE UPDATE restricted to rows with `anonymized_at is null`: a bulk update that includes an already-anonymized row fails the whole statement, and so does setting the marker and scrubbing in two statements. A later re-scrub is an explicit operations step: disable the trigger around it, as for a backfill. The same ticket may only clear a payment's proof columns. `payments_guard` (as replaced by TAT-66) also lets `note` be written in the one update that decides a submitted payment, or cleared; any other change to it reads `payments_guard: note cannot change`. `corrects_payment_id` is frozen like the money facts. The migration that adds it (`1791660000000`) refuses to apply while `payments` holds any `correction` row, because before it a correction named no payment and the new `payments_correction_target` check would reject it: delete such rows as the owner role (with `alter table payments disable trigger payments_guard` around the delete) or reset the development database, then migrate again. It also refuses to roll back while any correction exists, because the old schema has nowhere to keep which payment a reversal names and the next apply would then fail; both refusals raise a message that says so, and neither touches data. Once a payment is decided its `status` and `verified_at` are final, and its verifier can never change to another user: the only change allowed is to null, and only when that user's row no longer exists, which is what the `ON DELETE SET NULL` action finds after the account is deleted (the guard reads `public.users`, schema-qualified because of the pinned `search_path`); clearing it by hand while the account exists is refused. Because the check reads `public.users`, if `users` ever gets row-level security the check must read it through a SECURITY DEFINER helper, otherwise a hidden row would make it fail open. The app role holds UPDATE on every table, so these exceptions are enforced inside the triggers, not by privileges. A migration that backfills a frozen column on these tables must `ALTER TABLE … DISABLE TRIGGER <name>` around the backfill: the owner bypasses RLS but not triggers. A hard purge of a tenant that has payments is refused by the payments trigger's DELETE rule (the `tenants` cascade deletes payment rows), so purging such a tenant is an explicit operations step: disable the trigger around it, as for a backfill (a design claim, not something the suite tests). A trigger's `down()` must drop its function as well as the trigger. `tenants_date_policies` (a `before update` trigger on `tenants`) sets `policies_updated_at` whenever `deposit_policy`, `age_rule_text` or `walk_ins_text` changes value, whichever page wrote it; it pins the same `search_path`.
- **Dates and times of day (TAT-128).** `studio_hours.opens_at` / `closes_at` are `time` columns and `studio_closures.starts_on` / `ends_on` are `date` columns, the first of either in the schema. The generator types a `time` as `string` ("HH:mm:ss") and a `date` as a Luxon `DateTime` with `@column.date`; compare `yyyy-MM-dd` strings in SQL (`ends_on >= ?` with the studio's today from `todayIn`), never timestamps, and read a date back with `toISODate()`. `studio_hours.weekday` is 0 = Sunday ... 6 = Saturday, like `extract(dow)`.
- **Exclusion constraints and `btree_gist`.** `project_sessions` keeps one artist from being in two places with `EXCLUDE USING gist (artist_id WITH =, tstzrange(starts_at, ends_at) WITH &&) WHERE (active)`. Comparing a uuid with `=` in a gist index needs the `btree_gist` extension, which the migration creates with `create extension if not exists btree_gist` (the owner role runs migrations; on a managed Postgres check the provider allows the extension). `down()` leaves the extension in place. `active` is a stored generated column, so the definition of "blocks time" lives in one place; the half-open range makes back-to-back sessions legal. The error is SQLSTATE 23P01 with the constraint name `project_sessions_artist_no_overlap`: recognize it with `isExclusionViolation` (`#services/db_errors`), the way unique indexes use `isUniqueViolation`.
- **Operations.**
  - Every test-runner start needs a reachable Postgres, even `node ace test unit` (the boot guard queries the role), and the web and worker processes exit 1 if Postgres is down at boot. The functional suite needs `psql` on PATH (`setup_roles.spec.ts`).
  - Always migrate with `pnpm migrate`. The app role can write the migration bookkeeping tables, so a pure-DML migration run by mistake as the app role would be recorded as done.
  - In production keep `DB_MIGRATION_PASSWORD` out of the web and worker environment (`start/env.ts` requires only `DB_MIGRATION_USER`).
  - Creating the app role: run `setup_roles.sql` as a superuser, as compose and CI do. Its one `ALTER ROLE` names `NOSUPERUSER`, `NOBYPASSRLS`, `NOCREATEDB` and `NOREPLICATION`, and PostgreSQL 18 (checked on 18.6) refuses `NOSUPERUSER` to every non-superuser, even one holding `CREATEROLE`, `CREATEDB`, `REPLICATION` and `BYPASSRLS`; a `CREATEROLE`-only admin is also refused `NOBYPASSRLS`, `NOCREATEDB` and `NOREPLICATION` ("Only roles with the X attribute may change the X attribute"). On a managed Postgres without superuser access, create the role with the provider's tooling and run the script with that `ALTER ROLE` cut down to `LOGIN` and `PASSWORD` (a new role has none of those powers; the grants were not tried as a non-superuser). The app password appears in psql's argv, in the server log if the statement errors, and on success under `log_statement = ddl` or `all`, so use a throwaway or secret-managed value in production.
  - If an initdb script fails, Postgres can restart "healthy" without the app role. After fixing the script, recreate the volume (`podman-compose down -v`).
- **Production checklist.** None of this is covered by the test suite; check it against your deploy.
  - The API process's settings, reverse proxy, pool sizes and `idle_in_transaction_session_timeout`, logs and the server key are in the [public API production checklist](../docs/deploy.md#public-api-production-checklist).
  - Migrate from the build as the owner: `node build/ace.js migration:run --connection=owner --force` (`pnpm build` writes `build/ace.js`; `--force` is required when `NODE_ENV=production`; the owner's `DB_MIGRATION_USER` and `DB_MIGRATION_PASSWORD` must be in that process's environment). `migration:rollback`, `migration:fresh`, `migration:status` and `db:seed` take the same `--connection=owner`; without it they use the app role (a seeder's models still do). Even with it, a seeder's model writes must pass `{ connection: client.connectionName }` (`client` is `this.client`): a model instance keeps only a transaction client, so `Model.create(values, { client })` quietly writes as the app role and fails row-level security, while `Model.query({ client })` is honored. Run a new seeder once to find out, since neither the type checker nor the suite covers seeders.
  - A model imported in a migration uses the app role, so RLS applies: with no context its data changes silently affect 0 rows or fail the policy check. Use the migration's own client instead, `this.defer((db) => ...)`.
  - Set `TURNSTILE_SECRET_KEY` (required: with `NODE_ENV=production` the platform, the worker and every `ace` command that boots the app refuse to start without it): the secret key of the studio pages' Cloudflare Turnstile widget, whose public site key goes to the storefront (TAT-57).
