# Database conventions

PostgreSQL 18. Every migration follows these rules; the reasoning is in `docs/data-model.md` (Tenant ownership).

- **Primary keys are UUIDv7, generated by Postgres.** They are time-ordered, so inserts stay index-friendly, and they are safe to expose in URLs and the API. `uuidv7()` is built into Postgres 18. The first migration (`ensure_uuidv7`) does nothing there. On older Postgres it enables the `pg_uuidv7` extension and adds a `uuidv7()` wrapper, or fails with a clear error if the extension isn't available.

  ```ts
  table.uuid("id").primary().defaultTo(this.raw("uuidv7()"));
  ```

- **Instants are `timestamptz`, stored in UTC.** Pass `{ useTz: true }` explicitly. App code works with Luxon `DateTime` in UTC and converts to the studio's time zone only for display.

  ```ts
  table.timestamp("created_at", { useTz: true }).notNullable();
  ```

- **Every tenant-owned table has `tenant_id`.** That is every table except `users` and platform reference lists. The column is `uuid not null`, references `tenants`, and is indexed. References between tenant-owned rows include `tenant_id` in a composite foreign key, so the database rejects cross-tenant links. Row-level security is on for every tenant-owned table (see below).
- **Foreign keys are `uuid` columns with an index.**
- **Phone numbers are E.164,** defaulting to +977. **Money is an integer in minor units** (paisa) with a currency, `NPR` by default.
- **Business records are soft-deleted.** Tenant-owned tables (and `tenants` itself) get a nullable `deleted_at timestamptz`, and their models use the `withSoftDeletes` mixin (`#models/mixins/soft_deletes`). Unique rules that a deleted row must not block become partial indexes, `... WHERE deleted_at IS NULL` (for example, a removed member can be invited back). Keep a plain unique index when a deleted row should keep its value forever: tenant slugs stay reserved so a deleted studio's subdomain is never reused. Not soft-deleted: `users` (account and personal-data deletion must really erase), payments (never deleted at all), quotes (versioned history), and queue tables.

  ```ts
  table.timestamp("deleted_at", { useTz: true }).nullable();
  ```

`database/schema.ts` is generated by `pnpm migrate`; never edit it by hand. Never edit a migration that has run anywhere; add a new one instead.

## Row-level security

- **Two roles.** The owner (`DB_MIGRATION_USER`, `postgres` in dev and CI) owns the tables and runs migrations through the `owner` connection: `pnpm migrate` and `pnpm migrate:rollback` (plain `node ace migration:run` would run as the app role). The app (`DB_USER`, `tattoo_drip_app`) is `NOSUPERUSER NOBYPASSRLS` with data access only. `database/setup_roles.sql` creates it and runs once per database (compose, through `docker/postgres/init`, and CI do it). The server, the worker and the tests refuse to start as a role that bypasses RLS.
- **Context.** Each authenticated request and each `TenantJob` runs in one transaction that sets `app.user_id` and `app.tenant_id` (`app/services/db_context.ts`). Policies read them through `app_tenant_id()` and `app_user_id()`; with nothing set, queries return no rows. Raw `db` queries and Vine's `unique` and `exists` rules run outside that transaction, so they see nothing: use models, or `dbClient()`. Tests will not reveal a query that escapes the request transaction on its own (the request is a savepoint on the test's single connection), which is why a tripwire fails the test run and Biome forbids importing the db service under `app/`.
- **A new tenant-owned table.** In its migration, `for (const sql of enableTenantRls("quotes")) this.schema.raw(sql);` from `#database/helpers/tenant_rls` (RLS on, `UNIQUE (tenant_id, id)`, the `tenant_isolation` policy), and `tenantReference(table, "client_id", "clients")` for references to other tenant-owned tables. `tests/functional/rls/catalog_guard.spec.ts` fails for a table without them, and until you add the table's `tenant_isolation:ALL` entry to `EXPECTED_POLICIES` in that spec.
- **`ENABLE`, not `FORCE`.** The owner bypasses RLS, so data migrations behave the same on any Postgres. `users` is outside RLS: login and the session guard read it before any context exists.
- **Guard triggers.** `inquiries_guard_update` (the submitted fields are frozen) and `payments_guard` (append-only) are `FOR EACH ROW` plpgsql triggers that fail closed: they name the columns that may change and freeze every other column, so a column added later is frozen until its migration allows it. `inquiries_guard_update` covers UPDATE only, so an inquiry with no children can still be hard-deleted (nothing in the product does); `payments_guard` covers UPDATE and DELETE. Both functions pin `search_path = pg_catalog, pg_temp`, so a session cannot shadow the built-ins they call; keep the pin in any replacement function. Errors read `<trigger>: <column> cannot change`, so the prefix is `inquiries_guard_update:` or `payments_guard:` (a payment DELETE reads `payments_guard: payments are never deleted`, and putting a new value in the proof reads `payments_guard: proof can only be cleared`). The privacy deletion (TAT-42) scrubs an inquiry by setting `anonymized_at` in the same update as the scrub; while it is set, the contact snapshot and the free-text fields (`idea`, `placement`, `approximate_size`, `preferred_dates`, `budget`) may change, and `anonymized_at` itself never changes again. The same ticket may only clear a payment's proof columns. Once a payment is decided its `status` and `verified_at` are final, and its verifier can only become null (what deleting that user's account does). A migration that backfills a frozen column on these tables must `ALTER TABLE … DISABLE TRIGGER <name>` around the backfill: the owner bypasses RLS but not triggers. A hard purge of a tenant that has payments is refused by the payments trigger's DELETE rule (the `tenants` cascade deletes payment rows), so purging such a tenant is an explicit operations step: disable the trigger around it, as for a backfill (a design claim, not something the suite tests). A trigger's `down()` must drop its function as well as the trigger.
- **Operations.**
  - Every test-runner start needs a reachable Postgres, even `node ace test unit` (the boot guard queries the role), and the web and worker processes exit 1 if Postgres is down at boot. The functional suite needs `psql` on PATH (`setup_roles.spec.ts`).
  - Always migrate with `pnpm migrate`. The app role can write the migration bookkeeping tables, so a pure-DML migration run by mistake as the app role would be recorded as done.
  - In production keep `DB_MIGRATION_PASSWORD` out of the web and worker environment (`start/env.ts` requires only `DB_MIGRATION_USER`).
  - Creating the app role: run `setup_roles.sql` as a superuser, as compose and CI do. Its one `ALTER ROLE` names `NOSUPERUSER`, `NOBYPASSRLS`, `NOCREATEDB` and `NOREPLICATION`, and PostgreSQL 18 (checked on 18.6) refuses `NOSUPERUSER` to every non-superuser, even one holding `CREATEROLE`, `CREATEDB`, `REPLICATION` and `BYPASSRLS`; a `CREATEROLE`-only admin is also refused `NOBYPASSRLS`, `NOCREATEDB` and `NOREPLICATION` ("Only roles with the X attribute may change the X attribute"). On a managed Postgres without superuser access, create the role with the provider's tooling and run the script with that `ALTER ROLE` cut down to `LOGIN` and `PASSWORD` (a new role has none of those powers; the grants were not tried as a non-superuser). The app password appears in psql's argv, in the server log if the statement errors, and on success under `log_statement = ddl` or `all`, so use a throwaway or secret-managed value in production.
  - If an initdb script fails, Postgres can restart "healthy" without the app role. After fixing the script, recreate the volume (`podman-compose down -v`).
- **Production checklist.** None of this is covered by the test suite; check it against your deploy.
  - Migrate from the build as the owner: `node build/ace.js migration:run --connection=owner --force` (`pnpm build` writes `build/ace.js`; `--force` is required when `NODE_ENV=production`; the owner's `DB_MIGRATION_USER` and `DB_MIGRATION_PASSWORD` must be in that process's environment). `migration:rollback`, `migration:fresh`, `migration:status` and `db:seed` take the same `--connection=owner`; without it they use the app role (a seeder's models still do).
  - A model imported in a migration uses the app role, so RLS applies: with no context its data changes silently affect 0 rows or fail the policy check. Use the migration's own client instead, `this.defer((db) => ...)`.
  - Set the pool size explicitly (`pool: { min, max }` on the `pg` connection in `config/database.ts`). It is not set today, so knex's default applies (maximum 10), and every authenticated request holds one connection for its whole length.
  - Consider `ALTER ROLE tattoo_drip_app SET idle_in_transaction_session_timeout = '...'` (`setup_roles.sql` does not set it), so a request that stalls mid-transaction cannot hold its connection and locks indefinitely. Pick a value above your slowest legitimate request.
