# Storefront development

Read the relevant section before changing UI/forms, server functions or version-specific TanStack integration. General commands and boundaries are in [area instructions](../AGENTS.md).

Both apps use Tailwind CSS v4 and shadcn/ui (new-york, Radix, lucide) and the Stencil & Ink palette (TAT-97: warm paper, ink and line, the stencil violet for actions), kept as two copies of one token vocabulary until a shared design system replaces them: when you change a paper, ink, line or violet value, change `apps/platform/inertia/css/app.css` too (its comment holds the measured contrast). Storefront theme entry: `src/styles.css`. Environment validation: `src/env.ts`.

The unused `@tanstack/ai*` prototype packages are slated for removal; do not build on them.

## shadcn

Add components from `apps/storefront` with `pnpm dlx shadcn@latest add <component>`, then run a focused Biome check on the generated components from the root (see [validation](../../../docs/agent-workflow.md#validation)). The CLI imports `cn` from the `cn` package (shadcn's clsx + tailwind-merge replacement); older components (`dialog`, `sheet`) still use `#/lib/utils`.

Never run `shadcn add form`: `src/components/ui/form.tsx` is our TanStack Form toolkit, and the CLI would overwrite it with shadcn's react-hook-form version.

## Forms

- Build forms with `useAppForm` from `#/components/ui/form` (TanStack Form composition) and render fields with `<form.AppField name="…">`, using `field.TextField`, `field.TextareaField` or `field.ChoiceField` (native radios: one tap each, visible without opening anything). Add new field types to `form.tsx` rather than wiring inputs by hand; it imports its primitives by relative path so `node:test` can load it. There is no `SelectField`: it pulled Radix Select into the intake form's chunk (about 28 KB gzipped) and nothing used it, so add one when a form needs it. The intake form (`src/intake/components/intake-form.tsx`) is the reference.
- Validate with a plain function in `validators.onDynamic` that returns `{ fields }` (the intake's `validateIntake`), with `validationLogic: revalidateLogic({ mode: "submit", modeAfterSubmission: "change" })` for "validate on submit, then on change". Zod schemas work there too (TanStack Form 1.x reads Standard Schema), but each adds to the browser bundle.
- Put the API's field errors in `errorMap.onServer` with `form.setFieldMeta`, and clear a field's in a form-level `listeners.onChange`.
- Controls are 3rem tall with 1.0625rem text (iOS zooms into anything smaller), labels 1rem. Field errors are tied to their control by `aria-describedby` and not announced one by one: show an error summary and move focus to it.
- No skill covers TanStack Form 1.x: the skills.sh `tanstack-form` skill targets the pre-1.0 adapter API. Go by the installed package's types and shadcn's TanStack Form guide.

## Sentry

Sentry is initialised server-side in `instrument.server.mjs`, which `pnpm dev` and `pnpm start` load with `--import`. Instrument server functions: wrap the body of each `createServerFn` handler in a span.

```tsx
import * as Sentry from "@sentry/tanstackstart-react";

Sentry.startSpan({ name: "Load studio profile" }, async () => {
	// server work here
});
```

## Tenants and hosts

Every server request finds its studio from its `Host` header before any route runs (TAT-12): `src/start.ts` registers Start's CSRF check for server functions, then `tenantMiddleware` (`src/tenancy/`).

- `<slug>.<base>` is a studio: the API confirms it with `studio.get()` (5 s timeout). The current slug goes on; an old slug gets a 302 to the same path and query on the current subdomain (GET and HEAD; other methods get the 404 page). The base domain and `www.` show a static landing page at `/`.
- An unknown studio, a label that can't be a slug, a deeper name, an IP or another domain gets a static 404 page (`Cache-Control: public, max-age=0, s-maxage=60`, so a new studio shows within a minute). An API failure is a static 503 page with `Retry-After: 30`, logged with the slug, status and code.
- Only `Host` counts, never `X-Forwarded-Host`. Labels are checked against the stored slug shape only (`STORED_SLUG`, a copy of the platform's, pinned by a test); reserved and old slugs are the API's answer, so never copy the platform's reserved list.
- Server code reads the studio as `serverContext.studio` in loaders and `beforeLoad`, or with `requestStudio()` (`getRouter()`, server functions). The browser never reads it: it gets the slug through the router's dehydrated state ([API and data](#api-and-data)).
- Settings, server only, from `process.env` (not `src/env.ts`, whose `import.meta.env` holds only `VITE_` variables): `API_URL`, the API's origin, and `STOREFRONT_URL`, `http://{tenant}.localhost:3000` in development and `https://{tenant}.<domain>` in production, the same value as the platform's setting of that name. Both use https except on localhost. `pnpm dev` refuses to start without them; a build and `pnpm preview` don't need them at start (neither loads `.env.local`, so export the settings when previewing a studio). `STOREFRONT_SERVER_KEY` (required with `NODE_ENV=production`, optional in development; 32 to 256 letters, digits or `-._~+/`, then at most two `=` of padding, e.g. `openssl rand -base64 32`; one of the platform's `STOREFRONT_SERVER_KEYS`) is the secret the server sends with its API calls (`Authorization: Bearer`); a malformed one stops `pnpm dev` too.
- Unverified on Vercel (TAT-13 confirms it on the first deploy): the design assumes a function sees the studio's own domain in `Host` (from Vercel's docs, not yet observed), and that Vercel's CDN keys its cache by host. If `Host` shows another name there, tenant resolution needs another source and a new decision.
- Also check on the first deploy (TAT-13), right after it goes live:
  - Open the landing page. A bad production `API_URL` or `STOREFRONT_URL` is not checked at cold start: the settings are read on the first request, so a wrong value shows as a 500 on every page (the log line names the variable and its rule, never its value). Fix the environment and redeploy.
  - A server function call from the deployed studio page works (none exists yet; check with the first one). Start's CSRF fallback for clients that send no `Sec-Fetch-Site` compares `Origin` with `request.url`'s origin, and that URL's scheme is `http:` behind Vercel's TLS termination (`trustProxy` is off). Browsers send `Sec-Fetch-Site` and are unaffected; only old or non-browser clients could get a 403.
- Local development: run the platform, set `API_URL` to its address, and open `http://<slug>.localhost:3000` for a studio in its database. Chrome, Firefox, Edge and curl send `*.localhost` to this machine (for Safari: `curl -H 'Host: <slug>.localhost:3000' http://127.0.0.1:3000/`), and Vite allows those hosts. `http://localhost:3000` is the landing page.
- `src/start.ts` puts `startInstance` in `routeTree.gen.ts`'s Register footer. The Start Vite plugin writes that footer (`pnpm dev`, `pnpm build`); `tsr generate` writes none, so after `pnpm generate-routes`, run `pnpm build` before committing the route tree.
- Tests: `pnpm test` runs `test/**/*.test.ts` with `node:test` and `tsx`. Keep `src/tenancy/` free of React and TanStack imports (except `middleware.ts`) so its tests run in plain Node; its files import each other with `.ts` extensions.

## API and data

Pages read the API only through `@tattoo-drip/react` and `@tattoo-drip/sdk` (TAT-23, `src/api/`).

- `getRouter()` makes one `QueryClient` and one SDK client per server request and one of each per browser tab; never create either at module scope. The router context is `{ queryClient, tattoo, site }`, `tattoo.client` is the SDK client and `site.origin` the page's own origin ([studio page](#studio-page)). `TattooProvider` wraps the root shell (`src/routes/__root.tsx`), inside the `QueryClientProvider` that `setupRouterSsrQueryIntegration` adds, so the hooks work in any component.
- Server: the client uses `API_URL`, the slug the tenant middleware confirmed and `STOREFRONT_SERVER_KEY` when set; it waits 5 s and never retries. With the key, both server calls (the tenant lookup and this client) also send the visitor's address as `X-Visitor-IP` (`src/tenancy/visitor.ts`: the first `X-Forwarded-For` value, which Vercel's edge sets, else the socket address), so the API counts them per visitor (TAT-38); the browser's client never sends either, and `pnpm check:page` checks it. The middleware's studio is already in the cache, so a render asks the API once. Browser: the router's dehydrated state carries only `{ apiUrl, tenant }` and the page's own origin (`{ site: { origin } }`, all public), and the browser's client has no key and sends no cookies. Never parse the host in the browser.
- Loaders prefetch with `context.queryClient.query({ ...tattooQueries.<name>(context.tattoo.client), staleTime: "static" })` (cached data, else one fetch: TanStack Query 5.104's replacement for the deprecated `ensureQueryData`) and pass errors to `rethrowAsNotFound`, so the API's 404 shows the route's not-found component. `loadStudio` in `src/api/loaders.ts` is the example: the root route runs it and titles pages that set no head of their own with the studio's name. The two page routes set their own head from `src/studio/seo.ts` ([studio page](#studio-page)); a new route must set its own title, description and Open Graph tags too, or it shows the studio's name and nothing else.
- Defaults (`src/api/query-client.ts`): data stays fresh 60 s (the API's `max-age`), so hydrated queries aren't fetched again on mount. The browser retries timeouts, network errors and 5xx twice and a 429 once after a `Retry-After` of 10 s or less, never a 4xx. Only successful and pending queries are dehydrated: a failed server read is fetched again by the browser. The browser keeps the studio and artists queries for the page's lifetime (`hydrateApi` sets their `gcTime` to `Infinity`, because nothing observes them and an unobserved query is dropped after 5 minutes; the artists key also covers each artist's own query). Without that, a repeat navigation to the identical URL (a second tap on the same `#inquiry` link: the router reloads a page's loaders only then, or after an invalidation, not on a first hash change) would fetch them again, and an API failure would replace the page with the error page. A failed read replaces only the page's body, never the document: in this router version the root route's `shellComponent` wraps the route's error boundary (and the server's error path), and `defaultErrorComponent` (`RouteErrorPage`, `src/router.tsx`) applies to the root route too. Keep the document in `shellComponent`, not in the root `component`, or this stops being true.
- Secrets: only `src/tenancy/config.ts` reads `STOREFRONT_SERVER_KEY`, from `process.env`. Never give it a `VITE_` prefix, add it to `src/env.ts`, or put a client, a config object or the key in loader data, a `beforeLoad` return value or query data: the router serializes those into the page. `API_URL` is sent to browsers, so it must be the API's public origin. Two scripts guard this (below): `pnpm build` fails when the browser bundle holds server-only text, and `pnpm check:page` runs the build with a canary key.
- `@tattoo-drip/react` is used from source and must share the storefront's React and TanStack Query (`test/api/single-copy.test.ts`); if that test fails, align the versions (`pnpm why @tanstack/react-query`) instead of aliasing them.
- Tests: `test/api/` (`node:test` + `tsx`) covers the defaults, the context and the loaders; the glue (`src/api/request.ts`, `src/router.tsx`, `src/routes/__root.tsx`) is covered by `pnpm typecheck`, `pnpm build` and the two checks below.
- `pnpm build` ends with `scripts/check-client-bundle.mjs` (also `pnpm check:bundle`): it fails when `.output/public` holds server-only text (the settings, the key, the tenant middleware and its log line; the list is in the script) or lacks the SDK's own text (then it did not look at a browser build). CI's `pnpm build` runs it. When it fails, a module that reads the settings or the key has been imported by code the browser runs (typically a route's `beforeLoad` or loader calling `storefrontConfig()`); move that read behind `createServerFn` or `createServerOnlyFn`.
- `pnpm check:page` (`scripts/check-page.mjs`, after `pnpm build`) starts the built server against a stand-in API on two free local ports, with a canary `STOREFRONT_SERVER_KEY`: the page's `<title>` is the studio's name, the page carries only the API's origin, the slug and its own origin, the key is in no page, header or log line, a page costs one keyed lookup and one artists read (an artist's page the same two, never a single-artist read), a malformed slug or unknown path asks for no list, a failed artists read is a 500 error page inside the document with `Cache-Control: no-store`, and a failed lookup (5xx or hang) is a 503, not a not-found. The router's state carries the failed match's error message (the API's public envelope text), so the check does not look for it in the page. It takes about ten seconds and is not in CI: run it before a release and after changing how the router, the root route or the tenant middleware use the settings (TAT-13 runs it before the first deploy).

## Studio page

Two routes (TAT-48): `/`, the studio (profile, contact links, artists, the inquiry section), and `/artists/$slug`, one visible artist: the link an artist shares to be asked for by name. `/deposit` is the [deposit page](#deposit-page) (TAT-65b); any other path is the router's not-found page.

- Data: loaders (`src/studio/loaders.ts`) read the studio (already cached by the tenant middleware) and the artist list with `queryClient.query({ ...tattooQueries.x(client), staleTime: "static" })` and return view models (`src/studio/view-model.ts`). The artist page finds its artist in that list by exact slug: hidden, deleted, renamed and unknown artists aren't in it, and a malformed slug is a not-found before any API call. Components (`src/studio/components/`) take the view models as props, use plain anchors and no router or query hooks, so `test/studio/render.test.ts` renders them with `react-dom/server`.
- Safety: render API data only as text; never `dangerouslySetInnerHTML` or `style` props. Every link comes from `src/studio/links.ts`: the page's own paths and fragments, `https:`, `tel:`, `mailto:` and `viber://chat` only; web links get `rel="noopener noreferrer"` and nothing gets `target`. JSON-LD goes through `serializeJsonLd`, because the router inserts head script children raw.
- The first screen (TAT-105, `StudioPage` in `components/pages.tsx`): the name (`h1`), one location line (`StudioView.location`, `locationLine` in `text.ts`: the address's lines and commas on one line if that is at most 48 user-perceived characters, else its last two parts, else its last part, else nothing; the kind of studio when it is nothing or there is no address, so the line is never longer than that and never has an ellipsis; the whole address stays under Visit), "Send your idea" (primary, `#inquiry`) and "WhatsApp" (secondary, the plain chat link of the Chat group; only with a valid phone), then the 4-step strip, then the intro, then the contact groups. The buttons come before the intro so a long intro can't push them off a phone's first screen, and a studio that isn't taking inquiries shows its status line instead of both buttons and the steps. From 60rem the heading spans the top, the buttons and intro are on the left and the contact groups on the right. The contact block (`components/contact.tsx`) groups the links as Chat (WhatsApp, Viber, Call, Email), Follow (Instagram, Facebook, TikTok, website, other places) and Visit (the street address and its map link); a group with nothing in it is left out. The words are in `src/studio/copy.ts`.
- "How booking works" (TAT-105, `components/steps.tsx`): the same four steps (idea, a price on WhatsApp, a deposit holds your date, your session) twice, because a phone and a desktop want different places for them. The strip (titles only) sits under the hero's buttons, and above the form on an artist's page (`InquirySection`'s `stripAbove`, as an `h3`); the panel (a line for each step, the chat links, an `aside`) is sticky beside the form from 60rem. Each is `display: none` where it doesn't apply, so the steps are read once, and the form's own "Prefer to chat?" at its foot is hidden from 60rem too, since the panel carries the same links (`test/studio/assets.test.ts` pins both). The step lists are `ol role="list"` because `list-style: none` drops the list in WebKit, and the panel re-checks its chat links with `isAllowedHref` like the hero and the contacts. Every element that shows the studio's name wraps anywhere (`overflow-wrap: anywhere`: the step lines, the form's legends and paragraphs, the footer), so one long word can't widen the page; the same test pins them. The studio's own deposit policy is not in the public contract (`getStudio` never returns it), so the panel's deposit line is the fixed "you pay the studio directly; Tattoo Drip never handles your money"; show the policy itself only after a contract change.
- The `#inquiry` section (`src/studio/components/inquiry.tsx`): `InquiryState` says whether it is open, for which artist (`preferredArtist.id` is `createInquiry`'s `preferredArtistId`) and which artists can be chosen. Open, its heading is "Send your idea" (as the hero's button and the artist page's, so the words match what was tapped) and it holds the [intake form](#intake-form) in the left column (7/12) and the panel in the right (5/12); its server-rendered fallback is WhatsApp or email with a prefilled message. Closed, it has no panel.
- Head and caching: `src/studio/seo.ts` writes titles, descriptions, canonical and Open Graph tags; the canonical origin is the router context's `site` (`src/site/`), set on the server from `STOREFRONT_URL` and the confirmed slug and carried to the browser in the router's dehydrated state, like the API connection. The root route's head (`rootMeta`) titles a page that sets none with the studio's name, and gives a path no page route matches (and a failed studio read) the not-found or error head with `noindex`. Pages answer `Cache-Control: public, max-age=0, s-maxage=60, stale-while-revalidate=600`, not-found pages `s-maxage=60`, errors `no-store` (`src/studio/cache.ts`; an unmatched path gets no header of ours): a page holds no per-visitor data, and must not.
- No analytics and no third-party scripts, fonts or stylesheets, except the intake form's Cloudflare Turnstile (loaded only once someone starts filling the form in) (PostHog is gone from the source; its packages stay listed until TAT-53 removes the prototype's leftovers). Adding a storefront dependency re-resolves every `latest` specifier in the lockfile, so vendor small assets instead. Body text uses system fonts. Names and bios may be Nepali or right-to-left: keep `dir="auto"`, `<bdi>` around names inside sentences, `white-space: pre-line`, and no letter-spacing, uppercase, line clamps or ellipses on user text.
- Photos are the stored image (up to 2048 px, no smaller variant yet): roster photos load lazily, the artist page's photo first; `width` and `height` are always set.

### Fonts

The display face is Eczar 700 (SIL Open Font License 1.1), whose Latin and Devanagari were designed together. The three subset files and the licence are vendored in `src/assets/fonts/eczar/` (`eczar-latin-700-normal.woff2`, `eczar-latin-ext-700-normal.woff2`, `eczar-devanagari-700-normal.woff2`, `OFL.txt`), copied from the `@fontsource/eczar` 5.3.0 package (the tarball itself, about 0.96 MB with every weight and subset, is not kept; no dependency was added). `src/styles.css` declares one `@font-face` per subset with `font-display: optional`, so a slow first visit keeps the system serif instead of reflowing the page; each subset downloads only when the page holds its characters, and only the Latin file is preloaded (`src/routes/__root.tsx`). Body text stays on the system font stack, and the headings' stack is `Eczar, "Noto Serif Devanagari", "Noto Serif", Georgia, "Times New Roman", serif`. `test/studio/assets.test.ts` pins the three blocks, `font-display: optional`, the preload, the licence and the file sizes. To change the font, vendor new files the same way (download into an empty folder outside the repository, treat it as untrusted data, copy only the woff2 files and the licence) and update that test.

### Themes and branding

TAT-54 (`src/studio/theme/`). A theme is a set of React components of this app; a studio picks one by key and fills in its options, and never sends markup, CSS or scripts. There is one theme, `stencil-and-ink`, the page TAT-97 and TAT-105 built, and the API sends no configuration yet, so every studio gets it with its defaults.

- The seam: `storefrontInput(studio)` (`theme/source.ts`) reads the API studio's `storefront` property, which the contract does not have yet (`Studio` in `packages/types/openapi.yaml`) and the platform never sends, so it is `undefined` on every real page. TAT-56 adds `Studio.storefront` (shaped like `StorefrontConfiguration`) and then reads it there without the cast; nothing else changes. Tests put a configuration on a fixture studio (`withStorefront`, `test/studio/theme-fixtures.ts`).
- Checks (`theme/config.ts`, `parseThemeConfig(input, imageOrigin)`, called by the loaders): each value on its own, own properties only; a value that is missing, of the wrong type or not on its list falls back to its default alone, and anything but an object is the default theme. `theme`: a key of `THEME_KEYS` (an unknown one, like the contract's example `classic`, is the default). `branding.colors.accent` and `branding.colors.accentDark`: `#rrggbb`, lowercased (`readHexColor`); other colour keys are ignored. `branding.font`: `eczar`, `serif` or `sans` (`FONT_KEYS`), never a family name. `branding.logo` and `branding.heroImage`: the contract's `Image`; the URL passes `safeImageUrl`, has no space or control character, is on exactly the API's origin (`context.tattoo.connection.apiUrl`: the same scheme, host and port, which is the only rule on the scheme, since the API itself is https unless it runs on this machine); width and height are whole pixels from 1 to 10000; `alt` is read for the cover only (see Images below). `sections`: the `{ type, props }` items whose `type` the theme supports, in order, each once; `props` is not read; anything but a list is the default order.
- Sections (`THEME_SECTIONS`, rendered by `StudioSection` in `components/pages.tsx`): the studio page's `artists` and `inquiry`, in that order by default. A configuration can reorder them and hide the roster. `inquiry` is required (a client can always send an idea): a list without it gets it at the end, so the hero's `#inquiry` link always has its target. The first screen (name, location, buttons, steps strip, intro, contacts), the footer and the artist page's layout are fixed. Hiding the roster changes nothing else: the form still offers every open artist, the artist pages and the JSON-LD stay.
- Branding (`theme/branding.ts`, `brandingCss`): the accent and the display face become CSS variables in one `<style>` in the head (`themedHeadTags` in `theme/head.ts`, the two routes' `head`), never a `style` attribute: a `<style>` can hold the dark scheme's media query and can be allowed by nonce in a future `style-src` (the router adds its nonce once one is set; no CSP is sent yet). Our code never uses `dangerouslySetInnerHTML`; the router writes the text as it is, so it holds only checked `#rrggbb` values and fixed text, and `isSafeCss` refuses anything else before it leaves. Rules sit on `html:root`, which outranks `styles.css`'s `:root` wherever the tag lands, colours inside `@media (prefers-color-scheme: light)` and `(prefers-color-scheme: dark)`. The default theme writes no `<style>`.
- Contrast: an accent sets `--stencil`, `--stencil-strong` (a quarter of the way to the ink) and `--stencil-wash` (a tint of the paper) for a scheme only when it reads at 4.5:1 on that scheme's paper; otherwise that scheme keeps the theme's violet, all three tokens. The hover colour is kept only while the paper still reads on it at 4.5:1, the wash only while the accent, the ink and the muted ink read on it at 4.5:1 (else the paper itself). `--on-stencil` stays the paper. The dark scheme uses `accentDark` when it reads there, else the accent lightened toward white until it does. `LIGHT` and `DARK` in `theme/branding.ts` copy `styles.css`'s paper and ink values (`test/studio/theme-branding.test.ts` pins them): change both together.
- Fonts: `eczar` keeps the stack in [Fonts](#fonts); `serif` is Georgia with Noto Serif Devanagari, `sans` the body stack. Nothing is downloaded for a studio's choice; the Eczar Latin file stays preloaded either way.
- Images (`components/brand.tsx`): the logo sits above the name in the hero and before the name in the artist page's bar; the cover sits above the hero, about 3:1 and at most 16rem tall (so 4.5:1 on a wide screen), with the photos' stencil frame, cropped toward the top (`object-position: 50% 25%`: a centre crop of a portrait photo is a mid-body slice with the head cut off; a landscape photo shifts by up to a quarter of what the crop hides, more on a wide screen). Both are `<img>` with their width and height, never a CSS `url()`. The logo has `alt=""` (decoration beside the studio's name, which says the same in text) and `fetchPriority="low"`, because React 19 adds a `<link rel="preload">` for every image that is neither lazy nor low priority and a small logo should not compete with the cover and the font; the cover keeps `fetchPriority="high"` and its preload. The cover is a photograph, so it takes the API's `alt` (`readCoverImage`: plain text on one line through `cleanLine`, "" when missing, blank, not text or over 300 characters); the logo's `alt` is never read. The cover is the hero image: the platform should send TAT-116's cover photo as `branding.heroImage`, one image for both.
- Not themable: the intake form and `InquirySection` (every theme renders them as they are; the accent reaches them only through the page's variables), the deposit page (its route adds no brand `<style>`; its header shows only the checked logo, TAT-110), the status pages, and the link rules (`src/studio/links.ts`).
- The default look is pinned: `test/studio/default-theme.snapshot.json` holds the markup the two page components (`StudioPage` and `ArtistPage`, rendered by `renderToStaticMarkup`) produced before themes, recorded from that code; `default-theme.test.ts` and `theme-render.test.ts` compare against it, and a configuration whose every value is hostile must render the same markup. It is the markup of the components, not of the whole HTML document (see the next bullet). To accept a deliberate change to the default look, delete the file, run the tests twice (the first run records it and fails) and review its diff.
- What the browser receives: the router's dehydrated state carries the loader data, so every studio page holds the checked `theme` object (about 150 bytes for the default theme), and once the platform sends `Studio.storefront`, the raw object sits in the cached studio query as well (the tenant lookup caches the whole API studio). The loaders read that raw copy again (`storefrontInput`) on a client-side navigation, in the browser, so it has to stay there until the parsed theme is stored elsewhere. TAT-56 must cap the size of the stored configuration, and strip `storefront` from the studio before it is dehydrated once the parsed theme is stored elsewhere, so a large `sections` list is not sent with every page.
- Freshness: a saved theme change can take up to about 12 minutes to show on the studio page, not about a minute. The pages answer `s-maxage=60, stale-while-revalidate=600` ([Studio page](#studio-page)), so a CDN may serve a page for 60 s and then a stale one for up to 600 s while it fetches a new one, and that new page is built from a studio the server cached for up to 60 s. A preview link or a "saved" message for a studio's owner must say so, or bypass the cache.
- Known limits (outside TAT-54): artist photos still accept any http(s) origin (`safeImageUrl`), which is weaker than the brand images' rule of the API's origin only; and the Eczar Latin file stays preloaded for `serif` and `sans` studios, which never use it.
- Adding a theme: its key in `THEME_KEYS`, its sections in `THEME_SECTIONS`, its components in `THEMES` (`theme/registry.tsx`), and tests. Adding a section: its key in `SECTION_KEYS` and the theme's `order`, a case in `StudioSection`. Never name anything `parseStorefrontConfig` or `storefrontConfig`: those are the server settings (`src/tenancy/config.ts`), and `scripts/check-client-bundle.mjs` fails the build when either name reaches the browser.

## Intake form

The `#inquiry` section's form (TAT-57, `src/intake/`) sends `useCreateInquiry()` straight from the browser to the API, with a Turnstile token and TAT-55's honeypot.

- Mount: `IntakeMount` renders it only after hydration, from its own chunk (`React.lazy`); on the server, before hydration, without JavaScript or when the chunk fails to load, TAT-48's chat-link fallback shows. Nothing of the form is in the server-rendered HTML.
- Words above the form (TAT-105): one line, "Only {studio} sees what you send." (`copy.reassurance`), then "Everything is needed unless it says (optional)." The Cloudflare notice and its link are small print under Send (`copy.privacy`: who runs the page, and that a Cloudflare check runs in the browser; worded to read right below the Send button), not the first thing a nervous client reads.
- Pure modules, tested with `node:test`: `copy.ts` (every string, as templates; `fill` and `<Fill>`, which puts values in `<bdi>`, live in `template.ts` (the studio page and the deposit page import them from there, never `fill` from `copy.ts`, so they don't load the form's words; `test/deposit/guard.test.ts` pins the deposit side); a Nepali file would mirror the shape), `rules.ts` (limits pinned to `openapi.yaml`, a copy of the platform's `normalizePhone`, Devanagari digits turned into ASCII ones, `validateIntake`), `images.ts` (`prepareReference` behind an `ImageCodec`), `references.ts` (the photo tray), `submission.ts` (the SDK input), `problems.ts` (every API code to a field error or a notice), `challenge.ts` (Turnstile behind a `ChallengeHost`), `submit-flow.ts` (one attempt at a time). `browser-codec.ts` and `challenge-host.ts` touch the DOM and only the browser pass covers them.
- Photos: picked with `accept="image/jpeg,image/png,image/webp"` (iOS converts HEIC; a HEIC the browser can't decode gets a message), at most 5, prepared one at a time: decoded the right way up, drawn on white, re-encoded as JPEG at a long edge of 1600 px (0.85, then 0.72, then 1280 px until at most 1 MiB; refused over 3.5 MiB), so no EXIF or GPS leaves the phone and five stay under the API's 20 MB. Before any decode, `image-size.ts` reads the declared size from the first 256 KiB (PNG, JPEG or WebP header) and refuses over 100 megapixels, since a few hundred KB of PNG can declare a gigabyte of pixels; a decode or encode that takes over 20 s is given up on ("couldn't be opened"), so one stuck photo can't hold the tray on "Preparing…". Previews are object URLs of those JPEGs, revoked on remove, success and unmount. The pipeline is `prepareImage` with `REFERENCE_PROFILE`; the [deposit page](#deposit-page) runs it with a profile of its own.
- Sending: `fetch` reports no upload progress, so the status line names the phase and the size, and says "Still sending" after 15 s; the SDK's 120 s upload timeout stands; there is no cancel (a `beforeunload` prompt asks while sending). Everything entered stays after any refusal; "Send again" takes a new token. Writes never wait for a network (the QueryClient sets `mutations.networkMode: "always"`; TanStack's default pauses a write while the browser is offline and sends it on reconnect, with a spent token): offline, Send fails at once with "Your inquiry wasn't sent". A rate limit blocks Send for the `Retry-After` it gave (a minute without one) and says the wait in minutes or hours: the phone's limit is per day, and a photo the API's decoder refuses still counts against it.
- Bot check: `TURNSTILE_SITE_KEY` (a server setting read by `parseStorefrontConfig`; public; required with `NODE_ENV=production`, optional elsewhere, where no widget runs and no token is sent) reaches the browser in the router context's `site`. The script (`challenges.cloudflare.com`) loads on the first focus or tap in the form, runs at Send (`execution: "execute"`, `appearance: "interaction-only"`) and is reset after every attempt. To try it locally, set the storefront's `TURNSTILE_SITE_KEY=1x00000000000000000000AA` and the platform's `TURNSTILE_SECRET_KEY=1x0000000000000000000000000000000AA` (Cloudflare's always-pass pair; `3x00000000000000000000FF` forces the checkbox, `2x00000000000000000000AB` always fails); leave both unset to skip it.
- It is the page's one third-party script. No Content-Security-Policy is sent yet; one would need `script-src` and `frame-src https://challenges.cloudflare.com`, `connect-src` with `API_URL`, and `img-src blob:` plus the API's photo origin.
- Nothing is kept in storage (shared phones), nothing is tracked, and nothing about the person goes in a URL.
- Browser pass (no node test can do these), at 375 px and on a real phone when possible: a portrait iPhone photo arrives upright as a JPEG of at most 1600 px; a transparent PNG arrives on white; a HEIC picked from Files on Android Chrome gets the HEIC message; five 12 MP photos prepare one by one without the tab dying on a low-end Android phone; with DevTools' network at "Slow 3G" the status line shows the size, then "Still sending"; the widget stays hidden with the always-pass key and shows its checkbox with `3x…FF`; offline, Send says it wasn't sent and keeps everything; nothing reaches `challenges.cloudflare.com` before the first focus in the form.

## Deposit page

`/deposit#<token>` (TAT-65b; `src/deposit/`, route `src/routes/deposit.tsx`) is the page an owner's deposit link opens (TAT-65): the studio's header, what to pay and that it goes to the studio directly, three numbered steps (copy the reference code, pay with the studio's QR or details, send one screenshot of the payment), one way to pay at a time, and its deposit policy; once paid, the receipt. It reads the page with `useDeposit(token)` and sends the screenshot with `useSubmitDepositProof(token)`, straight from the browser to the API.

- The token is the link's fragment, 43 base64url characters (`readDepositToken`, pinned to the contract). Browsers never send a fragment to a server, so the server renders only the shell (the studio's name from the cached lookup, a loading state, the studio's WhatsApp and Viber links) and the deposit loads in the browser after hydration; a missing or malformed token shows the dead-link message without a request. The token goes only into the API's path, whose access log the platform's proxy turns off ([public API production checklist](../../platform/docs/deploy.md#public-api-production-checklist)). Never put it in a query string, a log, storage or the page's HTML, and never give the page an in-page `#` link: following one replaces the token (the error summary's items are buttons). The router keys its scroll positions in `sessionStorage` by history entry, else by path (`scrollRestorationKey` in `src/deposit/token.ts`, wired in `src/router.tsx`), never by href. The router's error page reloads the page for "Try again" (a link to the page's own address would only be a fragment navigation) and drops any fragment from its `href`. An old slug's 302 keeps the fragment: browsers carry it across a redirect. Instagram and Facebook rewrite outgoing links through `l.instagram.com/?u=…` and `l.facebook.com/l.php?u=…`, and that address carries the whole URL, fragment included, to Meta; WhatsApp and Viber open links as they are. Nothing in the page can change that (any link that holds a bearer token has it), so studios should send a deposit link by WhatsApp, Viber or SMS, never as an Instagram or Messenger link.
- Headers: `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, `X-Robots-Tag: noindex, nofollow`, the same robots and referrer rules in `<meta>`, and `referrerpolicy="no-referrer"` on the QR images. No analytics, no browser-side error reporter (the server's error reporting never sees the fragment) and no Turnstile on this page: the token and the API's per-link limits protect it. A browser-side reporter added later must drop the fragment from every URL it records.
- Layout (TAT-110, `components/deposit-page.tsx`, `steps.tsx`): the header (the studio's mark and name, then "with {artist}" once read) sits above the h1. The mark is the studio's checked logo (`DepositShell.logo`, from `parseThemeConfig(...).logo`: on the API's own origin only, `alt=""`, `referrerpolicy="no-referrer"`) or its initial (`studioInitial`, the first grapheme as typed: "का", "मी"), never the cover (a full stored photo on a payment page waits for small image sizes, TAT-112), and the accent stays violet; the route still writes no brand `<style>` (a guard test pins it). Under the amount: "You pay {studio} directly. Tattoo Drip never handles your money." (the footer only says who runs the page). Steps are numbered h2s (`StepHeading`: a hidden numeral and an `sr-only` "Step N: "), not an `<ol>`, so the desktop grid can put the picked method's panel beside them; "Deposit due" and the screenshot's legend are `sr-only` (the h1 and step 3 say it). Step 2 is `PayWith`: a native radio group (`name="pay-with"`, ids `pay-with-N`, outside the form so Enter sends nothing; arrow keys move and select; the dot stays visible) shown from two methods on; one method has no group and its panel opens with "Pay with {label}". A method's identity (`MethodView.id`) is its kind and its account or wallet number as shown, `bank:01234567890123` (the number URL-encoded, empty for a QR-only method), never its place in the list: the page refetches when the tab regains focus, and a studio that reordered its methods meanwhile must not move the client's pick to another one. Methods that can't be told apart that way (the same kind and number, or no number) take `#1`, `#2`… by their order among them, so a reorder between just those can still swap them (the panel is keyed by identity and QR, so its image is still a fresh one). The pick is `DepositLoaded`'s `picked` state (`MethodPick`: the identity, the kind and a count, made by `pickMethod`); `selectedMethod(methods, picked.id)` gives the method while it is still listed, else the first (a pick that has left the list shows the first method and touches nothing else). "How did you pay?" is set by an explicit pick only: `ProofForm`'s `pick` prop is that event, `answerFor(pick, appliedCount, kinds)` gives its kind once per count (so every pick reapplies, a second bank account after a hand-made answer included) and an effect applies it; a re-render, a refetch or a reorder never does, and a change in step 3 stays until the next pick. Nothing is answered before the first pick, though the first method shows (the form asks, "Choose how you paid", like any unanswered form), and one kind keeps its single default. Tapping the method that already shows is a pick too (a radio fires no change for it, so `onClick` covers it). Only the picked method is on the page, in `MethodPanel` keyed by its id, so a switch makes a fresh `<img>` (the previous QR never shows while the next loads: scanning the wrong code is the worst thing this page can do) and a fresh Copy button (no stale "Copied"); its QR is always eager. "I've paid" (`PaidBar`) is a `<button>`, never a `#proof-title` link: it calls `showProofStep()` (`browser.ts`), which scrolls step 3's heading to the top and focuses it (`tabIndex={-1}`) without touching the URL. It sticks to the bottom of the screen below 60rem while the client is in steps 1 and 2 and settles in its own place, above step 3, when they reach it; that needs `.deposit-due` to be a flex column (a grid item may only move inside its own cell), and `:root:has(.deposit-paid-bar)` sets `--deposit-bar-height` (4.5rem) once, used by the bar's `min-block-size` and by `scroll-padding-block-end` (plus half a rem and the device's bottom inset) so a keyboard focus is never hidden under it; a taller bar needs a larger value. The Pay with chips show one focus ring, the radio's own, like the form's choices (no ring on the label). From 60rem, while due with methods (`DepositFrame` `wide`), the page is two columns: the header, h1 and brief run across, the steps are on the left and the panel is sticky on the right (the bar and the same-phone hint are hidden); the `grid-area` names live only inside that media query, where the template defines them (a name the template lacks makes implicit lines and every item lands in one cell; `test/deposit/styles.test.ts`).
- Data: no polling. The query is always stale, so it refetches when the tab regains focus (coming back from the payment app) and on reconnect; a 404 at any time (a link replaced or expired, on a read or on the send) replaces the page with the dead-link message, even over data already shown, and the send's 404 stands until a read succeeds after it. A first read that can't start because the phone is offline would wait for ever (TanStack Query pauses it, so no error ever comes): the page says "We couldn't load your deposit. Check your connection." with Try again, and the read resumes by itself when the phone is back online. While Try again runs, the message and its button stay (the button `aria-disabled`, a polite status) so focus isn't lost, and each failed read is announced again. Amounts are the API's `dueText` and `amountText`; only `deposit.due` goes back, as `expectedAmount`. "Pay by" adds today, tomorrow or "in N days", counted in the studio's timezone, and the screenshot's time is shown in that timezone. A paid page also carries `nextSession` (`{ startsAt, artistName }`, TAT-110: the project's next session, `null` in every other state and when none is scheduled): the receipt shows "Your session" with `formatSessionStart` ("Sat 24 Oct 2026, 11:00 am", the studio's timezone, one time style with the screenshot's) in a `<time dateTime>` and "Artist" (the session's own artist, left out when null); a zone this browser doesn't know leaves the session rows out rather than showing UTC, and an API that doesn't send the field yet reads as no session. The page's one h1 (`headingTemplate`) says what the message under it says: the studio ("Pay your deposit to {studio}") while it loads and while it is due, the state's words once read (TAT-106), and "This link doesn't work", "Too many tries" or "We couldn't load your deposit" (`copy.headings.load`, TAT-119) for a dead link (a 404, or a missing or malformed token), a rate limit or a failed read; a problem wins over a page already shown.
- Tap targets: every link and button on the page, the Pay with chips and the I've paid button included, is at least 44 px tall, and the chat links under the page (`.deposit-contact .text-link` in `styles.css`) are at least 44 px wide too (`min-inline-size`; "Viber" alone is 37 px, TAT-119). Measure them in the browser pass.
- Screenshot: one, prepared by the intake form's pipeline (`prepareImage` with `PROOF_PROFILE` from `src/deposit/proof.ts`: the same type checks, decode bounds and timeouts, then a long edge of 2048 px at 0.85, 0.72, then 1600 px until at most 1.5 MiB, refused over 4 MiB), sent as `payment.jpg`. While it is being prepared or sent, the picker and Remove do nothing; the preview's object URL is revoked on replace, remove, success and unmount.
- Sending: Send is `aria-disabled` while a screenshot is being prepared, while sending and while a rate limit lasts; never retried; "Still sending" after 15 s; a `beforeunload` prompt while sending; offline it fails at once (`networkMode: "always"`). Refusals (`src/deposit/problems.ts`) are field errors in a focused summary, or one notice above Send (`role="alert"`). `deposit_changed`, `deposit_not_due`, a 404, a 408 (also a proxy's, without the API's envelope), a timeout and a network error read the page again; when it has left `due` (the upload landed after all, or the studio acted), focus moves to the new message. A proxy's 502 or 504 stays the generic notice (the spec lists what is read again); a second Send is safe, the API answers it 409. A 429 blocks Send for its `Retry-After`. Nothing on the page is natively `disabled` (a focused control that is disabled drops focus to the body: Enter on a radio sends the form), and from the moment Send is pressed until focus has moved the state message's live region is `aria-live="off"`, so the sent message is said once (by the focus move), while a change that arrives on its own is still announced. A failed Copy leaves after 6 s and every failed tap is announced.
- Pure modules, tested with `node:test` in `test/deposit/`: `token.ts`, `copy.ts` (every word; TAT-65's sentences verbatim; the four head strings live in `head-copy.ts`, which it carries whole, so the route's head in the shared entry chunk imports only those), `view-model.ts` (with `selectedMethod`, `formatSessionStart` and `studioInitial`), `proof.ts`, `problems.ts`, `seo.ts`, `loader.ts`, `styles.test.ts` (the layout rules above, read from `styles.css`); the components render with `react-dom/server`, and a guard test keeps storage, logging, analytics, `location.search` and `#` links out of `src/deposit/`, requires `referrerPolicy="no-referrer"` on every `<img>` there, keeps the route free of brand styles and `browser.ts` free of `location` and `history`. `browser.ts` (the clipboard and `showProofStep`) and the fragment hook in `components/deposit-screen.tsx` touch the DOM, so only the browser pass covers them. `pnpm check:page` checks the built `/deposit` (its headers and meta, the shell, and nothing asked of the API but the lookup).
- Browser pass (no node test can do these), at 375 px and on a real phone when possible: every state; a keyboard-only upload (Pay with and its arrow keys, I've paid and the focus it moves to step 3's heading, the radios, the picker, Send, focus on the sent message; the bar never covers a focused control); at 1280 the QR beside the steps and still in view when scrolling to Send; reduced motion makes I've paid jump instead of scroll; the upload arrives as a JPEG of at most 2048 px with no EXIF; a HEIC from Files on Android Chrome gets its message; Copy in Chrome and in Instagram's and Viber's in-app browsers; with DevTools' network at "Slow 3G", "Still sending"; offline, "Couldn't send"; a 404 after the page showed replaces it; an old slug's link still shows the deposit; and no request but the API's carries the token (no Referer anywhere, nothing in storage).
